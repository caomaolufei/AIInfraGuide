## 1. 推理优化的两个杠杆

大模型推理的性能瓶颈通常来自两处：

| 瓶颈 | 表现 | 优化杠杆 |
| --- | --- | --- |
| **算力不足** | 计算密集（Prefill 阶段、大 batch） | 量化（INT8/FP8）、算子融合 |
| **显存/带宽不足** | Decode 阶段 memory-bound、并发上不去 | KV Cache 优化（分页/量化/共享） |

- **量化**降低单次计算/搬运的数据量，直接提升算力上限与带宽效率；
- **KV Cache 优化**让同样的显存能服务更多并发请求、更长的序列。

两者叠加，往往能带来数倍于「原版 BF16」的吞吐提升——这也是推理引擎（MindIE/vLLM-Ascend）的核心价值。

## 2. 昇腾量化方案全景

昇腾支持的量化方案随 CANN/推理引擎版本演进，常见的有：

| 方案 | 含义 | 特点 |
| --- | --- | --- |
| **W8A8** | 权重 INT8 + 激活 INT8 | 通用性好，配合量化算子库 |
| **AWQ**（Activation-aware Weight Quantization） | 权重量化（4bit 为主） | 精度好，生态权重多 |
| **GPTQ** | 后训练权重量化 | 经典方案，社区权重丰富 |
| **FP8** | 权重/激活 FP8 | 新一代硬件支持，精度优于 INT8 |
| **KV Cache 量化** | KV 存为 INT8 等 | 显存优化利器，精度损失小 |

**量化工具链**：昇腾生态通过 AMCT 等工具支持量化模型的生成/转换，MindIE 与 vLLM-Ascend 则负责在推理时高效执行量化算子。

## 3. W8A8 与 AWQ：主流量化路线

### W8A8（权重+激活 INT8）

- 把 GEMM 的输入与权重都量化为 INT8，用 AI Cube 的 INT8 算力（昇腾 INT8 算力通常高于 FP16）。
- 依赖**量化校准**：统计激活分布，确定 scale。
- 收益：吞吐提升明显，尤其适合 Prefill/大 batch 场景。

### AWQ（4bit 权重量化）

- 只量化权重（激活保持高精度），按「激活幅度」保护重要通道，精度损失小。
- vLLM-Ascend 对 AWQ 支持良好，社区里 Qwen 等模型的 AWQ 权重可直接加载。
- 收益：模型体积减至约 1/4，单卡可驻留更大模型，Decode 吞吐受益。

**选型建议**：追求精度与易用 → AWQ（有现成权重）；追求极致算力 → W8A8/FP8。

## 4. FP8 量化与新一代硬件

新一代昇腾芯片（如 910C 及之后）逐步引入 FP8 支持：

- FP8（E4M3/E5M2）介于 INT8 与 FP16 之间，**范围与精度都好于 INT8**，是训练/推理的最新趋势。
- 推理引擎（MindIE/vLLM-Ascend）的 FP8 支持随 CANN 版本推进，需确认硬件 + 软件双端支持。
- **建议**：FP8 权重格式在生态中逐步普及，部署前先确认「权重格式 + 引擎版本 + 硬件」三者兼容。

## 5. KV Cache 优化：分页与量化

KV Cache 是显存开销的大头，两大优化手段：

**① 分页式 KV Cache（Paged KV Cache）**

```
无分页：每个请求预留整段连续显存 → 碎片化、浪费
分页：  显存按固定 Block 分配 → 按需申请、消除碎片
```

- 原理对应 GPU 的 PagedAttention（模块四讲过）；
- 昇腾上由 MindIE / vLLM-Ascend 实现，支持 `--kv-cache-dtype` 等配置。

**② KV Cache 量化**

- 把 K/V 存成 INT8 等低精度，显存占用直接减半（或更多）；
- 精度损失通常很小（对最终生成质量影响轻微），吞吐收益显著；
- 是「显存吃紧 + 并发要高」场景的第一选择。

## 6. 前缀共享与长序列优化

**前缀共享（Prefix Sharing / Prefix Caching）**：

- 多请求共享相同前缀（系统提示词、对话历史）时，KV 直接复用，不重复计算；
- RAG/Agent 场景（每次请求带长系统提示）收益极大；
- vLLM-Ascend 支持自动前缀缓存，MindIE 亦有对应能力。

**长序列优化**：

- 长序列下 KV Cache 随长度线性增长，需结合「分页 + 量化 + 前缀共享」综合规划；
- 配合**长度感知调度**（长请求与短请求混合批处理）平衡延迟与吞吐；
- 生产建议先压测「目标序列长度 × 并发」的显存账本，再定配置。

## 7. 调优决策框架

给一个可操作的决策流程：

```
1. 明确目标：要延迟（TTFT/TPOT）还是吞吐（tokens/s）？
2. 算显存账本：模型权重 + KV Cache（最大序列×并发）是否放得下？
3. 若显存不够：
   优先 KV Cache 量化 → 再考虑前缀共享 → 最后才考虑降并发
4. 若算力是瓶颈：
   上 AWQ/W8A8/FP8 量化，验证精度损失
5. 组合验证：量化 + KV 优化 + 引擎配置，用 Benchmark 量化收益
6. 回归：每步验证精度（量化）与指标（吞吐/延迟），防止「快了但错了」
```

**核心原则**：量化与 KV 优化不是「能上就上」，而是「按瓶颈对症下药 + 用数据验收」。

## 总结

- 推理优化两杠杆：**量化（算力/带宽）** 与 **KV Cache 优化（显存/并发）**。
- 主流方案：**W8A8（INT8 算力）/ AWQ（4bit 权重）/ FP8（新一代）/ KV 量化（显存）**。
- 分页式 KV Cache 消除碎片，KV 量化直接减半显存，前缀共享省去重复计算——三者叠加收益最大。
- 调优 = 明确目标 → 算显存账本 → 对症下药 → 数据验收。
