## 1. 压测前的四个决定
### 1.1 测离线引擎还是在线服务
离线测试绕过 HTTP、网关、网络和排队，适合回答：
> 给定一批已知输入，引擎本身最多能处理多少？
在线测试覆盖真实服务链路，适合回答：
> 在指定到达模式下，用户会看到什么延迟与吞吐？
二者都重要，但结果不能直接相减来推断“HTTP 开销”。在线调度、流式输出和离线批处理走的代码路径可能不同。
### 1.2 固定并发还是固定请求率
**固定并发**是闭环：
- 保持 N 个请求在途；一个完成后再补一个；服务变慢时，实际请求发起速率也随之下降。
它适合寻找系统饱和吞吐和容量上限。
**固定请求率**是开环：
- 请求按外部速率到达；服务变慢不会让未来用户自动变少；当到达率超过处理能力，队列与尾延迟会增长。
它更适合验证生产 SLO。📌 **关键点**：并发是“同时有多少活”，请求率是“每秒进来多少”；二者不是同一个旋钮。
### 1.3 用合成数据还是真实分布
合成固定长度便于控制变量，适合回归测试。真实数据能覆盖：
- 长度长尾；多轮对话结构；可缓存公共前缀；提前遇到 EOS。
最佳实践是两套都保留：
1. 固定形状的微基准用于定位变化。
2. 去敏并冻结的生产代表集用于验证外部有效性。
### 1.4 是否允许缓存
Prefix Cache 会让重复前缀请求显著改变 Prefill 工作量。若测试冷缓存：
- 每轮重启或清空缓存；让请求前缀足够不同；记录缓存相关配置。
若测试热缓存：
- 明确预热步骤；报告命中率；不与冷缓存结果混在一起。

## 2. vLLM 的三类 Benchmark
当前 vLLM Benchmark CLI 提供的命令会随版本演进。运行前先固定版本并查看本机帮助：
```bash
python - <<'PY'
import vllm
print(vllm.__version__)
PY
vllm bench --help
```
### 2.1 `vllm bench throughput`
用途：离线吞吐。它直接驱动离线推理，不要求预先启动 HTTP 服务。适合比较：
- 引擎参数；量化方案；Tensor Parallel 配置；固定数据集上的总处理能力。
不适合据此宣称在线 TTFT。命令模板：
```bash
vllm bench throughput \
  --model "$MODEL" \
  --dataset-name random \
  --input-len "$INPUT_LEN" \
  --output-len "$OUTPUT_LEN" \
  --num-prompts "$NUM_PROMPTS" \
  --seed "$SEED"
```
参数名称以已安装版本的 `--help` 为准。保存完整 stdout/stderr，不要只抄最后一行。
### 2.2 `vllm bench latency`
用途：离线延迟微基准。它更适合固定批次与形状下观察引擎延迟，不代表多用户在线排队。使用时记录：
- Batch 大小；输入/输出长度；预热轮次；重复轮次；是否启用 CUDA Graph/编译。
命令模板：
```bash
vllm bench latency \
  --model "$MODEL" \
  --input-len "$INPUT_LEN" \
  --output-len "$OUTPUT_LEN" \
  --batch-size "$BATCH_SIZE"
```
若你的版本不支持某参数，应以该版本官方 CLI 为准，不能为了“复现教程”盲目复制。
### 2.3 `vllm bench serve`
用途：在线服务压测。它从客户端测量 TTFT、TPOT、ITL、吞吐，并可按版本支持 E2E、Goodput 等统计。服务端先启动：
```bash
vllm serve "$MODEL" \
  --host 0.0.0.0 \
  --port "$PORT" \
  --tensor-parallel-size "$TP_SIZE" \
  2>&1 | tee "server-${RUN_ID}.log"
```
客户端与服务端最好分机部署。若同机运行，客户端 Tokenize、网络栈和日志写入可能与服务争用 CPU。

## 3. `vllm bench serve` 实战
### 3.1 先做可控冒烟
```bash
vllm bench serve \
  --backend vllm \
  --base-url "http://${SERVER_HOST}:${PORT}" \
  --endpoint /v1/completions \
  --model "$MODEL" \
  --dataset-name random \
  --input-len "$INPUT_LEN" \
  --output-len "$OUTPUT_LEN" \
  --num-prompts "$NUM_PROMPTS" \
  --request-rate "$REQUEST_RATE" \
  --max-concurrency "$MAX_CONCURRENCY" \
  --seed "$SEED" \
  --save-result \
  --save-detailed \
  --result-dir "$RESULT_DIR"
```
先执行：
```bash
vllm bench serve --help
```
确认你的版本是否使用 `--base-url`、结果目录与对应数据集参数。vLLM CLI 迭代较快，教程提供的是命令骨架，不是跨版本不变的 ABI。`--save-detailed` 会按版本保存生成文本、错误详情、逐请求时延与长度等字段；生成文本和错误内容可能含敏感信息，结果目录必须限制访问、设置保留期，并在共享前脱敏。
### 3.2 `--request-rate` 的含义
有限请求率通常按随机到达过程生成请求。它用于模拟互相独立的用户，而不是机械地每隔完全相同时间发一个请求。`--request-rate inf` 常表示尽快发送全部请求。这种模式适合压饱系统，不代表生产到达过程。
### 3.3 `--max-concurrency` 的含义
它限制客户端允许同时执行的请求数。当请求率很高、服务处理不够快时，并发上限会反过来限制实际发起速率。所以报告中应同时写：
- 配置请求率；最大并发；实际完成吞吐；Benchmark 持续时间。
### 3.4 生产代表数据
ShareGPT 等数据集能提供变长对话。模板：
```bash
vllm bench serve \
  --backend vllm \
  --base-url "http://${SERVER_HOST}:${PORT}" \
  --model "$MODEL" \
  --dataset-name sharegpt \
  --dataset-path "$DATASET_PATH" \
  --num-prompts "$NUM_PROMPTS" \
  --request-rate "$REQUEST_RATE" \
  --max-concurrency "$MAX_CONCURRENCY" \
  --seed "$SEED" \
  --save-result \
  --save-detailed \
  --result-dir "$RESULT_DIR"
```
同时计算数据文件哈希：
```bash
shasum -a 256 "$DATASET_PATH"
```
数据集名字相同不代表内容与预处理相同。
### 3.5 扫描负载曲线
不要只测一个并发点。先按低、中、高负载做阶梯扫描：
```bash
for rate in $REQUEST_RATES; do
  vllm bench serve \
    --backend vllm \
    --base-url "http://${SERVER_HOST}:${PORT}" \
    --model "$MODEL" \
    --dataset-name random \
    --input-len "$INPUT_LEN" \
    --output-len "$OUTPUT_LEN" \
    --num-prompts "$NUM_PROMPTS" \
    --request-rate "$rate" \
    --seed "$SEED" \
    --save-result \
    --save-detailed \
    --result-dir "${RESULT_ROOT}/rate-${rate}"
done
```
观察从“延迟平稳”到“排队快速增长”的拐点。脚本中的 `$REQUEST_RATES` 由实验者按硬件能力填写，本章不预设性能数值。
### 3.6 Goodput
部分 vLLM 版本支持 `--goodput` 一类配置，按 `ttft`、`tpot`、`e2el` 等阈值计算 Goodput。准确语法先查：
```bash
vllm bench serve --help | rg "goodput|percentile"
```
阈值来自业务 SLO，不应根据候选版本输出临时决定。

## 4. `benchmark_serving.py` 是什么
你会在旧文章、脚本和 vLLM 源码历史中看到：
```bash
python benchmarks/benchmark_serving.py ...
```
它是在线 Serving Benchmark 的源码脚本入口。在较新的发行版中，优先使用稳定公开入口：
```bash
vllm bench serve ...
```
理解二者关系有两个好处：
- 阅读旧实验记录时知道它测的仍是 Serving 路径；需要研究统计实现时，可以查看对应版本源码。
⚠️ 不要从 `main` 分支复制脚本去测试旧版已安装包。脚本、客户端协议和输出字段可能不匹配。复现历史结果时，应 checkout 其明确记录的 vLLM tag 或 commit。

## 5. GenAI-Perf 实战
GenAI-Perf 是 NVIDIA 面向生成式 AI 服务的压测工具。它能产生合成或数据集输入，输出 TTFT、ITL、请求吞吐、输出 Token 吞吐等，并保存 CSV/JSON。它适合统一测试 Triton、OpenAI 兼容服务等多种后端。

⚠️ **生命周期提示（2026-08）**：NVIDIA 已说明 GenAI-Perf 进入停止活跃开发阶段，新项目建议优先评估 AIPerf。下面保留 GenAI-Perf，是为了复现实验和维护已有流水线；新建压测平台时应先核对 AIPerf 的迁移文档与指标口径。

### 5.1 先固定工具版本
容器镜像应固定 digest，而不只写 `latest`：
```bash
docker image inspect "$GENAI_PERF_IMAGE" \
  --format '{{index .RepoDigests 0}}'
```
若使用 Python 包，也记录：
```bash
genai-perf --version
genai-perf profile --help
```
### 5.2 固定并发模板
```bash
genai-perf profile \
  -m "$MODEL" \
  --endpoint-type chat \
  --url "http://${SERVER_HOST}:${PORT}" \
  --streaming \
  --request-count "$NUM_PROMPTS" \
  --concurrency "$CONCURRENCY" \
  --random-seed "$SEED" \
  --tokenizer "$TOKENIZER" \
  --synthetic-input-tokens-mean "$INPUT_LEN" \
  --synthetic-input-tokens-stddev 0 \
  --output-tokens-mean "$OUTPUT_LEN" \
  --profile-export-file "$RESULT_DIR/profile.json"
```
选项随 GenAI-Perf 版本变化。必须让 `--help` 与固定版本文档共同成为实验附件。对 OpenAI 兼容服务，模型仍可能提前 EOS，因此应报告实际输出长度；`--output-tokens-mean-deterministic` 等能力有后端限制，不能不加说明地照搬 Triton 示例。
### 5.3 固定请求率模板
把：
```bash
--concurrency "$CONCURRENCY"
```
替换为：
```bash
--request-rate "$REQUEST_RATE"
```
不要在同一结果名下混合两种模式。固定并发更像“系统始终有活干”。固定请求率更像“外部世界按自己的节奏来”。
### 5.4 Sweep
支持该子命令的版本可以扫描负载：
```bash
genai-perf analyze \
  -m "$MODEL" \
  --sweep-type concurrency \
  --sweep-range "$START:$END" \
  <其余固定参数>
```
或：
```bash
genai-perf analyze \
  -m "$MODEL" \
  --sweep-type request_rate \
  --sweep-range "$START:$END:$STEP" \
  <其余固定参数>
```
范围由容量预实验决定，不应照抄教程中的任意数值。

## 6. 如何确认客户端没有成为瓶颈
压测器也需要被压测。检查以下信号：
- 客户端 CPU 是否长期满载；Tokenize 是否占用主要时间；客户端网络带宽是否接近上限；文件日志是否同步大量刷盘；实际发送率是否追不上配置请求率；增加客户端实例后服务吞吐是否继续上涨。
排查方法：
1. 客户端与服务端分机。
2. 预先生成并 Tokenize 数据（若工具支持）。
3. 减少非必要日志。
4. 用两台客户端重复同一到达率。
5. 服务端容量不变时，确认结果是否一致。
若多客户端改变结果，原客户端很可能在限流。

## 7. 结果解读与 trade-off
先做一个只用于校验口径的手算：若压测窗口为 $D$ 秒，成功请求实际输出 Token 总数为 $O$，则：
$$
\mathrm{OutputThroughput}=\frac{O}{D}
$$
假设教学样本中 $O=600$、$D=3$，输出吞吐为 $200\ \mathrm{tok/s}$。这不是任何模型或硬件的实测结果；工具报告若与按原始样本重算不一致，应先核对窗口起止、失败过滤与 Tokenizer。
### 7.1 请求吞吐上升，TTFT 尾延迟暴涨
可能原因：
- 系统进入排队区；Batch 更大，单请求等待更久；Prefill 干扰 Decode。
结论不是“这个点吞吐最好”，而是“这个点可能已经越过 SLO 容量”。
### 7.2 输出 tok/s 上升，请求 req/s 下降
先检查输出长度。如果候选请求平均生成更长，tok/s 会升，而完成请求数可能下降。同时报告长度分布才能解释。
### 7.3 TPOT 稳定，ITL P99 变差
平均 Decode 节奏没明显变化，但出现局部停顿。可能要检查：
- Chunked Prefill 插入；GC 或 CPU 调度；跨卡通信；抢占与重计算。
下一节会用时间线定位。
### 7.4 无限速结果很好，低请求率结果反而一般
高并发更容易形成大 Batch，使 GPU 利用充分。低流量场景 Batch 小，CPU launch 等固定开销更突出。这说明系统擅长饱和吞吐，不等于低负载延迟优秀。

## 9. 闭环与开环：用排队论理解压测器

### 9.1 闭环为何会“照顾”慢系统

固定并发 $N$ 的闭环中，一个虚拟用户通常遵循：

```text
发送请求 → 等待完成 → 可选 think time → 再发送
```

若平均响应时间为 $R$，平均 think time 为 $Z$，系统稳定时可用交互响应定律理解吞吐：

$$
X\approx\frac{N}{R+Z}
$$

当服务从 1 秒变成 2 秒，而 $N$ 与 $Z=0$ 不变，客户端发起吞吐会自然约减半。外部压力随系统变慢而减小，因此闭环不擅长暴露持续过载下的排队失控。

固定并发仍很有价值：

- 测“同时 N 个在途请求”下的稳定表现；
- 寻找饱和吞吐；
- 与连接池、上游信号量等真实闭环约束对应；
- 做可重复的容量曲线。

但报告必须写成“concurrency=N”，不能把完成的 req/s 反称为配置请求率。

### 9.2 开环为何能暴露 SLO 容量

开环先生成到达计划：

```text
a0, a1, a2, ...  （不由上一请求完成时间决定）
```

服务变慢时，新请求仍继续到达。设长期平均到达率为 $\lambda$，服务能力为 $\mu$：

- $\lambda<\mu$：可能达到稳态；
- $\lambda$ 接近 $\mu$：队列与尾延迟对波动高度敏感；
- $\lambda>\mu$：无有限队列控制时，积压会持续增长。

这解释了为什么“完成吞吐还没明显下降，P99 已先爆炸”。吞吐在饱和后可能停在 $\mu$，而排队时间继续增加。

### 9.3 Coordinated omission

如果压测器在服务慢时也推迟本应到达的请求，它就没有观测到那些排队延迟。这叫 coordinated omission。典型来源：

- 用单线程“发一个、等一个”模拟固定 RPS；
- `sleep(interval)` 后执行请求，但请求本身阻塞后续调度；
- 并发上限过低，使 `--request-rate` 的计划到达被客户端闸门延迟；
- 只按实际发送时间算 TTFT，不保留计划到达时间。

严谨的开环实验应区分：

```text
scheduled_at 计划到达
sent_at      实际发出
first_at     首事件到达
done_at      完成
```

若业务问题是“外部请求到达后的体验”，排队等待应从 `scheduled_at` 或真实入口接收时间开始计入。至少要报告 `sent_at - scheduled_at`，判断压测器是否追不上。

### 9.4 `max-concurrency` 是闸门，不是纯保护参数

开环请求率与最大并发一起使用时：

1. 到达过程决定请求何时“应该出现”；
2. 并发上限决定请求何时“允许执行”；
3. 服务过慢时，上限前会形成客户端侧等待；
4. 实际发送率可能低于配置请求率。

因此结果必须同时保存：

- 配置到达率；
- 计划到达数；
- 实际发送数与发送时间；
- 客户端等待；
- 最大在途数；
- 服务端入口到达率。

如果工具不导出计划时间，就不能证明它在严重过载时仍保持了纯开环语义。

## 10. Arrival process：平均 RPS 相同，压力可以完全不同

### 10.1 常量间隔

间隔固定为：

$$
\Delta t=\frac{1}{\lambda}
$$

它控制性强，适合回归；但比真实独立用户流量更平滑，可能低估瞬时排队。

### 10.2 泊松到达

泊松过程的相邻到达间隔服从指数分布：

$$
P(T>t)=e^{-\lambda t}
$$

其均值和标准差都是 $1/\lambda$，变异系数：

$$
CV=\frac{\sigma}{\mu}=1
$$

它允许短时间扎堆，也允许较长空隙。`vllm bench serve` 在有限 `--request-rate` 且 `--burstiness 1.0` 时采用这一思路。

### 10.3 Gamma 间隔与 burstiness

当前 vLLM 可用 Gamma 分布调整间隔，形状参数可由 `--burstiness` 控制。保持平均请求率相同：

- `burstiness < 1`：更强突发，$CV>1$；
- `burstiness = 1`：指数间隔，泊松到达；
- `burstiness > 1`：更平滑，$CV<1$；
- 趋近无限大：接近固定间隔。

命令骨架：

```bash
vllm bench serve \
  --backend vllm \
  --base-url "$BASE_URL" \
  --model "$MODEL" \
  --dataset-name random \
  --input-len "$INPUT_LEN" \
  --output-len "$OUTPUT_LEN" \
  --request-rate "$REQUEST_RATE" \
  --burstiness "$BURSTINESS" \
  --num-prompts "$NUM_PROMPTS" \
  --seed "$SEED" \
  --save-result \
  --save-detailed \
  --result-dir "$RESULT_DIR"
```

参数以固定版本的 `--help` 为准。比较 burstiness 时，数据顺序、请求率、请求数和 Seed 都应冻结，并重复多个 Seed。

### 10.4 Trace replay

生产流量常同时具有：

- 日夜周期；
- 秒级微突发；
- 租户相关到达；
- 多轮会话 think time；
- 长短请求与时段相关。

单一泊松过程无法表达这些结构。更真实的方法是导出脱敏 Trace：

```json
{"offset_ms":0,"request_id":"r1","input_tokens":128,"max_output_tokens":64}
{"offset_ms":17,"request_id":"r2","input_tokens":2048,"max_output_tokens":128}
{"offset_ms":18,"request_id":"r3","input_tokens":96,"max_output_tokens":32}
```

回放前必须确定：

- 时间是否整体缩放；
- 丢失请求如何处理；
- 请求内容与长度如何映射；
- 会话内 Prefix 是否保留；
- 高峰截取窗口是否有选择偏差。

Trace replay 更真实，但也更难归因。合成过程用于控制变量，Trace 用于验证代表性，两者互补。

### 10.5 用到达日志校验负载生成器

不要只相信 CLI 参数。对实际发送时间排序，计算相邻间隔，并检查：

```python
import json
import statistics

sent = []
with open("requests.jsonl", encoding="utf-8") as f:
    for line in f:
        row = json.loads(line)
        sent.append(row["sent_monotonic_ms"])

gaps = [b - a for a, b in zip(sent, sent[1:])]
print("count:", len(sent))
print("mean_gap_ms:", statistics.fmean(gaps))
print("gap_cv:", statistics.stdev(gaps) / statistics.fmean(gaps))
```

这段脚本只检查实际发送间隔。要识别并发闸门造成的 coordinated omission，还需要保存 `scheduled_monotonic_ms`。

## 11. Dataset、长度、采样与 Cache 的控制矩阵

### 11.1 不要只记录平均长度

至少保存：

- 输入 Token P50/P95/P99/max；
- 请求的目标输出长度与实际输出长度；
- 输入输出长度相关性；
- 多轮会话比例；
- 公共 Prefix 长度；
- 特殊 Token 与 Chat Template 版本。

两个数据集平均输入都为 1K Token，一个全是固定 1K，另一个在 32 与 16K 间长尾，对 KV Cache、调度和 Prefill 的压力完全不同。

### 11.2 固定输出长度不是一句 `max_tokens`

`max_tokens=128` 是上限，不保证实际生成 128 Token。模型可能提前 EOS。可复现实验应选择并说明：

1. 允许自然 EOS，报告实际长度分布；
2. 在工具和后端支持时忽略 EOS，固定工作量；
3. 使用输出长度可控的数据与停止条件；
4. 对自然生成结果按实际长度分层。

不同策略回答不同问题，不能混比。

### 11.3 Tokenizer 与 Chat Template

数据集原始文本相同，以下变化也会改变输入 Token：

- Tokenizer revision；
- BOS/EOS 插入；
- Chat Template；
- Tool schema 序列化；
- Reasoning 模式；
- 多模态占位 Token。

冻结 Tokenizer 后，应把预处理输出保存为清单：

```json
{"id":"r1","input_tokens":127,"requested_output_tokens":64,"prompt_sha256":"..."}
```

这样即使原始文本受许可证限制，也能核对工作量。

### 11.4 Cache 实验必须拆组

建议至少定义：

```yaml
cache_cases:
  cold_unique:
    reset_between_runs: true
    shared_prefix: false
  warm_shared_prefix:
    warmup_manifest: warmup.jsonl
    measured_manifest: measured.jsonl
    expected_shared_prefix_tokens: "<实测>"
  mixed_trace:
    cache_reset: once_per_run
    request_order: frozen
    report_hit_metrics: true
```

冷 Cache 不等于只重启客户端。服务端引擎 Cache、网关 Cache、模型文件页 Cache、编译 Cache 是不同层。要写清重置的是哪一层。

### 11.5 数据顺序也是变量

即使请求集合相同，顺序也会影响：

- Prefix Cache 命中；
- 动态 Batch 组合；
- 长请求阻塞；
- CUDA Graph Shape 命中；
- 显存碎片演化。

固定 Seed 只能在工具实现和数据版本相同的前提下复现顺序。最好直接保存最终请求 Manifest 与顺序哈希。

## 12. 可复现的 `vllm bench serve` 实验

下面是一份实验协议，不填任何虚构性能值。

### 12.1 冻结服务端

```bash
mkdir -p "$RESULT_ROOT/server" "$RESULT_ROOT/client"
python - <<'PY' > "$RESULT_ROOT/server/python-packages.txt"
import importlib.metadata
for name in ("vllm", "torch"):
    print(name, importlib.metadata.version(name))
PY
nvidia-smi -q > "$RESULT_ROOT/server/nvidia-smi-q.txt"
vllm serve "$MODEL" \
  --served-model-name "$SERVED_MODEL" \
  --tensor-parallel-size "$TP_SIZE" \
  --host 0.0.0.0 \
  --port "$PORT" \
  "${SERVER_ARGS[@]}" \
  2>&1 | tee "$RESULT_ROOT/server/service.log"
```

服务命令、环境变量、容器 digest 与模型 revision 要从部署系统直接导出，不能凭记忆补写。

### 12.2 冻结客户端接口

```bash
set -euo pipefail
mkdir -p "$RESULT_ROOT/client"
vllm bench serve --help > "$RESULT_ROOT/client/vllm-bench-serve-help.txt"
python - <<'PY' > "$RESULT_ROOT/client/tool-version.txt"
import vllm
print(vllm.__version__)
PY
python - "$INPUT_LEN" "$OUTPUT_LEN" "$NUM_PROMPTS" "$SEED" "$SERVED_MODEL" \
  > "$RESULT_ROOT/client/random-workload-manifest.json" <<'PY'
import json
import sys

input_len, output_len, num_prompts, seed = map(int, sys.argv[1:5])
json.dump(
    {
        "dataset_name": "random",
        "model": sys.argv[5],
        "input_len": input_len,
        "output_len": output_len,
        "num_prompts": num_prompts,
        "seed": seed,
    },
    sys.stdout,
    indent=2,
    sort_keys=True,
)
print()
PY
shasum -a 256 "$RESULT_ROOT/client/random-workload-manifest.json" \
  > "$RESULT_ROOT/client/random-workload-manifest.sha256"
```

这个协议使用 `random` 数据集，因此不读取 `DATASET_PATH`。它保存随机生成参数、Seed 与生成配置 Manifest；若改用外部数据集，再单独要求 `DATASET_PATH` 并保存文件哈希。`--save-detailed` 的逐请求结果用于核对实际长度和请求顺序，但仍要按敏感产物保护。

### 12.3 Pilot Run

先用少量请求验证：

- Endpoint 与模型名；
- Streaming 正常结束；
- Tokenizer 与服务一致；
- 结果文件确实生成；
- 服务无 OOM、错误和重启；
- 实际输出长度符合设计。

Pilot 结果不能混入正式统计。

### 12.4 泊松到达率 Sweep

```bash
set -euo pipefail
shopt -s nullglob

for rate in ${REQUEST_RATES}; do
  run_dir="${RESULT_ROOT}/client/rate-${rate}"
  if [[ -e "$run_dir" ]]; then
    echo "refusing to mix results in existing directory: $run_dir" >&2
    exit 1
  fi
  mkdir -p "$run_dir"
  vllm bench serve \
    --backend vllm \
    --base-url "http://${SERVER_HOST}:${PORT}" \
    --endpoint /v1/completions \
    --model "$SERVED_MODEL" \
    --dataset-name random \
    --input-len "$INPUT_LEN" \
    --output-len "$OUTPUT_LEN" \
    --num-prompts "$NUM_PROMPTS" \
    --request-rate "$rate" \
    --burstiness 1.0 \
    --seed "$SEED" \
    --save-result \
    --save-detailed \
    --result-dir "$run_dir" \
    2>&1 | tee "$run_dir/console.log"

  result_files=("$run_dir"/*.json)
  ((${#result_files[@]} > 0)) || {
    echo "benchmark produced no JSON result: $run_dir" >&2
    exit 1
  }
  python - "$NUM_PROMPTS" "${result_files[@]}" <<'PY'
import json
import pathlib
import sys

expected = int(sys.argv[1])
summaries = []
for raw_path in sys.argv[2:]:
    path = pathlib.Path(raw_path)
    with path.open(encoding="utf-8") as f:
        payload = json.load(f)
    if isinstance(payload, dict) and "completed" in payload:
        summaries.append((path, payload["completed"]))

if not summaries:
    raise SystemExit("no result JSON contains the required 'completed' field")
for path, completed in summaries:
    if not isinstance(completed, int) or not 0 < completed <= expected:
        raise SystemExit(f"invalid completed count in {path}: {completed!r}")
PY
done
```

`REQUEST_RATES` 来自容量 Pilot，不由教程提供。脚本以 `pipefail` 保留 `vllm` 的失败退出码，拒绝复用旧目录，并验证结果 JSON 可解析且 `completed` 合法；随后仍要按 12.5 的实验合同判断错误率和运行有效性。每个点重复多个 Seed，并在各轮间按 Cache 合同重置服务。

### 12.5 判定运行有效

每轮先检查：

1. 客户端实际发送率是否接近配置率；
2. 失败、取消、超时是否在合同内；
3. 服务端是否重启或 OOM；
4. 输入/实际输出长度是否与其他轮可比；
5. GPU、CPU 和网络是否有外部争用；
6. Benchmark 是否覆盖预热后的稳态窗口。

只有有效运行才进入负载—延迟曲线。

## 14. 完整案例：同为 8 req/s，为何一个通过、一个失败

以下是教学案例，只展示诊断逻辑，不代表真实硬件性能。

### 14.1 症状

固定数据集与服务配置，两个实验平均配置请求率都为 8 req/s：

- 实验 A：常量间隔；
- 实验 B：Gamma 突发到达。

A 的 TTFT 尾部稳定，B 出现周期性尖刺。团队怀疑 GPU 随机抖动。

### 14.2 到达证据

从客户端原始发送时间计算：

```text
A gaps(ms): 125, 125, 125, 125, 125, 125, 125, 125
B gaps(ms): 10, 15, 300, 12, 18, 320, 9, 316
```

两者长周期平均接近，但 B 经常在几十毫秒内连续到达多个请求。

### 14.3 长度与 Cache 证据

核对 Manifest：

```text
数据顺序：相同
输入/输出长度：相同
模型与 Tokenizer revision：相同
Cache：每轮重启，公共 Prefix 禁用
```

因此长度与 Cache 不是本次差异来源。

### 14.4 服务证据

服务端记录显示：

```text
A：队列深度大多为 0 或 1
B：突发时队列深度快速升高，突发后逐步清空
```

GPU 活跃时间与单步 Decode 没有对应的异常尖刺。TTFT 尖刺与 Queue Span 高度对齐。

### 14.5 结论

证据链：

1. 症状：同平均 RPS，B 的 TTFT P99 更差；
2. 到达证据：B 的间隔 CV 更高；
3. 控制证据：长度、顺序与 Cache 一致；
4. 服务证据：尖刺发生在排队，不是 GPU Step；
5. 结论：平均 RPS 不足以定义负载，突发性触发了瞬时排队。

正确报告应展示至少两条负载曲线：

- 平滑合成负载：用于稳定回归；
- 生产代表突发负载：用于 SLO 容量。

不能把 A 的结果当作 B 的生产承诺。

## 15. 压测评审清单

### 15.1 负载

- 闭环还是开环？
- 到达过程是常量、泊松、Gamma 还是 Trace？
- 配置率与实际率是否都保存？
- 是否有客户端并发闸门？
- Ramp、Warmup 与正式窗口如何分离？

### 15.2 数据

- 原始数据、预处理与最终 Manifest 是否有哈希？
- Tokenizer、Chat Template、采样和停止条件是否冻结？
- 目标输出长度与实际输出长度是否都报告？
- 请求顺序是否可复现？

### 15.3 Cache

- 重置、预热和测量步骤分别是什么？
- 命中率是否可观察？
- 公共 Prefix 是否属于业务事实还是实验泄漏？

### 15.4 工具与客户端

- 工具版本、帮助文本与完整命令是否保存？
- 客户端 CPU、网络和文件 I/O 是否有余量？
- 计划到达是否被实际发送落后？
- 多客户端验证是否改变结果？

### 15.5 结论

- 是否给出完整负载—延迟—Goodput 曲线？
- 是否把失败请求纳入护栏？
- 是否避免从 `request-rate=inf` 推导生产 SLO？
- 是否明确哪些数值是实测，哪些只是教学示例？

只有全部回答清楚，Benchmark 才从“命令跑通”升级为可审核实验。

- 离线 Benchmark 测引擎能力，在线 Benchmark 测用户可见链路；固定并发是闭环，固定请求率是开环；二者回答不同问题；`vllm bench throughput/latency/serve` 分别面向不同测量目标。
