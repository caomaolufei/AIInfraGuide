一次 Benchmark 证明“今天快”，回归门禁保证“明天不会悄悄变慢”。性能 CI 比单元测试难：硬件温度、邻居任务、编译缓存和随机流量都会让结果波动。所以门禁不是写一句“P95 退化 5% 就失败”，而是先测噪声，再定义合同。

## 1. 性能门禁到底防什么
门禁应捕获工程变更造成的可行动退化：
- Kernel 或算子变慢；调度策略使尾延迟恶化；默认参数变化降低吞吐；多卡通信重叠失效；显存增长导致可服务并发下降；输出处理或 Tokenize 成为 CPU 瓶颈；错误率上升却被“成功样本延迟”掩盖。
门禁不应把这些变化误判为代码退化：
- GPU 被其他 Job 争用；驱动或镜像未经记录地升级；数据集内容变化；温度、功耗限制或时钟策略变化；客户端无法维持配置到达率。
📌 **关键点**：先控制环境，再缩窄阈值；否则 CI 只是在测实验室噪声。
### 1.1 门禁是合同，不是排行榜
排行榜鼓励把数字推到极限。门禁关心：
> 候选版本是否仍满足预先声明的性能与质量合同？
因此门禁同时需要：
- 目标指标；护栏指标；质量检查；环境有效性检查；失败处理规则。

## 2. 三层测试金字塔
### 2.1 PR 级微基准
特点：
- 几分钟内完成；固定 Shape；低样本但高可控；只覆盖关键路径。
适合：
- 单 Kernel；单算子；固定 Batch 的 Prefill/Decode Step。
不适合代表真实在线尾延迟。
### 2.2 每日服务基准
特点：
- 启动完整服务；扫描若干请求率或并发；同时检查 TTFT、TPOT、ITL、吞吐、Goodput 与错误率；使用固定合成数据和代表数据各一套。
它是性能回归主力。
### 2.3 周期性长稳测试
特点：
- 时间更长；覆盖热稳定、内存碎片与缓存演化；可加入故障、扩缩容与多租户干扰。
它发现短 CI 看不到的慢性问题。
### 2.4 为什么不能只做端到端
端到端更真实，但噪声大、定位慢。微基准可控，但容易脱离真实调度。两者结合：
- 微基准快速指出“哪个部件变了”；服务基准判断“用户是否真的受影响”；长稳测试验证“影响是否随时间累积”。

## 3. 建立可复现环境
### 3.1 使用专用 Runner
理想的性能 Runner：
- 固定 GPU 型号与数量；无其他 GPU Job；固定 CPU 亲和性与 NUMA；固定功耗与时钟策略（若组织允许且记录完整）；固定驱动、固件与 CUDA；网络路径稳定。
共享 Runner 可以做趋势监控，不宜做很窄的硬门禁。
### 3.2 每次都做环境体检
保存：
```bash
nvidia-smi -q > "$ARTIFACT_DIR/nvidia-smi-q.txt"
nvidia-smi topo -m > "$ARTIFACT_DIR/nvidia-smi-topo.txt"
python -m torch.utils.collect_env > "$ARTIFACT_DIR/torch-env.txt"
python - <<'PY' > "$ARTIFACT_DIR/versions.txt"
import platform
import torch
print("python:", platform.python_version())
print("torch:", torch.__version__)
print("cuda:", torch.version.cuda)
print("cudnn:", torch.backends.cudnn.version())
PY
```
这些命令是模板。AMD 或其他加速器应替换为对应官方工具。
### 3.3 固定不可变产物
记录：
- 候选 commit；基线 commit；容器 image digest；模型 revision；Tokenizer revision；数据集 hash；服务与压测完整命令。
不要依赖：
- `latest`；浮动模型分支；在线会变化的数据 URL；未记录的环境变量。
### 3.4 预热合同
预热步骤本身也要版本化：
```yaml
warmup:
  server_ready_probe: true
  requests: "<固定数量或条件>"
  shapes: ["<覆盖正式测试 Shape>"]
  compile_complete_signal: "<日志或状态>"
  cache_policy: "<cold/warm>"
```
固定 Shape 的预热如果没覆盖正式 Shape，正式测试中仍可能发生编译或 CUDA Graph 捕获。
### 3.5 运行顺序
一直先跑 baseline、再跑 candidate，会把温度与时间漂移偏向一方。更稳妥的交替顺序：
```text
baseline → candidate → candidate → baseline
```
或按固定 Seed 随机化顺序。每次切换版本要确保服务、缓存与进程完全重置。

## 4. 设计指标合同
### 4.1 一个场景一份合同
交互式短回答：
```yaml
scenario: interactive-short
load:
  mode: request-rate
  rate: "<固定值>"
  input_output_lengths: "<固定分布>"
gates:
  quality: "<必须通过>"
  error_rate: "<绝对上限>"
  ttft_p95: "<绝对 SLO + 相对退化规则>"
  itl_p99: "<绝对 SLO + 相对退化规则>"
  goodput: "<绝对下限 + 相对退化规则>"
```
离线批处理：
```yaml
scenario: offline-batch
load:
  mode: offline
  dataset_hash: "<sha256>"
gates:
  quality: "<必须通过>"
  output_token_throughput: "<相对退化规则>"
  peak_memory: "<绝对上限>"
```
阈值必须来自本项目实测与业务 SLO，本章不提供虚构的通用百分比。
### 4.2 绝对阈值与相对阈值
绝对阈值回答：
> 是否仍满足用户承诺？
相对阈值回答：
> 相比健康基线是否发生可疑变化？
两者可以组合：
```text
Block =
  质量不通过
  OR 错误率超过绝对上限
  OR 延迟超过绝对 SLO
  OR 重复确认后的相对退化超过预算
```
### 4.3 多指标不能只取一个“综合分”
加权总分会互相抵消：
- 吞吐提升可能掩盖 TTFT 严重退化；均值改善可能掩盖 P99 恶化。
关键护栏使用独立条件。只有业务明确接受 trade-off 时，才使用 Pareto 或成本函数。
### 4.4 失败请求
最危险的门禁错误是只统计成功样本延迟。候选版本如果让慢请求超时失败，剩余成功请求可能看起来更快。必须先检查：
1. 请求总数一致。
2. 成功率达标。
3. 失败类型可解释。
4. 然后再比较延迟与吞吐。

## 5. 基线、重复与判定
### 5.1 不要永远和“上一次运行”比
上一次运行可能本身异常。可选基线：
- 发布版本固定基线；主分支最近一组健康运行；同一 Runner 上与候选交替重跑的 baseline commit。
对 PR 门禁，最后一种最能消除环境漂移，但成本更高。
### 5.2 先测噪声带
在没有代码变化时，重复运行同一版本。某指标相对基线变化：
$$
\Delta=\frac{M_{\mathrm{candidate}}-M_{\mathrm{baseline}}}{M_{\mathrm{baseline}}}
$$
对于“越低越好”的延迟，$\Delta>0$ 表示退化。对于“越高越好”的吞吐，可定义退化：
$$
\Delta_{\mathrm{bad}}=\frac{M_{\mathrm{baseline}}-M_{\mathrm{candidate}}}{M_{\mathrm{baseline}}}
$$
教学手算：
- 延迟基线 100 个抽象单位；候选 104 个抽象单位。
$$
(104-100)/100=4\%
$$
这只展示公式，不代表建议用 4% 作为门禁。阈值应明显大于同环境自然噪声，并结合业务预算。
### 5.3 使用稳健汇总
每个版本做多次独立运行。可优先比较：
- 多次运行中位数；置信区间或 Bootstrap 区间；配对运行差值。
不要：
- 把各轮 P99 平均后叫“总体 P99”；在结果不好时任意删掉某轮；只挑最优一轮发布。
### 5.4 灰区与复测
设置三态比简单 Pass/Fail 更实用：
- **Pass**：变化在安全区；**Retry/Investigate**：落入噪声灰区或环境体检可疑；**Fail**：重复确认后违反合同。
复测次数和触发条件要预先写入规则，不能看到结果后临时决定。
### 5.5 基线更新
仅在这些条件满足时更新：
- 变更已被审查并接受；质量与功能测试通过；性能变化有解释；新基线在专用 Runner 上重复稳定；关联实验产物长期保存。
绝不能为了让红灯变绿直接覆盖基线。

## 6. CI 命令与判定模板
### 6.1 目录结构
```text
perf-artifacts/
  metadata.yaml
  baseline/
    run-01.json
    run-02.json
  candidate/
    run-01.json
    run-02.json
  comparison.json
  report.md
  server-logs/
```
### 6.2 执行骨架
```bash
set -euo pipefail
RUN_ID="${CI_PIPELINE_ID:-local}-$(date -u +%Y%m%dT%H%M%SZ)"
ARTIFACT_DIR="perf-artifacts/${RUN_ID}"
mkdir -p "$ARTIFACT_DIR"
./scripts/collect-perf-env.sh "$ARTIFACT_DIR"
./scripts/run-perf-case.sh baseline "$ARTIFACT_DIR/baseline"
./scripts/run-perf-case.sh candidate "$ARTIFACT_DIR/candidate"
python scripts/compare-perf.py \
  --contract perf/contracts/interactive-short.yaml \
  --baseline "$ARTIFACT_DIR/baseline" \
  --candidate "$ARTIFACT_DIR/candidate" \
  --output "$ARTIFACT_DIR/comparison.json"
python scripts/render-perf-report.py \
  "$ARTIFACT_DIR/comparison.json" \
  > "$ARTIFACT_DIR/report.md"
```
这里的脚本名是项目设计模板，并不声称仓库已存在这些文件。
### 6.3 判定伪代码
```python
def evaluate(contract, baseline, candidate):
    violations = []
    if not candidate.quality_passed:
        violations.append("quality gate failed")
    if candidate.error_rate > contract.max_error_rate:
        violations.append("error-rate SLO violated")
    for gate in contract.metric_gates:
        result = compare_metric(
            baseline=baseline,
            candidate=candidate,
            gate=gate,
        )
        if result.confirmed_regression:
            violations.append(result.reason)
    return {
        "status": "fail" if violations else "pass",
        "violations": violations,
    }
```
真实实现还要处理：
- 缺失样本；NaN/Inf；工具版本不一致；环境体检失败；测试中断。
这些情况应标记“无效实验”，而不是默认为 Pass。
### 6.4 合同示例只放占位符
```yaml
metrics:
  ttft_p95_ms:
    direction: lower_is_better
    absolute_max: "<由 SLO 填写>"
    relative_regression_budget: "<由噪声实验填写>"
  output_throughput_tok_s:
    direction: higher_is_better
    relative_regression_budget: "<由噪声实验填写>"
  request_goodput_req_s:
    direction: higher_is_better
    absolute_min: "<由容量规划填写>"
```
不填“看起来合理”的默认数字，能迫使团队先做基线实验。
### 6.5 PR 报告
报告应包含：
- 运行有效性；Baseline/Candidate commit；环境差异；每个指标的原始值、方向和变化；阈值来源；重复运行分布；失败请求；原始产物链接；判定与下一步。
不要只评论“性能下降 3%”。

## 7. 失败后的定位流程
### 7.1 先判断实验是否有效
检查：
- 硬件型号与数量是否一致；是否存在邻居进程；温度/功耗/时钟是否异常；客户端是否达到配置请求率；模型与数据 hash 是否一致；服务日志是否有 OOM、重启或错误。
环境无效时重新排队，不要急着改代码。
### 7.2 确认是哪类指标
- TTFT：排队、Prefill、网关、缓存；TPOT：Decode 平均节奏；ITL 尾部：局部停顿、Prefill 干扰、CPU/通信尖刺；E2E：结合输出长度判断；Throughput：确认失败与长度；Goodput：找出违反哪条 SLO。
### 7.3 缩小提交范围
如果一段时间内出现回归：
```bash
git bisect start
git bisect bad "<bad-commit>"
git bisect good "<good-commit>"
```
自动化脚本应返回：
- `0`：性能通过；`1`：确认退化；`125`：环境无效，跳过该提交。
性能测试昂贵且有噪声，Bisect 每点需要重复确认。本节只说明方法，不建议在不受控 Runner 上机械 Bisect。
### 7.4 从 Benchmark 到 Trace
只在确认可复现后采 Profiler：
1. 选最小复现场景。
2. Baseline 与 Candidate 使用相同采集选项。
3. PyTorch Profiler 对比算子次数、Shape 与时间。
4. Nsight Systems 对齐 CPU/GPU/通信关键路径。
5. 必要时再用 Nsight Compute 检查目标 Kernel。
Trace 运行不用于更新门禁数值。
### 7.5 修复后验证
修复必须：
- 让原失败场景恢复；不破坏其他护栏指标；通过质量检查；在关闭 Profiler 后重跑；保存修复前后原始数据。

## 8. 门禁的 trade-off 与治理
### 8.1 灵敏度 vs 稳定性
阈值窄：
- 更早发现小退化；更多噪声误报。
阈值宽：
- CI 更稳定；小退化可能长期累积。
解决方式不是拍脑袋折中，而是提高环境稳定性、增加配对重复并分层测试。
### 8.2 CI 成本 vs 覆盖
每个 PR 跑完整负载曲线成本很高。用风险分层：
- 普通 PR：关键微基准；触及调度/Kernel/内存：增加服务基准；主分支每日：完整矩阵；发布前：长稳与多硬件。
### 8.3 自动阻断 vs 人工审查
确定性质量失败可以直接阻断。接近噪声边界的性能变化更适合标记并复测。每次 Override 必须记录：
- 谁批准；为什么接受；是否更新性能预算；后续跟踪任务。
### 8.4 指标漂移
业务负载会变化。定期检查固定数据集是否仍代表生产：
- 输入长度是否增长；输出是否更长；Cache 命中率是否变化；多模态或 Tool Calling 是否成为主流。
更新数据集时升 Benchmark 版本，并保留旧版本重叠运行一段时间。

## 9. 统计显著性：门禁要区分信号与噪声

### 9.1 先定义实验单位

一次请求不是总能作为独立重复。相同运行内的请求共享：

- GPU 温度与时钟；
- 服务进程状态；
- Cache；
- Batch；
- 到达突发；
- 编译与内存碎片。

把同一轮的十万请求当作十万个独立实验，会严重低估不确定性。性能 CI 通常应把“独立服务重启后的完整运行”作为高层实验单位，请求作为运行内样本。

### 9.2 技术重复与独立重复

- **技术重复**：同一服务进程连续发送更多请求；
- **独立重复**：重置服务、Cache 和采集状态后重新运行；
- **配对重复**：在相近时间和同一 Runner 上运行一对 Baseline/Candidate。

技术重复可稳定请求分位数，独立重复才能估计运行间波动。两者都需要。

### 9.3 显著不等于重要

统计显著性回答：

> 在假设与模型成立时，这个差异是否难以用随机波动解释？

工程重要性回答：

> 差异是否超过业务 SLO 或性能预算？

样本极大时，极小差异也可能统计显著；噪声很大时，业务上很严重的退化也可能暂时不显著。门禁要同时使用：

- Effect Size；
- 不确定区间；
- 业务阈值；
- 绝对 SLO；
- 环境有效性。

### 9.4 配对差值

第 $i$ 对运行的指标分别为 $B_i$ 与 $C_i$。延迟相对变化：

$$
d_i=\frac{C_i-B_i}{B_i}
$$

吞吐退化可以统一成“越大越坏”：

$$
d_i=\frac{B_i-C_i}{B_i}
$$

对 $d_i$ 做中位数与区间，通常比把所有 Baseline 合并、所有 Candidate 合并更能抵消时间漂移。

### 9.5 Bootstrap 的层级

若只对请求重采样，会忽略运行间变化。更稳妥的层级 Bootstrap：

1. 有放回抽取运行对；
2. 在每个抽中的运行内，有放回抽取请求；
3. 重算每轮指标；
4. 计算配对差值；
5. 重复得到差值分布。

尾分位数的 Bootstrap 仍需要足够原始样本。极端 P99.9 在小样本下不能靠 Bootstrap 变得可信。

### 9.6 一个可审查的配对 Bootstrap 骨架

```python
from __future__ import annotations

import numpy as np

def percentile(samples: np.ndarray, q: float) -> float:
    return float(np.percentile(samples, q, method="linear"))

def paired_bootstrap(
    baseline_runs: list[np.ndarray],
    candidate_runs: list[np.ndarray],
    q: float,
    iterations: int,
    seed: int,
) -> np.ndarray:
    if len(baseline_runs) != len(candidate_runs):
        raise ValueError("runs must be paired")
    rng = np.random.default_rng(seed)
    effects = []
    pair_count = len(baseline_runs)
    for _ in range(iterations):
        selected = rng.integers(0, pair_count, pair_count)
        pair_effects = []
        for index in selected:
            b = baseline_runs[index]
            c = candidate_runs[index]
            b_sample = rng.choice(b, size=len(b), replace=True)
            c_sample = rng.choice(c, size=len(c), replace=True)
            b_metric = percentile(b_sample, q)
            c_metric = percentile(c_sample, q)
            pair_effects.append((c_metric - b_metric) / b_metric)
        effects.append(float(np.median(pair_effects)))
    return np.asarray(effects)
```

这只是算法骨架，不是仓库现成脚本。生产实现还要检查空样本、失败请求、长度分层和运行有效性，并在元数据中固定 NumPy 版本、`method`、迭代数与 Seed。

### 9.7 置信区间式判定

设“可容忍相对退化预算”为 $\delta$，Bootstrap 差值区间为 $[L,U]$：

```text
U < δ                 → 没有证据表明超过预算，可 Pass
L > δ                 → 区间整体超过预算，可 Fail
L <= δ <= U           → 不确定，Retry/Investigate
```

同时只要绝对 SLO 已违反，就不必等相对比较显著才阻断。

### 9.8 多重比较

如果同时检查 50 个指标，每项都用独立的 5% 假阳性水平，整体误报概率会放大。解决方向：

- 只把少数关键指标设为硬门禁；
- 其余作为诊断指标；
- 预先定义主指标与次指标；
- 需要时使用多重检验校正；
- 不因某个未预先声明的 Dashboard 尖刺临时追加 Fail。

工程上最有效的往往不是复杂校正，而是减少硬门禁指标并提高每个指标的可解释性。

## 10. Noise budget：把波动拆成可以治理的来源

### 10.1 总噪声不是一个数

可把观测变化粗略写成：

$$
\mathrm{Observed}
=\mathrm{CodeEffect}
+\mathrm{EnvironmentNoise}
+\mathrm{WorkloadNoise}
+\mathrm{MeasurementNoise}
+\mathrm{OrderDrift}
$$

这不是严格可加的统计模型，而是排查框架。

### 10.2 环境噪声

包括：

- GPU 温度、时钟、功耗与节流；
- CPU 频率与 NUMA；
- 邻居进程；
- 网络拥塞；
- 驱动和固件变化；
- 云实例底层差异；
- 容器配额。

治理：

- 专用 Runner；
- 环境体检；
- 固定拓扑；
- 运行无效条件；
- Baseline/Candidate 配对。

### 10.3 工作负载噪声

包括：

- 随机到达；
- 请求顺序；
- 输入/输出长度；
- 自然 EOS；
- Cache 命中；
- Seed；
- 多轮会话状态。

治理：

- 冻结 Manifest；
- 保存计划与实际到达；
- 固定或分层长度；
- 明确 Cache 合同；
- 多 Seed 重复。

### 10.4 测量噪声

包括：

- 客户端时间精度；
- 网络库缓冲；
- Chunk/Token 口径；
- Profiler 扰动；
- 直方图桶；
- 丢失事件；
- 时钟跨机对齐误差。

治理：

- 同机单调时钟测 Duration；
- 原始事件 Schema；
- 工具版本冻结；
- 无 Profiler 性能运行；
- 分位数算法固定；
- 数据完整性检查。

### 10.5 顺序漂移

包括：

- 系统逐渐升温；
- Cache 或内存碎片逐渐变化；
- 长时间后台任务；
- 先运行的一方总是冷态。

治理：

- ABBA/BAAB；
- 轮间完整重置；
- 时间作为协变量；
- 随机化顺序；
- 长稳测试单独建模。

### 10.6 建立噪声预算表

```yaml
noise_budget:
  metric: ttft_p95_ms
  environment:
    estimated_range: "<同版本重复实测>"
    controls: ["dedicated-runner", "health-check"]
  workload:
    estimated_range: "<跨Seed实测>"
    controls: ["frozen-manifest", "paired-seed"]
  measurement:
    estimated_range: "<工具对照实测>"
    controls: ["raw-events", "fixed-percentile-method"]
  order:
    estimated_range: "<ABBA实验>"
    controls: ["paired-order"]
  business_regression_budget: "<产品与容量规划给出>"
```

若自然波动已接近业务预算，正确行动是降低噪声或增加重复，不是任意放宽阈值。

### 10.7 用方差分量决定投资

可以设计小型实验：

1. 同进程连续重复，估计运行内波动；
2. 重启服务重复，增加启动/Cache 波动；
3. 跨天重复，增加环境漂移；
4. 跨 Runner 重复，估计硬件差异；
5. 多 Seed 重复，估计负载随机性。

最大波动来源决定治理优先级。若跨 Runner 差异最大，就应做 Runner 分层基线，而不是继续增加同进程请求数。

门禁报告应该是原始数据的派生产物。只保存 Markdown 摘要，未来无法修正统计 Bug 或重新计算新指标。

### 11.6 Schema 治理

- Schema 有语义版本；
- 新增可选字段可兼容小版本；
- 改变字段含义必须升主版本；
- 单位写进字段名或 `unit`；
- 时间明确 ns/ms 与时钟来源；
- 枚举有文档；
- 解析器拒绝未知主版本；
- CI 对 Schema 做验证；
- 原始数据不可原地覆盖。

## 12. 基线治理：让“健康”可追溯

### 12.1 基线不是一个 JSON 文件

基线应是版本化对象：

```yaml
baseline:
  id: "<不可变ID>"
  contract_version: "<版本>"
  source_commit: "<完整SHA>"
  run_ids: ["<多次健康运行>"]
  runner_class: "<硬件与拓扑类别>"
  created_at: "<时间>"
  approved_by: ["<责任人>"]
  reason: "<发布/接受优化/环境迁移>"
  artifacts_digest: "<hash>"
  supersedes: "<旧基线ID或null>"
```

Dashboard 中的“当前基线”只是指向不可变对象的别名。

### 12.2 Runner 分层

即使 GPU 型号相同，不同 Runner 也可能有系统差异。可建立：

- 全局逻辑基线：同一 Commit 与合同；
- Runner Class 基线：同型号、拓扑、功耗策略；
- 单机校准因子：仅在被验证稳定时使用；
- 候选同机配对基线：最高可信但成本较高。

不要把 A 机历史结果直接与 B 机候选做窄阈值比较。

### 12.3 基线更新提案

更新必须携带：

1. 旧/新基线 ID；
2. 代码、环境、模型或数据为何变化；
3. 质量结果；
4. 性能 Effect 与区间；
5. 业务是否接受 Trade-off；
6. 审批人；
7. 回滚指针；
8. 原始产物。

“CI 一直红”不是更新理由。

### 12.4 环境迁移

驱动、固件、Runner 或模型升级时：

```text
旧环境 + 旧代码
新环境 + 旧代码
新环境 + 新代码
```

至少保留桥接运行，区分环境效应与代码效应。若旧环境已无法运行，应把历史可比性中断写入基线元数据。

### 12.5 基线老化

基线需要定期检查：

- 工作负载是否仍代表生产；
- SLO 是否变化；
- Runner 是否漂移；
- 软件依赖是否已不支持；
- 样本量是否满足当前尾分位数；
- 原始产物是否仍可读取。

老化基线不应静默继续阻断，而应触发治理任务。

## 13. CI 门禁状态机

### 13.1 先判 Validity

```text
START
  ├─ 环境不匹配/数据损坏/客户端未达负载 → INVALID
  ├─ 质量失败/错误率超绝对上限        → FAIL
  ├─ 绝对SLO违反                     → FAIL
  └─ 进入相对性能比较
```

`INVALID` 与 `FAIL` 必须分开。前者说明实验不能解释代码，后者说明有效实验违反合同。

### 13.2 相对比较

```text
区间完全在预算安全侧      → PASS
区间跨越预算              → RETRY
区间完全超过预算          → FAIL
效果很小但统计显著        → PASS并记录
效果很大但区间过宽        → RETRY/增加重复
```

### 13.3 Retry 有限且预定义

```yaml
retry_policy:
  max_attempts: "<预先设置>"
  rerun_scope: "完整Baseline/Candidate配对"
  trigger:
    - "interval_crosses_budget"
    - "transient_environment_warning"
  aggregation: "<预先设置>"
  exhausted_status: "investigate"
```

不能只重跑 Candidate，也不能一直重跑直到绿色。

### 13.4 硬门禁、软门禁与观察项

- 硬门禁：质量、错误率、绝对 SLO、确认的关键性能退化；
- 软门禁：区间不确定、非关键指标异常、预算接近耗尽；
- 观察项：资源利用、次要 Operator、实验性指标。

每个指标都变硬门禁会导致告警疲劳。

### 13.5 性能预算累积

多个 PR 各退化一点，单次都未过阈值，累计可能严重。除了 PR 配对门禁，还要：

- 每日与发布基线比较；
- 画长期趋势；
- 维护预算余额；
- 对连续同方向小退化告警；
- 发布前做完整基线复核。

## 14. 完整案例：一个看似 6% 的 TTFT 回归

以下数字是教学样本，不是推荐阈值，也不代表任何硬件。

### 14.1 症状

PR 报告：

```text
Baseline TTFT P95: 100 ms
Candidate TTFT P95: 106 ms
Relative change: +6%
```

旧规则是“超过 5% 失败”，CI 直接变红。

### 14.2 第一层证据：运行有效性

原始元数据显示：

```text
Baseline 运行在 Runner A
Candidate 运行在 Runner B
Runner B GPU功耗上限与A不同
数据集哈希相同
客户端工具版本相同
错误率均正常
```

结论：该比较混入 Runner 差异，不能作为代码回归证据。状态应是 `INVALID`，不是 `FAIL`。

### 14.3 第二层证据：同机配对

在同一专用 Runner 上按 ABBA 运行四对，得到教学差值：

```text
Pair 1: +1.0%
Pair 2: +2.5%
Pair 3: -0.5%
Pair 4: +1.8%
```

中位数约为：

$$
\mathrm{median}(-0.5,1.0,1.8,2.5)=1.4\%
$$

这与最初跨机 +6% 完全不同。

### 14.4 第三层证据：Noise budget

同版本历史配对显示：

```text
运行间波动：主要来自到达Seed与GPU温度
当前四对区间跨越“无变化”
业务绝对TTFT SLO：候选仍满足
```

因此证据不支持“确认回归超过预算”。

### 14.5 请求级证据

进一步按输入长度分桶：

```text
短输入桶：无一致变化
长输入桶：候选有同方向小幅上升
Cache命中率：一致
输出长度：一致
```

这提供了可调查线索，但样本不足以硬阻断。

### 14.6 决策

```text
最初跨Runner结果：INVALID
同机配对结果：PASS或软告警（取决于预先合同）
后续：增加长输入桶样本，在每日服务基准继续观察
```

### 14.7 如果结论相反

假如配对 Bootstrap 区间整体超过相对预算，且绝对 SLO 也接近上限，则应：

1. 标记 `FAIL`；
2. 用最小长输入场景复现；
3. 对比 Prefill、Queue 与 Cache；
4. 需要时采 PyTorch Profiler/Nsight Systems；
5. 修复后关闭 Profiler 重跑完整门禁。

### 14.8 案例结论

证据链：

```text
症状：摘要显示+6%
证据：Baseline/Candidate跨Runner
结论：初始实验无效
证据：同机ABBA差异显著缩小
证据：区间未证明超过预算，绝对SLO通过
最终：不按代码回归阻断，保留长输入软告警
```

门禁的价值不是“更容易红”，而是让红灯指向可行动的代码事实。

## 📝 总结
- 性能门禁首先要隔离环境噪声，再判断代码变化；PR 微基准、每日服务基准与周期性长稳测试各有职责；门禁合同应包含质量、错误率、延迟、吞吐和 Goodput 护栏；阈值来源是业务 SLO 与重复实验噪声，不是教程中的任意百分比；Baseline/Candidate 交替运行、保存原始样本和设置灰区能减少误报。
- 门禁失败后先验证实验，再用 Bisect、PyTorch Profiler 和 Nsight Systems 缩小根因。
