一次 Benchmark 证明“今天快”，回归门禁保证“明天不会悄悄变慢”。性能 CI 比单元测试难：硬件温度、邻居任务、编译缓存和随机流量都会让结果波动。所以门禁不是写一句“P95 退化 5% 就失败”，而是先测噪声，再定义合同。

## 1. 性能门禁到底防什么
门禁应捕获工程变更造成的可行动退化：
- Kernel 或算子变慢；调度策略使尾延迟恶化；默认参数变化降低吞吐；多卡通信重叠失效；显存增长导致可服务并发下降；输出处理或 Tokenize 成为 CPU 瓶颈；错误率上升却被“成功样本延迟”掩盖。
门禁不应把这些变化误判为代码退化：
- GPU 被其他 Job 争用；驱动或镜像未经记录地升级；数据集内容变化；温度、功耗限制或时钟策略变化；客户端无法维持配置到达率。
📌 **关键点**：先控制环境，再缩窄阈值；否则 CI 只是在测实验室噪声。
### 1.1 门禁是合同，不是排行榜
排行榜鼓励把数字推到极限。门禁关心：
> 候选版本是否仍满足预先声明的性能与质量合同？
因此门禁同时需要：
- 目标指标；护栏指标；质量检查；环境有效性检查；失败处理规则。

## 2. 三层测试金字塔
### 2.1 PR 级微基准
特点：
- 几分钟内完成；固定 Shape；低样本但高可控；只覆盖关键路径。
适合：
- 单 Kernel；单算子；固定 Batch 的 Prefill/Decode Step。
不适合代表真实在线尾延迟。
### 2.2 每日服务基准
特点：
- 启动完整服务；扫描若干请求率或并发；同时检查 TTFT、TPOT、ITL、吞吐、Goodput 与错误率；使用固定合成数据和代表数据各一套。
它是性能回归主力。
### 2.3 周期性长稳测试
特点：
- 时间更长；覆盖热稳定、内存碎片与缓存演化；可加入故障、扩缩容与多租户干扰。
它发现短 CI 看不到的慢性问题。
### 2.4 为什么不能只做端到端
端到端更真实，但噪声大、定位慢。微基准可控，但容易脱离真实调度。两者结合：
- 微基准快速指出“哪个部件变了”；服务基准判断“用户是否真的受影响”；长稳测试验证“影响是否随时间累积”。

## 3. 建立可复现环境
### 3.1 使用专用 Runner
理想的性能 Runner：
- 固定 GPU 型号与数量；无其他 GPU Job；固定 CPU 亲和性与 NUMA；固定功耗与时钟策略（若组织允许且记录完整）；固定驱动、固件与 CUDA；网络路径稳定。
共享 Runner 可以做趋势监控，不宜做很窄的硬门禁。
### 3.2 每次都做环境体检
保存：
```bash
nvidia-smi -q > "$ARTIFACT_DIR/nvidia-smi-q.txt"
nvidia-smi topo -m > "$ARTIFACT_DIR/nvidia-smi-topo.txt"
python -m torch.utils.collect_env > "$ARTIFACT_DIR/torch-env.txt"
python - <<'PY' > "$ARTIFACT_DIR/versions.txt"
import platform
import torch
print("python:", platform.python_version())
print("torch:", torch.__version__)
print("cuda:", torch.version.cuda)
print("cudnn:", torch.backends.cudnn.version())
PY
```
这些命令是模板。AMD 或其他加速器应替换为对应官方工具。
### 3.3 固定不可变产物
记录：
- 候选 commit；基线 commit；容器 image digest；模型 revision；Tokenizer revision；数据集 hash；服务与压测完整命令。
不要依赖：
- `latest`；浮动模型分支；在线会变化的数据 URL；未记录的环境变量。
### 3.4 预热合同
预热步骤本身也要版本化：
```yaml
warmup:
  server_ready_probe: true
  requests: "<固定数量或条件>"
  shapes: ["<覆盖正式测试 Shape>"]
  compile_complete_signal: "<日志或状态>"
  cache_policy: "<cold/warm>"
```
固定 Shape 的预热如果没覆盖正式 Shape，正式测试中仍可能发生编译或 CUDA Graph 捕获。
### 3.5 运行顺序
一直先跑 baseline、再跑 candidate，会把温度与时间漂移偏向一方。更稳妥的交替顺序：
```text
baseline → candidate → candidate → baseline
```
或按固定 Seed 随机化顺序。每次切换版本要确保服务、缓存与进程完全重置。

## 4. 设计指标合同
### 4.1 一个场景一份合同
交互式短回答：
```yaml
scenario: interactive-short
load:
  mode: request-rate
  rate: "<固定值>"
  input_output_lengths: "<固定分布>"
gates:
  quality: "<必须通过>"
  error_rate: "<绝对上限>"
  ttft_p95: "<绝对 SLO + 相对退化规则>"
  itl_p99: "<绝对 SLO + 相对退化规则>"
  goodput: "<绝对下限 + 相对退化规则>"
```
离线批处理：
```yaml
scenario: offline-batch
load:
  mode: offline
  dataset_hash: "<sha256>"
gates:
  quality: "<必须通过>"
  output_token_throughput: "<相对退化规则>"
  peak_memory: "<绝对上限>"
```
阈值必须来自本项目实测与业务 SLO，本章不提供虚构的通用百分比。
### 4.2 绝对阈值与相对阈值
绝对阈值回答：
> 是否仍满足用户承诺？
相对阈值回答：
> 相比健康基线是否发生可疑变化？
两者可以组合：
```text
Block =
  质量不通过
  OR 错误率超过绝对上限
  OR 延迟超过绝对 SLO
  OR 重复确认后的相对退化超过预算
```
### 4.3 多指标不能只取一个“综合分”
加权总分会互相抵消：
- 吞吐提升可能掩盖 TTFT 严重退化；均值改善可能掩盖 P99 恶化。
关键护栏使用独立条件。只有业务明确接受 trade-off 时，才使用 Pareto 或成本函数。
### 4.4 失败请求
最危险的门禁错误是只统计成功样本延迟。候选版本如果让慢请求超时失败，剩余成功请求可能看起来更快。必须先检查：
1. 请求总数一致。
2. 成功率达标。
3. 失败类型可解释。
4. 然后再比较延迟与吞吐。

## 5. 基线、重复与判定
### 5.1 不要永远和“上一次运行”比
上一次运行可能本身异常。可选基线：
- 发布版本固定基线；主分支最近一组健康运行；同一 Runner 上与候选交替重跑的 baseline commit。
对 PR 门禁，最后一种最能消除环境漂移，但成本更高。
### 5.2 先测噪声带
在没有代码变化时，重复运行同一版本。某指标相对基线变化：
$$
\Delta=\frac{M_{\mathrm{candidate}}-M_{\mathrm{baseline}}}{M_{\mathrm{baseline}}}
$$
对于“越低越好”的延迟，$\Delta>0$ 表示退化。对于“越高越好”的吞吐，可定义退化：
$$
\Delta_{\mathrm{bad}}=\frac{M_{\mathrm{baseline}}-M_{\mathrm{candidate}}}{M_{\mathrm{baseline}}}
$$
教学手算：
- 延迟基线 100 个抽象单位；候选 104 个抽象单位。
$$
(104-100)/100=4\%
$$
这只展示公式，不代表建议用 4% 作为门禁。阈值应明显大于同环境自然噪声，并结合业务预算。
### 5.3 使用稳健汇总
每个版本做多次独立运行。可优先比较：
- 多次运行中位数；置信区间或 Bootstrap 区间；配对运行差值。
不要：
- 把各轮 P99 平均后叫“总体 P99”；在结果不好时任意删掉某轮；只挑最优一轮发布。
### 5.4 灰区与复测
设置三态比简单 Pass/Fail 更实用：
- **Pass**：变化在安全区；**Retry/Investigate**：落入噪声灰区或环境体检可疑；**Fail**：重复确认后违反合同。
复测次数和触发条件要预先写入规则，不能看到结果后临时决定。
### 5.5 基线更新
仅在这些条件满足时更新：
- 变更已被审查并接受；质量与功能测试通过；性能变化有解释；新基线在专用 Runner 上重复稳定；关联实验产物长期保存。
绝不能为了让红灯变绿直接覆盖基线。

## 6. CI 命令与判定模板
### 6.1 目录结构
```text
perf-artifacts/
  metadata.yaml
  baseline/
    run-01.json
    run-02.json
  candidate/
    run-01.json
    run-02.json
  comparison.json
  report.md
  server-logs/
```
### 6.2 执行骨架
```bash
set -euo pipefail
RUN_ID="${CI_PIPELINE_ID:-local}-$(date -u +%Y%m%dT%H%M%SZ)"
ARTIFACT_DIR="perf-artifacts/${RUN_ID}"
mkdir -p "$ARTIFACT_DIR"
./scripts/collect-perf-env.sh "$ARTIFACT_DIR"
./scripts/run-perf-case.sh baseline "$ARTIFACT_DIR/baseline"
./scripts/run-perf-case.sh candidate "$ARTIFACT_DIR/candidate"
python scripts/compare-perf.py \
  --contract perf/contracts/interactive-short.yaml \
  --baseline "$ARTIFACT_DIR/baseline" \
  --candidate "$ARTIFACT_DIR/candidate" \
  --output "$ARTIFACT_DIR/comparison.json"
python scripts/render-perf-report.py \
  "$ARTIFACT_DIR/comparison.json" \
  > "$ARTIFACT_DIR/report.md"
```
这里的脚本名是项目设计模板，并不声称仓库已存在这些文件。
### 6.3 判定伪代码
```python
def evaluate(contract, baseline, candidate):
    violations = []
    if not candidate.quality_passed:
        violations.append("quality gate failed")
    if candidate.error_rate > contract.max_error_rate:
        violations.append("error-rate SLO violated")
    for gate in contract.metric_gates:
        result = compare_metric(
            baseline=baseline,
            candidate=candidate,
            gate=gate,
        )
        if result.confirmed_regression:
            violations.append(result.reason)
    return {
        "status": "fail" if violations else "pass",
        "violations": violations,
    }
```
真实实现还要处理：
- 缺失样本；NaN/Inf；工具版本不一致；环境体检失败；测试中断。
这些情况应标记“无效实验”，而不是默认为 Pass。
### 6.4 合同示例只放占位符
```yaml
metrics:
  ttft_p95_ms:
    direction: lower_is_better
    absolute_max: "<由 SLO 填写>"
    relative_regression_budget: "<由噪声实验填写>"
  output_throughput_tok_s:
    direction: higher_is_better
    relative_regression_budget: "<由噪声实验填写>"
  request_goodput_req_s:
    direction: higher_is_better
    absolute_min: "<由容量规划填写>"
```
不填“看起来合理”的默认数字，能迫使团队先做基线实验。
### 6.5 PR 报告
报告应包含：
- 运行有效性；Baseline/Candidate commit；环境差异；每个指标的原始值、方向和变化；阈值来源；重复运行分布；失败请求；原始产物链接；判定与下一步。
不要只评论“性能下降 3%”。

## 7. 失败后的定位流程
### 7.1 先判断实验是否有效
检查：
- 硬件型号与数量是否一致；是否存在邻居进程；温度/功耗/时钟是否异常；客户端是否达到配置请求率；模型与数据 hash 是否一致；服务日志是否有 OOM、重启或错误。
环境无效时重新排队，不要急着改代码。
### 7.2 确认是哪类指标
- TTFT：排队、Prefill、网关、缓存；TPOT：Decode 平均节奏；ITL 尾部：局部停顿、Prefill 干扰、CPU/通信尖刺；E2E：结合输出长度判断；Throughput：确认失败与长度；Goodput：找出违反哪条 SLO。
### 7.3 缩小提交范围
如果一段时间内出现回归：
```bash
git bisect start
git bisect bad "<bad-commit>"
git bisect good "<good-commit>"
```
自动化脚本应返回：
- `0`：性能通过；`1`：确认退化；`125`：环境无效，跳过该提交。
性能测试昂贵且有噪声，Bisect 每点需要重复确认。本节只说明方法，不建议在不受控 Runner 上机械 Bisect。
### 7.4 从 Benchmark 到 Trace
只在确认可复现后采 Profiler：
1. 选最小复现场景。
2. Baseline 与 Candidate 使用相同采集选项。
3. PyTorch Profiler 对比算子次数、Shape 与时间。
4. Nsight Systems 对齐 CPU/GPU/通信关键路径。
5. 必要时再用 Nsight Compute 检查目标 Kernel。
Trace 运行不用于更新门禁数值。
### 7.5 修复后验证
修复必须：
- 让原失败场景恢复；不破坏其他护栏指标；通过质量检查；在关闭 Profiler 后重跑；保存修复前后原始数据。

## 8. 门禁的 trade-off 与治理
### 8.1 灵敏度 vs 稳定性
阈值窄：
- 更早发现小退化；更多噪声误报。
阈值宽：
- CI 更稳定；小退化可能长期累积。
解决方式不是拍脑袋折中，而是提高环境稳定性、增加配对重复并分层测试。
### 8.2 CI 成本 vs 覆盖
每个 PR 跑完整负载曲线成本很高。用风险分层：
- 普通 PR：关键微基准；触及调度/Kernel/内存：增加服务基准；主分支每日：完整矩阵；发布前：长稳与多硬件。
### 8.3 自动阻断 vs 人工审查
确定性质量失败可以直接阻断。接近噪声边界的性能变化更适合标记并复测。每次 Override 必须记录：
- 谁批准；为什么接受；是否更新性能预算；后续跟踪任务。
### 8.4 指标漂移
业务负载会变化。定期检查固定数据集是否仍代表生产：
- 输入长度是否增长；输出是否更长；Cache 命中率是否变化；多模态或 Tool Calling 是否成为主流。
更新数据集时升 Benchmark 版本，并保留旧版本重叠运行一段时间。

## 📝 总结
- 性能门禁首先要隔离环境噪声，再判断代码变化；PR 微基准、每日服务基准与周期性长稳测试各有职责；门禁合同应包含质量、错误率、延迟、吞吐和 Goodput 护栏；阈值来源是业务 SLO 与重复实验噪声，不是教程中的任意百分比；Baseline/Candidate 交替运行、保存原始样本和设置灰区能减少误报。
- 门禁失败后先验证实验，再用 Bisect、PyTorch Profiler 和 Nsight Systems 缩小根因。
