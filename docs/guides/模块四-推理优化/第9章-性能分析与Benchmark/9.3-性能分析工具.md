## 1. 先建立定位漏斗
一次线上退化建议按四层下钻：
1. **客户端指标**：TTFT、ITL、TPOT、E2E、Goodput 哪个变了？
2. **服务端阶段**：排队、Prefill、Decode、通信还是输出处理？
3. **框架算子**：哪些 PyTorch Operator 或 Kernel 占时变化？
4. **Kernel 微架构**：访存、占用率、指令或分支哪里受限？
对应工具：
- 压测器负责第 1 层；服务日志、指标与 NVTX 负责第 2 层；PyTorch Profiler 负责第 3 层；Nsight Systems 连接第 2、3 层，并展示 CPU/GPU/通信全局关系；Nsight Compute 在假设已收敛到少数 Kernel 后负责第 4 层。
📌 **关键点**：不要因为“GPU 慢”就直接抓最重的 Nsight Compute 指标。如果根因是排队或 Python 线程阻塞，Kernel 报告再详细也没有答案。
### 1.1 先做无 Profiler 基线
Profiler 会扰动被测系统。因此先运行两份：
- 不开 Profiler 的性能基线；开 Profiler 的诊断运行。
诊断运行用于解释，不直接当最终 Benchmark 数字。
### 1.2 控制采样窗口
只抓能复现问题的短窗口。长 Trace 会带来：
- 更高采集开销；更大的文件；更难定位的时间线；Buffer 丢事件风险。
先预热，再采几个稳定 step 或请求。

## 2. PyTorch Profiler：框架与算子视角
PyTorch Profiler 可以收集 CPU Operator、CUDA Activity、Shape、调用栈和显存事件。最小示例：
```python
import torch
activities = [torch.profiler.ProfilerActivity.CPU]
if torch.cuda.is_available():
    activities.append(torch.profiler.ProfilerActivity.CUDA)
with torch.profiler.profile(
    activities=activities,
    record_shapes=True,
    profile_memory=True,
    with_stack=True,
) as prof:
    with torch.profiler.record_function("inference_region"):
        run_one_inference_step()
print(
    prof.key_averages().table(
        sort_by="self_cuda_time_total",
        row_limit=20,
    )
)
prof.export_chrome_trace("trace.json")
```
`run_one_inference_step()` 是占位函数，应替换成被测系统中可控的一步。如果没有 CUDA，应改用 CPU 排序列。
### 2.1 为什么需要 `record_function`
它给 Trace 增加有业务语义的范围：
```python
with torch.profiler.record_function("prefill"):
    run_prefill()
with torch.profiler.record_function("decode_step"):
    run_decode_step()
```
否则你只会看到大量 Operator 名称，很难对应请求阶段。标记本身有开销，生产热路径不要无限细分。
### 2.2 长循环使用 schedule
```python
import torch
schedule = torch.profiler.schedule(
    skip_first=5,
    wait=2,
    warmup=1,
    active=3,
    repeat=1,
)
with torch.profiler.profile(
    activities=[
        torch.profiler.ProfilerActivity.CPU,
        torch.profiler.ProfilerActivity.CUDA,
    ],
    schedule=schedule,
    on_trace_ready=torch.profiler.tensorboard_trace_handler(
        "./profiler-traces"
    ),
    record_shapes=True,
) as prof:
    for _ in range(20):
        run_one_inference_step()
        prof.step()
```
`prof.step()` 不能漏。它告诉 Profiler 当前迭代结束，schedule 才会推进。各阶段含义：
- `skip_first`：完全跳过最初迭代；`wait`：等待但不记录；`warmup`：启动采集机制，数据不写入最终活动窗口；`active`：正式记录；`repeat`：重复周期。
### 2.3 查看 Trace
TensorBoard：
```bash
tensorboard --logdir ./profiler-traces
```
或把 `trace.json` 用支持 Chrome Trace 格式的查看器打开。Trace 文件可能包含路径、函数名与输入 Shape，应按内部数据规则保存。
### 2.4 常见高开销选项
- `record_shapes=True`：记录 Shape，有助于识别异常批次；`with_stack=True`：记录调用栈，便于跳回源码，但开销更大；`profile_memory=True`：观察分配与释放，适合显存问题；`with_flops=True`：仅对支持估算的算子有意义，不等于真实硬件 FLOPS。
只启用当前假设需要的选项。

## 3. 读懂算子统计
Profiler 表格常见列：
- `CPU total`：算子及其子调用的 CPU 时间；`CPU self`：扣除子调用后的算子自身 CPU 时间；`CUDA total`：关联 CUDA 工作总时间；`CUDA self`：自身关联的 CUDA 时间；`# of Calls`：调用次数；输入 Shape 与显存变化（若启用）。
### 3.1 Self 与 Total 的手算
假设算子 A 的总时间为 10 ms。它内部调用 B 3 ms、C 4 ms。若无重叠并按简化层级计算：
$$
\mathrm{Self}(A)=10-3-4=3\ \mathrm{ms}
$$
这只是理解层级统计的算术示例。真实 CPU/GPU 异步与重叠使“逐项相加”不总等于墙钟时间。
### 3.2 不要把 CUDA 时间直接相加当 E2E
多个 Stream 可以并行。CPU 发射与 GPU 执行可以重叠。因此：
$$
\sum \text{Kernel Duration} \neq \text{Wall-clock Latency}
$$
左边是工作量统计，右边是关键路径。要理解关键路径，需要看时间线。
### 3.3 三个排查问题
看到 Top Operator 后依次问：
1. 它是“单次变慢”，还是“调用次数变多”？
2. 输入 Shape 是否变化？
3. 它是否在关键路径，还是与别的工作重叠？
如果候选版本某算子总时间翻倍，但调用次数也翻倍，根因可能是调度行为，而非 Kernel 退化。
### 3.4 同步陷阱
`torch.cuda.synchronize()` 会等待 GPU 完成。在微基准计时时它常用于获得正确墙钟时间。但把同步插入生产热路径会破坏异步重叠。Profiler 诊断代码必须与最终服务代码隔离。

## 4. Nsight Systems：系统级时间线
Nsight Systems（`nsys`）擅长展示：
- CPU 线程调度；CUDA API 调用；GPU Kernel 与 Memcpy；NVTX Range；NCCL/MPI 等通信（按实际支持与配置）。
它回答的是“谁在等谁”。
### 4.1 最小命令模板
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none \
  --force-overwrite=true \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT" "${APP_ARGS[@]}"
```
运行前记录：
```bash
nsys --version
nsys profile --help > "${RESULT_DIR}/nsys-profile-help.txt"
```
Trace 选项随版本和平台变化，以本机帮助为准。
### 4.2 用 CUDA Profiler API 限定范围
Python 示例：
```python
import torch
warmup()
torch.cuda.cudart().cudaProfilerStart()
run_target_region()
torch.cuda.cudart().cudaProfilerStop()
```
采集命令：
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop-shutdown \
  --kill=none \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
先确认当前 PyTorch/CUDA 组合支持对应调用。`stop-shutdown` 在 `cudaProfilerStop()` 后结束采集会话并生成报告；`--kill=none` 明确让目标进程继续运行，而不是依赖随版本或启动方式变化的默认终止行为。
### 4.3 用 NVTX 限定范围
应用中标记：
```python
import torch
torch.cuda.nvtx.range_push("benchmark_window")
run_target_region()
torch.cuda.nvtx.range_pop()
```
命令模板：
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --capture-range=nvtx \
  --nvtx-capture="benchmark_window" \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
复杂多进程服务中，Range 的进程与命名需要先做小实验确认。
### 4.4 查看与导出摘要
GUI 打开 `.nsys-rep`：
```bash
nsys-ui "${RESULT_DIR}/${RUN_ID}.nsys-rep"
```
无 GUI 环境先看统计：
```bash
nsys stats "${RESULT_DIR}/${RUN_ID}.nsys-rep"
```
摘要适合筛选方向，最终关键路径仍应回到时间线确认。
### 4.5 Profile 服务还是客户端
把 `nsys profile` 包在客户端外面，只能看到客户端进程。要分析 vLLM 服务，必须让 `nsys` 启动或附着目标服务进程，具体附着能力按版本与权限确认。常用策略：
1. 用 `nsys profile` 启动一个短生命周期的可复现服务实验。
2. 预热后通过 CUDA Profiler API/NVTX 开启采集窗口。
3. 客户端只在窗口内发送少量代表请求。

## 5. 读懂时间线的五类形态
### 5.1 GPU 长空洞，CPU 线程忙
可能是：
- Tokenize/Detokenize；Python 调度；Kernel launch 间隙；同步或锁竞争。
继续查看 CUDA API 与 CPU 线程状态。
### 5.2 GPU 长空洞，CPU 线程也在等待
可能是：
- 请求队列暂时为空；网络输入不足；跨进程通信；显式同步。
先排除负载生成不足。
### 5.3 Kernel 密集但很短，间隙明显
可能受 CPU launch 限制。检查：
- CUDA Graph 是否命中；Shape 是否频繁变化；图是否反复重捕获或回退 eager。
### 5.4 通信占关键路径
多卡时观察 NCCL 与计算是否重叠。如果通信完成后计算才开始，重叠不足。但“通信时间长”不自动等于网络问题，也可能是某 Rank 更晚到达 collective。
### 5.5 长 Memcpy 或频繁小拷贝
检查：
- Host-to-Device 输入是否重复搬运；Pinned Memory 是否生效；中间张量是否在设备间来回；结果是否过于频繁同步回 CPU。

## 6. 何时使用 Nsight Compute
Nsight Compute（`ncu`）用于单个或少数 CUDA Kernel 的微架构分析。只有满足这些条件才值得下钻：
- Nsight Systems 已确认目标 Kernel 在关键路径；候选与基线的 Shape、调用次数可比；你有明确假设，如访存带宽不足或 Occupancy 下降。
命令骨架：
```bash
ncu \
  --kernel-name "$KERNEL_FILTER" \
  --launch-skip "$LAUNCH_SKIP" \
  --launch-count "$LAUNCH_COUNT" \
  --set "$SECTION_SET" \
  --export "${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
详细指标采集可能重放 Kernel，多用户在线延迟会被严重扰动。不要把 `ncu` 下测得的请求延迟当生产性能。

## 7. 一个退化定位流程
场景：候选版本的 ITL P99 退化，TPOT 中位数变化不明显。步骤一：复测确认。
- 相同镜像基底、模型、数据、Seed 与负载；基线/候选交替运行，降低温度与时间漂移；保存原始 ITL 样本。
步骤二：按请求时间定位尖刺。
- 找到高 ITL 请求的时间戳；对齐服务端日志；判断是否伴随 Prefill、抢占、GC 或错误重试。
步骤三：PyTorch Profiler 小窗口。
- 给 Prefill、Decode、调度加语义 Range；比较调用次数、Shape 和 Top Operator。
步骤四：Nsight Systems。
- 只抓包含尖刺的短窗口；查看尖刺期间是 GPU Kernel、CPU 空洞还是通信等待。
步骤五：形成可证伪假设。示例：
> 候选版本在特定动态 Shape 下未命中 CUDA Graph，增加 CPU launch 间隙，导致 ITL 尾延迟。
步骤六：只改一个变量验证。
- 固定 Shape 或调整捕获配置；重跑同一负载；同时看 ITL 与吞吐护栏。
Profiler 的价值不是生成漂亮 Trace，而是让假设可以被验证。

```yaml
  vllm_version: "<实际值>"
  cuda_version: "<实际值>"
  driver_version: "<实际值>"
  profiler_name: "<torch.profiler/nsys/ncu>"
  profiler_version: "<实际值>"

  gpu: "<型号、数量>"
  cpu: "<型号与核数>"
  numa_binding: "<实际设置>"

  input_output_distribution: "<描述>"
  concurrency_or_rate: "<实际值>"
  warmup: "<步骤>"
capture:
  activities: ["<实际项>"]
  range: "<起止条件>"
  profiler_options: ["<完整参数>"]
artifacts:
  trace: "<路径>"
  logs: ["<路径>"]
  benchmark_raw: "<路径>"
```
Profiler 选项存在明确 trade-off：
- 更多事件带来更强解释力，也带来更高扰动；更长窗口覆盖更多异常，也让 Trace 更难读；更多调用栈更容易定位源码，也增加文件大小与敏感信息风险；Kernel 级指标更精细，但失去全局排队与关键路径视角。
报告应明确区分：
- **无 Profiler 性能结果**：用于比较；**有 Profiler 诊断证据**：用于解释。

## 9. 从服务指标选择 CPU、GPU 或 NCCL 路径

Profiler 之前先建立“症状—候选层—最小证据”的映射。

### 9.1 TTFT 上升，Queue 也上升

优先怀疑容量或调度：

- 到达率超过当前服务率；
- KV Cache 可用块不足；
- Prefill 被并发或长请求限制；
- Scheduler CPU 变慢；
- 上游并发闸门改变。

最小证据：

```text
request arrival rate
queue depth / waiting requests
running requests
KV cache usage
prefill tokens per step
scheduler loop duration
```

若 GPU 已持续饱和，问题可能是容量；若 GPU 有大量空洞而 Queue 非空，优先转向 CPU、同步或通信。

### 9.2 TTFT 上升，Queue 稳定，Prefill 时间上升

检查：

- 输入长度分布是否变化；
- Prefix Cache 命中率是否下降；
- Prefill Batch 形状是否变化；
- Attention/量化 Kernel 是否回退；
- Tensor Parallel 通信是否延长；
- GPU 时钟、功耗或温度是否异常。

这时 PyTorch Profiler 的 Shape 与 Operator 统计有价值，再用 Nsight Systems 判断计算和通信是否位于关键路径。

### 9.3 TPOT 上升且每步 GPU 时间上升

优先看 Decode：

- 每步 Batch/Sequence 数变化；
- KV Cache 访问和 Page 管理；
- CUDA Graph 是否回退 eager；
- 单步 Kernel 是否变慢；
- TP/EP collective 是否变长；
- 抢占与重计算。

不要先看 E2E，因为输出长度变化也会推高 E2E。

### 9.4 ITL 尾部尖刺但 TPOT 中位数稳定

这通常是间歇事件：

- Chunked Prefill 插入；
- Python GC、日志刷盘或线程抢占；
- CUDA Graph 新 Shape 捕获；
- Rank 偏斜导致 collective 等待；
- KV Cache 抢占；
- 网络或客户端接收停顿。

需要用请求时间戳把 ITL 尖刺与服务 Step、CPU 调度和 GPU 时间线对齐。

### 9.5 Goodput 下降但吞吐稳定

服务仍完成相似工作量，只是更多请求违反 SLO。优先检查：

- 排队公平性；
- 长短请求混部；
- 微突发；
- Batch 策略；
- 超时和失败类型；
- SLO 违反项到底是 TTFT、TPOT 还是 E2E。

Goodput 本身不告诉根因，必须展开为违反 SLO 的请求集合。

## 10. 轻量观测：先证明瓶颈在哪一侧

### 10.1 CPU 证据

建议收集：

- 进程与线程 CPU 利用率；
- Run Queue、上下文切换与调度等待；
- 用户态/内核态比例；
- NUMA Remote Access；
- Page Fault；
- 网络收发与软中断；
- Tokenize、Detokenize、序列化与日志耗时。

Linux 常用工具骨架：

```bash
pidstat -p "$SERVER_PID" -t 1 \
  > "$RESULT_DIR/pidstat-threads.txt"
mpstat -P ALL 1 \
  > "$RESULT_DIR/mpstat.txt"
vmstat 1 \
  > "$RESULT_DIR/vmstat.txt"
```

命令输出是时间序列，不要只保存最后一行。容器内看到的 CPU 配额与宿主机实际争用都要核对。

### 10.2 GPU 证据

轻量指标至少包括：

- GPU Utilization；
- 显存占用与带宽相关计数器；
- SM Active；
- 功率、时钟、温度与节流原因；
- 每个 Device 的指标，而不只看平均；
- PCIe/NVLink 流量（平台支持时）。

```bash
nvidia-smi dmon -s pucvmet -d 1 \
  -o DT \
  > "$RESULT_DIR/nvidia-smi-dmon.txt"
```

`GPU-Util=100%` 只表示采样窗口内有 Kernel 活跃，不证明计算单元满效率，也不区分计算、通信或低效 Kernel。

### 10.3 NCCL 证据

多卡退化先回答三个问题：

1. collective 本身是否更长？
2. 各 Rank 是否同时进入 collective？
3. 通信是否与计算重叠？

只看到 NCCL Range 很长，不能直接判定网络慢。如果 Rank 0 提前进入 AllReduce 并等待 Rank 3，长 Range 的前半段是 Rank 偏斜，不是链路传输。

诊断运行可临时提高 NCCL 日志：

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,GRAPH,COLL
```

日志量与开销可能很大，且可能含主机与拓扑信息。只在短诊断窗口启用，不作为正常 Benchmark 配置。

### 10.4 CPU/GPU/NCCL 决策表

```text
Queue非空 + GPU空洞 + CPU单核满       → CPU调度/launch/锁
Queue非空 + GPU连续忙 + step变长      → GPU计算/形状/频率
多卡step变长 + NCCL位于关键路径       → 通信或Rank偏斜
GPU空洞 + 所有CPU线程sleep            → 输入不足/IPC/同步等待
ITL尖刺 + 新Shape + graph miss         → Graph回退或捕获
TTFT变差 + cache hit下降               → Prefill工作量变化
```

这是选路规则，不是根因证明。

## 11. PyTorch Profiler 的可比采集协议

### 11.1 基线与候选必须同窗

两份 Trace 要冻结：

- 请求 Manifest 和顺序；
- 输入/输出 Shape；
- Batch/并发；
- Warmup；
- Profiler schedule；
- Activity 与开销选项；
- 软件、硬件与时钟状态。

若候选 Trace 多采了 Stack，时间本身就不可比。

### 11.2 用阶段和请求标记

```python
from torch.profiler import record_function

def run_request(request):
    with record_function(f"request/{request.trace_class}"):
        with record_function("stage/tokenize"):
            inputs = tokenize(request)
        with record_function("stage/prefill"):
            state = prefill(inputs)
        with record_function("stage/decode_loop"):
            return decode(state)
```

生产多请求并发时，不建议把高基数 Request ID 直接写入每个 Range。可用请求类别、长度桶或采样 ID，避免 Trace 膨胀。

### 11.3 导出原始表

除 Chrome Trace 外，保存机器可读统计：

```python
averages = prof.key_averages(
    group_by_input_shape=True,
    group_by_stack_n=0,
)
print(
    averages.table(
        sort_by="self_cuda_time_total",
        row_limit=100,
    ),
    file=open("operator-table.txt", "w", encoding="utf-8"),
)
prof.export_chrome_trace("torch-trace.json")
```

表格用来筛候选，时间线用来确认关键路径。Operator 聚合隐藏了单次尖刺，所以 ITL 问题不能只看平均表。

### 11.4 显存问题

启用 `profile_memory` 后，区分：

- 当前分配；
- 保留但未分配；
- 峰值；
- 短时分配尖峰；
- 跨 Step 未释放增长。

显存高不等于泄漏。KV Cache 预分配与 Memory Pool 会有意保留显存。判断泄漏要看相同负载阶段下的长期趋势与对象生命周期。

### 11.5 Trace 对齐

最好在压测原始事件和服务 Trace 同时写：

```text
run_id
request_id 或 sampled_request_id
monotonic timestamp
wall-clock timestamp（仅关联）
step_id
rank
```

多进程单调时钟不能假设共享零点。可用共同 NVTX 标记、日志事件或受控同步点建立映射，并说明误差。

## 12. Nsight Systems：可复现采集与时间线阅读

### 12.1 服务端采集脚本骨架

```bash
set -euo pipefail
mkdir -p "$RESULT_DIR"
nsys --version > "$RESULT_DIR/nsys-version.txt"
nsys profile --help > "$RESULT_DIR/nsys-profile-help.txt"
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop-shutdown \
  --kill=none \
  --force-overwrite=true \
  --output="$RESULT_DIR/server-${RUN_ID}" \
  "${SERVER_COMMAND[@]}" \
  2>&1 | tee "$RESULT_DIR/server-profile.log"
test -s "$RESULT_DIR/server-${RUN_ID}.nsys-rep"
nsys stats "$RESULT_DIR/server-${RUN_ID}.nsys-rep" \
  > "$RESULT_DIR/server-${RUN_ID}.stats.txt"
```

服务先启动并预热。然后由管理端或测试 Hook 在目标窗口调用 `cudaProfilerStart/Stop`。这里必须用 `stop-shutdown`，否则 `stop` 只停止采集、会话仍等待长驻服务退出，脚本可能迟迟不生成最终报告。`--kill` 控制会话关闭时向目标进程组发送什么：`none` 保留服务，`sigterm` 请求优雅退出，`sigkill` 强制终止；隔离的一次性实验可显式改成 `sigterm`，生产采样不要误用 `sigkill`。正式部署也不要长期保留未经保护的 Profile 控制接口。

### 12.2 多卡与 NCCL

在版本支持时，可把 NCCL 加入 Trace：

```bash
nsys profile \
  --trace=cuda,nvtx,osrt,nccl \
  --sample=none \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop-shutdown \
  --kill=none \
  --output="$RESULT_DIR/tp-${RUN_ID}" \
  "${SERVER_COMMAND[@]}"
```

具体可用 Trace 域以本机 `nsys profile --help` 为准。多进程可能生成多个报告或在一个报告中出现多个进程，采集前先用小规模实验确认。

### 12.3 先从宏观轨道读

推荐顺序：

1. 定位 Benchmark/NVTX 正式窗口；
2. 找到异常请求或 Step；
3. 看 GPU 是否有空洞；
4. 看空洞前后的 CUDA API；
5. 看 CPU 线程是 Running、Runnable 还是 Sleeping；
6. 多卡时比较各 Rank 的同一 collective；
7. 最后才展开具体 Kernel。

一开始就盯着 Kernel 名称，容易失去关键路径。

### 12.4 CPU launch-bound 形态

```text
CPU: [launch k1]---gap---[launch k2]---gap---[launch k3]
GPU:      [k1]____idle____[k2]____idle____[k3]
```

证据要求：

- Queue 非空；
- GPU 空洞与 CPU 发射间隔对齐；
- Kernel 自身时长没有显著增长；
- CPU 线程在 Running/Runnable 或锁上等待；
- 启用 CUDA Graph 或减少 Python 路径后空洞缩小。

只看到很多短 Kernel 不足以证明 launch-bound。

### 12.5 GPU compute-bound 形态

```text
GPU: [kernel A][kernel B][kernel C][kernel A][kernel B]...
     几乎无空洞，关键Kernel时长或调用量增加
```

继续区分：

- Shape 变大；
- Batch 变大；
- Kernel 调用次数增加；
- 时钟下降；
- 同 Shape 单 Kernel 退化。

只有最后一类才直接适合进入 Nsight Compute 做微架构对比。

### 12.6 Rank 偏斜形态

```text
Rank0 compute done ──> [........ NCCL wait/collective ........]
Rank1 compute done ───────> [..... NCCL collective .....]
Rank2 compute done ─────────────> [NCCL collective]
```

若 collective 结束时间接近、开始时间分散，先追查最晚 Rank 为什么迟到。可能是：

- 不同 Shape 或工作量；
- CPU 调度不均；
- NUMA 绑定；
- 上一通信未完成；
- 错误重试；
- 单卡降频。

### 12.7 摘要导出

```bash
nsys stats \
  "$RESULT_DIR/server-${RUN_ID}.nsys-rep" \
  > "$RESULT_DIR/nsys-stats.txt"
```

SQL/CSV 导出能力依 Nsight Systems 版本而异。要自动比较前，应保存版本、命令和 Schema，并对关键结论回到 GUI 时间线复核。

## 13. Nsight Compute：从关键 Kernel 到瓶颈模型

### 13.1 采集前先写假设

合格假设示例：

> 在相同 Shape 与相同 GPU 时钟下，候选版本目标 Attention Kernel 的 DRAM 吞吐占比接近上限，且执行时长增加，怀疑额外访存。

不合格假设：

> GPU 好像慢了，抓个 NCU 看看。

### 13.2 最小化重放

优先把目标 Kernel 抽成离线微基准，固定：

- 输入 Shape、dtype 和布局；
- Warmup 与迭代数；
- GPU 时钟/功耗状态；
- Kernel 过滤规则；
- NCU Section Set；
- Baseline/Candidate 采集顺序。

```bash
ncu \
  --set "$SECTION_SET" \
  --kernel-name "$KERNEL_FILTER" \
  --launch-skip "$LAUNCH_SKIP" \
  --launch-count "$LAUNCH_COUNT" \
  --export "$RESULT_DIR/${RUN_ID}.ncu-rep" \
  python "$MICROBENCH" \
  2>&1 | tee "$RESULT_DIR/ncu.log"
```

### 13.3 读 Roofline 前先确认工作量

候选 Kernel FLOP、字节数或输入 Shape变化时，算术强度也会变化。比较前先确认：

- 两边完成同样语义工作；
- 编译生成的 Kernel 范围相同；
- 是否发生 Kernel Fusion/Fission；
- NCU 采集的是同一调用阶段。

### 13.4 常见指标只提供方向

- Memory Throughput 高、SM 利用有限：可能 memory-bound；
- Occupancy 低：可能寄存器、Shared Memory 或线程块配置限制；
- Warp Stall：提示等待来源；
- Tensor Core 利用变化：提示矩阵路径覆盖；
- L2 Hit Rate：提示复用变化。

任何单指标都不能独立证明根因。验证应修改一个变量，并回到无 Profiler 的端到端场景确认收益。

## 14. 完整时间线案例：ITL P99 尖刺的证据链

以下时长均为教学示意，不代表真实系统性能。

### 14.1 症状

固定到达率、长度与 Cache 状态：

```text
TPOT P50：基线与候选接近
ITL P99：候选出现明显尖刺
吞吐：接近
错误率：均为零
```

由于均值稳定，怀疑是间歇性阻塞。

### 14.2 请求级对齐

从客户端原始 Chunk 事件找到异常：

```text
request_id=r17
chunk 31 at 12.400 s
chunk 32 at 12.620 s
chunk gap = 220 ms
```

服务日志显示同一窗口：

```text
step_id=884
running_requests=<稳定>
waiting_requests=<稳定>
prefill_scheduled=true
graph_shape=<新Shape>
```

这还不能区分 Prefill 干扰与 Graph 行为。

### 14.3 PyTorch Profiler 证据

短窗口 Trace 中：

- Decode Operator 的单次 CUDA 时间与基线接近；
- 候选在该 Step 出现一组额外 CPU Operator；
- Shape 分组显示首次出现的新 Batch Shape；
- CUDA Kernel 调用数增加，但单 Kernel 没有系统性变慢。

因此“某个 Decode Kernel 退化”缺乏支持。

### 14.4 Nsight Systems 证据

时间线示意：

```text
CPU scheduler:
  [prepare shape] [graph lookup] [eager launches...............]

GPU:
  [decode kernels]____idle__[many short kernels + gaps]__[decode]

NCCL:
  [short collectives separated by matching CPU launch gaps]
```

关键观察：

- GPU 空洞期间 Queue 非空；
- CPU 主调度线程持续 Running；
- 空洞与大量 CUDA API 发射间隔对齐；
- 各 Rank collective 进入时间接近，没有明显 Rank 偏斜；
- 目标 Kernel 时长没有突增。

### 14.5 假设与验证

假设：

> 候选版本对该动态 Shape 未命中已捕获 CUDA Graph，回退 eager 路径，CPU 发射间隙造成局部 ITL 尖刺。

只改一个变量：让测试 Shape 落入预先捕获集合，其他条件不变。验证要求：

- Nsight Systems 中 eager 发射空洞消失或显著缩小；
- 异常请求的 Chunk gap 恢复；
- 无 Profiler 重跑时 ITL 尾部恢复；
- TTFT、吞吐、显存与错误率护栏不退化。

### 14.6 结论边界

若验证成立，可以写：

> 在该固定工作负载和采集窗口中，Graph miss 导致 CPU launch gap，并与 ITL 尖刺对齐。

不能写：

> 所有 ITL 尖刺都由 CUDA Graph 导致。

结论强度必须匹配证据范围。

## 15. 另一个 NCCL 案例：通信长不等于网络慢

### 15.1 症状

Tensor Parallel 候选版本的 Decode Step 变长，Nsight 摘要显示 NCCL Range 占比上升。

### 15.2 时间线证据

逐 Rank 展开后发现：

```text
Rank 0/1/2：较早结束上一个计算阶段并进入 collective
Rank 3：CPU 上存在较长调度空洞，较晚发射最后一个计算 Kernel
所有 Rank：collective 在 Rank 3 到达后很快结束
```

### 15.3 结论

症状看似 NCCL 变长，真正关键路径是 Rank 3 到达 collective 较晚。下一步查 Rank 3：

- CPU 亲和性与 NUMA；
- 邻居进程；
- 单卡时钟/温度；
- 该 Rank 的输入与工作量；
- 前序同步。

在没有链路计数器和对照实验前，不能归因“NVLink 退化”。

## 📝 总结
- 定位应从客户端指标逐层下钻到阶段、算子和 Kernel；PyTorch Profiler 适合看 Operator、Shape、调用栈和显存事件；`Self`、`Total`、调用次数与 Shape 必须结合判断，Kernel 时间之和不等于 E2E；Nsight Systems 用时间线揭示 CPU、CUDA、通信与空洞的关键路径。
- Nsight Compute 只应在目标 Kernel 已被时间线证明重要后使用；Profiler 会扰动系统，最终性能数字必须来自关闭 Profiler 的独立运行。
