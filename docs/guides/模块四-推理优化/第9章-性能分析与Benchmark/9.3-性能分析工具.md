## 1. 先建立定位漏斗
一次线上退化建议按四层下钻：
1. **客户端指标**：TTFT、ITL、TPOT、E2E、Goodput 哪个变了？
2. **服务端阶段**：排队、Prefill、Decode、通信还是输出处理？
3. **框架算子**：哪些 PyTorch Operator 或 Kernel 占时变化？
4. **Kernel 微架构**：访存、占用率、指令或分支哪里受限？
对应工具：
- 压测器负责第 1 层；服务日志、指标与 NVTX 负责第 2 层；PyTorch Profiler 负责第 3 层；Nsight Systems 连接第 2、3 层，并展示 CPU/GPU/通信全局关系；Nsight Compute 在假设已收敛到少数 Kernel 后负责第 4 层。
📌 **关键点**：不要因为“GPU 慢”就直接抓最重的 Nsight Compute 指标。如果根因是排队或 Python 线程阻塞，Kernel 报告再详细也没有答案。
### 1.1 先做无 Profiler 基线
Profiler 会扰动被测系统。因此先运行两份：
- 不开 Profiler 的性能基线；开 Profiler 的诊断运行。
诊断运行用于解释，不直接当最终 Benchmark 数字。
### 1.2 控制采样窗口
只抓能复现问题的短窗口。长 Trace 会带来：
- 更高采集开销；更大的文件；更难定位的时间线；Buffer 丢事件风险。
先预热，再采几个稳定 step 或请求。

## 2. PyTorch Profiler：框架与算子视角
PyTorch Profiler 可以收集 CPU Operator、CUDA Activity、Shape、调用栈和显存事件。最小示例：
```python
import torch
activities = [torch.profiler.ProfilerActivity.CPU]
if torch.cuda.is_available():
    activities.append(torch.profiler.ProfilerActivity.CUDA)
with torch.profiler.profile(
    activities=activities,
    record_shapes=True,
    profile_memory=True,
    with_stack=True,
) as prof:
    with torch.profiler.record_function("inference_region"):
        run_one_inference_step()
print(
    prof.key_averages().table(
        sort_by="self_cuda_time_total",
        row_limit=20,
    )
)
prof.export_chrome_trace("trace.json")
```
`run_one_inference_step()` 是占位函数，应替换成被测系统中可控的一步。如果没有 CUDA，应改用 CPU 排序列。
### 2.1 为什么需要 `record_function`
它给 Trace 增加有业务语义的范围：
```python
with torch.profiler.record_function("prefill"):
    run_prefill()
with torch.profiler.record_function("decode_step"):
    run_decode_step()
```
否则你只会看到大量 Operator 名称，很难对应请求阶段。标记本身有开销，生产热路径不要无限细分。
### 2.2 长循环使用 schedule
```python
import torch
schedule = torch.profiler.schedule(
    skip_first=5,
    wait=2,
    warmup=1,
    active=3,
    repeat=1,
)
with torch.profiler.profile(
    activities=[
        torch.profiler.ProfilerActivity.CPU,
        torch.profiler.ProfilerActivity.CUDA,
    ],
    schedule=schedule,
    on_trace_ready=torch.profiler.tensorboard_trace_handler(
        "./profiler-traces"
    ),
    record_shapes=True,
) as prof:
    for _ in range(20):
        run_one_inference_step()
        prof.step()
```
`prof.step()` 不能漏。它告诉 Profiler 当前迭代结束，schedule 才会推进。各阶段含义：
- `skip_first`：完全跳过最初迭代；`wait`：等待但不记录；`warmup`：启动采集机制，数据不写入最终活动窗口；`active`：正式记录；`repeat`：重复周期。
### 2.3 查看 Trace
TensorBoard：
```bash
tensorboard --logdir ./profiler-traces
```
或把 `trace.json` 用支持 Chrome Trace 格式的查看器打开。Trace 文件可能包含路径、函数名与输入 Shape，应按内部数据规则保存。
### 2.4 常见高开销选项
- `record_shapes=True`：记录 Shape，有助于识别异常批次；`with_stack=True`：记录调用栈，便于跳回源码，但开销更大；`profile_memory=True`：观察分配与释放，适合显存问题；`with_flops=True`：仅对支持估算的算子有意义，不等于真实硬件 FLOPS。
只启用当前假设需要的选项。

## 3. 读懂算子统计
Profiler 表格常见列：
- `CPU total`：算子及其子调用的 CPU 时间；`CPU self`：扣除子调用后的算子自身 CPU 时间；`CUDA total`：关联 CUDA 工作总时间；`CUDA self`：自身关联的 CUDA 时间；`# of Calls`：调用次数；输入 Shape 与显存变化（若启用）。
### 3.1 Self 与 Total 的手算
假设算子 A 的总时间为 10 ms。它内部调用 B 3 ms、C 4 ms。若无重叠并按简化层级计算：
$$
\mathrm{Self}(A)=10-3-4=3\ \mathrm{ms}
$$
这只是理解层级统计的算术示例。真实 CPU/GPU 异步与重叠使“逐项相加”不总等于墙钟时间。
### 3.2 不要把 CUDA 时间直接相加当 E2E
多个 Stream 可以并行。CPU 发射与 GPU 执行可以重叠。因此：
$$
\sum \text{Kernel Duration} \neq \text{Wall-clock Latency}
$$
左边是工作量统计，右边是关键路径。要理解关键路径，需要看时间线。
### 3.3 三个排查问题
看到 Top Operator 后依次问：
1. 它是“单次变慢”，还是“调用次数变多”？
2. 输入 Shape 是否变化？
3. 它是否在关键路径，还是与别的工作重叠？
如果候选版本某算子总时间翻倍，但调用次数也翻倍，根因可能是调度行为，而非 Kernel 退化。
### 3.4 同步陷阱
`torch.cuda.synchronize()` 会等待 GPU 完成。在微基准计时时它常用于获得正确墙钟时间。但把同步插入生产热路径会破坏异步重叠。Profiler 诊断代码必须与最终服务代码隔离。

## 4. Nsight Systems：系统级时间线
Nsight Systems（`nsys`）擅长展示：
- CPU 线程调度；CUDA API 调用；GPU Kernel 与 Memcpy；NVTX Range；NCCL/MPI 等通信（按实际支持与配置）。
它回答的是“谁在等谁”。
### 4.1 最小命令模板
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none \
  --force-overwrite=true \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT" "${APP_ARGS[@]}"
```
运行前记录：
```bash
nsys --version
nsys profile --help > "${RESULT_DIR}/nsys-profile-help.txt"
```
Trace 选项随版本和平台变化，以本机帮助为准。
### 4.2 用 CUDA Profiler API 限定范围
Python 示例：
```python
import torch
warmup()
torch.cuda.cudart().cudaProfilerStart()
run_target_region()
torch.cuda.cudart().cudaProfilerStop()
```
采集命令：
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
先确认当前 PyTorch/CUDA 组合支持对应调用。
### 4.3 用 NVTX 限定范围
应用中标记：
```python
import torch
torch.cuda.nvtx.range_push("benchmark_window")
run_target_region()
torch.cuda.nvtx.range_pop()
```
命令模板：
```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --capture-range=nvtx \
  --nvtx-capture="benchmark_window" \
  --output="${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
复杂多进程服务中，Range 的进程与命名需要先做小实验确认。
### 4.4 查看与导出摘要
GUI 打开 `.nsys-rep`：
```bash
nsys-ui "${RESULT_DIR}/${RUN_ID}.nsys-rep"
```
无 GUI 环境先看统计：
```bash
nsys stats "${RESULT_DIR}/${RUN_ID}.nsys-rep"
```
摘要适合筛选方向，最终关键路径仍应回到时间线确认。
### 4.5 Profile 服务还是客户端
把 `nsys profile` 包在客户端外面，只能看到客户端进程。要分析 vLLM 服务，必须让 `nsys` 启动或附着目标服务进程，具体附着能力按版本与权限确认。常用策略：
1. 用 `nsys profile` 启动一个短生命周期的可复现服务实验。
2. 预热后通过 CUDA Profiler API/NVTX 开启采集窗口。
3. 客户端只在窗口内发送少量代表请求。

## 5. 读懂时间线的五类形态
### 5.1 GPU 长空洞，CPU 线程忙
可能是：
- Tokenize/Detokenize；Python 调度；Kernel launch 间隙；同步或锁竞争。
继续查看 CUDA API 与 CPU 线程状态。
### 5.2 GPU 长空洞，CPU 线程也在等待
可能是：
- 请求队列暂时为空；网络输入不足；跨进程通信；显式同步。
先排除负载生成不足。
### 5.3 Kernel 密集但很短，间隙明显
可能受 CPU launch 限制。检查：
- CUDA Graph 是否命中；Shape 是否频繁变化；图是否反复重捕获或回退 eager。
### 5.4 通信占关键路径
多卡时观察 NCCL 与计算是否重叠。如果通信完成后计算才开始，重叠不足。但“通信时间长”不自动等于网络问题，也可能是某 Rank 更晚到达 collective。
### 5.5 长 Memcpy 或频繁小拷贝
检查：
- Host-to-Device 输入是否重复搬运；Pinned Memory 是否生效；中间张量是否在设备间来回；结果是否过于频繁同步回 CPU。

## 6. 何时使用 Nsight Compute
Nsight Compute（`ncu`）用于单个或少数 CUDA Kernel 的微架构分析。只有满足这些条件才值得下钻：
- Nsight Systems 已确认目标 Kernel 在关键路径；候选与基线的 Shape、调用次数可比；你有明确假设，如访存带宽不足或 Occupancy 下降。
命令骨架：
```bash
ncu \
  --kernel-name "$KERNEL_FILTER" \
  --launch-skip "$LAUNCH_SKIP" \
  --launch-count "$LAUNCH_COUNT" \
  --set "$SECTION_SET" \
  --export "${RESULT_DIR}/${RUN_ID}" \
  python "$ENTRYPOINT"
```
详细指标采集可能重放 Kernel，多用户在线延迟会被严重扰动。不要把 `ncu` 下测得的请求延迟当生产性能。

## 7. 一个退化定位流程
场景：候选版本的 ITL P99 退化，TPOT 中位数变化不明显。步骤一：复测确认。
- 相同镜像基底、模型、数据、Seed 与负载；基线/候选交替运行，降低温度与时间漂移；保存原始 ITL 样本。
步骤二：按请求时间定位尖刺。
- 找到高 ITL 请求的时间戳；对齐服务端日志；判断是否伴随 Prefill、抢占、GC 或错误重试。
步骤三：PyTorch Profiler 小窗口。
- 给 Prefill、Decode、调度加语义 Range；比较调用次数、Shape 和 Top Operator。
步骤四：Nsight Systems。
- 只抓包含尖刺的短窗口；查看尖刺期间是 GPU Kernel、CPU 空洞还是通信等待。
步骤五：形成可证伪假设。示例：
> 候选版本在特定动态 Shape 下未命中 CUDA Graph，增加 CPU launch 间隙，导致 ITL 尾延迟。
步骤六：只改一个变量验证。
- 固定 Shape 或调整捕获配置；重跑同一负载；同时看 ITL 与吞吐护栏。
Profiler 的价值不是生成漂亮 Trace，而是让假设可以被验证。

## 8. 实验元数据与 trade-off
```yaml
profile_run:
  id: "<唯一 ID>"
  purpose: "<要验证的假设>"
  baseline_or_candidate: "<角色>"
software:
  git_commit: "<commit>"
  pytorch_version: "<实际值>"
  vllm_version: "<实际值>"
  cuda_version: "<实际值>"
  driver_version: "<实际值>"
  profiler_name: "<torch.profiler/nsys/ncu>"
  profiler_version: "<实际值>"
hardware:
  gpu: "<型号、数量>"
  cpu: "<型号与核数>"
  numa_binding: "<实际设置>"
workload:
  input_output_distribution: "<描述>"
  concurrency_or_rate: "<实际值>"
  warmup: "<步骤>"
capture:
  activities: ["<实际项>"]
  range: "<起止条件>"
  profiler_options: ["<完整参数>"]
artifacts:
  trace: "<路径>"
  logs: ["<路径>"]
  benchmark_raw: "<路径>"
```
Profiler 选项存在明确 trade-off：
- 更多事件带来更强解释力，也带来更高扰动；更长窗口覆盖更多异常，也让 Trace 更难读；更多调用栈更容易定位源码，也增加文件大小与敏感信息风险；Kernel 级指标更精细，但失去全局排队与关键路径视角。
报告应明确区分：
- **无 Profiler 性能结果**：用于比较；**有 Profiler 诊断证据**：用于解释。

## 📝 总结
- 定位应从客户端指标逐层下钻到阶段、算子和 Kernel；PyTorch Profiler 适合看 Operator、Shape、调用栈和显存事件；`Self`、`Total`、调用次数与 Shape 必须结合判断，Kernel 时间之和不等于 E2E；Nsight Systems 用时间线揭示 CPU、CUDA、通信与空洞的关键路径。
- Nsight Compute 只应在目标 Kernel 已被时间线证明重要后使用；Profiler 会扰动系统，最终性能数字必须来自关闭 Profiler 的独立运行。
