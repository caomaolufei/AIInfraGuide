## 1. 权威来自规则而非名气
可信 Benchmark 通常具备：
1. 明确任务与输入数据。
2. 明确模型或允许的模型变化。
3. 明确质量/准确率下限。
4. 明确系统边界与计时口径。
5. 明确负载生成与有效性检查。
6. 可供复核的配置、日志与实现。
7. 对结果进行校验、同行评审或审计。
“由知名厂商发布”不是充分条件。“代码开源”也不是充分条件。如果关键数据、模型 revision、运行参数或硬件拓扑缺失，别人仍无法复现。
### 1.1 Benchmark 是一份契约
把 Benchmark 看成契约：
- 输入方承诺按规则生成负载；被测系统承诺不识别并特判测试样本；计量方承诺用统一方法统计；发布者承诺披露复现所需信息。
排行榜只是这份契约执行后的一个视图。
### 1.2 快与好必须同时成立
推理系统可以通过牺牲质量换速度：
- 更激进的量化；更小模型替换；降低最大输出长度；修改采样或停止条件；跳过部分请求。
所以性能结果必须绑定质量检查。没有质量护栏的 tok/s 只说明“产生了多少 Token”，不说明这些 Token 是否满足任务。

## 2. 公平比较的六个对齐项
### 2.1 模型对齐
至少对齐：
- 模型家族与参数规模；权重 revision；Tokenizer revision；精度与量化方法；LoRA/Adapter；上下文长度与位置编码配置。
“都是某某 70B”仍可能是不同权重或不同量化。
### 2.2 质量对齐
记录：
- 质量数据集与版本；评价脚本 commit；采样参数；随机 Seed；通过阈值；是否采用高准确率类别或特殊规则。
质量略低但速度更高的系统，不应在没有说明的情况下宣称全面胜出。
### 2.3 硬件对齐
至少披露：
- GPU/加速器型号与数量；单卡显存；CPU、内存和 NUMA；GPU 互联与网络；功耗限制和时钟策略；单机还是多机；是否为预览硬件。
8 卡结果和 1 卡结果不能只比总 tok/s。
### 2.4 软件对齐
至少披露：
- 驱动、CUDA/ROCm；框架与推理引擎版本；Kernel 库；容器 digest；编译选项；服务启动参数。
“最新版”无法复现。应写 tag、commit 或不可变镜像 digest。
### 2.5 工作负载对齐
LLM 负载尤其要对齐：
- 输入长度分布；输出长度分布；到达模式；并发与请求率；Streaming；Prefix Cache 状态与命中率；请求失败、超时与取消规则；Benchmark 时长与样本数。
### 2.6 指标口径对齐
确认：
- tok/s 指输入、输出还是总 Token；延迟在客户端还是服务端测量；percentile 算法和聚合层级；失败请求是否从延迟统计中排除；Benchmark 持续时间从何时算起；Goodput 的 SLO 阈值是什么。
只有六项对齐后，数字比较才有意义。

## 3. MLPerf Inference 应该怎么看
MLPerf Inference 由 MLCommons 维护。它的重要性不在于覆盖所有真实业务，而在于提供一套可审核的共同规则。
### 3.1 Closed 与 Open Division
**Closed Division** 强调“苹果对苹果”：
- 使用规定模型与数据；对可修改部分有明确限制；按版本规则执行质量与性能测试。
**Open Division** 允许更多创新：
- 可能允许模型替换或重新训练；结果仍有价值，但不应与 Closed 直接混成一个结论。
阅读结果时先看 Division，再看数字。
### 3.2 场景不是装饰字段
MLPerf 不同版本和系统类型定义不同场景。常见思路包括：
- 强调批处理吞吐的场景；强调随机到达与延迟约束的服务场景；强调单请求或交互体验的场景。
具体名称与规则会随 Benchmark 版本演进。必须查对应轮次的规则，不能拿旧博客解释新结果。
### 3.3 质量测试先于性能结论
正式结果通常需要通过规定的准确率检查。因此查看提交时应同时寻找：
- Accuracy 日志；Performance 日志；Compliance/Audit 产物；System 描述；Implementation 配置。
只摘 Performance 数字会丢掉结果成立的前提。
### 3.4 Available 与 Preview
公开结果可能标记系统或软件的可用性类别。采购时应区分：
- 当前可获得的系统；预览或未来可获得的系统。
预览结果展示技术方向，不自动等于你今天可以买到并复现。
### 3.5 功耗结果
性能/功耗必须确认测量边界：
- 仅加速器；整机；多节点系统；是否包含空闲与网络设备。
不同边界的“每瓦性能”不能直接比较。
### 3.6 为什么版本不能跨轮次硬比
Benchmark 版本升级可能改变：
- 模型；数据集；质量阈值；场景规则；负载生成器；提交要求。
即使指标名相同，跨版本也可能不是同一实验。

## 4. LLM Serving Benchmark 的特殊陷阱
### 4.1 Tokenizer 不同
同一段文本用不同 Tokenizer 会得到不同 Token 数。tok/s 的分母单位看似一致，实际“一个 Token”包含的信息不同。跨模型比较 tok/s 时尤其谨慎。可以同时报告：
- 字符或字节吞吐；请求吞吐；任务质量；Tokenizer 信息。
### 4.2 输出长度由模型决定
如果没有强制输出长度，模型可能提前 EOS。更短输出会降低 E2E，也会改变 tok/s 与 req/s。必须报告实际输出长度分布，而不只写 `max_tokens`。
### 4.3 无限速灌入奖励吞吐策略
所有请求同时到达可形成大 Batch。它适合测饱和容量，却不代表真实用户的随机到达。交互服务需要负载—延迟曲线，而不是一个最大吞吐点。
### 4.4 Prefix Cache 泄漏
数据集若有大量共同系统 Prompt，热缓存系统会少做很多 Prefill。这可能正是生产收益，也可能是未披露的不公平优势。关键在于明确：
- 是否启用缓存；预热方法；命中率；对照系统是否具备同等机会。
### 4.5 客户端与网络边界
同机回环网络测到的不是跨机服务延迟。跨区域公网又会掩盖引擎差异。公平比较应固定客户端位置、网络路径与协议。
### 4.6 失败请求被“优化掉”
如果统计只保留成功请求，过载系统可能通过失败快速摆脱工作。报告必须含：
- 总请求数；成功数；各类失败数；超时和取消；重试规则。

## 5. 归一化与手算
归一化有助于回答特定问题，但不会自动创造公平。
### 5.1 每加速器吞吐
系统总输出吞吐为 $T$，加速器数为 $G$：
$$
T_{\mathrm{per\ accelerator}}=\frac{T}{G}
$$
教学示例：
- 系统 A：4 个加速器，总吞吐 400 单位/s；系统 B：8 个加速器，总吞吐 640 单位/s。
则：
$$
A=400/4=100
$$
$$
B=640/8=80
$$
A 的单设备吞吐高，B 的总吞吐高。二者回答不同采购问题。示例单位不代表任何真实硬件结果。
### 5.2 成本归一化
若单位时间基础设施成本为 $C$，Goodput 为 $Q$：
$$
\mathrm{CostPerGoodRequest}=\frac{C}{Q}
$$
不能用标价直接代替真实成本，至少说明：
- 云按需/预留/自建口径；CPU、网络和存储是否计入；利用率假设；币种与时间。
### 5.3 能效
若在相同测量边界内，吞吐为 $T$，平均功率为 $P$：
$$
\mathrm{Efficiency}=\frac{T}{P}
$$
单位可写 req/J 或 tok/J。平均功率测量窗口必须与性能窗口对齐。
### 5.4 扩展效率
单设备吞吐 $T_1$，$N$ 设备吞吐 $T_N$：
$$
\mathrm{ScalingEfficiency}=\frac{T_N}{N\times T_1}
$$
若 $T_1=100$、$T_4=340$ 个教学单位：
$$
340/(4\times100)=85\%
$$
损失可能来自通信、负载不均或固定开销。但若单卡与多卡配置、Batch 不同，这个数也不能解释为纯通信效率。

## 6. 复现一项公开结果
### 6.1 建立“声明—证据”表
对公开声明逐项找证据：
| 声明 | 所需证据 |
|---|---|
| 模型相同 | 权重与 Tokenizer revision |
| 精度达标 | Accuracy 日志与评分脚本 |
| 负载相同 | 数据、Seed、到达配置 |
| 硬件相同 | System JSON/拓扑 |
| 指标相同 | 计时与聚合实现 |
| 可复现 | 命令、配置、容器与原始日志 |
缺失项不等于结果必然错误。它意味着你无法验证对应声明，应降低结论强度。
### 6.2 固定上游版本
```bash
git clone <官方仓库 URL>
cd <仓库>
git checkout "<结果声明的 tag-or-commit>"
git submodule update --init --recursive
```
不要默认用当前 `main` 复现历史结果。保存：
```bash
git rev-parse HEAD
git submodule status
```
### 6.3 验证数据与模型
记录：
```yaml
artifacts:
  model_revision: "<固定值>"
  tokenizer_revision: "<固定值>"
  dataset_version: "<固定值>"
  dataset_sha256: "<实际 hash>"
  preprocessing_commit: "<commit>"
  accuracy_script_commit: "<commit>"
```
受许可证约束的数据不能随意再分发，但哈希和获取说明仍应保留。
### 6.4 先跑正确性，再跑性能
顺序：
1. 小样本冒烟。
2. 完整 Accuracy。
3. 规则校验。
4. 性能预热。
5. 正式 Performance。
6. 提交检查器或内部校验脚本。
速度快但 Accuracy 不达标的运行不应进入性能比较。
### 6.5 记录差异
如果无法获得原硬件，复现目标应改写为：
> 验证实现、数据处理与测量流程可运行。
而不是：
> 复现相同性能数值。
硬件不同，数值不同是预期，不是复现失败。

## 7. 结果解读与 trade-off
### 7.1 总吞吐 vs 单设备效率
大系统可能总吞吐领先，小系统可能单位设备或单位成本领先。采购扩容看总容量，资源效率看归一化指标。
### 7.2 延迟 vs 吞吐
更大 Batch 常提升吞吐，但可能损害 TTFT。公平的服务比较应在相同 SLO 下比 Goodput，或展示完整负载曲线。
### 7.3 专用优化 vs 通用性
针对固定 Shape、固定模型深度优化可能取得优秀基准结果。生产还需要评估：
- 多模型；变长请求；动态 LoRA；故障恢复；可观测性。
Benchmark 领先不等于运维总成本最低。
### 7.4 峰值 vs 稳态
短测试可能避开：
- 热降频；内存碎片；Cache 污染；日志轮转；长时间错误积累。
上线决策需要补充 Soak Test。

## 8. 发布内部 Benchmark 的模板
```yaml
benchmark_card:
  name: "<名称>"
  version: "<规则版本>"
  question: "<该基准回答什么>"
  non_goals: ["<不回答什么>"]
system:
  hardware: "<完整拓扑>"
  software: "<版本与 digest>"
model:
  id: "<标识>"
  revision: "<固定 revision>"
  tokenizer_revision: "<固定 revision>"
  precision: "<精度>"
quality:
  dataset: "<名称与版本>"
  metric: "<指标>"
  threshold: "<预先声明>"
workload:
  dataset_hash: "<sha256>"
  arrival_model: "<模式>"
  length_distribution: "<实际分布>"
  cache_policy: "<规则>"
measurement:
  clock_boundary: "<边界>"
  metrics: ["<指标与单位>"]
  percentiles: [50, 95, 99]
  failures: "<计入规则>"
reproduction:
  command: "<完整命令>"
  raw_artifacts: ["<路径>"]
  known_limitations: ["<限制>"]
```
给内部 Benchmark 设版本号。规则、模型或数据变化时升版本，避免同名指标悄悄换含义。

## 9. MLPerf 结果审计：从一行排行榜走到提交目录

MLPerf Inference 的结果不是一个孤立数字，而是一组相互约束的产物。审计时应从结果页记录：

- Benchmark 版本与提交轮次；
- Division；
- Category 与 Availability；
- Scenario；
- System ID；
- Submitter；
- Result 数值与单位；
- Accuracy 类别；
- Power 是否提交。

然后进入对应提交仓库或结果包，不要只看新闻稿截图。

### 9.1 先确认目录角色

正式提交通常会包含或引用这些角色的产物，具体目录以对应版本规则为准：

```text
systems/         系统硬件与软件描述
measurements/    实现参数、README、配置
results/         Accuracy 与 Performance 日志
compliance/      审计测试产物
code/            实现或构建说明
```

不同版本可能调整结构。审计目标不是背目录名，而是找到：

1. 系统是什么；
2. 运行了什么实现；
3. 用了什么参数；
4. 是否通过准确率；
5. 性能运行是否有效；
6. 审计检查是否通过。

### 9.2 审查 `systems` 描述

系统描述至少回答：

- Accelerator 型号、数量、显存；
- Host CPU、Socket、内存；
- 单机或多节点；
- 加速器互联与节点网络；
- 存储；
- 操作系统、驱动、运行时；
- 系统可用性；
- 功耗设置；
- 实现所需额外硬件。

若公开宣传写“8 GPU”，系统描述却包含多个节点、额外 DPU 或特殊网络，这些都属于结果边界。

### 9.3 审查 `measurements`

重点不是配置文件长什么样，而是配置是否与 Result 行一致：

- System ID；
- Benchmark 名；
- Scenario；
- Accuracy Target；
- Performance Sample Count；
- LoadGen 参数；
- Batch、并行与 Stream 数；
- 模型路径、精度与量化；
- 运行脚本和环境变量；
- README 中的构建与执行步骤。

同一提交者可能为不同系统维护多份配置。不能从一个相似系统复制参数解释目标结果。

### 9.4 审查 Performance 日志

查找对应版本规定的有效性结论，而不是只摘一行吞吐。常见审计问题：

- Scenario 是否正确；
- Performance Mode 是否正确；
- 最小运行时长或样本数是否满足；
- Latency Constraint 是否通过；
- 有效样本数是否满足；
- LoadGen 是否报告有效；
- 是否有错误、提前终止或警告；
- Result 单位与排行榜一致。

规则随版本变化，字段名不能脱离当轮规则解释。

### 9.5 审查 Accuracy 日志

性能实现必须与通过质量门槛的实现对应。核对：

- 数据集版本与预处理；
- 模型权重；
- 精度/量化；
- Accuracy 脚本；
- 评分输出；
- 阈值；
- High Accuracy 与普通 Accuracy 类别；
- 是否应用规则允许的校准或后处理。

Accuracy 不是“一次跑过就永久有效”。实现、模型或精度改变后，要确认是否仍有匹配的质量产物。

### 9.6 Compliance 不是装饰

Compliance/Audit 用来验证系统没有通过规则禁止的方式取得结果，例如样本处理、性能与准确率一致性等。审计时记录：

- 必需审计测试是否齐全；
- 运行是否通过；
- 豁免是否存在；
- 豁免适用范围；
- 提交后是否有修订或撤回。

有豁免不自动意味着结果无效，但必须把条件写入结论。

### 9.7 不跨版本套规则

审计记录要把规则链接固定到 tag、commit 或发布版本。若只链接 `main`，未来规则更新后，历史结论将失去上下文。

## 10. 厂商 LLM Benchmark 的配置审计

厂商自有 Benchmark 未必遵循 MLPerf 结构，因此要自己建立“配置差分”。

### 10.1 把自然语言声明转成字段

声明：

> 系统 B 比系统 A 快 1.8 倍。

先拆成：

```yaml
claim:
  numerator_metric: "<输出tok/s、请求/s或Goodput>"
  baseline_system: "A"
  candidate_system: "B"
  workload: "<数据与到达过程>"
  quality_constraint: "<阈值>"
  latency_constraint: "<阈值>"
  measurement_boundary: "<客户端/服务端>"
  normalization: "<总量/每GPU/每成本/每瓦>"
```

任何空字段都会降低“1.8 倍”的解释力。

### 10.2 命令行逐项差分

把两边服务和客户端命令规范化后比较：

```text
模型 revision
Tokenizer revision
dtype/量化
Tensor/Expert/Pipeline Parallel
KV Cache dtype
GPU memory utilization
max model length
max batched tokens
max sequences
Prefix Cache
Chunked Prefill
Speculative Decoding
CUDA Graph/编译
采样参数
停止条件
请求率/并发
数据集与Seed
```

“使用各框架最佳参数”可以是合法比较，但它回答的是“各自调优后的系统能力”，不是“单一优化的因果收益”。报告必须区分。

### 10.3 硬件频率与功耗配置

同型号 GPU 仍可能不同：

- Power Limit；
- Application Clock；
- Boost 行为；
- 散热条件；
- MIG/分区；
- ECC；
- 固件；
- 主机 BIOS；
- NUMA 与 CPU 频率策略。

如果一方解除功耗限制、另一方保持默认，总吞吐可比较但能效与部署约束不能直接外推。

### 10.4 软件成熟度

核对：

- 正式发布还是内部分支；
- 是否提供 commit；
- Kernel 是否可获得；
- 是否使用尚未发布的编译器；
- 是否需要特殊 Patch；
- 是否能在声明硬件上部署；
- 安全与稳定特性是否关闭。

预览软件的技术结果有参考价值，但不能直接当作今天的采购 TCO。

### 10.5 负载生成器边界

厂商结果常漏掉：

- 是否流式；
- 首 Token 是否在客户端计时；
- 网络是回环、同机、同机架还是公网；
- 请求是否一次性灌入；
- 并发上限；
- Warmup；
- 测量时长；
- 失败与重试；
- 客户端是否成为瓶颈。

如果只公布 tok/s 和平均延迟，应把结论限定为“公开信息下的摘要”，不能补写未披露条件。

## 11. 准确率与质量边界：快多少之前先问对不对

### 11.1 准确率阈值必须绑定参考

量化 Benchmark 常写“保持 99% 准确率”，但可能指：

- 绝对准确率 99%；
- 相对 FP16 基线保留 99%；
- 某个任务分数的 99%；
- 只在校准集上；
- 多个任务的平均。

必须给出公式。例如相对保留率：

$$
\mathrm{Retention}
=\frac{\mathrm{Score}_{candidate}}
{\mathrm{Score}_{reference}}
$$

如果指标可能为负或不是比率尺度，这个公式未必合适，应遵循具体任务规则。

### 11.2 生成质量不止一个 Accuracy

LLM 服务应考虑：

- 任务正确率；
- Perplexity；
- ROUGE/BLEU 等任务指标；
- Human/Judge 评价；
- Tool Call 成功率；
- JSON Schema 有效率；
- Reasoning 答案正确率；
- 安全与拒答行为。

吞吐优化改变采样、输出长度或 Reasoning 模式时，质量边界必须与实际业务相同。

### 11.3 输出长度是质量与性能共同变量

候选模型更早 EOS：

- E2E 下降；
- 完成 req/s 可能上升；
- 输出 tok/s 的变化不确定；
- 答案可能不完整。

因此报告至少同时给：

- 请求成功率；
- 实际输出长度分布；
- 任务质量；
- 停止原因分布；
- 性能指标。

### 11.4 非确定生成的比较

若 Temperature 非零：

- 固定 Seed 可能仍因并行与实现产生差异；
- 输出长度和路径会变化；
- 单次质量分数不稳定。

可选策略：

1. 性能运行使用确定性解码，质量另测；
2. 按规则运行多 Seed；
3. 固定请求并保存生成结果；
4. 报告质量置信区间；
5. 将输出长度作为协变量。

策略必须与 Benchmark 的目标一致。

### 11.5 Accuracy Run 与 Performance Run 一致性

重点核对：

- 模型与权重相同；
- 量化与精度相同；
- Tokenizer 与模板相同；
- 采样与停止条件相同或规则明确允许不同；
- 后处理相同；
- 实现路径相同；
- 不存在“准确率用慢配置，性能用低质量快配置”。

## 12. 功耗与能效边界：分母到底测了什么

### 12.1 三种常见边界

```text
芯片边界：只测加速器板卡功耗
系统边界：服务器墙插，包括CPU、内存、风扇、NIC
集群边界：计算节点 + 网络设备 + 可能的存储/冷却
```

边界越大越接近部署成本，但测量更复杂。不同边界的 tok/J 不可直接排序。

### 12.2 功率、能量与平均窗口

功率是瞬时速率，能量是积分：

$$
E=\int_{t_0}^{t_1}P(t)\,dt
$$

离散采样近似：

$$
E\approx\sum_i P_i\Delta t_i
$$

能效可写：

$$
\mathrm{RequestsPerJoule}
=\frac{\mathrm{CompletedRequests}}{E}
$$

或：

$$
\mathrm{OutputTokensPerJoule}
=\frac{\mathrm{ActualOutputTokens}}{E}
$$

`平均吞吐 / 平均功率` 只有在两个平均值覆盖同一窗口且边界一致时才等价。

### 12.3 是否包含空闲、Warmup 与冷却

短 Burst 的测量可能：

- 不含模型加载；
- 不含编译；
- 不含 Warmup；
- 测试结束前系统尚未热稳；
- 忽略请求间空闲功耗。

生产 TCO 可能更关心：

```text
一天总有效请求 / 一天总能量
```

而不是满载 60 秒的峰值 tok/J。两种结果都可发布，但问题不同。

### 12.4 外部功率计与板卡遥测

板卡遥测易采集，但不含 Host 与网络。外部功率计更接近系统边界，但要校准：

- 采样频率；
- 时间同步；
- 仪器误差；
- 三相/多电源汇总；
- 基线空闲功耗；
- 测量窗口；
- 数据缺失。

不能把 `nvidia-smi` 的单点功率读数当作整轮能量。

### 12.5 每瓦性能也需要质量与 SLO

系统可以通过降频降低功耗，但延迟违反 SLO；也可生成更短输出减少能量。更有业务意义的是：

$$
\mathrm{GoodRequestsPerJoule}
=\frac{\text{满足质量与延迟合同的请求数}}{E}
$$

合同与能量边界仍需预先声明。

## 13. 设计公平对比：先写问题，再写实验

### 13.1 四类常见问题

问题 A：哪个系统总容量更高？

- 固定质量、工作负载与 SLO；
- 比总 Goodput；
- 允许硬件数量不同；
- 同时报总成本与功耗。

问题 B：哪个软件栈效率更高？

- 固定同一硬件；
- 固定模型、精度、数据和服务边界；
- 双方允许同等程度调优；
- 比负载曲线与资源利用。

问题 C：哪个硬件单位设备更快？

- 每设备归一化；
- 仍报告总系统配置；
- 检查互联、显存容量与并行是否改变；
- 不把线性归一化当成真实可扩展性。

问题 D：哪个方案 TCO 更低？

- 以满足业务 SLO 的容量规划为基础；
- 包含 CPU、网络、存储、能耗与软件成本；
- 说明利用率与价格；
- 做敏感性分析。

四个问题不能靠同一个“tok/s”回答。

### 13.2 对称调优预算

公平不一定意味着参数相同。不同系统的最佳 Batch 不同。可以定义：

```yaml
tuning_budget:
  wall_clock_hours_per_system: "<相同>"
  allowed_parameters: ["batch", "parallelism", "cache", "compile"]
  forbidden_changes: ["model", "quality threshold", "dataset"]
  search_record_required: true
  final_selection_rule: "validation负载上最大Goodput"
```

必须避免只为候选精调、基线用默认参数。

### 13.3 训练/验证/测试式负载拆分

如果反复在同一负载上调参，会对 Benchmark 过拟合。可拆分：

- Tuning Workload：调参数；
- Validation Workload：选最终配置；
- Held-out Workload：一次性报告；
- Production Trace：验证外部有效性。

数据和阈值在测试前冻结。

### 13.4 负载曲线而非单点

对在线服务，用相同到达过程扫描请求率，展示：

```text
request rate
TTFT P50/P95/P99
TPOT P50/P95
ITL P99（注明chunk/token）
error rate
observed goodput
GPU/系统功耗
```

在相同 SLO 下比较最大可持续 Goodput，比在各自不同延迟点比较峰值吞吐更公平。

### 13.5 随机化和重复

基线与候选交替运行：

```text
A B B A / B A A B
```

并重复多个 Seed。保留每轮原始数据，不只公布最好一轮。统计显著性和噪声预算将在 9.5 详细展开。

## 14. 完整案例：审计“每瓦性能提升 2 倍”

以下是虚构审计材料，用于学习方法；不对应任何厂商或硬件。

### 14.1 公布的声明

```text
系统 B 的 LLM 每瓦性能是系统 A 的 2 倍。
```

图中只展示：

```text
B: 200 tokens/s/W
A: 100 tokens/s/W
```

### 14.2 第一轮证据：配置边界

补充材料显示：

```text
A：系统墙插功率，含CPU、内存、风扇
B：GPU板卡遥测功率
A：自然EOS
B：后端配置为固定最大输出
A：跨机客户端
B：同机回环
```

这三项已经使“2 倍”不能作为同边界比较。

### 14.3 第二轮证据：模型与质量

继续核对：

```text
模型家族：相同
权重 revision：未披露
A：BF16
B：INT4
质量数据集：只披露B通过一个内部小样本
准确率阈值：未披露
```

INT4 可能是合法优化，但没有共同质量门槛，无法判断速度是否以质量换取。

### 14.4 第三轮证据：Token 与窗口

原始数据进一步显示：

```text
A 输出 Token：使用模型官方 Tokenizer
B 输出 Token：使用另一版本 Tokenizer
A 能量窗口：含稳定前后的空闲
B 能量窗口：只含最繁忙区间
```

分子与分母都不一致。

### 14.5 可支持的结论

不能写：

> B 在相同条件下能效是 A 的 2 倍。

只能写：

> 发布摘要中的两个比值使用不同 Tokenizer、功耗边界、测量窗口和精度配置；现有证据不足以支持同条件 2 倍能效结论。

缺少证据并不证明 B 更差，只意味着该倍率不可审核。

### 14.6 重设计公平实验

共同合同：

1. 固定同一模型与 Tokenizer revision；
2. 规定共同质量阈值；
3. 冻结数据集、到达过程、输出策略；
4. 使用同一客户端网络边界；
5. 两边都测整机墙插能量；
6. 同一 Warmup 与稳态窗口；
7. 扫描负载，在相同 TTFT/TPOT SLO 下取 Goodput；
8. 计算 Good requests/J；
9. 重复并报告不确定性；
10. 同时披露总系统成本和硬件数量。

### 14.7 证据链

```text
症状：宣称2倍
证据：功耗边界不同
证据：Tokenizer和输出策略不同
证据：质量阈值缺失
结论：倍率不具备同条件可比性
行动：按共同合同重测
```

这就是 Benchmark 审计：不是寻找反驳，而是判断证据允许多强的结论。

## 15. 完整案例：MLPerf 结果与生产服务为何都有效却不同

### 15.1 症状

某团队复现了一个 MLPerf 提交的实现路径，但内部在线服务吞吐明显不同，于是怀疑官方结果“不真实”。

### 15.2 证据

审计发现：

- MLPerf 结果对应特定 Benchmark 版本与 Scenario；
- 提交按规则使用固定模型、数据与 LoadGen；
- Accuracy、Performance 和 Compliance 均有效；
- 内部服务使用不同输入/输出长度；
- 内部负载是带突发的开放到达；
- 内部启用 Prefix Cache；
- 内部 SLO 以 TTFT 与 TPOT 联合约束；
- 内部指标包含网关和跨机网络。

### 15.3 结论

两者都可能正确：

- MLPerf 结果回答规则化场景下的可审核系统性能；
- 内部结果回答生产代表负载下的客户端体验。

错误不在任一基准，而在把一个问题的答案外推到另一个问题。

---
## 16. 审计结论的置信等级

可用四级表达避免“真/假”二分：

```text
Level 0：只有营销摘要，关键配置缺失
Level 1：配置较完整，但无原始日志或质量证据
Level 2：配置、质量、性能日志可审，部分环境无法复现
Level 3：规则完整、产物齐全、独立复现或正式审计通过
```

等级描述的是可审核性，不是绝对性能高低。结论写法示例：

> 该结果在披露的模型、系统与工作负载内可复核；不能外推到不同 Tokenizer、SLO 或功耗边界。

## 17. Benchmark 审计清单

### 17.1 身份

- 版本、Division、Scenario、System ID 是否明确？
- 结果是否有修订、撤回或 Preview 标记？

### 17.2 系统

- GPU、CPU、内存、网络、拓扑是否完整？
- 软件 commit、镜像与构建参数是否可得？
- 功耗、时钟与可用性状态是否披露？

### 17.3 模型与质量

- 权重、Tokenizer、精度和量化是否一致？
- Accuracy 数据、脚本、阈值和日志是否齐全？
- Performance 与 Accuracy 是否同一实现语义？

### 17.4 负载与指标

- 数据集、长度、到达、Streaming、Cache 是否明确？
- Token、请求和时间边界是否一致？
- 失败、超时、重试如何处理？

### 17.5 功耗

- 芯片、整机还是集群边界？
- 能量窗口与性能窗口是否对齐？
- 是否含空闲、Warmup、网络与冷却？
- 仪器与采样方法是否披露？

### 17.6 结论

- 比的是总容量、单位设备、成本还是能效？
- 归一化有没有掩盖系统规模差异？
- 证据允许相关结论还是因果结论？
- 未披露项是否明确降低了结论强度？

## 📝 总结
- 权威 Benchmark 的核心是公开规则、质量护栏、可复核产物与审查流程；公平比较要对齐模型、质量、硬件、软件、工作负载和指标口径；MLPerf 的 Division、场景、版本、可用性与功耗边界都是结果的一部分；LLM Benchmark 特别容易被 Tokenizer、输出长度、缓存和失败过滤误导。
- 每设备、每成本和每瓦归一化回答不同问题，不能替代原始条件；复现先验证正确性和规则，再比较性能；不同硬件不应强求相同数值。
