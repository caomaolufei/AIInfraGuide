公开 Benchmark 最吸引人的部分是排行榜，最有价值的部分却是规则。没有规则，“更快”可能只是模型更小、输出更短、精度更低或硬件更多。本节不教你背冠军数字，而是教你判断两个结果是否真的可比。

## 1. 权威来自规则而非名气
可信 Benchmark 通常具备：
1. 明确任务与输入数据。
2. 明确模型或允许的模型变化。
3. 明确质量/准确率下限。
4. 明确系统边界与计时口径。
5. 明确负载生成与有效性检查。
6. 可供复核的配置、日志与实现。
7. 对结果进行校验、同行评审或审计。
“由知名厂商发布”不是充分条件。“代码开源”也不是充分条件。如果关键数据、模型 revision、运行参数或硬件拓扑缺失，别人仍无法复现。
### 1.1 Benchmark 是一份契约
把 Benchmark 看成契约：
- 输入方承诺按规则生成负载；被测系统承诺不识别并特判测试样本；计量方承诺用统一方法统计；发布者承诺披露复现所需信息。
排行榜只是这份契约执行后的一个视图。
### 1.2 快与好必须同时成立
推理系统可以通过牺牲质量换速度：
- 更激进的量化；更小模型替换；降低最大输出长度；修改采样或停止条件；跳过部分请求。
所以性能结果必须绑定质量检查。没有质量护栏的 tok/s 只说明“产生了多少 Token”，不说明这些 Token 是否满足任务。

## 2. 公平比较的六个对齐项
### 2.1 模型对齐
至少对齐：
- 模型家族与参数规模；权重 revision；Tokenizer revision；精度与量化方法；LoRA/Adapter；上下文长度与位置编码配置。
“都是某某 70B”仍可能是不同权重或不同量化。
### 2.2 质量对齐
记录：
- 质量数据集与版本；评价脚本 commit；采样参数；随机 Seed；通过阈值；是否采用高准确率类别或特殊规则。
质量略低但速度更高的系统，不应在没有说明的情况下宣称全面胜出。
### 2.3 硬件对齐
至少披露：
- GPU/加速器型号与数量；单卡显存；CPU、内存和 NUMA；GPU 互联与网络；功耗限制和时钟策略；单机还是多机；是否为预览硬件。
8 卡结果和 1 卡结果不能只比总 tok/s。
### 2.4 软件对齐
至少披露：
- 驱动、CUDA/ROCm；框架与推理引擎版本；Kernel 库；容器 digest；编译选项；服务启动参数。
“最新版”无法复现。应写 tag、commit 或不可变镜像 digest。
### 2.5 工作负载对齐
LLM 负载尤其要对齐：
- 输入长度分布；输出长度分布；到达模式；并发与请求率；Streaming；Prefix Cache 状态与命中率；请求失败、超时与取消规则；Benchmark 时长与样本数。
### 2.6 指标口径对齐
确认：
- tok/s 指输入、输出还是总 Token；延迟在客户端还是服务端测量；percentile 算法和聚合层级；失败请求是否从延迟统计中排除；Benchmark 持续时间从何时算起；Goodput 的 SLO 阈值是什么。
只有六项对齐后，数字比较才有意义。

## 3. MLPerf Inference 应该怎么看
MLPerf Inference 由 MLCommons 维护。它的重要性不在于覆盖所有真实业务，而在于提供一套可审核的共同规则。
### 3.1 Closed 与 Open Division
**Closed Division** 强调“苹果对苹果”：
- 使用规定模型与数据；对可修改部分有明确限制；按版本规则执行质量与性能测试。
**Open Division** 允许更多创新：
- 可能允许模型替换或重新训练；结果仍有价值，但不应与 Closed 直接混成一个结论。
阅读结果时先看 Division，再看数字。
### 3.2 场景不是装饰字段
MLPerf 不同版本和系统类型定义不同场景。常见思路包括：
- 强调批处理吞吐的场景；强调随机到达与延迟约束的服务场景；强调单请求或交互体验的场景。
具体名称与规则会随 Benchmark 版本演进。必须查对应轮次的规则，不能拿旧博客解释新结果。
### 3.3 质量测试先于性能结论
正式结果通常需要通过规定的准确率检查。因此查看提交时应同时寻找：
- Accuracy 日志；Performance 日志；Compliance/Audit 产物；System 描述；Implementation 配置。
只摘 Performance 数字会丢掉结果成立的前提。
### 3.4 Available 与 Preview
公开结果可能标记系统或软件的可用性类别。采购时应区分：
- 当前可获得的系统；预览或未来可获得的系统。
预览结果展示技术方向，不自动等于你今天可以买到并复现。
### 3.5 功耗结果
性能/功耗必须确认测量边界：
- 仅加速器；整机；多节点系统；是否包含空闲与网络设备。
不同边界的“每瓦性能”不能直接比较。
### 3.6 为什么版本不能跨轮次硬比
Benchmark 版本升级可能改变：
- 模型；数据集；质量阈值；场景规则；负载生成器；提交要求。
即使指标名相同，跨版本也可能不是同一实验。

## 4. LLM Serving Benchmark 的特殊陷阱
### 4.1 Tokenizer 不同
同一段文本用不同 Tokenizer 会得到不同 Token 数。tok/s 的分母单位看似一致，实际“一个 Token”包含的信息不同。跨模型比较 tok/s 时尤其谨慎。可以同时报告：
- 字符或字节吞吐；请求吞吐；任务质量；Tokenizer 信息。
### 4.2 输出长度由模型决定
如果没有强制输出长度，模型可能提前 EOS。更短输出会降低 E2E，也会改变 tok/s 与 req/s。必须报告实际输出长度分布，而不只写 `max_tokens`。
### 4.3 无限速灌入奖励吞吐策略
所有请求同时到达可形成大 Batch。它适合测饱和容量，却不代表真实用户的随机到达。交互服务需要负载—延迟曲线，而不是一个最大吞吐点。
### 4.4 Prefix Cache 泄漏
数据集若有大量共同系统 Prompt，热缓存系统会少做很多 Prefill。这可能正是生产收益，也可能是未披露的不公平优势。关键在于明确：
- 是否启用缓存；预热方法；命中率；对照系统是否具备同等机会。
### 4.5 客户端与网络边界
同机回环网络测到的不是跨机服务延迟。跨区域公网又会掩盖引擎差异。公平比较应固定客户端位置、网络路径与协议。
### 4.6 失败请求被“优化掉”
如果统计只保留成功请求，过载系统可能通过失败快速摆脱工作。报告必须含：
- 总请求数；成功数；各类失败数；超时和取消；重试规则。

## 5. 归一化与手算
归一化有助于回答特定问题，但不会自动创造公平。
### 5.1 每加速器吞吐
系统总输出吞吐为 $T$，加速器数为 $G$：
$$
T_{\mathrm{per\ accelerator}}=\frac{T}{G}
$$
教学示例：
- 系统 A：4 个加速器，总吞吐 400 单位/s；系统 B：8 个加速器，总吞吐 640 单位/s。
则：
$$
A=400/4=100
$$
$$
B=640/8=80
$$
A 的单设备吞吐高，B 的总吞吐高。二者回答不同采购问题。示例单位不代表任何真实硬件结果。
### 5.2 成本归一化
若单位时间基础设施成本为 $C$，Goodput 为 $Q$：
$$
\mathrm{CostPerGoodRequest}=\frac{C}{Q}
$$
不能用标价直接代替真实成本，至少说明：
- 云按需/预留/自建口径；CPU、网络和存储是否计入；利用率假设；币种与时间。
### 5.3 能效
若在相同测量边界内，吞吐为 $T$，平均功率为 $P$：
$$
\mathrm{Efficiency}=\frac{T}{P}
$$
单位可写 req/J 或 tok/J。平均功率测量窗口必须与性能窗口对齐。
### 5.4 扩展效率
单设备吞吐 $T_1$，$N$ 设备吞吐 $T_N$：
$$
\mathrm{ScalingEfficiency}=\frac{T_N}{N\times T_1}
$$
若 $T_1=100$、$T_4=340$ 个教学单位：
$$
340/(4\times100)=85\%
$$
损失可能来自通信、负载不均或固定开销。但若单卡与多卡配置、Batch 不同，这个数也不能解释为纯通信效率。

## 6. 复现一项公开结果
### 6.1 建立“声明—证据”表
对公开声明逐项找证据：
| 声明 | 所需证据 |
|---|---|
| 模型相同 | 权重与 Tokenizer revision |
| 精度达标 | Accuracy 日志与评分脚本 |
| 负载相同 | 数据、Seed、到达配置 |
| 硬件相同 | System JSON/拓扑 |
| 指标相同 | 计时与聚合实现 |
| 可复现 | 命令、配置、容器与原始日志 |
缺失项不等于结果必然错误。它意味着你无法验证对应声明，应降低结论强度。
### 6.2 固定上游版本
```bash
git clone <官方仓库 URL>
cd <仓库>
git checkout "<结果声明的 tag-or-commit>"
git submodule update --init --recursive
```
不要默认用当前 `main` 复现历史结果。保存：
```bash
git rev-parse HEAD
git submodule status
```
### 6.3 验证数据与模型
记录：
```yaml
artifacts:
  model_revision: "<固定值>"
  tokenizer_revision: "<固定值>"
  dataset_version: "<固定值>"
  dataset_sha256: "<实际 hash>"
  preprocessing_commit: "<commit>"
  accuracy_script_commit: "<commit>"
```
受许可证约束的数据不能随意再分发，但哈希和获取说明仍应保留。
### 6.4 先跑正确性，再跑性能
顺序：
1. 小样本冒烟。
2. 完整 Accuracy。
3. 规则校验。
4. 性能预热。
5. 正式 Performance。
6. 提交检查器或内部校验脚本。
速度快但 Accuracy 不达标的运行不应进入性能比较。
### 6.5 记录差异
如果无法获得原硬件，复现目标应改写为：
> 验证实现、数据处理与测量流程可运行。
而不是：
> 复现相同性能数值。
硬件不同，数值不同是预期，不是复现失败。

## 7. 结果解读与 trade-off
### 7.1 总吞吐 vs 单设备效率
大系统可能总吞吐领先，小系统可能单位设备或单位成本领先。采购扩容看总容量，资源效率看归一化指标。
### 7.2 延迟 vs 吞吐
更大 Batch 常提升吞吐，但可能损害 TTFT。公平的服务比较应在相同 SLO 下比 Goodput，或展示完整负载曲线。
### 7.3 专用优化 vs 通用性
针对固定 Shape、固定模型深度优化可能取得优秀基准结果。生产还需要评估：
- 多模型；变长请求；动态 LoRA；故障恢复；可观测性。
Benchmark 领先不等于运维总成本最低。
### 7.4 峰值 vs 稳态
短测试可能避开：
- 热降频；内存碎片；Cache 污染；日志轮转；长时间错误积累。
上线决策需要补充 Soak Test。

## 8. 发布内部 Benchmark 的模板
```yaml
benchmark_card:
  name: "<名称>"
  version: "<规则版本>"
  question: "<该基准回答什么>"
  non_goals: ["<不回答什么>"]
system:
  hardware: "<完整拓扑>"
  software: "<版本与 digest>"
model:
  id: "<标识>"
  revision: "<固定 revision>"
  tokenizer_revision: "<固定 revision>"
  precision: "<精度>"
quality:
  dataset: "<名称与版本>"
  metric: "<指标>"
  threshold: "<预先声明>"
workload:
  dataset_hash: "<sha256>"
  arrival_model: "<模式>"
  length_distribution: "<实际分布>"
  cache_policy: "<规则>"
measurement:
  clock_boundary: "<边界>"
  metrics: ["<指标与单位>"]
  percentiles: [50, 95, 99]
  failures: "<计入规则>"
reproduction:
  command: "<完整命令>"
  raw_artifacts: ["<路径>"]
  known_limitations: ["<限制>"]
```
给内部 Benchmark 设版本号。规则、模型或数据变化时升版本，避免同名指标悄悄换含义。

## 📝 总结
- 权威 Benchmark 的核心是公开规则、质量护栏、可复核产物与审查流程；公平比较要对齐模型、质量、硬件、软件、工作负载和指标口径；MLPerf 的 Division、场景、版本、可用性与功耗边界都是结果的一部分；LLM Benchmark 特别容易被 Tokenizer、输出长度、缓存和失败过滤误导。
- 每设备、每成本和每瓦归一化回答不同问题，不能替代原始条件；复现先验证正确性和规则，再比较性能；不同硬件不应强求相同数值。
