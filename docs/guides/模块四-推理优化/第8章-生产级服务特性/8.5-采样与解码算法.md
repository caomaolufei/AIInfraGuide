模型一次前向不会直接吐出“下一个词”，而是给词表中每个 Token 一个分数。采样器决定如何把这几万个分数变成一个选择。
Temperature、Top-k、Top-p 看起来只是三个 API 参数，实际共同定义了“候选池有多大、概率有多尖、随机性有多强”。而 `n`、Beam Search 和 Logprobs 还会改变序列数量、KV Cache 与返回体积。
调参不是找一组万能数字，而是为任务选择合适的搜索策略。
<!-- more -->

## 1. 从 Logits 到概率
模型最后一层为词表中每个 Token 输出 Logit $z_i$。Softmax 将其转换为概率：
$$ p_i = \frac{e^{z_i}}{\sum_j e^{z_j}} $$
采样器随后从分布 $p$ 中选一个 Token，追加到序列，再做下一步前向。
例如：
| Token | Logit | Softmax 概率（示意） |
|---|---:|---:|
| 北京 | 4.0 | 0.62 |
| 上海 | 3.2 | 0.28 |
| 杭州 | 2.1 | 0.09 |
| 香蕉 | -1.0 | 0.01 |
Greedy 每次选概率最大的“北京”；随机采样会偶尔选“上海”或“杭州”。
类比餐厅点菜：模型先给每道菜打分，采样器决定是永远点最高分，还是从高分菜单里按概率抽签。Temperature 改评分差距，Top-k 限制菜单项数，Top-p 限制菜单覆盖的总可信度。
---

## 2. Temperature
Temperature 在 Softmax 前缩放 Logits：
$$ p_i(T) = \frac{e^{z_i/T}} {\sum_j e^{z_j/T}} $$
### 2.1 T 小于 1
分布变尖，高分 Token 更占优势：
- 输出更稳定；
- 创造性下降；
- 重复高概率模式的风险可能增加。
### 2.2 T 大于 1
分布变平，低概率 Token 更有机会：
- 多样性增加；
- 事实和格式错误风险上升；
- 极高值可能产生无意义输出。
### 2.3 T 等于 0
在 vLLM 的 `SamplingParams` 语义中，`temperature=0` 表示 Greedy Sampling，即选择最高概率 Token。
这不是数学上直接把 $T=0$ 代入公式，而是实现层的特殊分支。
### 2.4 低 Temperature 不等于绝对可复现
即使 Greedy，也可能受到：
- 浮点精度；
- 不同 GPU 与 Kernel；
- 并行归约顺序；
- 模型 Revision；
- Chat Template；
- 调度与实现变化。
需要强回归时，应比较任务结果和结构，不要假设跨版本逐 Token 完全相同。
📌 **关键点**：Temperature 改的是候选之间的相对概率，不会主动删除候选。

## 3. Top-k 与 Top-p
### 3.1 Top-k
Top-k 只保留概率最高的 $k$ 个 Token，其余置零后重新归一化。
若 `top_k=2`，上表只留下“北京”和“上海”。
优点：
- 候选数量稳定；
- 易理解；
- 能排除长尾噪声。
缺点：
- 不看分布形状；
- 模型很确定时，仍保留固定数量；
- 模型不确定时，可能过早砍掉合理候选。
当前 vLLM `SamplingParams` 中，`top_k=0` 或 `-1` 表示考虑所有 Token；在线 OpenAI 兼容接口里 `top_k` 是 vLLM 扩展，通常通过 `extra_body` 传入。
### 3.2 Top-p
Top-p，也称 Nucleus Sampling，按概率从高到低累加，保留累计概率达到阈值 $p$ 的最小集合。
例如 `top_p=0.9`：
```text
北京 0.62  累计 0.62
上海 0.28  累计 0.90  ← 到此停止
```
候选集大小随模型置信度动态变化：
- 分布很尖时，可能只保留 1 个；
- 分布很平时，可能保留很多个。
### 3.3 两者的直觉区别
- Top-k 问：“最多看前几名？”
- Top-p 问：“看多少候选才能覆盖足够概率？”
Top-k 是固定席位，Top-p 是按总票数划线。

## 4. 参数组合与顺序
实际采样链路还可能包含：
- repetition/frequency/presence penalty；
- allowed/bad words；
- structured output mask；
- Temperature；
- Top-k、Top-p、Min-p；
- 最终 multinomial sampling。
具体处理顺序属于实现细节，应以锁定 vLLM 版本源码和文档为准；但理解上可记为：
```text
原始 Logits
  → 规则与惩罚
  → 结构化输出合法集合
  → Temperature 缩放
  → Top-k / Top-p 截断
  → 归一化并采样
```
### 4.1 同时设置 Top-k 与 Top-p
两者通常取交集效果：先缩小一遍，再按另一个规则继续缩小。参数都很激进时，候选可能接近 Greedy。
例如：
```text
temperature=0.2, top_k=5, top_p=0.5
```
三个参数都在压低多样性。若输出过于僵硬，不要只改单个参数而忽略组合。
### 4.2 与结构化输出组合
结构化输出先把不合法 Token 排除，采样参数只在合法集合中选择。
若语法状态只允许 `}`，无论 Temperature 多高都必须生成 `}`。这解释了为何强约束下调 Temperature 可能几乎无效果。

## 5. vLLM SamplingParams 与在线 API
### 5.1 离线推理
```python
from vllm import LLM, SamplingParams
llm = LLM(
    model="Qwen/Qwen3-8B",
    generation_config="vllm",
)
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    top_k=50,
    max_tokens=256,
    seed=42,
)
outputs = llm.generate(
    ["用三个要点解释 PagedAttention"],
    params,
)
```
### 5.2 generation_config 的影响
vLLM 可能读取模型仓库的 `generation_config.json` 作为默认采样参数。于是两个模型即使请求里都没写 Temperature，实际默认也可能不同。
若希望使用 vLLM 默认值，可以在初始化时显式设置：
```python
LLM(model=model_id, generation_config="vllm")
```
生产中更建议在请求或服务配置中显式声明关键参数，避免模型 Revision 更新悄悄改变默认行为。
### 5.3 OpenAI 兼容接口
```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "写一句产品标语"}],
    temperature=0.8,
    top_p=0.95,
    max_tokens=64,
    extra_body={"top_k": 50},
)
```
`temperature`、`top_p` 属于常见 OpenAI 字段；`top_k` 是 vLLM 扩展。扩展字段和允许范围应以当前 OpenAI-Compatible Server 文档为准。

## 6. Logprobs 的正确理解
Logprob 是概率的自然对数：
$$ \log p_i \le 0 $$
越接近 0，概率越高。例如：
```text
logprob = -0.1  → p ≈ 0.905
logprob = -2.3  → p ≈ 0.100
logprob = -6.9  → p ≈ 0.001
```
### 6.1 输出 Token Logprobs
`SamplingParams(logprobs=k)` 请求每个生成位置返回若干高概率 Token，并总是包含实际选中的 Token。因此结果数量可能达到 `k+1`。
`logprobs=-1` 可表示返回全词表，但成本很高：
- GPU/CPU 数据搬运；
- 序列化；
- 网络响应体；
- 客户端内存。
在线服务不应默认开放无限制全词表 Logprobs。
### 6.2 Prompt Logprobs
`prompt_logprobs` 返回 Prompt 各位置 Token 的概率信息，可用于：
- 计算文本似然；
- 比较候选答案；
- 调试 Tokenization。
它不是“模型对整段 Prompt 的置信度”。长度不同的文本直接相加会偏向短文本，常需做长度归一化。
### 6.3 Chat API 字段
OpenAI 风格 Chat 请求通常使用：
```python
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "天空通常是什么颜色？"}],
    logprobs=True,
    top_logprobs=5,
)
```
vLLM 还可能提供 `prompt_logprobs`、`logprob_token_ids` 等扩展。后者适合只关心少数标签 Token 的评分任务，比索取全词表更经济。
### 6.4 Logprobs 不是校准概率
模型给“正确”很高概率，不代表现实中 90% 正确。语言模型概率首先描述 Token 在上下文中的相对偏好。
若用于风险决策，需要在目标数据上做：
- Calibration；
- 阈值评估；
- 类别 Token 设计；
- 分布漂移监控。

## 7. 并行采样 n 与 best_of
### 7.1 n
`n` 表示每个 Prompt 返回多少条输出。多样化生成、候选重排和自洽投票常用它。
```python
params = SamplingParams(
    n=4,
    temperature=0.8,
    top_p=0.95,
    max_tokens=128,
)
```
四条序列共享 Prompt Prefill 的机会，但 Decode 后会分叉，各自需要 KV 状态和计算。
粗略理解：
$$ M_{\text{decode KV}} \propto n \times L_{\text{generated}} $$
所以 `n=4` 绝不是“只多返回三段字符串”，它可能显著放大 Decode 显存和时延。
### 7.2 best_of
`best_of` 表示内部生成更多候选，再返回其中较优的一部分。它可以提高结果质量，却把未返回候选的计算完全留在服务端。
客户端看到一条结果，不代表服务端只解码了一条序列。

⚠️ **版本边界**：`best_of` 属于旧 V0 路径，在当前 vLLM V1 中已弃用/不支持，不能把它当成通用在线能力。V1 场景可根据目标使用 `n` 返回候选、独立 Beam Search，或在应用侧执行评分与重排，并重新核算 KV Cache 和算力预算。
### 7.3 调度影响
大量并行候选会：
- 增加活跃序列数；
- 占用更多 KV Block；
- 降低其他请求可用并发；
- 放大尾延迟；
- 增加取消和超时后的浪费。
若仍维护 V0，生产网关应限制每请求 `n`、`best_of` 与 `max_tokens` 的组合预算；V1 则限制实际使用的 `n`、Beam 或应用侧候选数量。
---

## 8. Beam Search
Beam Search 每一步保留累计得分最高的 $B$ 条部分序列，而不是独立随机抽样。
### 8.1 基本过程
若 Beam Width 为 3：
1. 从起点扩展多个 Token；
2. 保留累计得分最高的 3 条；
3. 每条再次扩展；
4. 在所有新候选中继续保留 3 条；
5. 直到结束条件。
它像同时沿三条最有希望的路线搜索，每个路口都淘汰落后的路线。
### 8.2 长度偏置
直接累加 Logprob 往往偏爱短序列，因为每增加一个 Token 都加上非正数。Beam Search 常配合 Length Penalty：
```text
score = cumulative_logprob / length_penalty_term
```
具体公式和参数语义需以实现为准。
### 8.3 vLLM 离线接口
当前官方生成模型文档展示独立的 `BeamSearchParams` 与 `LLM.beam_search`：
```python
from vllm import LLM
from vllm.sampling_params import BeamSearchParams
llm = LLM(model="facebook/opt-125m")
params = BeamSearchParams(
    beam_width=5,
    max_tokens=50,
)
outputs = llm.beam_search(
    [{"prompt": "Hello, my name is "}],
    params,
)
```
OpenAI 兼容协议不是以 Beam Search 为核心设计。vLLM 的在线扩展曾提供或当前可能提供 `use_beam_search` 等字段，使用前必须检查目标版本接口，优先依赖当前官方示例。
### 8.4 Beam Search 不总比采样好
它常用于：
- 机器翻译；
- 语音识别；
- 有明确序列似然目标的任务。
开放式对话中，Beam Search 可能：
- 输出更保守、同质；
- 增加计算与 KV Cache；
- 牺牲流式首选结果的直观性；
- 未必提高事实正确率。
Beam Width 也不是越大越好。搜索目标若与业务质量不一致，更努力优化 Logprob 只会更确定地得到错误目标。

## 9. 质量、性能与可复现性
### 9.1 性能成本地图
| 参数 | 主要质量影响 | 主要系统成本 |
|---|---|---|
| Temperature | 随机性 | 通常较小 |
| Top-k/Top-p | 候选多样性 | 采样器开销，通常较小 |
| Logprobs | 可观测候选概率 | 搬运、序列化、网络 |
| n | 多候选 | Decode 计算与 KV 近似放大 |
| best_of | 服务端搜索质量 | 隐藏候选计算 |
| Beam Width | 高似然序列搜索 | 分支、排序、KV 与延迟 |
### 9.2 Seed
Seed 有助于同环境复现实验，但不是跨硬件、跨版本的永久承诺。
要记录完整实验配置：
```text
model revision
tokenizer revision
vLLM version
GPU / dtype / quantization
chat template hash
sampling params
seed
prompt bytes
```
### 9.3 停止条件
`max_tokens`、EOS、Stop String 和最小生成长度也属于解码策略。
Stop String 可能跨 Token 边界；截断时是否保留 Stop 文本、是否忽略 EOS 等行为会影响客户端拼接。流式接口尤其要回归测试。
### 9.4 线上防滥用
为请求建立“解码预算”：
$$ \text{budget} \approx \text{num prompts} \times \text{candidate count} \times \text{max output tokens} $$
这不是精确 FLOPs，但适合网关限流。一个 `n=8, max_tokens=4096` 的请求不应与 `n=1, max_tokens=64` 计为相同配额。

## 10. 场景化选型
### 10.1 事实问答
```text
temperature: 0–0.3; top_p: 0.9–1.0; n: 1
```
低随机性有助于稳定，但事实正确性主要靠检索、工具和验证，不靠把 Temperature 调到 0。
### 10.2 创意写作
起点建议：
```text
temperature: 0.7–1.0; top_p: 0.9–0.98; n: 1–4
```
再用规则或模型重排候选。不要同时把 Temperature、Top-k、Top-p 都压得很低。
### 10.3 分类
优先使用结构化 Choice 或限制标签 Token，再请求少量目标 Token 的 Logprobs。
这通常比生成自然语言解释后做字符串匹配更可靠。
📌 **实践原则**：先定义可测质量指标和延迟预算，再搜索参数。没有指标的“感觉更自然”很容易被少量样例误导。

## 📝 总结
- 模型输出 Logits，采样器把词表分数转成下一个 Token。
- Temperature 改变分布尖锐程度；Top-k 固定候选数；Top-p 按累计概率动态选候选。
- 强结构约束会先缩小合法集合，使采样参数的作用变弱。
- vLLM 可能继承模型 `generation_config.json`，生产配置应显式记录关键默认值。
- Logprobs 描述 Token 偏好，不是天然校准的业务置信度；全词表返回成本很高。
- `n`、`best_of` 和 Beam Width 会放大活跃序列、KV Cache、计算与尾延迟。
- Beam Search 优化累计序列得分，不保证开放式生成质量更高。
