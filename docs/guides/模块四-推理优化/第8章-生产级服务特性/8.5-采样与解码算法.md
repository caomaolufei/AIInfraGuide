模型一次前向不会直接吐出“下一个词”，而是给词表中每个 Token 一个分数。采样器决定如何把这几万个分数变成一个选择。
Temperature、Top-k、Top-p 看起来只是三个 API 参数，实际共同定义了“候选池有多大、概率有多尖、随机性有多强”。而 `n`、Beam Search 和 Logprobs 还会改变序列数量、KV Cache 与返回体积。
调参不是找一组万能数字，而是为任务选择合适的搜索策略。
<!-- more -->

## 1. 从 Logits 到概率
模型最后一层为词表中每个 Token 输出 Logit $z_i$。Softmax 将其转换为概率：
$$ p_i = \frac{e^{z_i}}{\sum_j e^{z_j}} $$
采样器随后从分布 $p$ 中选一个 Token，追加到序列，再做下一步前向。
例如：
| Token | Logit | Softmax 概率（示意） |
|---|---:|---:|
| 北京 | 4.0 | 0.62 |
| 上海 | 3.2 | 0.28 |
| 杭州 | 2.1 | 0.09 |
| 香蕉 | -1.0 | 0.01 |
Greedy 每次选概率最大的“北京”；随机采样会偶尔选“上海”或“杭州”。
类比餐厅点菜：模型先给每道菜打分，采样器决定是永远点最高分，还是从高分菜单里按概率抽签。Temperature 改评分差距，Top-k 限制菜单项数，Top-p 限制菜单覆盖的总可信度。
---

## 2. Temperature
Temperature 在 Softmax 前缩放 Logits：
$$ p_i(T) = \frac{e^{z_i/T}} {\sum_j e^{z_j/T}} $$
### 2.1 T 小于 1
分布变尖，高分 Token 更占优势：
- 输出更稳定；
- 创造性下降；
- 重复高概率模式的风险可能增加。
### 2.2 T 大于 1
分布变平，低概率 Token 更有机会：
- 多样性增加；
- 事实和格式错误风险上升；
- 极高值可能产生无意义输出。
### 2.3 T 等于 0
在 vLLM 的 `SamplingParams` 语义中，`temperature=0` 表示 Greedy Sampling，即选择最高概率 Token。
这不是数学上直接把 $T=0$ 代入公式，而是实现层的特殊分支。
### 2.4 低 Temperature 不等于绝对可复现
即使 Greedy，也可能受到：
- 浮点精度；
- 不同 GPU 与 Kernel；
- 并行归约顺序；
- 模型 Revision；
- Chat Template；
- 调度与实现变化。
需要强回归时，应比较任务结果和结构，不要假设跨版本逐 Token 完全相同。
📌 **关键点**：Temperature 改的是候选之间的相对概率，不会主动删除候选。

## 3. Top-k 与 Top-p
### 3.1 Top-k
Top-k 只保留概率最高的 $k$ 个 Token，其余置零后重新归一化。
若 `top_k=2`，上表只留下“北京”和“上海”。
优点：
- 候选数量稳定；
- 易理解；
- 能排除长尾噪声。
缺点：
- 不看分布形状；
- 模型很确定时，仍保留固定数量；
- 模型不确定时，可能过早砍掉合理候选。
当前 vLLM `SamplingParams` 中，`top_k=0` 或 `-1` 表示考虑所有 Token；在线 OpenAI 兼容接口里 `top_k` 是 vLLM 扩展，通常通过 `extra_body` 传入。
### 3.2 Top-p
Top-p，也称 Nucleus Sampling，按概率从高到低累加，保留累计概率达到阈值 $p$ 的最小集合。
例如 `top_p=0.9`：
```text
北京 0.62  累计 0.62
上海 0.28  累计 0.90  ← 到此停止
```
候选集大小随模型置信度动态变化：
- 分布很尖时，可能只保留 1 个；
- 分布很平时，可能保留很多个。
### 3.3 两者的直觉区别
- Top-k 问：“最多看前几名？”
- Top-p 问：“看多少候选才能覆盖足够概率？”
Top-k 是固定席位，Top-p 是按总票数划线。

## 4. 小词表手算：每一步都算出来

设词表只有五个 Token：`A、B、C、D、EOS`，原始 Logits 分别为：

| Token | A | B | C | D | EOS |
|---|---:|---:|---:|---:|---:|
| Logit | 2.0 | 1.0 | 0.5 | 0.0 | -1.0 |

### 4.1 原始 Softmax

为避免溢出，实际计算会减最大值 $m=2$：

$$
p_i=\frac{e^{z_i-m}}{\sum_j e^{z_j-m}}
$$

```text
A: exp( 0.0) = 1.0000 -> 0.5630
B: exp(-1.0) = 0.3679 -> 0.2071
C: exp(-1.5) = 0.2231 -> 0.1256
D: exp(-2.0) = 0.1353 -> 0.0762
E: exp(-3.0) = 0.0498 -> 0.0280
sum             1.7761
```

Greedy 选 A；随机采样有约 2.8% 概率提前选 EOS。

### 4.2 Temperature = 0.5

Logits 除以 0.5，相对差距翻倍：

```text
A exp( 0) = 1.0000 -> 0.8293
B exp(-2) = 0.1353 -> 0.1122
C exp(-3) = 0.0498 -> 0.0413
D exp(-4) = 0.0183 -> 0.0152
E exp(-6) = 0.0025 -> 0.0021
```

Temperature 没删除 EOS，只把它从 2.8% 压到约 0.2%。

### 4.3 Temperature = 2.0

相对差距减半：

```text
A exp( 0.00) = 1.0000 -> 0.3745
B exp(-0.50) = 0.6065 -> 0.2272
C exp(-0.75) = 0.4724 -> 0.1769
D exp(-1.00) = 0.3679 -> 0.1378
E exp(-1.50) = 0.2231 -> 0.0836
```

高 Temperature 显著提高长尾和 EOS 概率。

### 4.4 Top-k = 2

保留 A、B 后重新归一化：

$$
p'(A)=\frac{0.5630}{0.5630+0.2071}=0.7311,\quad
p'(B)=0.2689
$$

C、D、EOS 概率严格为 0。

### 4.5 Top-p = 0.8

```text
A 0.5630 cumulative 0.5630
B 0.2071 cumulative 0.7701
C 0.1256 cumulative 0.8957  <- 首次达到 0.8
```

保留 A、B、C，再归一化为 `0.6285、0.2312、0.1402`。实现通常保留使累计值首次达到或超过阈值的 Token，否则 A+B 的累计概率还不到 0.8。

### 4.6 三者组合

若先用 $T=0.5$，再 `top_k=3`，A/B/C 归一化约为：

```text
A 0.8438, B 0.1142, C 0.0420
```

再用 `top_p=0.9`，A 的累计值不够，加入 B 后为 0.958，最终只剩 A/B。参数顺序影响中间分布，解释框架结果时必须核对实现。

## 5. Penalty：三种不同的 Logit 变换

### 5.1 Presence 与 Frequency

常见定义：

$$
z'_i=z_i-\lambda_p\mathbf{1}[c_i>0]-\lambda_f c_i
$$

$c_i$ 是 Token 已出现次数。Presence 只看是否出现；Frequency 随次数增长。

若 A 出现 2 次、B 出现 1 次，`presence_penalty=0.3`、`frequency_penalty=0.2`：

```text
A: 2.0 - 0.3 - 2*0.2 = 1.3
B: 1.0 - 0.3 - 1*0.2 = 0.5
C: 0.5
D: 0.0
E:-1.0
```

B 与 C 现在并列。

### 5.2 Repetition Penalty

常见 repetition penalty 使用乘除式：

$$
z'_i=
\begin{cases}
z_i/r,&z_i>0\land c_i>0\\
z_i\cdot r,&z_i\le0\land c_i>0\\
z_i,&c_i=0
\end{cases}
$$

$r>1$ 时降低已出现 Token。负 Logit 不能简单除以 $r$，否则它会更接近 0，概率反而提高。

不同实现对 Prompt 是否计数、特殊 Token 是否排除、上下文窗口取多长可能不同，必须核对目标版本。

### 5.3 Tokenization 陷阱

“苹果”和带前导空格的“ 苹果”可能是不同 Token，一个词也可能拆成多个 Token。Token 级惩罚不等于词级去重。过强 Penalty 可能：

- 破坏代码变量复用；
- 阻止 JSON 合法重复值；
- 让专有名词变成错误近义词；
- 在长文本后期迫使模型选长尾。

## 6. 参数组合与顺序
实际采样链路还可能包含：
- repetition/frequency/presence penalty；
- allowed/bad words；
- structured output mask；
- Temperature；
- Top-k、Top-p、Min-p；
- 最终 multinomial sampling。
具体处理顺序属于实现细节，应以锁定 vLLM 版本源码和文档为准；但理解上可记为：
```text
原始 Logits
  → 规则与惩罚
  → 结构化输出合法集合
  → Temperature 缩放
  → Top-k / Top-p 截断
  → 归一化并采样
```
### 6.1 同时设置 Top-k 与 Top-p
两者通常取交集效果：先缩小一遍，再按另一个规则继续缩小。参数都很激进时，候选可能接近 Greedy。
例如：
```text
temperature=0.2, top_k=5, top_p=0.5
```
三个参数都在压低多样性。若输出过于僵硬，不要只改单个参数而忽略组合。
### 6.2 与结构化输出组合
结构化输出先把不合法 Token 排除，采样参数只在合法集合中选择。
若语法状态只允许 `}`，无论 Temperature 多高都必须生成 `}`。这解释了为何强约束下调 Temperature 可能几乎无效果。
---

### 6.3 空候选与数值稳定

采样器通常使用 log-sum-exp 避免指数溢出。Mask 后若所有 Token 都是 `-inf`，Softmax 分母为 0，会产生 NaN 或明确错误。

结构化输出、bad words、min tokens 和 stop 组合时可能造成空候选。引擎应返回可诊断失败，不能任意解除一条安全约束继续生成。

## 7. 从零实现一个可核对采样器

下面代码用于教学和小词表验证，不替代 vLLM 的 GPU Sampler：

```python
import math
import random


def softmax(logits):
    finite = [x for x in logits if math.isfinite(x)]
    if not finite:
        raise ValueError("all tokens are masked")
    maximum = max(finite)
    weights = [
        math.exp(x - maximum) if math.isfinite(x) else 0.0
        for x in logits
    ]
    total = sum(weights)
    return [x / total for x in weights]


def apply_penalties(
    logits, counts, presence=0.0, frequency=0.0, repetition=1.0
):
    result = list(logits)
    for token_id, count in counts.items():
        if count == 0:
            continue
        value = result[token_id]
        if repetition != 1.0:
            value = value / repetition if value > 0 else value * repetition
        result[token_id] = value - presence - frequency * count
    return result


def truncate(probs, top_k=None, top_p=1.0):
    order = sorted(
        range(len(probs)), key=probs.__getitem__, reverse=True
    )
    if top_k is not None and top_k > 0:
        order = order[:top_k]

    top_k_total = sum(probs[i] for i in order)
    normalized = {
        token_id: probs[token_id] / top_k_total for token_id in order
    }
    kept, cumulative = [], 0.0
    for token_id in order:
        kept.append(token_id)
        cumulative += normalized[token_id]
        if cumulative >= top_p:
            break

    total = sum(normalized[i] for i in kept)
    result = [0.0] * len(probs)
    for token_id in kept:
        result[token_id] = normalized[token_id] / total
    return result


def sample(
    logits,
    counts,
    *,
    temperature=1.0,
    top_k=None,
    top_p=1.0,
    allowed_token_ids=None,
    seed=42,
):
    work = apply_penalties(logits, counts)
    if allowed_token_ids is not None:
        allowed = set(allowed_token_ids)
        work = [
            value if i in allowed else -math.inf
            for i, value in enumerate(work)
        ]
    if temperature == 0:
        return max(range(len(work)), key=work.__getitem__)
    if temperature < 0:
        raise ValueError("temperature must be non-negative")

    probs = softmax([x / temperature for x in work])
    probs = truncate(probs, top_k=top_k, top_p=top_p)
    rng = random.Random(seed)
    return rng.choices(range(len(probs)), weights=probs, k=1)[0]
```

核对：

```python
logits = [2.0, 1.0, 0.5, 0.0, -1.0]
assert sample(logits, {}, temperature=0) == 0
assert sample(
    logits, {}, temperature=0, allowed_token_ids={2, 3}
) == 2

for seed in range(10_000):
    token = sample(
        logits, {}, temperature=1.0, top_k=2, seed=seed
    )
    assert token in {0, 1}
```

运行 100,000 个不同 seed，A/B 经验频率应接近手算的 0.731/0.269。每次重置成同一 seed 得到的是重复实验，不是独立样本。

## 8. vLLM SamplingParams 与在线 API
### 8.1 离线推理
```python
from vllm import LLM, SamplingParams
llm = LLM(
    model="Qwen/Qwen3-8B",
    generation_config="vllm",
)
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    top_k=50,
    max_tokens=256,
    seed=42,
)
outputs = llm.generate(
    ["用三个要点解释 PagedAttention"],
    params,
)
```
### 8.2 generation_config 的影响
vLLM 可能读取模型仓库的 `generation_config.json` 作为默认采样参数。于是两个模型即使请求里都没写 Temperature，实际默认也可能不同。
若希望使用 vLLM 默认值，可以在初始化时显式设置：
```python
LLM(model=model_id, generation_config="vllm")
```
生产中更建议在请求或服务配置中显式声明关键参数，避免模型 Revision 更新悄悄改变默认行为。
### 8.3 OpenAI 兼容接口
```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "写一句产品标语"}],
    temperature=0.8,
    top_p=0.95,
    max_tokens=64,
    extra_body={"top_k": 50},
)
```
`temperature`、`top_p` 属于常见 OpenAI 字段；`top_k` 是 vLLM 扩展。扩展字段和允许范围应以当前 OpenAI-Compatible Server 文档为准。

### 8.4 显式记录实际参数

网关应记录解析后的实际值，而不只是“请求没传”：

```json
{"temperature":0.7,"top_p":0.9,"top_k":50,"presence_penalty":0.0,"frequency_penalty":0.0,"repetition_penalty":1.0,"seed":42,"max_tokens":256,"generation_config_source":"request"}
```

模型仓库默认配置变化时，这个快照能解释相同请求为何行为改变。

## 9. Logprobs 的正确理解
Logprob 是概率的自然对数：
$$ \log p_i \le 0 $$
越接近 0，概率越高。例如：
```text
logprob = -0.1  → p ≈ 0.905
logprob = -2.3  → p ≈ 0.100
logprob = -6.9  → p ≈ 0.001
```
### 9.1 输出 Token Logprobs
`SamplingParams(logprobs=k)` 请求每个生成位置返回若干高概率 Token，并总是包含实际选中的 Token。因此结果数量可能达到 `k+1`。
`logprobs=-1` 可表示返回全词表，但成本很高：
- GPU/CPU 数据搬运；
- 序列化；
- 网络响应体；
- 客户端内存。
在线服务不应默认开放无限制全词表 Logprobs。
### 9.2 Prompt Logprobs
`prompt_logprobs` 返回 Prompt 各位置 Token 的概率信息，可用于：
- 计算文本似然；
- 比较候选答案；
- 调试 Tokenization。
它不是“模型对整段 Prompt 的置信度”。长度不同的文本直接相加会偏向短文本，常需做长度归一化。
### 9.3 Chat API 字段
OpenAI 风格 Chat 请求通常使用：
```python
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "天空通常是什么颜色？"}],
    logprobs=True,
    top_logprobs=5,
)
```
vLLM 还可能提供 `prompt_logprobs`、`logprob_token_ids` 等扩展。后者适合只关心少数标签 Token 的评分任务，比索取全词表更经济。
### 9.4 Logprobs 不是校准概率
模型给“正确”很高概率，不代表现实中 90% 正确。语言模型概率首先描述 Token 在上下文中的相对偏好。
若用于风险决策，需要在目标数据上做：
- Calibration；
- 阈值评估；
- 类别 Token 设计；
- 分布漂移监控。

### 9.5 序列得分手算

若三个输出 Token 概率为 `[0.8, 0.5, 0.25]`：

$$
\log P=\log0.8+\log0.5+\log0.25
\approx-0.223-0.693-1.386=-2.302
$$

联合概率约 $0.1$，平均 Token Logprob 为 $-0.767$，困惑度：

$$
\operatorname{PPL}=e^{0.767}\approx2.15
$$

联合 Logprob 偏爱短序列；平均值或长度惩罚改变了目标，又可能偏爱冗长文本。评分公式要在业务验证集上选择。

### 9.6 返回的是哪一个分布

Logprobs 对应原始模型分布、Penalty 后分布，还是 Top-k/Top-p 截断后的分布，属于 API/实现语义。用于审计前应在目标版本构造可控 Logits 实验验证，不能想当然。

## 10. 并行采样 n 与 best_of
### 10.1 n
`n` 表示每个 Prompt 返回多少条输出。多样化生成、候选重排和自洽投票常用它。
```python
params = SamplingParams(
    n=4,
    temperature=0.8,
    top_p=0.95,
    max_tokens=128,
)
```
四条序列共享 Prompt Prefill 的机会，但 Decode 后会分叉，各自需要 KV 状态和计算。
粗略理解：
$$ M_{\text{decode KV}} \propto n \times L_{\text{generated}} $$
所以 `n=4` 绝不是“只多返回三段字符串”，它可能显著放大 Decode 显存和时延。
### 10.2 best_of
`best_of` 表示内部生成更多候选，再返回其中较优的一部分。它可以提高结果质量，却把未返回候选的计算完全留在服务端。
客户端看到一条结果，不代表服务端只解码了一条序列。

⚠️ **版本边界**：`best_of` 属于旧 V0 路径，在当前 vLLM V1 中已弃用/不支持，不能把它当成通用在线能力。V1 场景可根据目标使用 `n` 返回候选、独立 Beam Search，或在应用侧执行评分与重排，并重新核算 KV Cache 和算力预算。
### 10.3 V1 的 best_of 边界

明确区分：

```text
n=4
  -> 生成并返回 4 个候选

V0 best_of=4, n=1
  -> 内部生成 4 个，按服务端得分返回 1 个

应用侧 rerank
  -> 引擎返回候选，业务按独立指标选 1 个
```

当前 vLLM V1 不支持旧 `best_of` 语义。迁移时把 `best_of=4,n=1` 直接改成 `n=4`，会改变响应体、网络成本、客户端行为和隐私面，而且缺少原选择规则。必须明确重排发生在哪里。

### 10.4 调度影响
大量并行候选会：
- 增加活跃序列数；
- 占用更多 KV Block；
- 降低其他请求可用并发；
- 放大尾延迟；
- 增加取消和超时后的浪费。
若仍维护 V0，生产网关应限制每请求 `n`、`best_of` 与 `max_tokens` 的组合预算；V1 则限制实际使用的 `n`、Beam 或应用侧候选数量。

## 11. Beam Search
Beam Search 每一步保留累计得分最高的 $B$ 条部分序列，而不是独立随机抽样。
### 11.1 基本过程
若 Beam Width 为 3：
1. 从起点扩展多个 Token；
2. 保留累计得分最高的 3 条；
3. 每条再次扩展；
4. 在所有新候选中继续保留 3 条；
5. 直到结束条件。
它像同时沿三条最有希望的路线搜索，每个路口都淘汰落后的路线。
### 11.2 两步小词表手算

设 Beam width $B=2$。第一步：

```text
P(A)=0.6, P(B)=0.3, P(EOS)=0.1
log scores: A=-0.511, B=-1.204, EOS=-2.303
```

保留 A、B。第二步条件概率：

```text
after A: P(EOS)=0.5, P(A)=0.3, P(B)=0.2
after B: P(EOS)=0.8, P(A)=0.1, P(B)=0.1
```

累计得分：

```text
A EOS: log(0.6)+log(0.5) = -1.204
A A:   log(0.6)+log(0.3) = -1.715
A B:   log(0.6)+log(0.2) = -2.120
B EOS: log(0.3)+log(0.8) = -1.427
B A:   log(0.3)+log(0.1) = -3.507
B B:   log(0.3)+log(0.1) = -3.507
```

全局前二是 `A EOS` 和 `B EOS`。不能让每条旧 Beam 各自保留固定数量，否则可能错过多个都来自同一父节点的最佳候选。

### 11.3 长度偏置
直接累加 Logprob 往往偏爱短序列，因为每增加一个 Token 都加上非正数。Beam Search 常配合 Length Penalty：
```text
score = cumulative_logprob / length_penalty_term
```
具体公式和参数语义需以实现为准。
### 11.4 vLLM 离线接口
当前官方生成模型文档展示独立的 `BeamSearchParams` 与 `LLM.beam_search`：
```python
from vllm import LLM
from vllm.sampling_params import BeamSearchParams
llm = LLM(model="facebook/opt-125m")
params = BeamSearchParams(
    beam_width=5,
    max_tokens=50,
)
outputs = llm.beam_search(
    [{"prompt": "Hello, my name is "}],
    params,
)
```
OpenAI 兼容协议不是以 Beam Search 为核心设计。vLLM 的在线扩展曾提供或当前可能提供 `use_beam_search` 等字段，使用前必须检查目标版本接口，优先依赖当前官方示例。
### 11.5 Beam Search 不总比采样好
它常用于：
- 机器翻译；
- 语音识别；
- 有明确序列似然目标的任务。
开放式对话中，Beam Search 可能：
- 输出更保守、同质；
- 增加计算与 KV Cache；
- 牺牲流式首选结果的直观性；
- 未必提高事实正确率。
Beam Width 也不是越大越好。搜索目标若与业务质量不一致，更努力优化 Logprob 只会更确定地得到错误目标。

### 11.6 系统成本

Beam 共享 Prompt Prefill，但每个分支保留后续 KV、累计分数、完成状态和父指针：

$$
M_{\text{beam KV}}\propto B\times L_{\text{generated}}
$$

每一步还要从约 $B\times|V|$ 候选中选全局 Top-$B$。高性能实现不做完整排序，但 Top-k Kernel、分支重排和 KV Block 管理仍有成本。

## 12. 可复现实验：参数扫描而非凭感觉

### 12.1 固定环境

```bash
python -m venv .venv
source .venv/bin/activate
pip install -U vllm openai
python -c 'import vllm; print(vllm.__version__)'
vllm serve Qwen/Qwen3-8B
```

锁定模型/Tokenizer Revision、服务参数、GPU、dtype 和 Chat Template Hash。

### 12.2 扫描脚本

```python
import hashlib
import itertools
import json
import time
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")
prompts = [
    "用一句话解释 PagedAttention。",
    "为推理平台写一句不超过20字的标语。",
    "把状态分类为 healthy、degraded 或 down：错误率35%。",
]
grid = [
    (0.0, 1.0, 0, 0.0),
    *itertools.product(
        [0.3, 0.8],
        [0.8, 0.95, 1.0],
        [0, 20, 50],
        [0.0, 0.5],
    ),
]

records = []
for temperature, top_p, top_k, frequency_penalty in grid:
    for prompt in prompts:
        for seed in range(10):
            start = time.perf_counter()
            response = client.chat.completions.create(
                model="Qwen/Qwen3-8B",
                messages=[{"role": "user", "content": prompt}],
                temperature=temperature,
                top_p=top_p,
                frequency_penalty=frequency_penalty,
                max_tokens=96,
                seed=seed,
                extra_body={"top_k": top_k},
            )
            records.append({
                "prompt_sha": hashlib.sha256(prompt.encode()).hexdigest(),
                "temperature": temperature,
                "top_p": top_p,
                "top_k": top_k,
                "frequency_penalty": frequency_penalty,
                "seed": seed,
                "elapsed_ms": (time.perf_counter() - start) * 1000,
                "completion_tokens": response.usage.completion_tokens,
                "finish_reason": response.choices[0].finish_reason,
                "text": response.choices[0].message.content,
            })

with open("sampling-results.jsonl", "w") as f:
    for row in records:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
```

### 12.3 质量与系统指标

不同任务使用不同指标：

- 分类：exact match、混淆矩阵、校准误差；
- 结构化：Schema 与业务校验通过率；
- 摘要：事实一致性、覆盖率、长度；
- 创意：Distinct-n、自重复率、人工偏好；
- 代码：测试通过率。

系统侧记录：

```text
sampling_seconds{strategy}
request_ttft_seconds{profile}
request_tpot_seconds{profile}
active_sequences{n_or_beam}
kv_cache_blocks_used
logprobs_response_bytes
finish_reason_total
cancelled_wasted_tokens
```

Temperature/Top-p 的微小采样开销常被模型 Decode 掩盖；`n`、Beam 和 Logprobs 则可能显著改变资源，报告要分开。

### 12.4 经验分布回归

对固定 Prompt 和固定 Logit 位置采样大量 seed，比较目标 Token 频率。可使用极小测试模型或自定义 Logits Processor 构造可控分布。

升级回归不要求每个 seed 永久逐字一致，而应确保参数错误语义、Greedy 任务正确率、分布统计、P99、KV、停止条件和 Logprobs 结构都在预算内。

## 13. 生产失败模式与版本边界

### 13.1 参数冲突造成近似 Greedy

低 Temperature、低 top-p 和小 top-k 叠加后只剩一个候选。记录实际组合，避免只看到 `temperature=0.8` 就误判有多样性。

### 13.2 Penalty 破坏协议

工具参数、代码和 JSON 经常合法重复 Token。结构化任务应降低通用重复惩罚，由 Schema 控制格式。

### 13.3 Logprobs 放大响应

长输出乘以 `top_logprobs` 会放大搬运和 JSON。网关按：

$$
\text{max output tokens}\times\text{top logprobs}
$$

设预算；全词表 Logprobs 只开放给受控离线任务。

### 13.4 候选爆炸

`n=8,max_tokens=4096` 或大 Beam 会占满活跃序列。按候选 Token 预算限流，而不是只按请求数。

### 13.5 Stop 跨 Token

Stop String 可能横跨 Token，流式服务需暂存可能构成 stop 的后缀，否则客户端会先看到随后应删除的文本。

### 13.6 版本边界

部署时逐项核对：

- vLLM V1 的 `best_of` 不支持边界；
- `top_k`、`repetition_penalty` 等扩展字段；
- Beam Search 独立 API 与 OpenAI 在线接口差异；
- `logprobs=-1`、`prompt_logprobs`、目标 Token ID 扩展；
- generation config 默认继承；
- Penalty 公式及 Prompt 是否计数；
- Sampler 处理顺序；
- Stop、EOS、min tokens 与 finish reason；
- Seed 支持与确定性范围。

公式描述常见算法，不保证每个 API 都采用完全相同定义。

## 14. 质量、性能与可复现性
### 14.1 性能成本地图
| 参数 | 主要质量影响 | 主要系统成本 |
|---|---|---|
| Temperature | 随机性 | 通常较小 |
| Top-k/Top-p | 候选多样性 | 采样器开销，通常较小 |
| Logprobs | 可观测候选概率 | 搬运、序列化、网络 |
| n | 多候选 | Decode 计算与 KV 近似放大 |
| best_of | 服务端搜索质量 | 隐藏候选计算 |
| Beam Width | 高似然序列搜索 | 分支、排序、KV 与延迟 |
### 14.2 Seed
Seed 有助于同环境复现实验，但不是跨硬件、跨版本的永久承诺。
要记录完整实验配置：
```text
model revision
tokenizer revision
vLLM version
GPU / dtype / quantization
chat template hash
sampling params
seed
prompt bytes
```
### 14.3 停止条件
`max_tokens`、EOS、Stop String 和最小生成长度也属于解码策略。
Stop String 可能跨 Token 边界；截断时是否保留 Stop 文本、是否忽略 EOS 等行为会影响客户端拼接。流式接口尤其要回归测试。
### 14.4 线上防滥用
为请求建立“解码预算”：
$$ \text{budget} \approx \text{num prompts} \times \text{candidate count} \times \text{max output tokens} $$
这不是精确 FLOPs，但适合网关限流。一个 `n=8, max_tokens=4096` 的请求不应与 `n=1, max_tokens=64` 计为相同配额。

## 15. 场景化选型
### 15.1 事实问答
```text
temperature: 0–0.3; top_p: 0.9–1.0; n: 1
```
低随机性有助于稳定，但事实正确性主要靠检索、工具和验证，不靠把 Temperature 调到 0。
### 15.2 创意写作
起点建议：
```text
temperature: 0.7–1.0; top_p: 0.9–0.98; n: 1–4
```
再用规则或模型重排候选。不要同时把 Temperature、Top-k、Top-p 都压得很低。
### 15.3 分类
优先使用结构化 Choice 或限制标签 Token，再请求少量目标 Token 的 Logprobs。
这通常比生成自然语言解释后做字符串匹配更可靠。
📌 **实践原则**：先定义可测质量指标和延迟预算，再搜索参数。没有指标的“感觉更自然”很容易被少量样例误导。

## 📝 总结
- 模型输出 Logits，采样器把词表分数转成下一个 Token。
- Temperature 改变分布尖锐程度；Top-k 固定候选数；Top-p 按累计概率动态选候选。
- 强结构约束会先缩小合法集合，使采样参数的作用变弱。
- vLLM 可能继承模型 `generation_config.json`，生产配置应显式记录关键默认值。
- Logprobs 描述 Token 偏好，不是天然校准的业务置信度；全词表返回成本很高。
- `n`、`best_of` 和 Beam Width 会放大活跃序列、KV Cache、计算与尾延迟。
- Beam Search 优化累计序列得分，不保证开放式生成质量更高。
