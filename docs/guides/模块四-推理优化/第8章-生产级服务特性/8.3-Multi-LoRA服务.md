一家平台有 50 个业务租户，每个租户都基于同一个 8B 底座训练了 LoRA。最直观的部署方式是拉起 50 份模型服务，但底座权重也会复制 50 份，GPU 很快被吃光。
Multi-LoRA 的目标，是让所有租户共享那份昂贵的底座权重，只为每个租户保存较小的低秩增量，并在请求到来时选择对应 Adapter。
听起来像“免费多租户”，实际却把问题从底座显存转移到了 Adapter 槽位、搬运、调度和隔离。
<!-- more -->

## 1. 从 LoRA 公式看服务机制
对线性层权重 $W \in \mathbb{R}^{d_{out}\times d_{in}}$，LoRA 不直接保存完整的新权重，而是学习低秩增量：
$$ y = Wx + \frac{\alpha}{r}BAx $$
其中：
- $A \in \mathbb{R}^{r\times d_{in}}$；
- $B \in \mathbb{R}^{d_{out}\times r}$；
- $r$ 是远小于原始维度的 rank；
- $W$ 对所有租户共享；
- 每个 Adapter 有自己的 $A$、$B$。
若为每个租户单独合并权重：
$$ W_i = W + \Delta W_i $$
就需要多份接近完整模型大小的权重。Multi-LoRA 保留共享 $W$，在执行层里按请求选择不同的低秩矩阵。
类比一下：底座模型像一台昂贵的数控机床，LoRA 是可更换刀头。为每种零件买一台机床太浪费；共享机床、切换刀头更经济。但刀头架容量、换刀时间和同时加工不同零件的调度仍然要付成本。
📌 **关键点**：Multi-LoRA 节省的是**底座副本**，不是让 Adapter 的存储、加载和计算变成零成本。
---

## 2. Multi-LoRA 的执行路径
一个请求携带 Adapter 名称后，大致经历：
1. API 层把 `model` 名称解析为底座或 LoRA；
2. Adapter 管理器检查它是否已注册；
3. 若不在 GPU 活跃槽位，可能从 CPU 缓存或存储加载；
4. 调度器把请求与对应 LoRA ID 组批；
5. LoRA Kernel 按请求 ID 选择 $A_i$、$B_i$；
6. 基础线性结果与低秩增量相加；
7. 请求结束后，Adapter 可继续留在缓存等待复用。
### 2.1 同一批如何使用不同 Adapter
设批次中四个请求分别使用：
```text
request:  A  B  C  D
adapter:  2  2  7  0
```
其中 `0` 可表示底座。Kernel 需要根据每个 Token 或序列对应的 LoRA ID，路由到正确矩阵。
这比整批只用同一个 Adapter 更复杂：
- 索引和元数据增加；
- 不同 Adapter 数量影响 Kernel 形态；
- GPU 上必须有足够活跃槽位；
- Adapter 分布会影响组批效率。
### 2.2 额外计算量
LoRA 增量包含两次低秩矩阵乘：
$$ x \rightarrow Ax \rightarrow B(Ax) $$
rank 越大、挂载层越多，额外计算越多。与完整模型相比通常仍较小，但在 Decode 的小 Batch、低延迟场景中，Kernel 调度和内存访问也可能明显。

## 3. vLLM 启动与请求
### 3.1 启动时注册 Adapter
当前官方示例使用 `--enable-lora` 与 `--lora-modules`：
```bash
vllm serve meta-llama/Llama-3.2-3B-Instruct \
  --enable-lora \
  --max-loras 4 \
  --max-lora-rank 64 \
  --max-cpu-loras 16 \
  --lora-modules sql=/models/lora/sql support=/models/lora/support
```
启动后查询模型列表：
```bash
curl http://localhost:8000/v1/models
```
通常会看到底座和已注册 Adapter。请求时把 Adapter 名称作为 `model`：
```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
response = client.chat.completions.create(
    model="sql",
    messages=[
        {"role": "user", "content": "查询最近 7 天新增用户数"}
    ],
)
```
### 3.2 离线 LoRARequest
离线推理可使用 `LoRARequest` 指定名称、内部 ID 和路径。其具体构造签名属于代码 API，版本演进比 HTTP 协议快，使用时应查看对应版本 API 文档。
### 3.3 Adapter 兼容前提
加载前至少验证：
- `base_model_name_or_path` 与底座匹配；
- `peft_type` 是目标 LoRA 类型；
- rank 不超过服务配置；
- `target_modules` 是模型支持的层；
- Tokenizer 和额外词表是否匹配；
- Adapter 文件来自可信来源。
名称相同不代表权重兼容，路径可读也不代表能安全加载。

## 4. 三个核心容量参数
### 4.1 max_loras
`max_loras` 控制一个 Batch 中可同时活跃的 LoRA 数量，也影响预分配槽位。
它不是“平台注册 Adapter 总数”。平台注册 100 个 Adapter，不代表同一步必须把 100 个都放在 GPU 上。
调大后：
- 异构租户更容易同批执行；
- GPU LoRA 槽位显存增加；
- Kernel 和图捕获策略可能更复杂。
调小后：
- 显存更省；
- 热点集中时效率高；
- 多 Adapter 混合负载可能排队或频繁切换。
### 4.2 max_lora_rank
`max_lora_rank` 是服务允许的最大 rank。官方建议设置为计划加载 Adapter 的实际最大值。
如果 rank 集合是 `[8, 16, 64]`，配置 64 比盲目配置 256 更合理，因为槽位通常要按上界预留。
⚠️ 该参数允许值、默认值与内核限制可能随版本变化，应查看当前 `vllm serve --help`。
### 4.3 max_cpu_loras
`max_cpu_loras` 控制 CPU 内存缓存可保留的 LoRA 数量，要求通常不小于 `max_loras`。
它像机床旁的刀头柜：
- GPU 槽位是机器当前可快速使用的刀头；
- CPU Cache 是旁边的刀头柜；
- 远端对象存储是仓库。
从 CPU 搬到 GPU 比从对象存储下载快，但仍有 PCIe 传输和同步成本。

## 5. 显存怎样增长
单个线性层 LoRA 参数量近似：
$$ N_{\text{LoRA}} = r(d_{in}+d_{out}) $$
若数据类型每元素 $b$ 字节，挂载多个层后：
$$ M_{\text{adapter}} \approx b \cdot r \sum_{l\in \mathcal{L}}(d_{in,l}+d_{out,l}) $$
GPU 侧预分配还可能按最大 rank 和槽位数放大：
$$ M_{\text{slots}} \propto \text{max\_loras} \times \text{max\_lora\_rank} \times \text{target dimensions} $$
这是容量规划中最容易忽略的一点：实际 Adapter rank 是 8，不代表配置上限 256 没有成本。
### 5.1 还有哪些显存
总显存不只 LoRA：
$$ M_{\text{total}} = M_{\text{base}} + M_{\text{KV}} + M_{\text{LoRA slots}} + M_{\text{CUDA graph}} + M_{\text{workspace}} + M_{\text{activations}} $$
提高 `max_loras` 或 `max_lora_rank` 后，可用于 KV Cache 的空间可能减少，最终表现为并发下降，而不只是“LoRA 多占了一点显存”。
### 5.2 不要只按文件大小估算
Adapter 磁盘文件可能压缩、分片或使用不同 dtype。GPU 上还涉及：
- 对齐与 Padding；
- 最大 rank 槽位；
- Layer Mapping 元数据；
- Kernel Workspace；
- CUDA Graph 专门化副本。
正确方法是在目标 GPU、目标 vLLM 版本和目标模型上测启动后显存，再逐步增加槽位。

## 6. 动态加载与卸载
vLLM 支持运行时 LoRA 更新端点。按当前官方说明，需要显式允许：
```bash
export VLLM_ALLOW_RUNTIME_LORA_UPDATING=True
vllm serve meta-llama/Llama-3.2-3B-Instruct \
  --enable-lora \
  --max-loras 2 \
  --max-lora-rank 64
```
加载示例：
```bash
curl -X POST http://localhost:8000/v1/load_lora_adapter \
  -H "Content-Type: application/json" \
  -d '{
    "lora_name": "tenant-a-v3",
    "lora_path": "/models/lora/tenant-a-v3"
  }'
```
卸载示例：
```bash
curl -X POST http://localhost:8000/v1/unload_lora_adapter \
  -H "Content-Type: application/json" \
  -d '{"lora_name": "tenant-a-v3"}'
```
### 6.1 为什么官方发出安全警告
运行时加载意味着服务进程会接收路径或解析 Adapter 内容。若端点暴露给不可信调用方，可能带来：
- 任意本地路径探测；
- 恶意或损坏权重；
- 资源耗尽；
- Adapter 名称覆盖；
- 未审计模型变更。
官方在线服务文档对这类动态端点给出仅限受控环境的警告。生产平台应把它放在控制面后方，不直接暴露到数据面。
### 6.2 更稳妥的控制面
推荐流程：
1. Adapter 上传到隔离仓库；
2. 扫描格式、大小与来源；
3. 校验底座 Revision、rank、target modules；
4. 分配不可变版本名；
5. 控制面调用加载；
6. 健康检查和黄金请求验证；
7. 更新租户路由；
8. 旧版本排空后卸载。
动态能力不等于省略发布流程，而是让发布流程无需重启底座。

## 7. 调度、缓存与抖动
### 7.1 热点 Adapter
若 90% 流量集中在两个 Adapter，较小 GPU 槽位就能取得高命中率。若 100 个租户均匀随机访问，槽位会频繁替换。
后者类似只有两口灶，却来了 100 道不同菜，每道菜都要换锅和调料。灶本身很快，换菜准备反而成为主要延迟。
### 7.2 Head-of-Line Blocking
当某 Adapter 未就绪时：
- 是只阻塞该租户？
- 还是整个 Batch 等待？
- 能否先调度已命中 Adapter？
- 加载失败如何快速返回？
这些策略会影响 P99，不能只看平均 Token 吞吐。
### 7.3 按 Adapter 感知组批
把相同 Adapter 请求聚在一起可减少活跃 LoRA 数和切换，但会增加等待时间。
这是经典权衡：
- 等更久，Batch 更同质、吞吐更高；
- 立即执行，延迟更低、Kernel 更异构。
### 7.4 CUDA Graph 的关系
活跃 LoRA 数变化会影响图形态。当前 vLLM 提供与 LoRA 图专门化相关的配置，但这些优化属于快速演进区：可能增加启动时间和显存，以换取可变 LoRA 数量下的运行性能。
不要把实验参数固化成平台默认值。先测工作负载分布，再决定是否启用。

## 8. 生产治理与安全
### 8.1 租户隔离
API 层不能允许用户随意传任意 `model` 名称。应维护：
```text
tenant_id -> allowed_adapter_revision
```
并在网关完成映射。否则租户 A 可能请求租户 B 的 Adapter。
### 8.2 版本不可变
不要让 `tenant-a` 永远指向可被原地覆盖的目录。使用：
```text
tenant-a-v17
tenant-a-v18
```
路由别名可以变化，底层 Artifact 应不可变且有 Hash。
### 8.3 基础模型漂移
Adapter 对底座 Revision 敏感。底座升级可能导致质量变化或加载失败，因此发布元数据至少记录：
- Base Model ID 与 Revision；
- Tokenizer Revision；
- PEFT 版本；
- LoRA rank、alpha、target modules；
- 训练数据与评测版本；
- Artifact Hash。
### 8.4 可观测性
按 Adapter 维度记录：
- 请求量与活跃租户；
- GPU/CPU Cache 命中率；
- 加载和换入耗时；
- TTFT、TPOT、错误率；
- 被驱逐次数；
- 每 Batch 活跃 LoRA 数；
- 版本和底座映射。
没有 Adapter 维度，平均指标会掩盖冷门租户的严重抖动。

## 9. 选型和压测
### 9.1 适合 Multi-LoRA
- 共享同一底座；
- Adapter 较小；
- 租户流量有热点；
- 允许控制面管理版本；
- 需要比独立服务更高的 GPU 利用率。
### 9.2 不一定适合
- 每个租户底座不同；
- Adapter 修改范围或 rank 很大；
- 租户需要强故障隔离；
- 单租户流量足以独占 GPU；
- 长尾 Adapter 数极多且访问均匀；
- 合规要求禁止权重共驻。
### 9.3 压测矩阵
不要只测一个 Adapter。至少覆盖：
| 维度 | 测试点 |
|---|---|
| 活跃 Adapter 数 | 1、`max_loras`、超过 `max_loras` |
| rank | 最小、常见、最大 |
| 流量分布 | 单热点、Zipf、均匀随机 |
| Cache 状态 | 全热、CPU 热、全冷 |
| 请求长度 | 短 Prompt、长 Prompt、长输出 |
| 事件 | 加载、卸载、灰度切换、加载失败 |
重点看 P95/P99 TTFT、KV Cache 容量变化和 Adapter 换入时间。
如果后续与 SGLang 的 LoRA 服务比较，应固定相同底座、Adapter 集合、热度分布和显存预算，再比较 Goodput；只测热 Adapter 峰值吞吐没有代表性。
---

## 📝 总结
- Multi-LoRA 共享底座权重，为每个请求选择不同低秩增量。
- `max_loras` 控制同批活跃槽位，`max_lora_rank` 控制秩上界，`max_cpu_loras` 控制 CPU 缓存。
- 槽位显存通常随最大活跃数和最大 rank 增长，并会挤压 KV Cache。
- 动态加载适合受控控制面，不应把加载端点直接暴露给不可信用户。
- 长尾 Adapter 会造成缓存抖动和 TTFT 尖刺，平均吞吐无法反映问题。
- 生产平台要做租户授权、Artifact 不可变、底座绑定、灰度和按 Adapter 观测。
