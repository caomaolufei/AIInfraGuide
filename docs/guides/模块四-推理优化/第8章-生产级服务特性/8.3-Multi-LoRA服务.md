一家平台有 50 个业务租户，每个租户都基于同一个 8B 底座训练了 LoRA。最直观的部署方式是拉起 50 份模型服务，但底座权重也会复制 50 份，GPU 很快被吃光。
Multi-LoRA 的目标，是让所有租户共享那份昂贵的底座权重，只为每个租户保存较小的低秩增量，并在请求到来时选择对应 Adapter。
听起来像“免费多租户”，实际却把问题从底座显存转移到了 Adapter 槽位、搬运、调度和隔离。
<!-- more -->

## 1. 从 LoRA 公式看服务机制
对线性层权重 $W \in \mathbb{R}^{d_{out}\times d_{in}}$，LoRA 不直接保存完整的新权重，而是学习低秩增量：
$$ y = Wx + \frac{\alpha}{r}BAx $$
其中：
- $A \in \mathbb{R}^{r\times d_{in}}$；
- $B \in \mathbb{R}^{d_{out}\times r}$；
- $r$ 是远小于原始维度的 rank；
- $W$ 对所有租户共享；
- 每个 Adapter 有自己的 $A$、$B$。
若为每个租户单独合并权重：
$$ W_i = W + \Delta W_i $$
就需要多份接近完整模型大小的权重。Multi-LoRA 保留共享 $W$，在执行层里按请求选择不同的低秩矩阵。
类比一下：底座模型像一台昂贵的数控机床，LoRA 是可更换刀头。为每种零件买一台机床太浪费；共享机床、切换刀头更经济。但刀头架容量、换刀时间和同时加工不同零件的调度仍然要付成本。
📌 **关键点**：Multi-LoRA 节省的是**底座副本**，不是让 Adapter 的存储、加载和计算变成零成本。
---

## 2. Multi-LoRA 的执行路径
一个请求携带 Adapter 名称后，大致经历：
1. API 层把 `model` 名称解析为底座或 LoRA；
2. Adapter 管理器检查它是否已注册；
3. 若不在 GPU 活跃槽位，可能从 CPU 缓存或存储加载；
4. 调度器把请求与对应 LoRA ID 组批；
5. LoRA Kernel 按请求 ID 选择 $A_i$、$B_i$；
6. 基础线性结果与低秩增量相加；
7. 请求结束后，Adapter 可继续留在缓存等待复用。
### 2.1 同一批如何使用不同 Adapter
设批次中四个请求分别使用：
```text
request:  A  B  C  D
adapter:  2  2  7  0
```
其中 `0` 可表示底座。Kernel 需要根据每个 Token 或序列对应的 LoRA ID，路由到正确矩阵。
这比整批只用同一个 Adapter 更复杂：
- 索引和元数据增加；
- 不同 Adapter 数量影响 Kernel 形态；
- GPU 上必须有足够活跃槽位；
- Adapter 分布会影响组批效率。
### 2.2 额外计算量
LoRA 增量包含两次低秩矩阵乘：
$$ x \rightarrow Ax \rightarrow B(Ax) $$
rank 越大、挂载层越多，额外计算越多。与完整模型相比通常仍较小，但在 Decode 的小 Batch、低延迟场景中，Kernel 调度和内存访问也可能明显。

## 3. vLLM 启动与请求
### 3.1 启动时注册 Adapter
当前官方示例使用 `--enable-lora` 与 `--lora-modules`：
```bash
vllm serve meta-llama/Llama-3.2-3B-Instruct \
  --enable-lora \
  --max-loras 4 \
  --max-lora-rank 64 \
  --max-cpu-loras 16 \
  --lora-modules sql=/models/lora/sql support=/models/lora/support
```
启动后查询模型列表：
```bash
curl http://localhost:8000/v1/models
```
通常会看到底座和已注册 Adapter。请求时把 Adapter 名称作为 `model`：
```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
response = client.chat.completions.create(
    model="sql",
    messages=[
        {"role": "user", "content": "查询最近 7 天新增用户数"}
    ],
)
```
### 3.2 离线 LoRARequest
离线推理可使用 `LoRARequest` 指定名称、内部 ID 和路径。其具体构造签名属于代码 API，版本演进比 HTTP 协议快，使用时应查看对应版本 API 文档。
### 3.3 Adapter 兼容前提
加载前至少验证：
- `base_model_name_or_path` 与底座匹配；
- `peft_type` 是目标 LoRA 类型；
- rank 不超过服务配置；
- `target_modules` 是模型支持的层；
- Tokenizer 和额外词表是否匹配；
- Adapter 文件来自可信来源。
名称相同不代表权重兼容，路径可读也不代表能安全加载。

## 4. 三个核心容量参数
### 4.1 max_loras
`max_loras` 控制一个 Batch 中可同时活跃的 LoRA 数量，也影响预分配槽位。
它不是“平台注册 Adapter 总数”。平台注册 100 个 Adapter，不代表同一步必须把 100 个都放在 GPU 上。
调大后：
- 异构租户更容易同批执行；
- GPU LoRA 槽位显存增加；
- Kernel 和图捕获策略可能更复杂。
调小后：
- 显存更省；
- 热点集中时效率高；
- 多 Adapter 混合负载可能排队或频繁切换。
### 4.2 max_lora_rank
`max_lora_rank` 是服务允许的最大 rank。官方建议设置为计划加载 Adapter 的实际最大值。
如果 rank 集合是 `[8, 16, 64]`，配置 64 比盲目配置 256 更合理，因为槽位通常要按上界预留。
⚠️ 该参数允许值、默认值与内核限制可能随版本变化，应查看当前 `vllm serve --help`。
### 4.3 max_cpu_loras
`max_cpu_loras` 控制 CPU 内存缓存可保留的 LoRA 数量，要求通常不小于 `max_loras`。
它像机床旁的刀头柜：
- GPU 槽位是机器当前可快速使用的刀头；
- CPU Cache 是旁边的刀头柜；
- 远端对象存储是仓库。
从 CPU 搬到 GPU 比从对象存储下载快，但仍有 PCIe 传输和同步成本。

## 5. 低秩计算到底省了多少

### 5.1 参数量推导

完整线性层参数量：

$$
N_W=d_{\text{out}}d_{\text{in}}
$$

LoRA 参数量：

$$
N_L=r(d_{\text{in}}+d_{\text{out}})
$$

比例为：

$$
\frac{N_L}{N_W}
=\frac{r(d_{\text{in}}+d_{\text{out}})}
{d_{\text{in}}d_{\text{out}}}
$$

若方阵 $d_{\text{in}}=d_{\text{out}}=d$：

$$
\frac{N_L}{N_W}=\frac{2r}{d}
$$

例如 $d=4096,r=16$，单层 LoRA 参数约为完整方阵的：

$$
\frac{32}{4096}=0.78125\%
$$

这个比例只适用于被挂载的矩阵。实际 Adapter 大小还取决于 `target_modules`，不能拿单个方阵比例直接乘整个模型。

### 5.2 FLOPs 推导

对一个 Token 的矩阵向量乘，基础线性层乘加量近似：

$$
C_W\approx2d_{\text{out}}d_{\text{in}}
$$

LoRA 两次乘法：

$$
C_L\approx2r d_{\text{in}}+2d_{\text{out}}r
=2r(d_{\text{in}}+d_{\text{out}})
$$

因此理论计算比例与参数比例相同。对 $4096\times4096,r=16$：

```text
base: 2 * 4096 * 4096 = 33,554,432 FLOPs/token
lora: 2 * 16 * (4096 + 4096) = 262,144 FLOPs/token
ratio: 0.78125%
```

但在线 Decode 中不能据此断言“延迟只增加 0.78%”。低秩 GEMM 很小，可能受 Kernel launch、索引、读 Adapter 权重和不规则 Batch 支配，硬件利用率远低于大 GEMM。

### 5.3 Prefill 与 Decode 的不同

设当前层输入为 $X\in\mathbb{R}^{T\times d_{\text{in}}}$：

$$
Y=XW^\top+\frac{\alpha}{r}(XA^\top)B^\top
$$

Prefill 的 $T$ 较大，低秩矩阵乘更容易形成有效 GEMM；Decode 每序列通常只贡献一个新 Token，需要跨 Batch 聚合才能提高效率。于是同一个 Adapter：

- 长 Prompt 场景更接近 FLOPs 模型；
- 小 Batch Decode 更容易暴露固定开销；
- 混合多个 Adapter 后，路由和访存局部性更差。

### 5.4 一个 32 层模型的手算

假设隐藏维度 4096，中间维度 11008，32 层，LoRA rank 16，挂载：

```text
attention: q_proj, k_proj, v_proj, o_proj
MLP: gate_proj, up_proj, down_proj
```

每层参数：

$$
N_{\text{attn}}
=4\times16(4096+4096)
=524{,}288
$$

MLP 三个矩阵：

$$
N_{\text{mlp}}
=2\times16(4096+11008)
+16(11008+4096)
=724{,}992
$$

全模型：

$$
N_L\approx32\times(524{,}288+724{,}992)
=39{,}976{,}960
$$

BF16 权重原始数据约：

$$
39{,}976{,}960\times2
\approx76.25\text{ MiB}
$$

若只挂 q/v 两个投影，则约：

$$
32\times2\times16\times8192\times2
=16\text{ MiB}
$$

这 4.8 倍差异来自 target modules，而不是 rank。配置容量时必须读取 Adapter 元数据和张量形状。

## 6. 显存、槽位与实际 Adapter 的区别
单个线性层 LoRA 参数量近似：
$$ N_{\text{LoRA}} = r(d_{in}+d_{out}) $$
若数据类型每元素 $b$ 字节，挂载多个层后：
$$ M_{\text{adapter}} \approx b \cdot r \sum_{l\in \mathcal{L}}(d_{in,l}+d_{out,l}) $$
GPU 侧预分配还可能按最大 rank 和槽位数放大：
$$ M_{\text{slots}} \propto \text{max\_loras} \times \text{max\_lora\_rank} \times \text{target dimensions} $$
这是容量规划中最容易忽略的一点：实际 Adapter rank 是 8，不代表配置上限 256 没有成本。
### 6.1 还有哪些显存
总显存不只 LoRA：
$$ M_{\text{total}} = M_{\text{base}} + M_{\text{KV}} + M_{\text{LoRA slots}} + M_{\text{CUDA graph}} + M_{\text{workspace}} + M_{\text{activations}} $$
提高 `max_loras` 或 `max_lora_rank` 后，可用于 KV Cache 的空间可能减少，最终表现为并发下降，而不只是“LoRA 多占了一点显存”。
### 6.2 不要只按文件大小估算
Adapter 磁盘文件可能压缩、分片或使用不同 dtype。GPU 上还涉及：
- 对齐与 Padding；
- 最大 rank 槽位；
- Layer Mapping 元数据；
- Kernel Workspace；
- CUDA Graph 专门化副本。
正确方法是在目标 GPU、目标 vLLM 版本和目标模型上测启动后显存，再逐步增加槽位。

### 6.3 物理槽位为何按上界预留

高性能 Kernel 希望 Adapter 张量具有稳定地址和规则 Shape。一个概念槽位可视作：

```text
slot[adapter_index][layer][module][A_or_B][max_rank_dimension]
```

rank 小于 `max_lora_rank` 时，可能通过 Padding、元数据或专门 Kernel 使用；具体布局取决于版本。容量上应采用保守上界：

$$
M_{\text{GPU slots}}
\lesssim S\times b\times r_{\max}
\sum_l\sum_{m\in\mathcal{M}_l}
(d_{\text{in},lm}+d_{\text{out},lm})
+M_{\text{metadata/workspace}}
$$

其中 $S=\text{max_loras}$。这不是 vLLM 对所有版本的精确分配公式，而是解释参数增长方向的容量模型。

### 6.4 张量并行下怎么估

若底座层按 TP 切分，LoRA 的 A/B 也会根据 ColumnParallel/RowParallel 方式分片或复制。不能简单把单卡 LoRA 显存都除以 TP：

- 某个因子可能分片；
- 另一个因子可能复制；
- 元数据每卡都有；
- 不同 target module 的切分方向不同；
- Pipeline Parallel 则按层归属分配。

应先用全局参数量估集群总量，再以实际并行布局和每 Rank `memory_allocated` 校准。

### 6.5 槽位挤压 KV Cache 的手算

假设单卡可用于运行时数据的余量为 12 GiB，原本 KV Cache 规划 10 GiB。将 GPU LoRA 槽从 2 调到 8，实测每个最大 rank 槽位增加 220 MiB：

```text
新增 LoRA = (8 - 2) * 220 MiB = 1320 MiB
KV 余量约从 10 GiB 降到 8.71 GiB
```

若单请求平均 KV 占 350 MiB，粗略并发上界从：

```text
10 GiB / 350 MiB ≈ 29
8.71 GiB / 350 MiB ≈ 25
```

减少约 4 个长序列槽。真实系统受 Block 粒度、序列长度分布和 CUDA Graph 影响，但这个手算能说明：扩大 LoRA 能力会通过 KV 间接降低 Goodput。

## 7. Adapter 的三级驻留与缓存策略

将 Adapter 生命周期分成三级更清晰：

```text
artifact store -> CPU cache -> GPU active slots
```

### 7.1 Artifact Store

保存不可变 Adapter 文件、配置和签名。访问延迟通常最高，可能经过对象存储、网络文件系统或镜像分发。

需要记录：

- content hash；
- 字节数和张量清单；
- base model revision；
- tokenizer/extra vocabulary；
- rank、alpha、target modules；
- dtype；
- 签名与来源。

### 7.2 CPU Cache

CPU Cache 保存已读取和反序列化的 Adapter，避免重复下载。命中仍要支付：

- CPU 到 pinned memory 的准备；
- PCIe/NVLink 搬运；
- GPU 槽位写入；
- 必要同步。

缓存大小不应只按“个数”理解。一个 rank 64、全模块 Adapter 与 rank 8、q/v-only Adapter 差异很大；若版本只提供个数上限，平台还要在控制面限制单 Artifact 字节数。

### 7.3 GPU Active Slots

GPU 槽位命中时请求可直接进入调度；未命中时需要换入。换入延迟近似：

$$
T_{\text{swap-in}}
\approx T_{\text{queue}}
+\frac{M_{\text{adapter}}}{BW_{\text{host-to-device}}}
+T_{\text{layout/copy}}
+T_{\text{sync}}
$$

一个 100 MiB Adapter 在理论 24 GB/s PCIe 链路上纯传输约 4.2 ms，但实际会因 pageable memory、并发复制、张量碎片和同步更慢。不要拿峰值带宽当 P99。

### 7.4 驱逐策略

纯 LRU 在长尾多租户下不一定最佳。可考虑：

- LRU：实现简单；
- LFU/频率衰减：保护长期热点；
- 租户配额：避免大租户挤掉所有槽；
- admission control：只在预计复用时缓存；
- pinned adapter：保留系统默认/高优先级；
- size-aware：避免大 Adapter 造成频繁搬运；
- load-aware：高峰期拒绝冷加载。

命中率本身不够，要按“避免了多少加载字节”和“节省了多少延迟”加权。

## 8. 动态加载控制面：把权重发布当软件发布

### 8.1 为什么数据面不能直接加载

如果每个请求都能携带 `lora_path`，请求者实际上获得了模型进程文件系统和显存资源的间接控制权。正确边界是：

```text
tenant request -> model alias -> approved immutable adapter revision
```

数据面只能选已批准别名，不能提供路径、URL 或内部 ID。

### 8.2 状态机

控制面可用以下状态：

```text
UPLOADED
 -> SCANNED
 -> COMPATIBLE
 -> STAGED
 -> LOADED
 -> VERIFIED
 -> SERVING
 -> DRAINING
 -> UNLOADED
```

失败进入带原因的 `REJECTED` 或 `LOAD_FAILED`，而不是反复自动重试。

### 8.3 两阶段发布

第一阶段准备：

1. 下载到隔离临时目录；
2. 验证 Hash/签名；
3. 使用安全张量格式并检查文件清单；
4. 检查所有 Shape、rank 和 target modules；
5. 估算 CPU/GPU 占用；
6. 分配不可变内部 ID。

第二阶段激活：

1. 在候选副本加载；
2. 执行黄金 Prompt；
3. 检查数值异常与 TTFT；
4. 原子更新 `tenant -> revision` 路由；
5. 观察错误预算；
6. 排空旧 Revision 后卸载。

### 8.4 并发控制

两个控制器同时加载同名 Adapter 会造成竞态。操作应以 `(base_revision, adapter_revision)` 为幂等键，并使用 compare-and-swap 更新路由。

卸载前检查：

- 是否仍有新请求被路由；
- 是否有 running sequence 引用槽位；
- 是否有排队请求；
- 是否有回滚窗口要求；
- 其他租户是否共享该 Revision。

不能仅看到“QPS=0”就立即释放。

### 8.5 回滚

路由层保存最近稳定 Revision：

```text
tenant-a -> adapter-v18
previous -> adapter-v17
```

质量、错误率或延迟越过阈值时，先停止新流量并切回 v17；v18 在排空后留在隔离状态供分析。回滚不应依赖重新从对象存储下载旧版。

## 9. vLLM 动态加载与卸载
vLLM 支持运行时 LoRA 更新端点。按当前官方说明，需要显式允许：
```bash
export VLLM_ALLOW_RUNTIME_LORA_UPDATING=True
vllm serve meta-llama/Llama-3.2-3B-Instruct \
  --enable-lora \
  --max-loras 2 \
  --max-lora-rank 64
```
加载示例：
```bash
curl -X POST http://localhost:8000/v1/load_lora_adapter \
  -H "Content-Type: application/json" \
  -d '{
    "lora_name": "tenant-a-v3",
    "lora_path": "/models/lora/tenant-a-v3"
  }'
```
卸载示例：
```bash
curl -X POST http://localhost:8000/v1/unload_lora_adapter \
  -H "Content-Type: application/json" \
  -d '{"lora_name": "tenant-a-v3"}'
```
### 9.1 为什么官方发出安全警告
运行时加载意味着服务进程会接收路径或解析 Adapter 内容。若端点暴露给不可信调用方，可能带来：
- 任意本地路径探测；
- 恶意或损坏权重；
- 资源耗尽；
- Adapter 名称覆盖；
- 未审计模型变更。
官方在线服务文档对这类动态端点给出仅限受控环境的警告。生产平台应把它放在控制面后方，不直接暴露到数据面。
### 9.2 更稳妥的控制面
推荐流程：
1. Adapter 上传到隔离仓库；
2. 扫描格式、大小与来源；
3. 校验底座 Revision、rank、target modules；
4. 分配不可变版本名；
5. 控制面调用加载；
6. 健康检查和黄金请求验证；
7. 更新租户路由；
8. 旧版本排空后卸载。
动态能力不等于省略发布流程，而是让发布流程无需重启底座。

### 9.3 Resolver Plugin 的边界

Resolver 可把名称解析为 Adapter Artifact，但它不是授权系统。即便路径解析由插件完成，仍应在进入 Resolver 前完成租户到允许 Revision 的映射，并对下载大小、来源、并发和超时设限。

自动按需解析可能把冷加载放进请求关键路径。高 SLO 服务更适合预热或异步返回“Adapter preparing”，避免一个远端存储抖动拖住整个 Batch。

## 10. Adapter-aware Batching 的收益与代价
### 10.1 热点 Adapter
若 90% 流量集中在两个 Adapter，较小 GPU 槽位就能取得高命中率。若 100 个租户均匀随机访问，槽位会频繁替换。
后者类似只有两口灶，却来了 100 道不同菜，每道菜都要换锅和调料。灶本身很快，换菜准备反而成为主要延迟。
### 10.2 Head-of-Line Blocking
当某 Adapter 未就绪时：
- 是只阻塞该租户？
- 还是整个 Batch 等待？
- 能否先调度已命中 Adapter？
- 加载失败如何快速返回？
这些策略会影响 P99，不能只看平均 Token 吞吐。
### 10.3 按 Adapter 感知组批
把相同 Adapter 请求聚在一起可减少活跃 LoRA 数和切换，但会增加等待时间。
这是经典权衡：
- 等更久，Batch 更同质、吞吐更高；
- 立即执行，延迟更低、Kernel 更异构。
### 10.4 一个组批目标函数

可以把调度器目标写成概念形式：

$$
\text{score(batch)}
=w_1\cdot\text{tokens}
-w_2\cdot\text{unique adapters}
-w_3\cdot\text{queue age}
-w_4\cdot\text{cold loads}
$$

只优化 `unique adapters` 会饿死长尾租户；只优化 queue age 会让每批极度异构。生产策略需要最大等待时间，保证请求最终被服务。

### 10.5 Token 级路由

Continuous Batching 中，请求在不同时间进入和结束。某一步的 Token 到 Adapter 映射可能是：

```text
token rows:     0 1 2 3 4 5 6 7
sequence ids:   A A B C C D D D
adapter ids:    2 2 7 2 2 0 0 0
```

Kernel 可以按 ID gather 对应 LoRA 权重，或先按 Adapter 重排 Token 行再执行分组 GEMM。前者简单但访存分散，后者提高局部性却增加重排。不同 vLLM/Kernel 版本会选择不同策略，所以“同批 LoRA 数”是必要观测维度。

### 10.6 CUDA Graph 的关系
活跃 LoRA 数变化会影响图形态。当前 vLLM 提供与 LoRA 图专门化相关的配置，但这些优化属于快速演进区：可能增加启动时间和显存，以换取可变 LoRA 数量下的运行性能。
不要把实验参数固化成平台默认值。先测工作负载分布，再决定是否启用。

## 11. 可复现实验：rank、槽位、热度三维扫描

### 11.1 准备 Adapter

选择同一底座、相同数据流程训练或准备 rank 8、16、64 三个 Adapter。确保 target modules 一致，否则无法单独归因 rank。

记录每个 Adapter：

```python
import json
from pathlib import Path

for path in Path("/models/lora").iterdir():
    config = json.loads((path / "adapter_config.json").read_text())
    total_bytes = sum(
        p.stat().st_size for p in path.rglob("*") if p.is_file()
    )
    print(path.name, config["r"], config["target_modules"], total_bytes)
```

### 11.2 启动矩阵

分别启动：

```text
max_loras:      1, 2, 4, 8
max_lora_rank:  8, 16, 64
max_cpu_loras:  max_loras, 2*max_loras
```

每次记录服务就绪后的：

- 每卡 allocated/reserved 显存；
- KV Cache 块数；
- CUDA Graph 内存；
- 服务启动时间；
- Adapter 首次加载时间。

不能在同一进程中反复改参数后比较，因为碎片和缓存状态会污染结果。

### 11.3 工作负载

生成三类 Adapter ID 序列：

```python
import random

rng = random.Random(42)
adapters = [f"a{i}" for i in range(32)]

hot = ["a0"] * 90 + ["a1"] * 10
uniform = adapters
zipf_like = (
    ["a0"] * 40 + ["a1"] * 20 + ["a2"] * 10
    + adapters[3:]
)

def sample(pool, n=1000):
    return [rng.choice(pool) for _ in range(n)]
```

固定 Prompt/输出长度，分别执行：

1. 单 Adapter 全热；
2. `unique adapters == max_loras`；
3. 工作集略大于 GPU 槽位；
4. 工作集大于 CPU Cache；
5. 运行中灰度加载新 Revision；
6. 一个 Adapter 文件损坏。

### 11.4 观测指标

按 Adapter 和缓存层记录：

```text
lora_request_total{adapter,revision}
lora_gpu_cache_hit_total{adapter}
lora_cpu_cache_hit_total{adapter}
lora_load_seconds{source,result}
lora_load_bytes_total{source}
lora_eviction_total{tier,adapter}
lora_active_per_batch
lora_rank_per_batch
lora_queue_seconds{cache_state}
lora_kernel_seconds{phase,prefill_or_decode}
kv_cache_available_blocks
```

结果报告不能只给平均吞吐。至少给：

- TTFT P50/P95/P99，按全热/CPU 热/全冷分组；
- TPOT 与输出吞吐；
- GPU/CPU Cache 的请求命中率与字节命中率；
- 每次驱逐后短时间内重新加载比例；
- 每批唯一 Adapter 数；
- KV Cache 抢占/排队；
- 控制面发布耗时与失败率。

### 11.5 计算开销隔离

为了区分加载和 LoRA Kernel：

```text
base model, no adapter
one adapter, preloaded, rank 8
one adapter, preloaded, rank 64
four adapters, all preloaded, homogeneous batches
four adapters, all preloaded, mixed batches
```

全部预热后再测 TPOT，避免把第一次 H2D 搬运算成低秩计算成本。

## 12. 生产失败模式

### 12.1 Base Revision 误配

Shape 可能恰好兼容但语义底座不同，加载不一定报错，质量却崩溃。必须按不可变 Revision 和权重 Hash 绑定，不只比较模型名称。

### 12.2 Rank 上限与目标层不兼容

加载时应明确失败并保持旧路由。不能部分加载可识别层后继续服务，否则得到不可审计的混合 Adapter。

### 12.3 缓存惊群

热点 Adapter 被驱逐后，大量请求同时触发加载。使用 singleflight：同一 Revision 同时只有一个加载任务，其他请求等待同一 Future 或快速失败。

### 12.4 CPU OOM

`max_cpu_loras` 按个数控制时，超大 Adapter 仍可能打爆内存。控制面增加总字节预算，并监控进程 RSS、pinned memory 和反序列化峰值。

### 12.5 卸载正在使用的 Adapter

若引用计数、generation epoch 或排空协议错误，可能产生错误权重或崩溃。控制面必须等待所有旧 epoch 请求结束。

### 12.6 名称复用导致缓存混淆

`tenant-a` 原地指向新文件，而 GPU/CPU Cache 仍按名称命中旧权重。缓存键必须含不可变 Revision/Hash；别名只存在于路由层。

### 12.7 长尾租户饥饿

过度追求同 Adapter 组批会让低 QPS Adapter 长时间等待。设置最大 queue age，并单独报告按租户 P99。

### 12.8 动态加载压垮数据面

发布风暴占满网络、CPU 和 PCIe，正常推理 TTFT 尖刺。加载要有全局/每节点并发限制，并与在线请求错峰或设带宽优先级。

## 13. 生产治理与安全
### 13.1 租户隔离
API 层不能允许用户随意传任意 `model` 名称。应维护：
```text
tenant_id -> allowed_adapter_revision
```
并在网关完成映射。否则租户 A 可能请求租户 B 的 Adapter。
### 13.2 版本不可变
不要让 `tenant-a` 永远指向可被原地覆盖的目录。使用：
```text
tenant-a-v17
tenant-a-v18
```
路由别名可以变化，底层 Artifact 应不可变且有 Hash。
### 13.3 基础模型漂移
Adapter 对底座 Revision 敏感。底座升级可能导致质量变化或加载失败，因此发布元数据至少记录：
- Base Model ID 与 Revision；
- Tokenizer Revision；
- PEFT 版本；
- LoRA rank、alpha、target modules；
- 训练数据与评测版本；
- Artifact Hash。
### 13.4 可观测性
按 Adapter 维度记录：
- 请求量与活跃租户；
- GPU/CPU Cache 命中率；
- 加载和换入耗时；
- TTFT、TPOT、错误率；
- 被驱逐次数；
- 每 Batch 活跃 LoRA 数；
- 版本和底座映射。
没有 Adapter 维度，平均指标会掩盖冷门租户的严重抖动。
---

### 13.5 Artifact 安全

优先使用不执行代码的权重格式。即使使用 safetensors，也要限制：

- 文件总大小和张量数量；
- 单张量维度与 dtype；
- 路径穿越和符号链接；
- 下载域名、Hash 与签名；
- 解压后大小；
- Adapter 配置中的未知字段。

模型加载进程不应拥有写 Artifact 仓库、访问租户数据或任意网络出口的权限。

### 13.6 版本边界

以下行为需按 vLLM 目标版本验证：

- `max_loras` 是每 Batch、并发槽位还是两者共同约束；
- 槽位是否按最大 rank 预分配；
- 支持的 rank、bias、extra vocabulary 与量化组合；
- runtime update API 的路径、开关和错误语义；
- Resolver Plugin 生命周期；
- TP/PP 下 LoRA 分片；
- CUDA Graph 与 LoRA 的兼容参数；
- metrics 名称。

公式用于容量上界，不能替代目标版本实测。

## 14. 选型和压测
### 14.1 适合 Multi-LoRA
- 共享同一底座；
- Adapter 较小；
- 租户流量有热点；
- 允许控制面管理版本；
- 需要比独立服务更高的 GPU 利用率。
### 14.2 不一定适合
- 每个租户底座不同；
- Adapter 修改范围或 rank 很大；
- 租户需要强故障隔离；
- 单租户流量足以独占 GPU；
- 长尾 Adapter 数极多且访问均匀；
- 合规要求禁止权重共驻。
### 14.3 压测矩阵
不要只测一个 Adapter。至少覆盖：
| 维度 | 测试点 |
|---|---|
| 活跃 Adapter 数 | 1、`max_loras`、超过 `max_loras` |
| rank | 最小、常见、最大 |
| 流量分布 | 单热点、Zipf、均匀随机 |
| Cache 状态 | 全热、CPU 热、全冷 |
| 请求长度 | 短 Prompt、长 Prompt、长输出 |
| 事件 | 加载、卸载、灰度切换、加载失败 |
重点看 P95/P99 TTFT、KV Cache 容量变化和 Adapter 换入时间。
如果后续与 SGLang 的 LoRA 服务比较，应固定相同底座、Adapter 集合、热度分布和显存预算，再比较 Goodput；只测热 Adapter 峰值吞吐没有代表性。
---

## 📝 总结
- Multi-LoRA 共享底座权重，为每个请求选择不同低秩增量。
- `max_loras` 控制同批活跃槽位，`max_lora_rank` 控制秩上界，`max_cpu_loras` 控制 CPU 缓存。
- 槽位显存通常随最大活跃数和最大 rank 增长，并会挤压 KV Cache。
- 动态加载适合受控控制面，不应把加载端点直接暴露给不可信用户。
- 长尾 Adapter 会造成缓存抖动和 TTFT 尖刺，平均吞吐无法反映问题。
- 生产平台要做租户授权、Artifact 不可变、底座绑定、灰度和按 Adapter 观测。
