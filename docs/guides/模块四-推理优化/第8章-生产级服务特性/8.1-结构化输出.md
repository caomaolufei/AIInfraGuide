让模型“只返回 JSON”很容易，让它在第一万次请求仍返回**可解析且符合 Schema 的 JSON**很难。
提示词只能表达愿望。模型仍可能多说一句“当然可以”、漏掉右括号，或者把数字写成字符串。生产系统若把这段文本直接交给解析器，失败会一路传到重试、队列和用户延迟。
结构化输出换了一种思路：不在生成后祈祷，而是在生成时限制每一步能选的 Token。
<!-- more -->

## 1. 提示约束为什么不够
假设订单接口需要：
```json
{"sku":"A-17","quantity":2,"expedited":false}
```
只写“请输出 JSON”至少有四类风险：
1. **语法风险**：缺引号、缺逗号、括号不配对；
2. **形状风险**：字段缺失、多字段、嵌套层级错误；
3. **类型风险**：`quantity` 变成 `"two"`；
4. **语义风险**：SKU 格式合法，但仓库根本没有这个商品。
受约束解码主要解决前三类中的“可由语法描述的部分”。第四类仍要业务系统校验。
类比一下：提示词像在考场门口贴“请勿带手机”，受约束解码像安检门。前者影响行为概率，后者直接阻止不合法对象通过。但安检门只能判断“像不像手机”，不能判断来访者有没有恶意。
📌 **关键点**：结构化输出保证的是**形式约束**，不是事实正确性、权限正确性或业务可执行性。

## 2. Constrained Decoding 的机制
普通采样在每一步得到词表大小的 Logits：
$$ p(x_t \mid x_{<t}) = \operatorname{softmax}(z_t) $$
受约束解码多做一步：根据当前已生成前缀和语法状态，算出允许 Token 集合 $A_t$，把其他 Token 的 Logit 设为负无穷：
$$ z'_t(i)= \begin{cases} z_t(i), & i \in A_t \\ -\infty, & i \notin A_t \end{cases} $$
之后 Temperature、Top-k、Top-p 等采样只在合法集合内工作。
例如已输出：
```text
{"quantity":
```
Schema 规定 `quantity` 是整数，那么 `"two"` 的开引号不能被选中；数字、负号或符合规则的空白仍可进入候选。
### 2.1 难点不在字符，而在 Token
模型不是逐字符生成，而是逐 Token 生成。一个 Token 可能是：
- 单个字符；
- 多个数字；
- 一段带前导空格的文本；
- 甚至同时跨过几个语法字符。
因此约束引擎不能只问“下一个字符是否合法”，还要判断“这个 Token 解码成的字符序列能否让语法状态继续前进”。
### 2.2 状态机如何参与每一步
约束后端通常会：
1. 把 JSON Schema、Regex 或 Grammar 编译成可匹配结构；
2. 维护每个请求当前的语法状态；
3. 为当前状态计算允许 Token 的位图；
4. 在 GPU 采样前应用位图；
5. 接收选中 Token，推进状态；
6. 到达接受状态后允许结束。
可以把它想成导航系统：模型仍决定走哪条风景更好的路，但导航把“逆行、断头路、未开放道路”从候选路线里划掉。
### 2.3 合法不代表自然
约束越强，模型自由度越小。当合法集合中只剩一个 Token 时，Temperature 已没有作用；当 Schema 与模型常见表达冲突时，生成虽然合法，却可能拗口或质量下降。
🔑 **核心概念**：Constrained Decoding 不是生成后修复，而是**在每次采样前改变候选空间**。

## 3. 四种常用约束
vLLM 当前结构化输出文档主要展示四类约束。
### 3.1 Choice
输出必须精确等于候选之一：
```python
extra_body={
    "structured_outputs": {
        "choice": ["approve", "reject", "manual_review"]
    }
}
```
适合分类、路由和有限状态决策。它比让模型生成长解释再做字符串匹配可靠得多。
### 3.2 Regex
输出必须匹配正则：
```python
extra_body={
    "structured_outputs": {
        "regex": r"ORD-[0-9]{8}"
    }
}
```
适合短格式：订单号、日期、固定标签。正则能描述局部模式，但不擅长复杂递归结构。
### 3.3 JSON Schema
Schema 能描述对象字段、数组、类型、枚举和部分值约束，是业务 API 最常用的选择。
优势是工具链成熟：Pydantic、TypeScript Schema、OpenAPI 都能生成或消费 JSON Schema。
### 3.4 EBNF Grammar
Grammar 可以定义小语言，例如受限 SQL、DSL 或配置表达式：
```text
root   ::= "SELECT " column " FROM users"
column ::= "name" | "email" | "created_at"
```
Grammar 最强，也最容易写出“语法允许但业务危险”的规则。受限 SQL 即使语法合法，也必须经过只读账户、表级白名单和执行预算保护。
📌 **选择顺序**：能用 Choice 不用 Regex，能用 JSON Schema 不手写复杂 Grammar；约束应尽量简单、可测试。

## 4. vLLM 在线接口
先启动 OpenAI 兼容服务：
```bash
vllm serve Qwen/Qwen3-8B
```
当前官方接口支持标准风格的 `response_format`，也支持 vLLM 扩展的 `structured_outputs`。扩展字段可通过 OpenAI Python Client 的 `extra_body` 传递。
### 4.1 使用 response_format
```python
from openai import OpenAI
from pydantic import BaseModel, Field
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
class Order(BaseModel):
    sku: str = Field(pattern=r"^[A-Z]-[0-9]{2}$")
    quantity: int = Field(ge=1, le=20)
    expedited: bool
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[
        {"role": "user", "content": "订购 2 件 A-17，不加急"}
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "order",
            "schema": Order.model_json_schema(),
        },
    },
)
order = Order.model_validate_json(response.choices[0].message.content)
```
注意最后一行仍做了 Pydantic 校验。这不是多余：服务升级、客户端拼接、Schema 支持差异和异常响应都可能绕开你的理想路径。
### 4.2 使用 vLLM 扩展
```python
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "判断：库存不足"}],
    extra_body={
        "structured_outputs": {
            "choice": ["approve", "reject", "manual_review"]
        }
    },
)
```
对 Regex、Grammar 等非标准能力，`extra_body` 是保持 OpenAI Client 调用方式的实用途径。
⚠️ **版本提示**：字段命名与后端配置经历过演进。新代码优先按当前文档使用 `structured_outputs` / `response_format`，维护旧系统时再核对历史 `guided_*` 字段，不要把旧博客当成最新契约。

## 5. JSON Schema 实战
### 5.1 Schema 要小而明确
不要把整个数据库对象直接暴露给模型。推荐：
- 只保留本次任务需要的字段；
- 使用 `required` 明确必填；
- 用 `enum` 限制状态；
- 控制数组最大长度；
- 避免过深嵌套；
- 给字段写清楚描述，但不要依赖描述完成硬约束。
### 5.2 Prompt 与 Schema 要一致
如果 Prompt 要求“解释原因”，Schema 却只有 `label`，模型会在语义目标与语法目标之间拉扯。
可以把解释加入 Schema：
```python
class Decision(BaseModel):
    label: str
    reason: str
```
或者明确告诉模型只给分类结果。Schema 是护栏，Prompt 是路标，两者方向必须一致。
### 5.3 流式输出不是逐块合法 JSON
开启 `stream=True` 时，中间 Chunk 往往只是 JSON 前缀：
```text
{"sku":
```
它对完整语法是“尚未结束”，并非可独立解析的 JSON。客户端应累计增量，等完成后再解析；若要边生成边展示，应使用能处理 JSON 前缀的 UI，而不是对每个 Chunk 调 `json.loads`。

## 6. Regex 与 EBNF Grammar
### 6.1 Regex 示例
```python
result = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "生成一个订单号"}],
    extra_body={
        "structured_outputs": {
            "regex": r"ORD-(2026|2027)-[0-9]{6}"
        }
    },
)
```
正则越复杂，越要建立正反例测试集。尤其注意锚点、换行、Unicode 与 Tokenizer 对空白的处理。
### 6.2 Grammar 示例
```python
grammar = r'''
root   ::= "SELECT " column " FROM users" condition?
column ::= "name" | "email"
condition ::= " WHERE active = " ("true" | "false")
'''
result = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "查询活跃用户邮箱"}],
    extra_body={"structured_outputs": {"grammar": grammar}},
)
```
EBNF 方言和支持细节取决于实际后端。上线前应在锁定版本上编译所有 Grammar，并覆盖最长路径、空白、转义与 Unicode。
### 6.3 不要把 Grammar 当沙箱
Grammar 可以限制 SQL 形状，却不能取代数据库权限：
- 只读数据库账号；
- 可访问表和列白名单；
- 查询超时与行数上限；
- 审计日志；
- 参数化执行。
语法约束保护“怎么写”，权限系统保护“能做什么”。

## 7. 后端、缓存与性能
vLLM 的结构化输出可以由 xgrammar、guidance 等后端承载，当前版本还可能提供其他后端或自动选择逻辑。具体可用集合应以对应版本文档和 `vllm serve --help` 为准。
服务端可通过类似下面的配置选择后端：
```bash
vllm serve Qwen/Qwen3-8B \
  --structured-outputs-config.backend auto
```
### 7.1 编译成本
Schema/Grammar 首次出现时，需要编译为内部状态表示。复杂且高基数的动态 Schema 会造成：
- CPU 编译开销；
- 首请求 TTFT 上升；
- 编译缓存占用；
- 缓存命中率下降。
生产中应优先使用有限、版本化的 Schema 集合，而不是让每个用户任意上传一个新 Schema。
### 7.2 每 Token 成本
每一步都要更新状态并生成 Token Mask。高效后端会使用预计算状态、位图和缓存减少开销，但约束并非绝对免费。
约束很宽时，质量接近普通采样，却仍有状态开销；约束很窄时，候选减少可能让输出更稳定，但也可能迫使模型沿低概率路径生成。
### 7.3 后端兼容性
不同后端对 JSON Schema 关键字、Tokenizer、Grammar 方言和模型类型的覆盖并不完全相同。`auto` 能减少配置负担，但不能免除测试。
升级检查至少包括：
1. Schema 是否能编译；
2. 首次与缓存命中延迟；
3. 流式和非流式结果；
4. Unicode、转义与长数组；
5. 与 reasoning 模型组合时的行为。
若后续需要比较 SGLang 的结构化生成，只比较相同 Schema、相同模型、相同请求分布下的编译延迟与每 Token 开销，不要只看功能列表。SGLang 的 grammar backend、Frontend Language 与 Agent 组合方式见 [12.5 结构化生成与 Agent 能力](/AIInfraGuide/inference/模块四-推理优化/第12章-深入sglang/125-结构化生成与agent能力)。

## 8. 从 Grammar 到 Token Mask：把链路走完整

只说“用状态机限制输出”还不够，因为运行时面对的不是字符，而是 Tokenizer 的词表。下面把编译期与逐 Token 路径展开。

### 8.1 Grammar 的语言语义

以一个极小 JSON 子集为例：

```ebnf
root    ::= object
object  ::= "{" ws "\"ok\"" ws ":" ws boolean ws "}"
boolean ::= "true" | "false"
ws      ::= [ \t\n\r]*
```

它定义了一个语言 $\mathcal{L}(G)$：所有能从 `root` 推导出的字符序列。解析器读取前缀 $s$ 时，不只判断“$s$ 是否已经是完整句子”，还要区分三种状态：

1. **accepting**：$s\in\mathcal{L}(G)$，此时可以结束；
2. **live prefix**：$s\notin\mathcal{L}(G)$，但存在后缀 $u$ 使 $su\in\mathcal{L}(G)$；
3. **dead prefix**：不存在任何后缀能补救。

受约束解码真正要阻止的是第三种状态。前缀 `{"ok":t` 不是完整 JSON，却仍是 live prefix；`{"ok":x` 已经进入 dead prefix。

### 8.2 NFA、DFA 与带栈状态

正则表达式可以先变成 NFA，再按需确定化为 DFA。DFA 状态转移可以写成：

$$
q_{t+1}=\delta(q_t,c)
$$

其中 $c$ 是一个字符或字节。对 JSON 对象、数组这类递归结构，仅靠有限状态机不能表达无限嵌套，实际后端会组合：

- 有限状态自动机：字符串、数字、枚举、正则；
- 栈或递归语法状态：括号嵌套、对象/数组；
- Schema 状态：当前字段、必填字段集合、数组计数；
- 词法状态：是否处于字符串、转义、Unicode escape 或数字指数中。

因此“FSM”常被用作统称，但不要误以为完整 JSON Schema 必然被压成一个小型纯 DFA。实现可能是 pushdown automaton、解析表、位集和缓存状态的组合。

### 8.3 字符状态如何提升到 Token 状态

设 Tokenizer 词表为 $V$，Token $v$ 解码后的字节串为 $D(v)$。当前语法状态为 $q$，允许集合定义为：

$$
A(q)=\{v\in V\mid \delta^*(q,D(v))\neq\bot\}
$$

$\delta^*$ 表示把 Token 的全部字节依次喂给状态机，$\bot$ 表示进入死状态。关键是**整个 Token**都必须可消费，而不是首字符合法就放行。

假设词表片段是：

```text
id  decoded bytes
10  "true"
11  "false"
12  "tru"
13  "tree"
14  "}"
15  " true"
```

当前前缀为 `{"ok":`：

- Token 10、11 合法；
- Token 12 也是 live prefix，可以先生成；
- Token 13 在第四个字符进入死状态；
- Token 14 不合法，因为布尔值缺失；
- Token 15 是否合法取决于 Grammar 是否允许该位置的空白。

这也解释了为什么“字符正则测试通过”仍可能在某个 Tokenizer 上失败：Token 边界、前导空格、byte fallback 和特殊 Token 都参与判定。

### 8.4 Token healing 与词表陷阱

Prompt 最后一个 Token 可能跨越“用户文本—模型输出”的逻辑边界。例如模板结尾和目标 JSON 的第一个字符被 Tokenizer 合成一个 Token。某些后端会做 token healing 或回退重编码，避免边界把合法首 Token 锁死。

上线前要覆盖：

- UTF-8 多字节字符；
- byte fallback Token；
- 引号、反斜杠和 `\uXXXX`；
- 特殊 Token 是否可被 Grammar 意外接受；
- added tokens 与普通词表的优先级；
- Prompt 尾部空白和模板终止符。

Tokenizer Revision 是约束编译缓存键的一部分，而不是模型旁边一个无关文件。

### 8.5 从允许集合到 GPU Logit Mask

允许集合通常编码成长度为 $|V|$ 的布尔向量或位图 $m_q$：

$$
m_q[i]=
\begin{cases}
1,&i\in A(q)\\
0,&i\notin A(q)
\end{cases}
$$

采样前执行：

```python
masked_logits = where(mask, logits, -inf)
```

如果词表有 128K Token，朴素布尔数组按 1 byte 需要 128 KiB/状态；bitset 约 16 KiB/状态。真实实现还要考虑 GPU 对齐、批量状态、稀疏集合与 Mask 传输。缓存所有可达状态的全词表 Mask 可能很贵，所以后端会在以下方案间取舍：

- 预计算高频状态；
- 按需计算并缓存；
- 用 Token trie 同时遍历多个 Token 前缀；
- 以稀疏允许列表表示窄状态；
- 在 CPU 生成 Mask，再批量传给 GPU；
- 在 GPU 侧执行部分 Mask 操作。

若某状态允许 95% 词表，稀疏“允许列表”并不划算；若只允许 `true`/`false` 的几个前缀，全量扫描又很浪费。后端性能来自表示选择，不只是“用了 C++”。

### 8.6 一次生成循环的伪代码

```python
compiled = compile_schema(schema, tokenizer)
state = compiled.initial_state()

while not state.accepting:
    logits = model.forward(next_input)
    mask = compiled.token_mask(state)
    if not mask.any():
        raise ConstraintDeadEnd(state, generated)
    token_id = sampler(mask_logits(logits, mask), params)
    emitted = tokenizer.token_bytes(token_id)
    state = compiled.advance(state, emitted)
    generated.append(token_id)
    next_input = token_id
```

生产实现会批处理多个请求；批中每个请求可能处于不同语法状态，因此要生成二维 Mask 或状态索引：

$$
M\in\{0,1\}^{B\times |V|}
$$

这正是受约束请求与普通请求混批时的额外成本来源。

## 9. 首请求编译与每 Token 成本推导

### 9.1 延迟拆分

把一次约束请求的端到端时间写成：

$$
T_{\text{request}}
=T_{\text{queue}}
+T_{\text{template}}
+\mathbf{1}_{\text{miss}}T_{\text{compile}}
+T_{\text{prefill}}
+\sum_{t=1}^{L}(T_{\text{decode},t}+T_{\text{mask},t}+T_{\text{advance},t})
+T_{\text{serialize}}
$$

冷请求额外支付 $T_{\text{compile}}$；热请求仍要支付每步状态推进和 Mask 成本。于是：

$$
\Delta T_{\text{cold}}\approx T_{\text{compile}}+L\bar T_{\text{guided-token}}
$$

$$
\Delta T_{\text{hot}}\approx L\bar T_{\text{guided-token}}
$$

其中：

$$
\bar T_{\text{guided-token}}
=\bar T_{\text{mask}}
+\bar T_{\text{advance}}
+\bar T_{\text{sync}}
$$

`sync` 包含 CPU/GPU 边界、批处理等待和 Mask 搬运，常常比纯状态转移更值得关注。

### 9.2 编译复杂度来自哪里

编译成本不是只看 Schema 字节数。主要驱动项包括：

- `$ref` 展开后的节点数；
- `oneOf` / `anyOf` 分支数；
- 大型 `enum` 的总字符和公共前缀；
- Regex 的状态数与确定化膨胀；
- 对象可选字段造成的排列；
- 数组边界与递归深度；
- Tokenizer 词表大小及 Token trie 构建；
- 后端是否已缓存同构结构。

一个 2 KiB、含 500 个枚举值的 Schema，可能比 20 KiB 的线性对象更难编译。

### 9.3 缓存命中模型

设编译缓存命中率为 $h$，平均额外首请求成本：

$$
E[\Delta T_{\text{first}}]=(1-h)T_{\text{compile}}+L\bar T_{\text{guided-token}}
$$

若租户每次把描述文字、字段顺序或无关元数据写成不同 Schema，语义相同也可能得到不同 Hash，$h$ 会下降。应先规范化：

```text
remove non-semantic metadata
canonicalize key order
resolve stable $ref
attach schema_version
hash(canonical_schema, tokenizer_revision, backend_version)
```

不能只用 Schema 文本 Hash：相同 Grammar 在不同 Tokenizer 下对应不同 Token Mask。

### 9.4 每 Token 成本何时显著

设普通 Decode 每 Token 为 $T_d$，约束开销占比：

$$
\rho=\frac{T_m+T_a+T_s}{T_d}
$$

大模型 Decode 很慢时，固定 Mask 成本可能被隐藏；小模型、低并发、极快 GPU 或 Speculative Decoding 下，$T_d$ 下降，$\rho$ 反而上升。只在 70B 模型上得出“约束免费”的结论，不能外推到 1B 路由模型。

Batch 也会改变结论。若同一状态可共享 Mask，摊销很好；若每个请求使用动态 Schema 且状态不同，Mask 生成与传输更接近 $O(B|V|)$。

### 9.5 如何测而不是猜

至少测四组：

```text
plain                       # 无约束基线
guided-cold-unique          # 每次唯一 Schema
guided-hot-same-schema      # 编译缓存命中
guided-hot-divergent-state  # 同 Schema、不同输出前缀
```

报告：

- Schema compile wall time 与 CPU time；
- cache hit/miss；
- TTFT cold/hot；
- TPOT 与 inter-token latency；
- Mask 生成、应用、状态推进时间；
- Batch size 和每批唯一 Grammar 状态数；
- GPU 利用率、CPU 核利用率；
- Schema 有效通过率与任务正确率。

## 10. XGrammar 与 guidance：比较执行模型，不比功能勾选

vLLM 的可选后端与默认值会变化，下面比较的是稳定的工程维度，不承诺某版本的固定支持矩阵。

### 10.1 XGrammar 的典型取向

XGrammar 面向高吞吐推理中的结构化生成，重点通常包括：

- 将 Grammar 编译为高效内部表示；
- Tokenizer-aware 的合法 Token 计算；
- bitmask 与批处理友好的运行路径；
- 编译结果和状态 Mask 缓存；
- 与 GPU Logit Mask 应用协作。

它适合把“每 Token 约束”放在高并发服务热路径中评估。收益是否兑现，取决于目标 Schema、Tokenizer、Batch 和 vLLM 集成版本。

### 10.2 guidance 的典型取向

guidance 生态强调用 Grammar/模板组织生成过程，也能作为约束后端参与 token-level decoding。它的价值不只是某个 JSON Schema 关键字，而是：

- 表达生成控制流；
- 将文本片段和受约束变量组合；
- 支持正则、选择与 Grammar；
- 在 Python/应用编排中有更丰富的控制抽象。

当它作为 vLLM 后端使用时，应只比较引擎实际调用的那条热路径；不要把 guidance 上层语言能力与 XGrammar 内核性能混成一个“谁功能更多”的问题。

### 10.3 公平基准

公平比较必须固定：

```text
vLLM commit/version
backend version
model + tokenizer revision
GPU and CPU affinity
schema canonical bytes
prompt/output token lengths
concurrency and batch policy
cache warmness
streaming mode
seed and sampling params
```

测试集合至少包含：

1. 小型枚举对象；
2. 大枚举且有公共前缀；
3. 深层嵌套数组/对象；
4. Unicode 与转义密集字符串；
5. 多分支 `oneOf`；
6. 业务实际 Schema。

比较编译 P50/P99、热 TPOT、CPU 占用、缓存内存、失败语义与关键字覆盖。若后端 A 不支持某 Schema，结果应记为“不兼容”，不能悄悄改小 Schema 后宣称更快。

### 10.4 兼容性比峰值更先

需要逐项验证：

- unsupported keyword 是报错、忽略还是降级；
- `additionalProperties: false` 是否严格执行；
- 数字范围与浮点格式；
- 字符串 `pattern`、`format` 的支持语义；
- 递归 `$ref`；
- 非 ASCII 属性名；
- nullable/union 的具体方言；
- 达到 `max_tokens` 时返回何种 finish reason。

“生成出来看似是 JSON”不是 Schema 兼容测试。

## 11. 完整 JSON Schema 可复现实验

下面的实验同时验证嵌套对象、枚举、范围、数组长度、Regex 和禁止额外字段。

### 11.1 环境与服务

```bash
python -m venv .venv
source .venv/bin/activate
pip install -U vllm openai pydantic httpx
python -c 'import vllm; print(vllm.__version__)'
vllm serve Qwen/Qwen3-8B \
  --host 127.0.0.1 \
  --port 8000 \
  --structured-outputs-config.backend auto
```

最后一个参数的精确 CLI 拼写属于版本边界。若目标版本不接受，先运行 `vllm serve --help`，按该版本文档配置后端；不要静默删掉约束继续测试。

### 11.2 实验脚本

```python
import json
import statistics
import time

from openai import OpenAI
from pydantic import BaseModel, ConfigDict, Field
from typing import Literal


class Item(BaseModel):
    model_config = ConfigDict(extra="forbid")
    sku: str = Field(pattern=r"^[A-Z]{2}-[0-9]{4}$")
    quantity: int = Field(ge=1, le=20)


class Shipping(BaseModel):
    model_config = ConfigDict(extra="forbid")
    method: Literal["standard", "express"]
    address_id: str = Field(pattern=r"^addr_[a-f0-9]{8}$")


class Order(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^ord_[0-9]{8}$")
    currency: Literal["CNY", "USD"]
    items: list[Item] = Field(min_length=1, max_length=3)
    shipping: Shipping
    note: str | None = Field(default=None, max_length=40)


client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")
schema = Order.model_json_schema()
prompt = """
生成测试订单：订单号 ord_20260813，人民币；
商品 AB-0042 两件、ZX-9001 一件；
快递，地址 addr_deadbeef；备注留空。
只根据这些信息填写。
""".strip()


def once():
    start = time.perf_counter()
    response = client.chat.completions.create(
        model="Qwen/Qwen3-8B",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,
        max_tokens=256,
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name": "order_v1",
                "strict": True,
                "schema": schema,
            },
        },
    )
    elapsed_ms = (time.perf_counter() - start) * 1000
    message = response.choices[0].message
    order = Order.model_validate_json(message.content)
    return elapsed_ms, response.usage, order


samples = []
for i in range(11):
    elapsed_ms, usage, order = once()
    print(i, round(elapsed_ms, 2), usage, order.model_dump())
    if i:
        samples.append(elapsed_ms)

print({
    "warm_p50_ms": statistics.median(samples),
    "warm_max_ms": max(samples),
    "schema_sha_input": json.dumps(schema, sort_keys=True),
})
```

### 11.3 预期断言

不能只断言 `json.loads` 成功，应断言：

```python
assert order.order_id == "ord_20260813"
assert order.currency == "CNY"
assert len(order.items) == 2
assert order.items[0].sku == "AB-0042"
assert order.shipping.method == "express"
assert order.shipping.address_id == "addr_deadbeef"
assert order.note is None
```

再构造负例：让 Prompt 要求第四个商品、非法地址或 `quantity=30`。观察模型是否选择合法替代、遗漏语义，或因 Token 预算结束。约束会保证形式，却可能“修正”为一个业务上错误的合法值，所以必须对照输入做语义断言。

### 11.4 冷热编译实验

依次运行：

1. 重启服务后首次请求，记录冷 TTFT；
2. 相同 Schema 连续请求，记录热值；
3. 只改变 `name`，观察缓存键是否受影响；
4. 改变属性描述但不改变约束，观察是否重新编译；
5. 每次增加一个唯一 enum，模拟高基数租户；
6. 恢复第一个 Schema，验证是否被 LRU 驱逐。

若 API 不返回 compile 指标，可同时采集服务日志/Trace，并以“总 TTFT 差值”作为上界，不要把整个差值都归因于编译。

### 11.5 每 Token 实验

设计相同输出长度的两类 Schema：

- **窄路径**：每个字段几乎只有一个合法值；
- **宽路径**：字符串和枚举允许大量 Token。

固定 Prompt、输出 Token 数、并发，比较热缓存 TPOT。再把并发从 1 提升到 8、32，记录每批唯一状态数。这样能区分“编译慢”和“每步 Mask 慢”。

## 12. 失败模式与工程边界
### 12.1 Schema 无解
Prompt、最大生成长度和 Schema 可能共同造成无解。例如要求输出 100 个对象，却只给 20 个 Token 预算。此时应返回明确错误或截断状态，不能假设结果仍合法。
### 12.2 Schema 太复杂
深层递归、巨大枚举和大量分支会增加编译与状态空间。拆成“先分类、再按分类使用小 Schema”通常更容易运维。
### 12.3 合法幻觉
模型可以生成：
```json
{"sku":"A-17","quantity":999999,"expedited":true}
```
即使它通过语法约束，也可能违反库存、额度或用户权限。接收端必须继续做领域校验。
### 12.4 解析链路不一致
服务端约束用一个 Schema，客户端却用旧版类型，会出现“服务端合法、客户端拒绝”。Schema 应版本化并与客户端代码一起发布。
### 12.5 把响应原文直接执行
结构化只是数据边界，不是信任边界。文件路径、URL、SQL、Shell 参数和工具调用参数都要二次校验与授权。
---

### 12.6 后端静默忽略关键字

最危险的兼容方式不是明确报错，而是接受 Schema 却忽略 `pattern`、范围或额外字段限制。上线门禁应为每个关键字准备必过正例和必拒负例。

### 12.7 编译缓存污染与 DoS

允许用户提交任意高复杂度 Schema，会把结构化输出接口变成 CPU 和内存放大器。控制措施包括：

- Schema 字节、节点、分支、枚举总长度上限；
- 编译超时与并发隔离；
- 只允许注册过的 `schema_id`；
- 每租户缓存配额；
- 编译失败负缓存；
- 避免失败请求无限重试。

### 12.8 截断与取消

客户端取消、网关超时或 `max_tokens` 用尽时，已生成内容可能只是合法前缀，不是完整实例。响应必须携带明确结束原因；客户端只在正常接受状态下提交业务对象。

## 13. 选型、观测与版本门禁
| 需求 | 推荐约束 | 主要代价 |
|---|---|---|
| 三分类 | Choice | 表达能力有限 |
| 订单号/日期 | Regex | 复杂结构难维护 |
| 业务对象 | JSON Schema | 编译与 Schema 兼容性 |
| 小型 DSL | EBNF Grammar | 规则复杂、测试成本高 |
| 自由文本 | 无硬约束 | 需要后处理与容错 |
调优时关注四组指标：
- **正确性**：解析成功率、Schema 校验通过率、业务校验通过率；
- **延迟**：冷编译 TTFT、热缓存 TTFT、TPOT；
- **资源**：CPU 编译时间、缓存大小、GPU Mask 开销；
- **质量**：约束前后任务成功率，而不只是 JSON 合法率。

建议建立以下仪表盘：

```text
structured_compile_seconds{backend,schema_id,result}
structured_compile_cache_hit_total{backend,schema_id}
structured_mask_seconds{backend}
structured_dead_end_total{schema_id,state}
structured_finish_total{finish_reason,schema_id}
structured_validation_total{stage,result,schema_version}
```

请求 Trace 至少关联 `schema_id`、规范化 Hash、后端、Tokenizer Revision、compile cache hit、最终接受状态。不要把完整、可能含租户隐私的动态 Schema 无限制写进日志。

### 13.1 版本边界

以下都必须按部署版本核对：

- vLLM 的 `structured_outputs`、历史 `guided_*` 与 OpenAI `response_format` 映射；
- `--structured-outputs-config` 的字段和 backend 默认值；
- xgrammar/guidance 的可用性与版本；
- 支持的 JSON Schema 方言及关键字；
- `strict` 是否被透传及其具体含义；
- streaming、reasoning 与 tool calling 的组合支持；
- 错误码和 finish reason。

文中公式与状态机机制稳定，CLI 名称和支持矩阵不是稳定 API。发布清单应保存 `vllm --version`、依赖锁文件和服务启动参数。

### 13.2 升级门禁

升级前后对同一黄金集比较：

1. 所有正例可完成且客户端校验通过；
2. 所有负例不能穿透关键约束；
3. 冷编译 P99 不超过预算；
4. 热 TPOT 回归不超过阈值；
5. 缓存内存和驱逐率无异常；
6. streaming 聚合结果与非流式等价；
7. 截断、取消和 dead-end 返回可识别错误；
8. 业务正确率没有因“更严格合法”而下降。

📌 **实践建议**：先用最小约束解决真实失败，再逐步加严。过度复杂的 Schema 可能把模型“锁”进合法但低质量的角落。

## 📝 总结
- 提示词只能提高格式正确的概率，Constrained Decoding 在采样前屏蔽不合法 Token。
- 约束引擎维护语法状态，并将允许 Token 集合应用到每一步 Logits。
- Choice、Regex、JSON Schema、EBNF Grammar 分别适合从简单分类到小型语言的不同任务。
- vLLM 在线接口优先使用 `response_format` 和 `structured_outputs`，扩展字段通过 `extra_body` 传入。
- xgrammar、guidance 等后端的支持范围与参数会演进，应锁版本并做回归。
- 结构合法不代表业务正确、安全或事实可信，接收端校验永远不能省。
