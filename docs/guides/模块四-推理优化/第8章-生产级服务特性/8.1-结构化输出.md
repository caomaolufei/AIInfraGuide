让模型“只返回 JSON”很容易，让它在第一万次请求仍返回**可解析且符合 Schema 的 JSON**很难。
提示词只能表达愿望。模型仍可能多说一句“当然可以”、漏掉右括号，或者把数字写成字符串。生产系统若把这段文本直接交给解析器，失败会一路传到重试、队列和用户延迟。
结构化输出换了一种思路：不在生成后祈祷，而是在生成时限制每一步能选的 Token。
<!-- more -->

## 1. 提示约束为什么不够
假设订单接口需要：
```json
{"sku":"A-17","quantity":2,"expedited":false}
```
只写“请输出 JSON”至少有四类风险：
1. **语法风险**：缺引号、缺逗号、括号不配对；
2. **形状风险**：字段缺失、多字段、嵌套层级错误；
3. **类型风险**：`quantity` 变成 `"two"`；
4. **语义风险**：SKU 格式合法，但仓库根本没有这个商品。
受约束解码主要解决前三类中的“可由语法描述的部分”。第四类仍要业务系统校验。
类比一下：提示词像在考场门口贴“请勿带手机”，受约束解码像安检门。前者影响行为概率，后者直接阻止不合法对象通过。但安检门只能判断“像不像手机”，不能判断来访者有没有恶意。
📌 **关键点**：结构化输出保证的是**形式约束**，不是事实正确性、权限正确性或业务可执行性。
---

## 2. Constrained Decoding 的机制
普通采样在每一步得到词表大小的 Logits：
$$ p(x_t \mid x_{<t}) = \operatorname{softmax}(z_t) $$
受约束解码多做一步：根据当前已生成前缀和语法状态，算出允许 Token 集合 $A_t$，把其他 Token 的 Logit 设为负无穷：
$$ z'_t(i)= \begin{cases} z_t(i), & i \in A_t \\ -\infty, & i \notin A_t \end{cases} $$
之后 Temperature、Top-k、Top-p 等采样只在合法集合内工作。
例如已输出：
```text
{"quantity":
```
Schema 规定 `quantity` 是整数，那么 `"two"` 的开引号不能被选中；数字、负号或符合规则的空白仍可进入候选。
### 2.1 难点不在字符，而在 Token
模型不是逐字符生成，而是逐 Token 生成。一个 Token 可能是：
- 单个字符；
- 多个数字；
- 一段带前导空格的文本；
- 甚至同时跨过几个语法字符。
因此约束引擎不能只问“下一个字符是否合法”，还要判断“这个 Token 解码成的字符序列能否让语法状态继续前进”。
### 2.2 状态机如何参与每一步
约束后端通常会：
1. 把 JSON Schema、Regex 或 Grammar 编译成可匹配结构；
2. 维护每个请求当前的语法状态；
3. 为当前状态计算允许 Token 的位图；
4. 在 GPU 采样前应用位图；
5. 接收选中 Token，推进状态；
6. 到达接受状态后允许结束。
可以把它想成导航系统：模型仍决定走哪条风景更好的路，但导航把“逆行、断头路、未开放道路”从候选路线里划掉。
### 2.3 合法不代表自然
约束越强，模型自由度越小。当合法集合中只剩一个 Token 时，Temperature 已没有作用；当 Schema 与模型常见表达冲突时，生成虽然合法，却可能拗口或质量下降。
🔑 **核心概念**：Constrained Decoding 不是生成后修复，而是**在每次采样前改变候选空间**。

## 3. 四种常用约束
vLLM 当前结构化输出文档主要展示四类约束。
### 3.1 Choice
输出必须精确等于候选之一：
```python
extra_body={
    "structured_outputs": {
        "choice": ["approve", "reject", "manual_review"]
    }
}
```
适合分类、路由和有限状态决策。它比让模型生成长解释再做字符串匹配可靠得多。
### 3.2 Regex
输出必须匹配正则：
```python
extra_body={
    "structured_outputs": {
        "regex": r"ORD-[0-9]{8}"
    }
}
```
适合短格式：订单号、日期、固定标签。正则能描述局部模式，但不擅长复杂递归结构。
### 3.3 JSON Schema
Schema 能描述对象字段、数组、类型、枚举和部分值约束，是业务 API 最常用的选择。
优势是工具链成熟：Pydantic、TypeScript Schema、OpenAPI 都能生成或消费 JSON Schema。
### 3.4 EBNF Grammar
Grammar 可以定义小语言，例如受限 SQL、DSL 或配置表达式：
```text
root   ::= "SELECT " column " FROM users"
column ::= "name" | "email" | "created_at"
```
Grammar 最强，也最容易写出“语法允许但业务危险”的规则。受限 SQL 即使语法合法，也必须经过只读账户、表级白名单和执行预算保护。
📌 **选择顺序**：能用 Choice 不用 Regex，能用 JSON Schema 不手写复杂 Grammar；约束应尽量简单、可测试。

## 4. vLLM 在线接口
先启动 OpenAI 兼容服务：
```bash
vllm serve Qwen/Qwen3-8B
```
当前官方接口支持标准风格的 `response_format`，也支持 vLLM 扩展的 `structured_outputs`。扩展字段可通过 OpenAI Python Client 的 `extra_body` 传递。
### 4.1 使用 response_format
```python
from openai import OpenAI
from pydantic import BaseModel, Field
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
class Order(BaseModel):
    sku: str = Field(pattern=r"^[A-Z]-[0-9]{2}$")
    quantity: int = Field(ge=1, le=20)
    expedited: bool
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[
        {"role": "user", "content": "订购 2 件 A-17，不加急"}
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "order",
            "schema": Order.model_json_schema(),
        },
    },
)
order = Order.model_validate_json(response.choices[0].message.content)
```
注意最后一行仍做了 Pydantic 校验。这不是多余：服务升级、客户端拼接、Schema 支持差异和异常响应都可能绕开你的理想路径。
### 4.2 使用 vLLM 扩展
```python
response = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "判断：库存不足"}],
    extra_body={
        "structured_outputs": {
            "choice": ["approve", "reject", "manual_review"]
        }
    },
)
```
对 Regex、Grammar 等非标准能力，`extra_body` 是保持 OpenAI Client 调用方式的实用途径。
⚠️ **版本提示**：字段命名与后端配置经历过演进。新代码优先按当前文档使用 `structured_outputs` / `response_format`，维护旧系统时再核对历史 `guided_*` 字段，不要把旧博客当成最新契约。

## 5. JSON Schema 实战
### 5.1 Schema 要小而明确
不要把整个数据库对象直接暴露给模型。推荐：
- 只保留本次任务需要的字段；
- 使用 `required` 明确必填；
- 用 `enum` 限制状态；
- 控制数组最大长度；
- 避免过深嵌套；
- 给字段写清楚描述，但不要依赖描述完成硬约束。
### 5.2 Prompt 与 Schema 要一致
如果 Prompt 要求“解释原因”，Schema 却只有 `label`，模型会在语义目标与语法目标之间拉扯。
可以把解释加入 Schema：
```python
class Decision(BaseModel):
    label: str
    reason: str
```
或者明确告诉模型只给分类结果。Schema 是护栏，Prompt 是路标，两者方向必须一致。
### 5.3 流式输出不是逐块合法 JSON
开启 `stream=True` 时，中间 Chunk 往往只是 JSON 前缀：
```text
{"sku":
```
它对完整语法是“尚未结束”，并非可独立解析的 JSON。客户端应累计增量，等完成后再解析；若要边生成边展示，应使用能处理 JSON 前缀的 UI，而不是对每个 Chunk 调 `json.loads`。

## 6. Regex 与 EBNF Grammar
### 6.1 Regex 示例
```python
result = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "生成一个订单号"}],
    extra_body={
        "structured_outputs": {
            "regex": r"ORD-(2026|2027)-[0-9]{6}"
        }
    },
)
```
正则越复杂，越要建立正反例测试集。尤其注意锚点、换行、Unicode 与 Tokenizer 对空白的处理。
### 6.2 Grammar 示例
```python
grammar = r'''
root   ::= "SELECT " column " FROM users" condition?
column ::= "name" | "email"
condition ::= " WHERE active = " ("true" | "false")
'''
result = client.chat.completions.create(
    model="Qwen/Qwen3-8B",
    messages=[{"role": "user", "content": "查询活跃用户邮箱"}],
    extra_body={"structured_outputs": {"grammar": grammar}},
)
```
EBNF 方言和支持细节取决于实际后端。上线前应在锁定版本上编译所有 Grammar，并覆盖最长路径、空白、转义与 Unicode。
### 6.3 不要把 Grammar 当沙箱
Grammar 可以限制 SQL 形状，却不能取代数据库权限：
- 只读数据库账号；
- 可访问表和列白名单；
- 查询超时与行数上限；
- 审计日志；
- 参数化执行。
语法约束保护“怎么写”，权限系统保护“能做什么”。

## 7. 后端、缓存与性能
vLLM 的结构化输出可以由 xgrammar、guidance 等后端承载，当前版本还可能提供其他后端或自动选择逻辑。具体可用集合应以对应版本文档和 `vllm serve --help` 为准。
服务端可通过类似下面的配置选择后端：
```bash
vllm serve Qwen/Qwen3-8B \
  --structured-outputs-config.backend auto
```
### 7.1 编译成本
Schema/Grammar 首次出现时，需要编译为内部状态表示。复杂且高基数的动态 Schema 会造成：
- CPU 编译开销；
- 首请求 TTFT 上升；
- 编译缓存占用；
- 缓存命中率下降。
生产中应优先使用有限、版本化的 Schema 集合，而不是让每个用户任意上传一个新 Schema。
### 7.2 每 Token 成本
每一步都要更新状态并生成 Token Mask。高效后端会使用预计算状态、位图和缓存减少开销，但约束并非绝对免费。
约束很宽时，质量接近普通采样，却仍有状态开销；约束很窄时，候选减少可能让输出更稳定，但也可能迫使模型沿低概率路径生成。
### 7.3 后端兼容性
不同后端对 JSON Schema 关键字、Tokenizer、Grammar 方言和模型类型的覆盖并不完全相同。`auto` 能减少配置负担，但不能免除测试。
升级检查至少包括：
1. Schema 是否能编译；
2. 首次与缓存命中延迟；
3. 流式和非流式结果；
4. Unicode、转义与长数组；
5. 与 reasoning 模型组合时的行为。
若后续需要比较 SGLang 的结构化生成，只比较相同 Schema、相同模型、相同请求分布下的编译延迟与每 Token 开销，不要只看功能列表。SGLang 的 grammar backend、Frontend Language 与 Agent 组合方式见 [12.5 结构化生成与 Agent 能力](/AIInfraGuide/inference/模块四-推理优化/第12章-深入sglang/125-结构化生成与agent能力)。

## 8. 失败模式与工程边界
### 8.1 Schema 无解
Prompt、最大生成长度和 Schema 可能共同造成无解。例如要求输出 100 个对象，却只给 20 个 Token 预算。此时应返回明确错误或截断状态，不能假设结果仍合法。
### 8.2 Schema 太复杂
深层递归、巨大枚举和大量分支会增加编译与状态空间。拆成“先分类、再按分类使用小 Schema”通常更容易运维。
### 8.3 合法幻觉
模型可以生成：
```json
{"sku":"A-17","quantity":999999,"expedited":true}
```
即使它通过语法约束，也可能违反库存、额度或用户权限。接收端必须继续做领域校验。
### 8.4 解析链路不一致
服务端约束用一个 Schema，客户端却用旧版类型，会出现“服务端合法、客户端拒绝”。Schema 应版本化并与客户端代码一起发布。
### 8.5 把响应原文直接执行
结构化只是数据边界，不是信任边界。文件路径、URL、SQL、Shell 参数和工具调用参数都要二次校验与授权。

## 9. 选型与权衡
| 需求 | 推荐约束 | 主要代价 |
|---|---|---|
| 三分类 | Choice | 表达能力有限 |
| 订单号/日期 | Regex | 复杂结构难维护 |
| 业务对象 | JSON Schema | 编译与 Schema 兼容性 |
| 小型 DSL | EBNF Grammar | 规则复杂、测试成本高 |
| 自由文本 | 无硬约束 | 需要后处理与容错 |
调优时关注四组指标：
- **正确性**：解析成功率、Schema 校验通过率、业务校验通过率；
- **延迟**：冷编译 TTFT、热缓存 TTFT、TPOT；
- **资源**：CPU 编译时间、缓存大小、GPU Mask 开销；
- **质量**：约束前后任务成功率，而不只是 JSON 合法率。
📌 **实践建议**：先用最小约束解决真实失败，再逐步加严。过度复杂的 Schema 可能把模型“锁”进合法但低质量的角落。

## 📝 总结
- 提示词只能提高格式正确的概率，Constrained Decoding 在采样前屏蔽不合法 Token。
- 约束引擎维护语法状态，并将允许 Token 集合应用到每一步 Logits。
- Choice、Regex、JSON Schema、EBNF Grammar 分别适合从简单分类到小型语言的不同任务。
- vLLM 在线接口优先使用 `response_format` 和 `structured_outputs`，扩展字段通过 `extra_body` 传入。
- xgrammar、guidance 等后端的支持范围与参数会演进，应锁版本并做回归。
- 结构合法不代表业务正确、安全或事实可信，接收端校验永远不能省。
