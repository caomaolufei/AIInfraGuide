## 本章简介

前几章解决的是“模型怎样跑得快、装得下”，本章处理的是另一半生产问题：**模型怎样稳定地成为一个可编程服务**。

真实应用不会满足于一段看起来正确的自然语言。订单系统要合法 JSON，Agent 要调用正确的函数，多租户平台要在同一底座上切换 LoRA，视觉助手要接住图片，搜索与评分服务还要精确控制候选 Token。任一环节只靠提示词“劝模型听话”，都可能在边界输入上失效。

可以把推理服务想成一座现代港口：

- 结构化输出是海关规则，决定什么格式的货物可以放行；
- Tool Calling 与 Parser 是报关单翻译器，把模型文本变成应用可执行的动作；
- Multi-LoRA 是可快速更换的生产模具，一套底座服务多个业务；
- 多模态 Encoder 是货物预处理区，把图片、音频或视频变成语言模型能消费的表示；
- 采样与解码是调度规则，决定每一步从哪些候选里选出下一个 Token。

这些能力互相独立又会叠加。例如，一个视觉 Agent 可能先编码图片，再输出工具调用；工具参数又需要 JSON Schema 约束；不同租户还要选择不同 LoRA。生产设计不能只验证“单项功能能跑”，还要验证组合后的协议、显存、延迟与失败模式。

## 本章边界

本章以 **vLLM 当前官方文档与 OpenAI 兼容接口**为主，重点解释稳定的机制与使用方式。命令行参数、受支持模型和 Parser 名称会随版本演进，因此文中的示例是检查点，不是永恒契约：

1. 部署时锁定 vLLM 版本；
2. 查对应版本文档与 `vllm serve --help`；
3. 用目标模型、Chat Template 和真实请求做回归测试；
4. 升级时重新验证流式输出、并行调用和显存峰值。

后续 SGLang 专章会从另一套引擎的视角讨论相应能力。本章只在有必要时指出比较维度，不提前展开，也不创建跨章内容。

## 学习建议

不要只记参数名。建议每节都回答三个问题：

1. 这项能力在 Token 生成链路的哪一层生效？
2. 它把“不确定性”转移到了哪里？
3. 它增加的是 CPU、GPU、显存、网络，还是协议复杂度？

带着这三个问题阅读，你会发现生产特性并非彼此孤立。结构化输出在采样前改 Logits，Tool Parser 在采样后解释文本，LoRA 在模型层改变权重，多模态 Encoder 在语言模型前生成输入表示。定位不同，故障排查路径也完全不同。

## 贯穿本章的生产原则

- **协议兼容不等于行为一致**：OpenAI 兼容描述的是请求与响应形状，不保证所有模型都具备同样的工具调用能力。
- **语法合法不等于业务正确**：JSON Schema 能保证类型和字段，不能保证库存真的存在。
- **缓存命中不等于免费**：缓存占内存，也需要 Hash、查找、复制和淘汰。
- **动态加载不等于无成本切换**：LoRA 的搬运、校验和槽位竞争会进入尾延迟。
- **参数可用不等于适合在线服务**：Beam Search 与全词表 Logprobs 都可能显著放大资源消耗。
- **模型能力与引擎能力必须成对验证**：引擎能解析某种格式，不代表模型会稳定地产生该格式。

## 本章完成后的能力

学完本章，你应当能够：

- 为 API 设计合适的结构化输出约束，并区分语法校验与业务校验；
- 搭建一次完整的工具调用循环，而不是只拿到一个函数名；
- 估算 Multi-LoRA 的槽位、秩和缓存对显存与延迟的影响；
- 画出 VLM 从媒体输入到文本输出的缓存与计算链路；
- 根据任务目标选择采样参数，并解释为什么某组参数会更慢或更随机；
- 为 vLLM 升级建立针对 Parser、Schema、多模态和解码行为的回归测试。
