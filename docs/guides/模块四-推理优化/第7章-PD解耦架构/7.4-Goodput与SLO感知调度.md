## 📑 本节目标

推理服务最常见的误判是： “吞吐涨了，所以系统更好了。” 如果完成的请求中有一半首 token 等了 10 秒， 这些请求对交互业务可能已经没有价值。 本节会：

- 定义请求级 SLO 与 Goodput。
- 区分 Throughput、Goodput 和 SLO attainment。
- 用手算解释为何超载后 Goodput 反而下降。
- 设计阶段感知路由、准入和降级策略。
- 用 `vllm bench serve` 建立可核实的负载曲线。

## 1. 快递类比

一家快递站一天处理 10,000 件包裹， 听起来吞吐很高。 但若承诺“当日达”， 只有 6,000 件按时到达， 真正符合服务承诺的产出只有 6,000 件。 LLM 请求也一样。 完成了但 TTFT 超时， 用户已经离开。 生成完但 TPOT 太高， 用户看到的是断断续续的输出。 因此系统优化目标应从“处理多少”升级为“按时处理多少”。

## 2. 三类基础指标

### 2.1 Throughput

常见形式包括：

- 完成请求数 / 秒。
- 输入 token / 秒。
- 输出 token / 秒。
- 总 token / 秒。

它描述系统做了多少工作， 不直接描述每个用户等了多久。

### 2.2 SLO attainment

设观测窗口内有 \(N\) 个有效请求， 满足全部 SLO 的请求数为 \(N_{good}\)。

\[
Attainment=\frac{N_{good}}{N}
\]

例如 1000 个请求中 920 个达标：

\[
Attainment=92\%
\]

### 2.3 观测 Goodput

设观测窗口长度为 \(\Delta t\)：

\[
Goodput=\frac{N_{good}}{\Delta t}
\]

单位通常是 req/s。 它同时体现完成量与达标比例。 若总吞吐为 12 req/s， 达标率为 75%：

\[
Goodput=12\times75\%=9\text{ req/s}
\]

## 3. 一个请求怎样算 good

设业务定义：

- \(S_{TTFT}=800\) ms。
- \(S_{TPOT}=50\) ms/token。
- \(S_{E2E}=12\) s。

对请求 \(i\)，定义：

\[
good_i= \mathbb{1}( TTFT_i<S_{TTFT} \land TPOT_i<S_{TPOT} \land E2E_i<S_{E2E})
\]

任一条件失败， 该请求就不计入 Goodput。 是否使用 `<` 还是 `<=` 应在组织内统一。 更重要的是， SLO 必须在压测前定义，不能看完结果再挑阈值。

## 4. TPOT 与 ITL 的边界

TPOT 常按首 token 到末 token 的平均间隔计算。 它适合请求级 SLO， 也被 vLLM Goodput 参数直接支持。 但平均会隐藏一次长停顿。 例如 5 个 ITL：

```text
20, 20, 220, 20, 20 ms
```

平均 ITL 为 60 ms， 但用户实际经历一次 220 ms 卡顿。 因此生产看板建议同时保留：

- 请求级 TPOT SLO。
- token 级 ITL P95/P99。
- 最大单次 stall。

这里计算的是**观测 Goodput（observed request goodput）**：在一个已经完成的压测窗口里，每秒有多少请求同时满足全部 SLO。它是核心容量指标，不是唯一体验指标。

## 5. 为什么超载后 Goodput 会下降

假设服务的物理吞吐上限约 10 req/s。 当输入 6 req/s：

- 完成吞吐约 6 req/s。
- 98% 达标。
- Goodput 约 5.88 req/s。

当输入 10 req/s：

- 完成吞吐约 9.8 req/s。
- 92% 达标。
- Goodput 约 9.02 req/s。

当输入 14 req/s：

- 完成吞吐仍约 10 req/s。
- 排队使达标率跌到 40%。
- Goodput 只剩 4 req/s。

系统更忙了， 有效产出却比输入 10 req/s 时更低。 这就是容量曲线的“拥塞悬崖”。

## 6. P/D 解耦中的双 SLO

Prefill 主要影响：

- 排队到开始 Prefill。
- Prefill 执行。
- KV handoff。
- 首个 Decode step。

这些共同构成 TTFT。 Decode 主要影响：

- 每步排队。
- Batch 执行时间。
- KV 读取与增长。
- 流式传输。

这些共同构成 TPOT/ITL。 解耦后可以分别观察：

\[
TTFT=T_{queue,P}+T_{prefill}+T_{xfer}+T_{queue,D}+T_{first,D}
\]

\[
TPOT\approx T_{queue\ per\ step,D}+T_{execute,D}
\]

若只测 P 实例的 Prefill 时间， 会漏掉 KV 和 D 交接。

## 7. 容量 Goodput 的正式表述

DistServe 一类论文还会使用另一种口径：在给定 SLO attainment 下，系统可承载的**最大到达率**。为避免和上一节的观测值混淆，本文称它为 capacity goodput。可写成：

\[
\max_{\lambda}\ \lambda
\]

满足同一批请求的联合约束：

\[
P(TTFT\le S_{TTFT}\land TPOT\le S_{TPOT})\ge p
\]

其中 \(p\) 例如 90% 或 99%。如果比较不同 GPU 数量的系统，还应报告：

\[
Goodput_{\text{per-GPU}}=\frac{\lambda_{\max}}{N_{\text{GPU}}}
\]

工程上通常通过离散负载扫描近似求解，而不是期待一个闭式公式。报告时必须写清是在说“窗口内达标请求/秒”，还是“满足 attainment 的最大可承载到达率”。

## 8. 负载扫描方法

固定以下变量：

- 模型和 revision。
- dtype、量化和并行配置。
- 输入/输出长度分布。
- 到达过程。
- SLO。
- 测试持续时间和预热。

依次提高到达率：

```text
1, 2, 4, 6, 8, 10, 12 req/s
```

每个点记录：

- 成功率与错误率。
- 完成 Throughput。
- Goodput。
- TTFT P50/P95/P99。
- TPOT P50/P95/P99。
- ITL P95/P99。
- P、D、网络利用率。

找到 Goodput 峰值和 SLO 达标率仍满足目标的最大输入率。

## 9. vLLM 可核实命令

先查看本机版本支持的参数：

```bash
vllm bench serve --help | rg \
  "request-rate|goodput|percentile-metrics|metric-percentiles"
```
一个示例压测：
```bash
vllm bench serve \
  --backend openai-chat \
  --base-url http://127.0.0.1:8000 \
  --endpoint /v1/chat/completions \
  --model Qwen/Qwen2.5-7B-Instruct \
  --dataset-name random \
  --random-input-len 2048 \
  --random-output-len 256 \
  --num-prompts 1000 \
  --request-rate 6 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,95,99 \
  --goodput ttft:800 tpot:50 e2el:12000 \
  --save-result \
  --save-detailed
```
`--goodput` 的值单位是毫秒。 允许的指标和 CLI 细节会随版本变化， 以 `--help` 和对应版本官方文档为准。
## 10. 到达过程会改变结果
`--request-rate` 有限时， vLLM benchmark 可按随机到达过程发请求。 默认无限速往往意味着瞬时突发， 更像压力上限而不是稳定在线流量。 生产流量通常有：
- 日周期。
- 短时突发。
- 热点租户。
- 多轮会话关联。
- Prompt 长度与时间相关。
最好从脱敏日志构建重放数据。 若只能用合成流量， 至少同时测稳定到达和 burst。
## 11. SLO 感知的 P 池调度
P 队列不能只按先来先服务。
### 11.1 按 token 工作量
短 Prompt 可以快速完成， 降低整体排队。 但纯 Shortest Job First 会让长 Prompt 饥饿， 需要 aging 或租户公平约束。
### 11.2 按 TTFT slack
估计请求剩余 Prefill 与传输时间：
\[
slack_P=deadline_{TTFT}-now-\hat T_{P}-\hat T_{xfer}
\]
slack 越小越紧急。 预测误差要持续校准， 尤其是多模态输入和 Prefix Cache 命中场景。
### 11.3 分桶
按 Prompt 长度分为：
- short。
- medium。
- long。
每桶独立队列与 token budget， 能避免少量超长请求淹没短请求， 实现也比精确服务时间预测简单。
## 12. SLO 感知的 D 池调度
D 池的重点是稳定迭代。 路由时考虑：
- 当前活跃序列数。
- 每序列上下文长度。
- 可用 KV blocks。
- 最近 ITL。
- 预期输出长度。
- Prefix/会话 KV 是否已在本实例。
仅用“活跃请求数”会误导： 32 个接近结束的短上下文请求， 与 32 个 64K 上下文请求的成本完全不同。
## 13. P-D 配对的网络代价
若路由器选了最空闲的 D， 但它与 P 跨越低速链路， TTFT 可能更差。 可定义配对代价：
\[
Cost(P,D)= \alpha Q_P+ \beta Q_D+ \gamma \frac{KVBytes}{BW_{P,D}}+ \delta Risk_{SLO}
\]
其中：
- \(Q_P\)：P 队列工作量。
- \(Q_D\)：D 队列工作量。
- \(BW_{P,D}\)：测得的有效带宽。
- \(Risk_{SLO}\)：预测违约风险。
系数不是拍脑袋永久固定， 应通过离线回放和在线指标校准。
## 14. 准入控制
当预测请求已不可能达标时， 继续无上限排队会拖累所有请求。 准入控制可选择：
- 立即返回过载错误。
- 进入有界等待队列。
- 降低最大输出长度。
- 路由到宽松 SLO 的降级集群。
- 对低优先级租户限流。
拒绝请求会降低成功吞吐， 但可能保护高优先级 Goodput。 策略必须对业务透明， 不能静默篡改用户生成参数。
## 15. 多租户与公平性
只优化全局 Goodput， 可能让短请求租户占满系统。 应同时约束：
- 每租户 SLO attainment。
- 每租户并发与 token rate。
- 长请求最大等待时间。
- 优先级预算。
- 抢占后的重算成本。
一种常见做法是分层：
1. 租户级配额与优先级。
2. 租户内按 slack 或工作量排序。
3. 全局保留少量紧急容量。
## 16. 指标埋点骨架
每个请求至少记录以下时间戳：
```text
arrival
prefill_queue_enter / prefill_start / prefill_end
kv_transfer_start / kv_transfer_end
decode_queue_enter / decode_start
first_token
each_token
finish / cancel / error
```
还需关联：
```text
request_id
tenant_id
prefill_worker
decode_worker
input_tokens / output_tokens
kv_bytes
cache_hit_tokens
model_revision
```
没有阶段时间戳， 只能知道 TTFT 变慢， 无法判断是 P 排队、KV 传输还是 D 交接。
## 17. 常见错误
### 只报告平均延迟
平均值无法保护尾部用户。 至少报告目标 SLO 对应的分位数与达标率。
### 只比较相同并发
并发不是到达率。 不同系统完成速度不同， 相同并发可能产生不同实际压力。
### 把取消请求从分母删除
若用户因等待过久取消， 删除它会美化 SLO。 应预先定义取消和错误如何计入。
### 在两个系统上使用不同数据分布
输入输出长度变化足以改变结论。 对照实验应共享请求清单与到达时间。
### 用一次峰值定义容量
容量要经过足够长的稳态、突发和故障测试。 一次短跑的最高点不等于可运营容量。

## 18. 三种 Goodput 口径必须同时写全

“Goodput 是 8 req/s”仍然不完整。至少区分：

### 18.1 Observed goodput

在某个已运行窗口 \([t_a,t_b]\) 中：

\[
G_{obs}=
\frac{
\sum_i
\mathbb 1(
arrival_i\in[t_a,t_b]
\land completed_i
\land good_i
)
}{
t_b-t_a
}
\]

它描述这个实验点真正交付了多少达标请求。报告必须附带：

```text
offered arrival rate
completed throughput
SLO attainment
window duration
warmup/drain policy
error/cancel accounting
```

### 18.2 Capacity goodput

给定负载分布 \(\mathcal W\)、联合 SLO \(\mathcal S\) 和达标目标 \(p\)：

\[
G_{cap}=
\sup\{
\lambda:
A(\lambda,\mathcal W,\mathcal S)\ge p
\}
\]

其中：

\[
A=
\frac{
\sum_i
\mathbb 1(good_i)
}{
N_{offered}
}
\]

Capacity goodput 是“最大可承载到达率”，不是峰值完成吞吐，也不是某个窗口的达标请求数。

### 18.3 Per-GPU capacity goodput

\[
G_{cap/GPU}=\frac{G_{cap}}{N_{GPU}}
\]

若 P 使用 4 GPU、D 使用 8 GPU、Router 用 CPU：

\[
N_{GPU}=4+8=12
\]

不能只除以 D GPU，也不能把 P/D 各自容量相加。每个请求依次通过两个阶段，系统 capacity 是串联系统的共同流量。

### 18.4 为什么需要三者

```text
G_obs          回答：这个实验窗口实际交付多少？
G_cap          回答：这套部署最多承载多大输入率？
G_cap/GPU      回答：为达到该容量付出多少 GPU？
```

解耦可能提高 \(G_{cap}\)，但复制权重后 \(G_{cap/GPU}\) 下降；也可能在目标负载点降低 ITL P99，却不改变 \(G_{cap}\)。这三种结论可以同时成立。

## 19. 联合 SLO 不是分位数的简单拼接

联合约束为：

\[
good_i=
\mathbb 1(
TTFT_i\le800
\land TPOT_i\le50
\land E2E_i\le12000
)
\]

以下条件：

```text
TTFT P99 <= 800 ms
TPOT P99 <= 50 ms
```

并不自动推出 99% 请求同时满足两个条件。最坏情况下，TTFT 违约和 TPOT 违约发生在不同请求上，联合达标率可能只有约 98%。

必须在请求级 join 后计算：

```python
good = (
    (ttft_ms <= 800)
    & (tpot_ms <= 50)
    & (e2e_ms <= 12000)
)
attainment = good.sum() / offered_requests
```

分位数用于描述分布，联合 Goodput 必须逐请求求交集。

### 19.1 ITL 怎样加入

若业务要求“任何一次可见停顿不超过 200 ms”，可以定义：

\[
good_i=
\mathbb 1(
TTFT_i\le800
\land TPOT_i\le50
\land \max_j ITL_{i,j}\le200
)
\]

但投机解码一次 chunk 含多个 token 时，chunk 间隔不是 token ITL。需要记录 chunk token 数，或明确把约束命名为 `max_stream_chunk_gap`。

## 20. 一次联合 SLO 负载扫描手算

假设同一请求时间线在 1P:2D、共 3 GPU 配置上得到：

```text
λ=2 req/s:
  completion=2.00, attainment=99.5%
  G_obs=1.99 req/s

λ=4 req/s:
  completion=3.98, attainment=99.0%
  G_obs=3.94 req/s

λ=6 req/s:
  completion=5.92, attainment=97.0%
  G_obs=5.74 req/s

λ=8 req/s:
  completion=7.65, attainment=91.0%
  G_obs=6.96 req/s

λ=10 req/s:
  completion=8.10, attainment=62.0%
  G_obs=5.02 req/s
```

若目标 attainment 是 99%：

\[
G_{cap}\approx4\text{ req/s}
\]

\[
G_{cap/GPU}=4/3\approx1.33\text{ req/s/GPU}
\]

Observed goodput 的峰值出现在 \(\lambda=8\) 附近，约 6.96 req/s；但它不满足 99% attainment，所以不能称作该 SLO 下的 capacity goodput。

### 20.1 在边界附近二分

粗扫发现 4 达标、6 不达标后，再测：

```text
4.5, 5.0, 5.5 req/s
```

假设：

```text
4.5 -> 99.2%
5.0 -> 98.8%
5.5 -> 98.0%
```

则离散估计：

\[
G_{cap}=4.5\text{ req/s}
\]

不要在 4.5 与 5.0 之间线性插值后声称精确到小数点后两位；排队系统在拐点附近通常非线性。

## 21. 按输入/输出长度做联合扫描

只扫描单一 2048/256 会掩盖配比变化。至少准备：

```text
LPLD: input 128–512, output 32–128
LPHD: input 128–512, output 512–2048
HPLD: input 4K–16K, output 32–128
HPHD: input 4K–16K, output 512–2048
```

再构建业务混合，例如：

```text
LPLD 50%
LPHD 20%
HPLD 20%
HPHD 10%
```

每个 \(\lambda\) 保持相同请求清单和到达时间，比较共置与不同 P:D 配置。

### 21.1 为什么必须保留联合分布

不能独立抽样输入长度和输出长度后随意配对。真实业务可能：

- 长文摘要：长输入、短输出。
- 内容生成：短输入、长输出。
- Agent：中等输入、短输出但多轮。

破坏相关性会改变 P/D 负载比例和 KV 生命周期。

## 22. 阶段预算与端到端联合约束

把 TTFT budget 分为：

\[
S_{TTFT}
=B_{qP}+B_P+B_x+B_{qD}+B_{firstD}
\]

例如：

```text
P queue        150 ms
Prefill        450 ms
KV handoff      80 ms
D queue         70 ms
first D step    50 ms
total          800 ms
```

阶段预算用于定位，不应用来改变请求级 Goodput 定义。若某请求 P queue 200 ms、Prefill 300 ms，虽然 P queue 超阶段预算，但端到端 TTFT 仍可能达标；运营告警可以报阶段风险，容量 Goodput仍按联合端到端 SLO算。

### 22.1 Decode 的两个约束

```text
TPOT <= 50 ms/token
max ITL <= 200 ms
```

TPOT 保护平均阅读节奏，max/P99 ITL 保护瞬时 stall。前者可纳入请求级 Goodput，后者可作为附加联合条件或独立安全门槛，但报告必须说明。

## 23. 统计窗口、预热和未完成请求

### 23.1 Arrival-window 口径

选择在测量窗口内到达的请求作为分母，然后继续 drain 直到它们完成或达到统一超时：

```text
warmup
measurement arrivals
stop new arrivals
drain
classify success/error/timeout/cancel
```

这避免在窗口结束时删除仍排队的慢请求。

### 23.2 Completion-window 偏差

若只统计窗口内完成的请求，慢请求更可能跨出窗口而被排除，SLO 被美化。尤其在超载点，结果会产生 survivorship bias。

### 23.3 错误和取消

预先定义：

```text
server 5xx          not good，进入 offered 分母
admission reject    单独报告；容量口径通常进入 offered 分母
client timeout      not good
user semantic cancel 可单列，但不能事后选择性删除
invalid request     通常从有效 offered workload 排除
```

## 24. 置信度与重复实验

99% attainment 若只测 100 个请求，理论上只能容许 1 个违约，结论对偶然抖动极敏感。至少：

- 每个点使用足够请求数和持续时间。
- 运行多个随机种子。
- 同时报告请求数和置信区间。
- 边界点做更长稳态。

对 \(N\) 个请求、达标比例 \(\hat p\)，可用 Wilson interval 评估二项比例不确定性。无需手工在教程里推完整公式，但容量门禁应采用置信区间下界：

\[
p_{lower}\ge p_{target}
\]

如果点估计 99.1%，下界只有 98.5%，不能自信宣称满足 99%。

## 25. P/D 联合扫描的实现流程

### 25.1 每个候选配置

```text
1. 重启或清理到同一 cache 初态
2. 预热
3. 以相同 seed 生成 arrival schedule
4. 运行固定 duration
5. drain
6. 请求级 join P、KV、D 和客户端事件
7. 计算 good_i
8. 输出 G_obs、attainment 和资源指标
```

### 25.2 负载扫描伪代码

```python
for config in configs:
    for rate in coarse_rates:
        result = replay(config, workload, rate)
        result.attainment = joint_attainment(result.requests)
        result.observed_goodput = result.good / result.measurement_seconds

    lo, hi = bracket_attainment_boundary(config)
    for rate in refine_rates(lo, hi):
        replay_and_record(config, workload, rate)

    config.capacity_goodput = max(
        r.rate for r in config.results
        if r.attainment_lower_bound >= target
    )
    config.per_gpu = config.capacity_goodput / config.num_gpus
```

## 26. SLO 感知调度的收益如何归因

若新策略 Goodput 提高，应做消融：

```text
A: Round Robin
B: + token-workload routing
C: + network cost
D: + SLO slack
E: + admission control
```

逐步比较：

- P queue 时间变化。
- handoff 变化。
- D queue/ITL 变化。
- reject 数变化。
- 联合 attainment 变化。

否则“Goodput 上升”可能只是更激进拒绝低优先级请求，或 workload 恰好更短。

## 27. 排障闭环

### Observed goodput 高，但 capacity goodput 低

检查该点 attainment 是否低于目标。系统可以完成很多请求，但没按时完成。

### Per-GPU 结果反常

核对 GPU 分母是否包含：

- 所有 P 副本。
- 所有 D 副本。
- Mixed/standby GPU。
- 故障冗余是否作为 provisioned capacity 计入。

建议同时报告 active 与 provisioned 两种成本口径。

### TTFT 达标、TPOT 违约

- D 数量或 HBM 带宽不足。
- D batch 过大导致 iteration 超预算。
- 长上下文集中到少数 D。
- Connector recompute 把 Prefill 带入 D。

### TPOT 达标、TTFT 违约

- P queue 或长 Prompt head-of-line blocking。
- KV handoff/注册慢。
- D 预留过早或交接等待。
- Prefix Cache 命中率与基线不同。

### 联合 attainment 低于两个单项 attainment

这是集合交集的正常结果。检查请求级相关性：

\[
P(A\cap B)=P(A)+P(B)-P(A\cup B)
\]

不要用 `min(TTFT attainment, TPOT attainment)` 代替联合值。

### 负载点之间抖动大

- 测试时间过短。
- 到达 burst 随机性过强。
- 请求长度清单未固定。
- cache 初态不一致。
- GPU 时钟、邻居流量或网络路径变化。

## 28. 本节闭环

```text
问题：吞吐不能代表按 SLO 交付的有效容量
  ↓
机制：逐请求联合 TTFT/TPOT/E2E/可选 ITL 判定
  ↓
公式：G_obs、G_cap、G_cap/GPU 三种口径
  ↓
实现：arrival-window + drain + 请求级阶段时间戳
  ↓
实验：二维工作负载 × 到达率粗扫/细扫 × 配置
  ↓
排障：核对分母、未完成请求、联合集合与 GPU 成本
```

## 📝 总结
1. Throughput 统计完成量；observed goodput、capacity goodput 和 per-GPU capacity goodput回答三个不同问题。
2. P/D 解耦下 TTFT 包含 P 排队、Prefill、KV 传输和 D 交接。
3. Goodput 随负载可能先升后降，最大忙碌度不是最佳运营点。
4. P 池适合按 token 工作量和 TTFT slack 调度，D 池要保护迭代节奏与 KV 容量。
5. 路由必须把 P-D 有效带宽纳入成本。
6. 准入控制、租户公平与阶段埋点是 SLO 调度的一部分。
