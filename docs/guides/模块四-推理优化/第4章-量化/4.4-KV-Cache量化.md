## 先说人话：把每位客人的笔记本变薄
模型权重像餐厅的固定装修。KV Cache 像服务员为每桌客人持续记录的点菜单。客人越多、聊天越长，点菜单就越厚。
权重只加载一次，KV Cache 却按请求、按 token 增长。
长上下文服务中，即使量化模型权重后还有空余显存，KV Cache 也可能很快把容量吃满。KV Cache 量化就是把每页笔记换成更紧凑的记法。
它可能带来：
- 同一 GPU 容纳更多 token；
- 支持更长上下文；
- 增加并发请求数；
- 减少 Attention 读取 KV 的带宽。

代价是：
- 每次写入要量化；
- 每次读取要反量化或由 Kernel 原生处理；
- 历史误差会影响后续每个 token；
- Attention Kernel 必须支持目标格式。
## KV Cache 保存了什么
自回归 Transformer 在第 \(l\) 层为历史 token 保存：
\[K_l=XW^K_l\]
\[V_l=XW^V_l\]
生成下一个 token 时，新 Query 会与历史 Key 计算注意力分数：
\[A=\operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_h}} \right)\]
再与 Value 相乘：
\[O=AV\]
历史 K、V 若不缓存，每一步都要从头重算。因此 KV Cache 用显存换计算。量化 KV Cache 则在这个交换中再次折中：
> 少用显存和带宽，但接受低精度历史状态。
## 容量公式
忽略分页碎片和元数据，单个序列的 KV Cache 字节数近似为：
\[M= L\times T\times 2\times H_{kv}\times D_h\times B\]
其中：
- \(L\)：Transformer 层数；
- \(T\)：缓存 token 数；
- `2`：Key 和 Value 两份；
- \(H_{kv}\)：KV head 数；
- \(D_h\)：每个 head 的维度；
- \(B\)：每个元素字节数。

批量请求还要乘以各序列 token 总数。若使用 MHA：
\[H_{kv}=H_q\]
若使用 GQA/MQA：
\[H_{kv}<H_q\]
因此 GQA/MQA 本身已经在减少 KV Cache。KV 量化与 GQA 是可叠加的两个方向。
## 手算容量
假设一个教学模型：
- 32 层；
- 8 个 KV heads；
- head dimension 为 128；
- 上下文长度 4096；
- FP16，每元素 2 bytes。

代入：
\[M=32\times4096\times2\times8\times128\times2\]
得到：
\[M=536{,}870{,}912\ \text{bytes}\]
约为：
\[512\ \text{MiB}\]
这是一个序列的理论 K/V 数据。若改为 1-byte FP8，理论数据部分约减半。若改为 2 bit，原始数据部分理论上约为 FP16 的八分之一。
但真实显存还要加入：
- scale；
- block padding；
- allocator 元数据；
- 页表；
- 尚未完全利用的 block；
- Attention workspace。

所以实际容量不会严格按位宽比例变化。

## 问题驱动：KV 预算到底能承载多少请求
生产问题通常不是“单序列占多少”，而是：

> 在权重、CUDA graph、workspace 和安全余量都扣除后，PagedAttention 能分配多少物理 block，又能在给定长度分布下稳定承载多少请求？

先把公式扩展到批量和 Tensor Parallel。第 \(r\) 个序列缓存 \(T_r\) 个 token，单卡保存的 KV head
数记作 \(H_{kv}^{\text{rank}}\)，元素位宽为 \(b\)，则数据本体：

\[
M_{\text{data,rank}}
=L\left(\sum_{r=1}^{R}T_r\right)
\times2\times H_{kv}^{\text{rank}}\times D_h\times\frac b8
\]

若 KV heads 能均匀按 TP 切分：

\[
H_{kv}^{\text{rank}}=\frac{H_{kv}}{TP}
\]

但 MQA/GQA 中 \(H_{kv}<TP\) 时，runtime 可能复制 KV heads，而不是继续切分，因此不能盲目除以 TP。
应以各 rank 实际 cache shape 为准。

每 token、每层、每 rank 的数据字节数：

\[
C_{\text{token}}
=2H_{kv}^{\text{rank}}D_h\frac b8
\]

给定可用于 KV 的字节预算 \(M_{\text{budget}}\)，忽略元数据时理论 token 上界：

\[
T_{\text{capacity}}
=\left\lfloor
\frac{M_{\text{budget}}}
{L C_{\text{token}}}
\right\rfloor
\]

这个 \(T_{\text{capacity}}\) 是**所有活跃序列 token 的总和**，不是每个请求的最大长度。

## 把 scale、残差窗口和分页算进容量
设量化数据每元素 \(b\) bit，每 \(G\) 个元素共享一个 \(b_s\)-bit scale 和
\(b_z\)-bit zero-point，则每元素有效位宽近似：

\[
b_{\text{eff}}=b+\frac{b_s+b_z}{G}
\]

若 scale/zero-point 因对齐按更宽类型存储，应使用物理字节而不是逻辑 bit。对 KIVI 类保留
\(R_{\text{res}}\) 个高精度 token 的方案，单序列近似：

\[
M
=L\times2\times H_{kv}D_h
\left[
(T-R_{\text{res}})\frac{b_{\text{eff}}}{8}
+R_{\text{res}}B_{\text{high}}
\right]
\]

其中 \(T\le R_{\text{res}}\) 时全部是高精度，不能让第一项变成负数。

PagedAttention 再引入 block 取整。若每 block 有 \(P\) token，第 \(r\) 个请求实际占：

\[
N_r^{\text{blocks}}=\left\lceil\frac{T_r}{P}\right\rceil
\]

物理数据预算：

\[
M_{\text{paged}}
=\sum_r N_r^{\text{blocks}}M_{\text{one block}}
+M_{\text{block tables}}
+M_{\text{workspace}}
\]

最后一个未满 block 的内部碎片：

\[
F_r=P\left\lceil\frac{T_r}{P}\right\rceil-T_r
\]

短请求很多时，理论按 token 计算的压缩比与实际可分配请求数差异会变大。

### 更完整的手算
沿用前面的教学模型：

```text
L=32, H_kv=8, D_h=128, T=4096
```

每 token、所有层的 FP16 KV：

\[
32\times2\times8\times128\times2
=131{,}072\ \text{bytes}=128\ \text{KiB}
\]

所以 4096 token 是：

\[
4096\times128\ \text{KiB}=512\ \text{MiB}
\]

若 TP=4 且 8 个 KV heads 均匀切分，每 rank 是 2 heads，数据本体为 128 MiB；4 张卡合计仍是
512 MiB。若 runtime 因 head 数小于 TP 而复制，公式必须改用实际
\(H_{kv}^{\text{rank}}\)，总集群字节可能不再保持不变。

假设 page size \(P=16\)，一个 4100-token 请求需：

\[
\lceil4100/16\rceil=257\ \text{blocks}
\]

分配 4112 个 token 槽，碎片为 12 个 token。这个例子说明容量规划要用 block 数，不只用
`max_model_len`。

## KV 的逻辑形状与物理布局
概念形状常写作：

```text
K, V: [layers, batch, kv_heads, tokens, head_dim]
```

但 PagedAttention 通常按层分别分配 cache，并把 token 维换成 block：

```text
K cache: [num_blocks, block_size, kv_heads, head_dim]  # 仅为逻辑示意
V cache: [num_blocks, block_size, kv_heads, head_dim]
```

真实 backend 可能把 `head_dim` 再分成 vector lane，或交换 `block_size`、`kv_heads` 轴，以获得
合并访存。scale layout 必须随之明确。例如：

- per-token/per-head：`scale[num_blocks, block_size, kv_heads]`；
- per-channel：`scale[num_blocks, groups_along_tokens, kv_heads, groups_along_head_dim]`；
- per-tensor/per-layer：每层 K、V 各一个标量；
- per-block：每个物理 page 的 K、V 各若干 scale。

“per-channel”必须说明 channel 是 head_dim 元素、整个 head，还是展开后的 hidden channel。
KIVI 论文中的 Key per-channel 指沿 channel 分组并跨 token 统计；Value per-token 指每个 token
内部沿 channel 分组。它们的归约轴正交。

## KIVI 的 streaming 布局与执行
记 Key cache 长度为 \(l\)，沿 token 每 \(G\) 个组成一个可做 per-channel 统计的组。拆成：

\[
X_K=[X_{K_g};X_{K_r}]
\]

其中：

\[
|X_{K_g}|=l-r,\quad |X_{K_r}|=r,\quad
(l-r)\bmod G=0
\]

`grouped` 部分保存低 bit codes、scale 和 zero-point；不足一组或策略指定的近期
`residual` 部分保留高精度。新 Key 先追加到残差，达到阈值后批量量化。

Value 的 per-token 量化天然符合流式追加，但 KIVI 仍保留近期高精度队列；队列达到 residual
length 后，把最旧 Value 按 token 量化并移入 grouped cache。

Decode 时注意力不是先恢复整个 cache：

\[
\text{logits}
=
\left[
Q\,\operatorname{dequant}(K_g)^\top,\
QK_r^\top
\right]
\]

Softmax 后再分别与 grouped/residual Value 做加权和并合并。高效实现应在 tile 内反量化
\(K_g,V_g\)，近期窗口走高精度分支。

KIVI 论文中的“asymmetric”同时涉及非对称低 bit quantizer，而工程讨论中还常说 K/V 采用
不对称粒度。文档和配置要分别写清：

```text
numeric scheme: affine/asymmetric with scale + zero-point
axis scheme: Key per-channel, Value per-token
```

## 2-bit 手算的 zero-point 修正
前文例子使用 \(z=2\) 时，`q=0` 的反量化应严格按：

\[
\hat x=s(q-z)
\]

得到：

```text
q = [0, 2, 3, 3]
x_hat = [-1.333, 0.000, 0.667, 0.667]
```

为什么 `-1.0` 没映射回 `-1.0`？因为 \(z^*=1.5\) 被舍入成 2。另一种 affine 约定是先选
\(s=(x_{\max}-x_{\min})/3\)，再保存浮点 offset/min，而不是强制实数零精确映射；这样端点行为会不同。
KIVI checkpoint/runtime 必须共享同一公式，不能只交换 codes。

## FP8 KV scale 的两种方向
有些文档把 scale 定义为“除数”：

\[
q=\operatorname{FP8}(x/s),\qquad \hat x=s\operatorname{float}(q)
\]

另一些 API 保存 inverse scale：

\[
q=\operatorname{FP8}(x\cdot s_{\text{inv}}),\qquad
\hat x=\operatorname{float}(q)/s_{\text{inv}}
\]

若 E4M3 最大有限幅值记为 \(F\)，amax 缩放的除数形式是：

\[
s=\frac{\max|x|}{F}
\]

把除数误当乘数会造成严重饱和或下溢。配置字段名 `scale` 也不能代替公式定义。

### 静态与动态 FP8 KV
静态 per-layer scale：

- 写入时不需要每 token 做 amax reduction；
- 依赖校准数据覆盖 K/V 在线分布；
- scale 元数据少，Attention Kernel 简单。

动态 per-token/per-head scale：

- 可跟随当前 K/V；
- 每层每 token 都需要归约；
- scale 与每个 block 一起读写；
- prefix cache、block copy 和 KV transfer 都要携带 scale。

FP8 是存储 dtype，不自动表示 Attention 点积使用 FP8 Tensor Core。常见实现会把 KV tile
反量化为 FP16/BF16，与 Query 计算；收益主要来自 cache 容量和 DRAM 读取减少。

## 可复现实验：容量计算器

```python
from math import ceil

def kv_bytes(
    layers,
    tokens_per_request,
    kv_heads_per_rank,
    head_dim,
    data_bits,
    page_size,
    scale_bits=0,
    zero_bits=0,
    values_per_scale=1,
):
    total_slots = sum(
        ceil(tokens / page_size) * page_size
        for tokens in tokens_per_request
    )
    elements = layers * total_slots * 2 * kv_heads_per_rank * head_dim
    effective_bits = data_bits + (scale_bits + zero_bits) / values_per_scale
    return {
        "logical_tokens": sum(tokens_per_request),
        "allocated_slots": total_slots,
        "fragmentation_tokens": total_slots - sum(tokens_per_request),
        "bytes_without_allocator_metadata": ceil(elements * effective_bits / 8),
    }

fp16 = kv_bytes(
    layers=32,
    tokens_per_request=[4096],
    kv_heads_per_rank=8,
    head_dim=128,
    data_bits=16,
    page_size=16,
)
fp8 = kv_bytes(
    layers=32,
    tokens_per_request=[4096],
    kv_heads_per_rank=8,
    head_dim=128,
    data_bits=8,
    page_size=16,
    scale_bits=32,       # 教学假设：32-bit scale
    values_per_scale=128,
)
print("FP16:", fp16)
print("FP8 + assumed scales:", fp8)
```

`values_per_scale` 必须从实际 backend layout 获取。脚本没有加入 block table、allocator、workspace
和 residual window，输出只能作为容量下界模型。

## 可复现实验：Key per-channel 与 Value per-token

```python
import torch

torch.manual_seed(3)
# [tokens, channels]
k = torch.randn(8, 4)
v = torch.randn(8, 4)
k[:, 1] *= 12                 # 某个 Key channel 有较大范围
v[5, :] *= 10                 # 某个 Value token 有较大范围

def affine_qdq(x, dim, bits=2):
    qmin, qmax = 0, 2**bits - 1
    xmin = x.amin(dim=dim, keepdim=True)
    xmax = x.amax(dim=dim, keepdim=True)
    scale = ((xmax - xmin) / (qmax - qmin)).clamp_min(1e-12)
    zp = torch.clamp(torch.round(qmin - xmin / scale), qmin, qmax)
    q = torch.clamp(torch.round(x / scale) + zp, qmin, qmax)
    return scale * (q - zp)

# Key per-channel：沿 token 归约，每个 channel 一个 scale。
k_pc = affine_qdq(k, dim=0)
# Value per-token：沿 channel 归约，每个 token 一个 scale。
v_pt = affine_qdq(v, dim=1)

q = torch.randn(4)
logits_ref = q @ k.T
logits_q = q @ k_pc.T
prob_ref = torch.softmax(logits_ref, dim=-1)
prob_q = torch.softmax(logits_q, dim=-1)
out_ref = prob_ref @ v
out_q = prob_q @ v_pt

print("K logits max error:", (logits_q - logits_ref).abs().max().item())
print("attention output relative L2:", ((out_q - out_ref).norm() / out_ref.norm()).item())
```

再交换轴（Key per-token、Value per-channel）比较误差。这个合成实验说明轴的意义，不证明 KIVI
在任意模型上都优于交换方案。

## Attention backend 的真实执行路径
写 cache：

```text
QKV projection output
  -> rotary embedding（K 的量化发生在 RoPE 前后由实现规定）
  -> K/V amax 或 min/max reduction
  -> cast/round + scale metadata
  -> 写入物理 page
```

读 cache：

```text
block table -> 物理 page 地址
  -> 合并读取 quantized K + scale
  -> tile 内反量化
  -> QK dot + online softmax
  -> 合并读取 quantized V + scale
  -> tile 内反量化并做 P@V
  -> 输出高精度 attention result
```

需要检查量化点与 RoPE 的相对位置。K 在应用 RoPE 后缓存是常见路径，但某些架构/缓存策略可能不同；
scale 校准必须观察真正写入 cache 的张量。

FlashAttention、FlashInfer、Triton 和厂商后端是实现家族，不是永久支持表。相同 vLLM 版本在
不同 head size、dtype、prefix caching 或 sliding window 下可能选择不同 backend。

## 质量与性能测量
### 质量
建立长度分桶：

```text
短：1K 左右，检查常规能力
中：业务主体长度
长：接近上线 max_model_len
边界：跨 page、跨 residual flush、跨 sliding-window 边界
```

每桶测 NLL/任务指标，还要单独测 exact retrieval、multi-hop、复制、长代码依赖。对 FP8 scale
校准，报告每层 K/V saturation rate；对低 bit affine，报告 codes 分布和 residual flush 前后误差。

### 容量
从引擎日志读取实际 block 数，用以下关系交叉检查：

\[
\text{measured bytes per block}
\approx
\frac{\text{KV pool bytes}}{\text{number of physical blocks}}
\]

再与逻辑 layout 估算对照。两者差异可定位 scale、padding 或额外 buffer。

### 性能
固定权重、调度和流量，只改变 KV dtype。扫描 context length，分别报告：

- cache write/quantize 时间；
- decode Attention Kernel 时间；
- TPOT 与 P99；
- 最大稳定并发；
- preemption/recompute；
- prefix cache 命中率。

短上下文变慢、长上下文变快是完全可能的，交叉点才是决策依据。

## 更完整的失败模式与决策边界
- **把 MHA head 数代入 GQA 模型**：容量高估数倍。
- **盲目除以 TP**：MQA/GQA head 复制使 per-rank 公式错误。
- **scale 方向相反**：`scale` 与 `inverse_scale` 混用。
- **RoPE 前后统计错位**：校准张量不是实际 cache 张量。
- **prefix block 只复制 codes**：scale/zero-point 未复制，复用请求输出损坏。
- **residual flush 抖动**：每达到阈值触发批量量化，尾延迟呈周期尖峰。
- **后端因 feature 组合回退**：单独 FP8 可用，打开 sliding window/prefix/PD 后不可用。
- **只看最大长度**：长文可生成但检索能力已下降。

选择边界：

- KV pool 限制并发/长度：优先比较 FP8 KV；
- context 很短且 Attention 占比小：量化写入成本可能不值得；
- 需要 2/4-bit KIVI 类方案：只有 runtime 有正式融合 Kernel 和完整功能兼容时才进入生产候选；
- PD 解耦或跨节点传输：发送端、接收端和 Connector 必须共享格式版本；
- 质量门槛未过：先提高 KV 位宽或缩小量化粒度，不要用权重量化结果替代评测。

## 版本与硬件边界
KIVI 结论以 ICML 2024 论文及官方仓库为准；论文实验数字不应迁移到不同模型、GPU 和引擎。
截至 **2026-08-13**，本文核对了 vLLM **v0.27.1** 的 quantized KV cache 文档与 cache 配置源码；仍须按当前安装版本核对
KV dtype、scale 计算和 Attention backend。支持“FP8 KV cache”不等于支持 KIVI 2-bit，也不等于
使用 FP8 Tensor Core 做 Attention。

部署记录必须包含 vLLM 版本/commit、实际 Attention backend、GPU compute capability、
KV dtype、scale 来源、block size、head size、prefix/sliding-window/PD 等功能开关。
## 为什么 KV 量化不同于权重量化
权重：
- 固定；
- 可离线校准；
- 可花时间优化；
- 所有请求共享。

KV Cache：
- 每个请求实时生成；
- 每层、每 token 都变化；
- 写入和读取都在推理关键路径；
- 生命周期与请求调度绑定；
- 误差会持续影响后续注意力。

因此不能直接把 GPTQ/AWQ 权重算法套到 KV 上。KV 量化更关注：
- 在线 scale 如何计算；
- scale 按 token、channel 还是 block；
- Key 与 Value 是否使用不同粒度；
- PagedAttention 如何保存元数据；
- Decode 读取是否融合反量化。
## KV Cache 的数据分布
Key 和 Value 的统计特征不完全相同。KIVI 论文观察到：
- Key 的不同通道可能存在明显离群特征；
- Value 的离群行为更适合按 token 处理。

这促成了非对称粒度：
- Key 采用 per-channel 量化；
- Value 采用 per-token 量化。

这里的“非对称”是策略不对称，不要与有 zero-point 的 asymmetric quantization 混淆。实际实现还可能使用：
- per-head；
- per-tensor；
- per-block；
- 固定 scale；
- 动态 scale。

粒度必须与 Attention Kernel 配合。
## FP8 KV Cache
### 直觉
FP8 每个元素通常占 1 byte，相对 FP16/BF16 的 2 bytes，理论数据量减半。由于仍保留指数位，它比同位宽整数更能覆盖大动态范围。
这让 FP8 成为较容易落地的 KV Cache 压缩方案。
### E4M3 与 E5M2
FP8 常见两种格式：
- E4M3：4 位指数、3 位尾数；
- E5M2：5 位指数、2 位尾数。

粗略理解：
- E4M3 精度更细，范围相对小；
- E5M2 范围更大，尾数更粗。

具体可表示范围还与 finite-only 等格式定义有关。不要只根据名称手写边界，应以框架和硬件采用的 FP8 规范为准。
### scale 的作用
即使 FP8 有指数，通常仍使用 scale 把张量范围映射到合适区间：
\[q=\operatorname{cast}_{FP8}(x/s)\]
\[\hat{x}=\operatorname{cast}_{high}(q)\times s\]
scale 太大，有效尾数利用不足。scale 太小，大值可能饱和。scale 可以来自：
- checkpoint 校准；
- 运行时动态统计；
- 固定默认值；
- 每层独立统计。

不同 vLLM 版本的支持方式可能变化，必须查当前官方文档。
## KIVI 的 2-bit 思路
KIVI 是面向 KV Cache 的 tuning-free 非对称 2-bit 量化方案。
它的核心观察不是“所有 KV 都能直接压成 2 bit”，而是利用 K、V 不同的离群模式设计粒度。概念上：
- Key 采用 per-channel 方式；
- Value 采用 per-token 方式；
- 使用分组量化；
- 保留近期 token 的高精度残差窗口；
- 较旧缓存批量量化。

为什么保留近期窗口？在线生成一个 token 时，单个 token 不一定能立刻凑成适合高效量化的 group。
先保留一小段高精度缓存，达到阈值后再成组量化，能简化摊销并保护近期信息。具体残差长度、group size 和实现细节，应以论文及实际代码为准。
## 一个 2-bit 手算
假设使用无符号 2-bit 编码：
```text
q in [0, 3]
```
一组值：
```text
x = [-1.0, -0.2, 0.4, 1.0]
```
非对称 scale：
\[s=\frac{1-(-1)}{3}=\frac{2}{3}\]
zero-point：
\[z\approx\operatorname{round}(0-(-1)/(2/3))=2\]
量化可得到近似：
```text
q = [0, 2, 3, 3]
```
反量化：
```text
[-1.333, 0.0, 0.667, 0.667]
```
2 bit 的刻度非常粗。这个简化例子说明：
- 粒度选择极其重要；
- 离群值会显著影响主体；
- 2-bit 不能只靠朴素 min-max；
- Attention 对误差的容忍必须实测。
## PagedAttention 中怎样存
vLLM 把 KV Cache 切成固定大小 block，再用逻辑到物理 block 的映射组织请求。
量化后一个 block 不只包含 K/V 数据，还可能需要：
- K scale；
- V scale；
- zero-point；
- 每层或每 head 的元数据；
- 对齐 padding。

设计时要回答：
1. scale 与数据是否连续存放？
2. block copy 或 prefix cache 复用时是否一起复制？
3. beam/fork 请求共享哪些元数据？
4. swap 或 KV transfer 是否理解量化布局？
5. Tensor Parallel 各 rank 保存哪部分 scale？

这也是“算法论文可行”到“生产引擎可用”之间的距离。
## Attention Kernel 约束
### 读取路径
Decode Attention 每步都读取历史 K/V。理想 Kernel 会：
1. 读取低比特 K/V；
2. 读取对应 scale；
3. 在寄存器中反量化；
4. 立即参与点积或加权求和；
5. 避免写回完整高精度 K/V。

如果先反量化整个 Cache 到临时 buffer，显存和带宽收益会被大幅削弱。
### 写入路径
新 token 的 K/V 要被量化并写入 Cache。动态 scale 可能需要归约最大值。
对每层、每 token 都执行时，小 batch 下开销尤其值得关注。
### 后端差异
FlashAttention、FlashInfer、Triton、厂商特定后端对 KV dtype 的支持可能不同。
“vLLM 支持 FP8 KV Cache”不代表所有 Attention backend 都支持同一组合。要确认：
- GPU 架构；
- vLLM 版本；
- Attention backend；
- KV dtype；
- head size；
- block size；
- prefix cache 等功能组合。
## 质量风险从哪里来
### Key 误差
Key 参与：
\[QK^\top\]
误差会改变 attention logits。Softmax 对相对差异敏感，小误差也可能改变注意力排序。
### Value 误差
Value 参与加权和：
\[AV\]
误差会直接进入 Attention 输出。
### 长上下文累积
旧 token 的量化误差在后续每一步都可能被访问。长上下文评测不能只测试“能否生成到目标长度”，还要测试是否保持检索、推理和位置鲁棒性。
### 特殊任务
KV 量化可能对以下任务更敏感：
- needle-in-a-haystack；
- 多跳检索；
- 长代码依赖；
- 精确复制；
- 长文档问答；
- 多轮对话记忆。

这些任务需要单独报告，不能被短文本平均分掩盖。
## 容量与速度的 trade-off
KV 量化最确定的收益通常是容量潜力。速度收益则取决于：
- Attention 是否受 KV 带宽限制；
- 反量化是否融合；
- scale 元数据开销；
- 上下文长度；
- batch；
- GPU 对 FP8/低比特的支持；
- backend 实现成熟度。

短上下文时，KV 读取占比可能不高，量化开销反而更显眼。长上下文 Decode 时，减少 K/V 读取更可能有价值。所以报告中应把两类收益分开：
- 容量收益；
- 延迟/吞吐收益。
## vLLM 使用思路
先检查版本和参数：
```bash
python -c "import vllm; print(vllm.__version__)"
vllm serve --help | less
```
当前版本若支持，通常会在服务参数中提供 KV Cache dtype 相关选项。命令形态示意：
```bash
# 参数取值必须以本机 `vllm serve --help` 为准
vllm serve MODEL \
  --kv-cache-dtype <supported-kv-dtype>
```
这里故意不写死某个版本的完整参数组合。原因是：
- 可选 dtype 会变化；
- scale 读取/计算方式会变化；
- 后端与硬件限制会变化。

若官方文档要求提供校准 scale，不要在没有评测的情况下使用默认值。
## 验证计划
至少比较：
1. BF16/FP16 KV Cache；
2. FP8 KV Cache；
3. 更低位 KV 方案（仅当当前引擎正式支持）。

固定：
- 模型 revision；
- 权重量化方式；
- GPU 与并行度；
- vLLM 和 backend；
- block size；
- 请求数据；
- 采样参数。

扫描：
- 1K、4K、16K 等上下文桶；
- 不同并发；
- 不同输入/输出比例；
- prefix cache 开启与关闭（若业务使用）。

记录：
- 最大可缓存 token 数；
- 峰值显存；
- TTFT；
- TPOT；
- P95/P99；
- Attention Kernel；
- 质量指标。

不要虚构“节省比例”。用实际引擎日志和 GPU 指标计算。
## 常见失败模式
### 只改 dtype，没校准 scale
大值饱和或有效精度不足，质量出现隐蔽回退。
### backend 不支持
引擎报错、切换后端，或回退到不符合预期的路径。
### 容量估算忽略分页
理论字节数与可分配 block 数不一致。
### 长文本能跑但不会答
只验证 OOM，没有验证长上下文信息保持。
### 权重量化与 KV 量化混为一谈
前者减少共享模型权重，后者减少按请求增长的状态。它们解决的容量问题不同。
### 传输链路不兼容
在 PD 解耦、KV Connector 或跨节点场景，发送端与接收端必须理解同一 KV 格式和 scale。
## 本节小结
KV Cache 随层数、KV head 数、head dimension、token 数和元素字节数线性增长。
FP8 可以把理论数据字节数从 FP16 的 2 bytes 降为 1 byte，并保留一定动态范围。
KIVI 类 2-bit 方案通过 Key/Value 的不同粒度、分组量化和残差窗口进一步压缩。
真实系统中，scale、分页布局、写入量化、读取反量化和 Attention backend共同决定可用性。
上线前必须同时验证容量、Kernel、SLO 和长上下文质量。
