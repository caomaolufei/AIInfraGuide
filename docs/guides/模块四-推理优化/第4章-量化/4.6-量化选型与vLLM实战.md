## 先说人话：先问哪儿堵，再选工具
量化不是一把万能加速开关。它更像医院里的不同处方：权重放不下，需要减少模型占用；Decode 搬权重太慢，需要减少权重带宽；长上下文并发不足，需要压缩 KV Cache；Hopper 上大矩阵计算重，需要利用 FP8；Blackwell 上工具链成熟，才考虑 NVFP4；质量要求极严，可能继续使用 BF16。
如果没有先诊断瓶颈，就容易出现：文件变小，延迟没变；吞吐提高，质量不达标；单卡能跑，多卡 Kernel 回退；短文本变快，长文本尾延迟恶化。
本节给出一套可复现流程，不承诺任何脱离环境的性能数字。
## 第一步：明确优化目标
只写“希望更快”不够。把目标改写为可测量问题。
### 容量目标
例如：单卡是否能加载模型；目标并发下是否 OOM；能否支持 32K 上下文；每张 GPU 能缓存多少 token；是否能减少 Tensor Parallel 卡数。
### 延迟目标
至少区分：TTFT：首 token 延迟；TPOT：后续 token 间延迟；E2E latency：请求总延迟；P95/P99：尾延迟。
### 吞吐目标
至少区分：request throughput；input token throughput；output token throughput；goodput：满足 SLO 的有效吞吐。
### 质量目标
必须写成门槛：业务准确率最多下降多少；哪些关键子集不允许下降；结构化输出成功率门槛；安全与拒答行为要求；长上下文检索门槛。
## 第二步：建立未量化基线
没有基线，就无法判断量化带来了什么。记录：模型 ID 与 revision；tokenizer revision；GPU 型号和数量；驱动、CUDA；vLLM 版本；dtype；max model length；Tensor/Pipeline Parallel；KV Cache 配置；完整启动命令；请求数据集与随机种子。

```bash

```

```bash

```

## 问题驱动：从假设到可证伪实验
每次量化实验写一条可证伪假设：

```text
因为 Decode 的 Linear 受权重带宽限制，
所以 W4A16 在相同模型、KV dtype 和并发下应降低 TPOT，
且业务质量下降不超过预先定义的门槛。
```

把它拆成四个 gate：

1. **格式 gate**：checkpoint 配置、codes、scales 和 tokenizer 完整；
2. **正确性 gate**：固定输入可生成，无 NaN/重复/功能回退；
3. **质量 gate**：公开与业务指标过线；
4. **SLO gate**：在相同负载下容量、TTFT/TPOT/P99 至少一项改善，其他项不越界。

任何 gate 失败就停止推广。不要因为“量化已经花了很多时间”而降低事先设定的门槛。

## 可运行转换一：LLM Compressor W4A16
下面是以 vLLM v0.27.1 官方 INT4 页面为依据的完整脚本。它需要可访问的 Hugging Face 模型和数据集，
量化真实大模型需要 GPU 与足够主机内存。

将以下内容保存为 `quantize_w4a16.py`：

```python
import argparse
import json
from pathlib import Path

import torch
from datasets import load_dataset
from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import GPTQModifier
from transformers import AutoModelForCausalLM, AutoTokenizer


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--model", required=True)
    parser.add_argument("--revision", default="main")
    parser.add_argument("--output", required=True)
    parser.add_argument("--dataset", default="allenai/c4")
    parser.add_argument("--dataset-config", default="en")
    parser.add_argument("--dataset-split", default="train")
    parser.add_argument("--text-column", default="text")
    parser.add_argument("--samples", type=int, default=512)
    parser.add_argument("--max-seq-length", type=int, default=2048)
    parser.add_argument("--seed", type=int, default=42)
    args = parser.parse_args()

    torch.manual_seed(args.seed)
    output = Path(args.output)
    output.mkdir(parents=True, exist_ok=False)

    tokenizer = AutoTokenizer.from_pretrained(
        args.model,
        revision=args.revision,
        use_fast=True,
    )
    model = AutoModelForCausalLM.from_pretrained(
        args.model,
        revision=args.revision,
        dtype="auto",
        device_map="auto",
    )
    dataset = load_dataset(
        args.dataset,
        args.dataset_config,
        split=f"{args.dataset_split}[:{args.samples}]",
    )
    if args.text_column != "text":
        dataset = dataset.rename_column(args.text_column, "text")
    dataset = dataset.map(
        lambda batch: tokenizer(
            batch["text"],
            truncation=True,
            max_length=args.max_seq_length,
            padding=False,
        ),
        batched=True,
        remove_columns=dataset.column_names,
    )

    recipe = GPTQModifier(
        targets="Linear",
        scheme="W4A16",
        ignore=["lm_head"],
    )
    oneshot(
        model=model,
        dataset=dataset,
        recipe=recipe,
        max_seq_length=args.max_seq_length,
        num_calibration_samples=args.samples,
    )
    model.save_pretrained(output, save_compressed=True)
    tokenizer.save_pretrained(output)

    manifest = {
        "base_model": args.model,
        "revision": args.revision,
        "dataset": args.dataset,
        "dataset_config": args.dataset_config,
        "dataset_split": args.dataset_split,
        "samples": args.samples,
        "max_seq_length": args.max_seq_length,
        "seed": args.seed,
        "recipe": "GPTQModifier(W4A16, ignore=lm_head)",
    }
    (output / "quantization-run.json").write_text(
        json.dumps(manifest, indent=2),
        encoding="utf-8",
    )


if __name__ == "__main__":
    main()
```

运行：

```bash
python quantize_w4a16.py \
  --model YOUR_ORG/YOUR_MODEL \
  --revision YOUR_IMMUTABLE_REVISION \
  --output ./artifacts/model-w4a16
```

不要在正式实验中使用可移动的 `main`。使用 commit SHA 或不可变 revision，并把校准数据 revision/哈希
补进 manifest。若模型要求自定义 chat template 或数据预处理，应在脚本中显式完成，而不是依赖工具默认值。

### 展开 group 配置
v0.27.1 文档给出的显式 W4A16-G128 配置核心是：

```python
from compressed_tensors.quantization import (
    QuantizationArgs,
    QuantizationScheme,
    QuantizationStrategy,
    QuantizationType,
)

recipe = GPTQModifier(
    targets="Linear",
    config_groups={
        "group_0": QuantizationScheme(
            targets=["Linear"],
            weights=QuantizationArgs(
                num_bits=4,
                type=QuantizationType.INT,
                strategy=QuantizationStrategy.GROUP,
                group_size=128,
                symmetric=True,
                dynamic=False,
                actorder="weight",
            ),
        ),
    },
    ignore=["lm_head"],
    update_size=args.samples,
    dampening_frac=0.01,
)
```

只有需要锁定这些细节时才替换简写 recipe。`actorder`、`dampening_frac` 和 group size 变化都要重新过
质量与 Kernel gate。

## 可运行转换二：SmoothQuant W8A8
以 v0.27.1 官方 INT8 W8A8 recipe 为边界，把 W4A16 脚本中的 recipe 替换为：

```python
from llmcompressor.modifiers.smoothquant import SmoothQuantModifier

recipe = [
    SmoothQuantModifier(smoothing_strength=0.8),
    GPTQModifier(
        targets="Linear",
        scheme="W8A8",
        ignore=["lm_head"],
    ),
]
```

仍调用同一个 `oneshot(... dataset=..., max_seq_length=..., num_calibration_samples=...)`，
并 `save_compressed=True`。这里的 `0.8` 是该文档示例值，不是普遍最优 alpha。正式实验至少扫描预先
登记的候选，并用独立 selection split 选择。

如果安装版本不接受这些参数，说明 API 边界不同；应查看该版本 LLM Compressor 文档，不要为了“跑通”
随意删除 modifier。

## 可运行转换三：动态 FP8
v0.27.1 官方 FP8 页面给出的 LLM Compressor 路线不需要校准数据：

```python
from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import QuantizationModifier
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "YOUR_ORG/YOUR_MODEL"
revision = "YOUR_IMMUTABLE_REVISION"
output = "./artifacts/model-fp8-dynamic"

model = AutoModelForCausalLM.from_pretrained(
    model_id,
    revision=revision,
    dtype="auto",
    device_map="auto",
)
tokenizer = AutoTokenizer.from_pretrained(model_id, revision=revision)
recipe = QuantizationModifier(
    targets="Linear",
    scheme="FP8_DYNAMIC",
    ignore=["lm_head"],
```

动态 FP8 每次前向要计算 activation range；官方文档也提醒该模式延迟改善可能受限。无校准不等于无质量评测。

转换后先列出并解析配置，不要立刻启动：

```bash
python - ./artifacts/model-w4a16 <<'PY'
```


### FP8 KV Cache 独立实验

## 自动冒烟与确定性回归
将评测集保存为 JSONL，每行至少包含稳定 ID 和 prompt：

```json
{"id":"copy-001","prompt":"严格原样输出：alpha-42","max_tokens":16}
{"id":"math-001","prompt":"只输出 17*23 的整数结果。","max_tokens":8}
```

以下客户端可直接运行，输出逐样本结果供基线/候选比较：

```python
import argparse
import json
import time

import requests

parser = argparse.ArgumentParser()
parser.add_argument("--input", required=True)
parser.add_argument("--output", required=True)
parser.add_argument("--base-url", default="http://127.0.0.1:8000")
parser.add_argument("--model", default="quant-eval")
args = parser.parse_args()

rows = [
    json.loads(line)
    for line in open(args.input, encoding="utf-8")
    if line.strip()
]

with open(args.output, "w", encoding="utf-8") as fout:
    for row in rows:
        payload = {
            "model": args.model,
            "prompt": row["prompt"],
            "temperature": 0,
            "max_tokens": row.get("max_tokens", 128),
            "seed": 42,
        }
        started = time.perf_counter()
        response = requests.post(
            f"{args.base_url}/v1/completions",
            json=payload,
            timeout=300,
        )
        elapsed = time.perf_counter() - started
        response.raise_for_status()
        body = response.json()
        result = {
            "id": row["id"],
            "text": body["choices"][0]["text"],
            "finish_reason": body["choices"][0]["finish_reason"],
            "usage": body.get("usage"),
            "wall_seconds": elapsed,
        }
        fout.write(json.dumps(result, ensure_ascii=False) + "\n")
```

运行两次：

```bash
python run_regression.py --input eval.jsonl --output baseline.jsonl
# 切换到候选服务后
python run_regression.py --input eval.jsonl --output candidate.jsonl
```

temperature 0 和固定 seed 仍不保证不同 Kernel 输出字符串完全一致。回归判定应按任务：

- exact-copy/JSON/schema：确定性规则；
- 数学/选择题：答案解析器；
- 代码：隔离环境中的测试；
- 开放问答：参考答案指标或盲评；
- 安全：违规率与关键样本零容忍 gate。

### 最小 exact-match gate

```python
import json
import sys

def load(path):
    return {
        row["id"]: row
        for row in (
            json.loads(line)
            for line in open(path, encoding="utf-8")
            if line.strip()
        )
    }

baseline = load(sys.argv[1])
candidate = load(sys.argv[2])
missing = sorted(set(baseline) ^ set(candidate))
changed = sorted(
    key for key in set(baseline) & set(candidate)
    if baseline[key]["text"].strip() != candidate[key]["text"].strip()
)
print(json.dumps({"missing": missing, "changed": changed}, indent=2))
raise SystemExit(1 if missing else 0)
```

这个 gate 只把缺失样本视为失败；是否允许文本变化由任务评测器决定，不能用基线字符串一致率代替质量。

## NLL/perplexity 回归的公式边界
对 token 序列 \(x_{1:T}\)：

\[
\mathrm{NLL}
=-\frac1{T-1}\sum_{t=1}^{T-1}
\log p(x_{t+1}\mid x_{\le t})
\]

\[
\mathrm{PPL}=\exp(\mathrm{NLL})
\]

比较时必须使用同一个 tokenizer、截断、stride、BOS/EOS 处理和 loss mask。PPL 差异能发现整体语言建模退化，
却不能替代 tool calling、代码执行和业务指标。

建立预注册 gate，例如：

```text
公开 NLL：相对变化 <= 预设阈值
业务准确率：绝对变化 >= -预设百分点
JSON 合法率：不得低于门槛
关键安全集：不得新增严重失败
```

阈值必须由业务风险决定，教程不编造通用数字。

## goodput 与容量曲线
吞吐 \(R\) 不等于 goodput。给每个请求定义 SLO 指示函数：

\[
I_i=
\mathbf1[
\mathrm{TTFT}_i\le S_{\mathrm{TTFT}}
\land
\mathrm{TPOT}_i\le S_{\mathrm{TPOT}}
\land
\mathrm{quality}_i=pass
]
\]

观察窗口 \(\Delta t\) 内：

\[
\mathrm{goodput}
=\frac{\sum_i I_i}{\Delta t}
\]

量化允许更高 batch，却让 P99 越线时，请求吞吐可能上升而 goodput 下降。决策树最后应比较
最大满足 SLO 的 request rate，而不是某个饱和点的峰值 token/s。

## Kernel 执行与 profiler gate
为每个候选画出实际算子路径：

```text
checkpoint codes/scales
  -> loader validation
  -> optional runtime repack
  -> activation quantize or cast
  -> selected GEMM kernel
  -> accumulator + epilogue
  -> attention with configured KV dtype
  -> collective communication
```

若需系统级证据，可按 v0.27.1 profiling 文档使用 Nsight Systems：

```bash
nsys profile \
  --trace-fork-before-exec=true \
  --cuda-graph-trace=node \
  --capture-range=cudaProfilerApi \
  --capture-range-end repeat \
  vllm serve "$MODEL_QUANT" \
    --served-model-name quant-eval \
    --profiler-config.profiler cuda
```

客户端：

```bash
vllm bench serve \
  --backend vllm \
  --model quant-eval \
  --dataset-name random \
  --random-input-len 512 \
  --random-output-len 32 \
  --num-prompts 2 \
  --profile
```

该接口也可能变化，执行前核对本机 help。检查：

- 是否出现预期 INT8/FP8/Marlin/FP4 GEMM；
- quantize/dequantize 是否融合；
- layout conversion 是否每步重复；
- fallback Linear 占比；
- NCCL 与 Attention 是否成为新瓶颈。

## 决策树：从硬约束逐层剪枝
按以下顺序执行，前一项不满足就不要进入后一项：

```text
1. checkpoint + runtime + GPU 是否有明确兼容组合？
   否 -> 排除
   是 -> 2

2. 优化目标是什么？
   权重容量 / Decode 带宽 -> W4A16 GPTQ/AWQ/Marlin 候选
   Prefill GEMM            -> Hopper/Ada FP8 或成熟 W8A8 候选
   KV 容量/长上下文        -> FP8 KV 独立候选
   Blackwell 原生 FP4      -> 先区分 NVFP4 与 MXFP4
   通信                    -> 量化权重可能不是主解

3. Kernel 是否在真实 TP shard 和业务 shape 上命中？
   否 -> 换兼容 recipe/layout，或排除
   是 -> 4

4. 正确性和质量 gate 是否通过？
   否 -> 提高位宽、缩小 group、保留敏感层或回退
   是 -> 5

5. 在相同流量和 KV 配置下，SLO/goodput 是否改善？
   否 -> 保留基线
   是 -> 6

6. 组合权重 + KV 量化是否仍分别可归因？
   否 -> 回到单变量实验
   是 -> 灰度、监控、保留回滚
```

### 快速候选矩阵
- **非 Hopper/Ada 的 NVIDIA GPU**：不要预设原生 W8A8 FP8；先核对 weight-only/INT4 路径。
- **Ada/Hopper**：比较 FP8 W8A8、INT8 W8A8 与 INT4，具体支持以当前矩阵为准。
- **Blackwell**：区分 NVFP4/MXFP4 和工具链版本；不要从旧 INT8 路径外推。
- **AMD/CPU/其他后端**：使用对应平台支持表，NVIDIA Kernel 名不能迁移。
- **短输入、长输出、小 batch**：重点看 Decode TPOT 与权重带宽。
- **长输入、短输出**：重点看 Prefill TTFT 和大 GEMM。
- **长上下文、高并发**：先核算 KV，而不是只压权重。

## 转换、质量、性能各自的失败模式
### 转换
- base revision 与 tokenizer revision 不一致；
- 校准文本未应用线上 chat template；
- 数据集 streaming/slicing 语义变化，实际样本数不符；
- 量化中途 OOM 后留下不完整 output 目录；
- `main` revision 移动，无法重现。

### 部署
- 自动识别到错误 quant method；
- runtime repack 占用额外峰值显存；
- TP 后 group/K 维不对齐；
- activation dtype 与 Kernel 支持不符；
- 打开 prefix cache、LoRA 或 structured output 后 backend 回退。

### 质量
- 用同一数据选择 recipe 并汇报；
- 只看 PPL，不测任务；
- greedy 字符串变化被误判为能力下降或无变化；
- 平均值掩盖数学、代码、长上下文和安全长尾；
- 权重量化与 KV 量化同时开启，无法归因。

### 性能
- 客户端与服务端同机争用 CPU；
- 没有 warmup，包含 JIT/CUDA graph 初始化；
- 基线与候选 KV block 数不同却强制相同并发，比较目标不清；
- 只报峰值吞吐，不报越过 SLO 的尾延迟；
- 用 `nvidia-smi` 采样替代 Kernel profiler。

## 上线的停止条件和回滚条件
在实验前写明：

- 任一关键质量 gate 失败，停止；
- 出现新 NaN/重复/格式失败，停止；
- Kernel 回退且收益来源无法解释，停止；
- P99、OOM 或 preemption 超门槛，停止；
- 线上代理质量持续越界，自动回滚到已验证 checkpoint。

量化格式、vLLM image、Attention backend、TP 和 KV dtype 应作为一个不可分割的发布单元。
## 第三步：定位瓶颈
### 权重容量瓶颈
现象：模型加载即 OOM；为了放下模型需要很多 GPU；KV Cache 预算被权重挤压。
优先候选：Weight-only INT4；FP8 权重；硬件支持时的 NVFP4；更小模型或并行策略调整。
### Decode 权重带宽瓶颈
现象：每步处理 token 较少；GPU 算力利用率不高；显存带宽较忙；Linear 权重读取占主导。
优先候选：AWQ/GPTQ INT4；其他引擎正式支持的 Weight-only 格式；结合 Continuous Batching 提高有效 batch。
### Prefill 计算瓶颈
现象：输入很长；GEMM 规模大；Tensor Core 利用率较高；TTFT 是主要 SLO。
优先候选：Hopper 上 FP8；有高效 Kernel 的 W8A8；Blackwell 上经过验证的 FP4；Chunked Prefill 等调度优化。
### KV Cache 容量或带宽瓶颈
现象：长上下文或高并发时 OOM；权重占用不是主要部分；Decode Attention 读取大量历史 K/V。
优先候选：FP8 KV Cache；GQA/MQA 模型；引擎正式支持的更低位 KV；限制上下文或改进缓存策略。
### 通信瓶颈
现象：多卡 collective 占比高；增加 GPU 反而扩展效率差。
量化权重未必解决激活通信。还需考虑：并行策略；通信 dtype；NVLink/网络拓扑；Expert Parallel；调度和 batch。
## 选型决策树
可以按以下顺序判断。
### 1. 模型是否放得下
如果放不下：优先看 Weight-only INT4；Hopper 可比较 FP8；Blackwell 可比较 NVFP4；同时核算 KV Cache 预算。
如果放得下，继续判断性能瓶颈。
### 2. 主要是 Prefill 还是 Decode
Prefill 为主：比较 W8A8 与 FP8；确认大矩阵命中原生 Tensor Core；关注 TTFT。
Decode 为主：比较 AWQ/GPTQ INT4；确认融合反量化 Kernel；关注 TPOT 和带宽。
### 3. 长上下文是否限制容量
是：单独评估 FP8 KV Cache；不要只量化权重；做长上下文质量集。
否：KV 量化可能不是第一优先级。
### 4. 硬件是否原生支持
非 Hopper GPU：不要预设 FP8 GEMM 收益；Hopper：优先验证 FP8；Blackwell：可验证 FP8、NVFP4/MXFP4；其他加速器：查看对应 vLLM 平台文档。
### 5. 质量是否允许回退
几乎不允许：从 BF16、FP8、W8A8 开始；对敏感层保留高精度。
允许有限回退以换容量：比较 AWQ/GPTQ INT4；必须设业务门槛。
极端压缩：只在明确硬件、Kernel 和质量证据下使用。
## 方案对照
### BF16/FP16
适合：质量基线；硬件缺少目标低精度路径；模型和 KV 都有足够显存。
注意：BF16 与 FP16 的范围不同；不能默认两者质量和稳定性完全一致。
### W8A8 / SmoothQuant
适合：INT8 Tensor Core 路径成熟；Prefill 大 GEMM 占比高；可准备代表性校准集；希望比 INT4 更保守。
关注：激活离群值；alpha；静态/动态 scale；算子覆盖。
### GPTQ / AWQ INT4
适合：权重显存或 Decode 带宽是重点；激活希望保持 BF16/FP16；目标 GPU 有成熟融合 Kernel。
关注：group size；zero-point；act-order；checkpoint 布局；Marlin 等 Kernel 兼容性。
### FP8
适合：Hopper 或更新 GPU；权重与激活低精度计算；也可单独用于 KV Cache。
关注：E4M3/E5M2；scale 粒度；静态或动态量化；累加与输出 dtype。
### NVFP4 / MXFP4
适合：Blackwell 及匹配软件栈；需要更激进压缩；已有对应 checkpoint 与 Kernel；有完整质量验证预算。
关注：两种格式不能混淆；block scale；工具链版本；硬件原生路径；敏感层回退。
### KV Cache 量化
适合：长上下文；高并发；KV 容量或带宽成为瓶颈。
关注：Attention backend；scale 来源；PagedAttention block 布局；长上下文质量；PD 解耦传输兼容。
## vLLM：先让模型可识别
量化模型目录通常至少包含：模型配置；权重分片；tokenizer 文件；量化配置或相关字段。
先检查模型卡和配置，确认：基础模型；量化算法；bit width；group size；scale 类型；推荐 runtime；是否要求自定义代码。
不要用目录名猜量化方法。启动前可做最小环境记录：
```bash
python - <<'PY'
import json
import platform
import torch
import vllm
print("python:", platform.python_version())
print("torch:", torch.__version__)
print("vllm:", vllm.__version__)
print("cuda:", torch.version.cuda)
print("gpu:", torch.cuda.get_device_name(0))
PY
```
这段代码使用 PyTorch 与 vLLM 的公开 Python 属性。若环境没有 GPU，`torch.cuda.get_device_name(0)` 会失败。
## 启动浮点基线
一个最小命令形态：
```bash
vllm serve /path/to/base-model \
  --dtype bfloat16
```
是否支持 `bfloat16`、是否应使用 `auto`，取决于模型和当前 vLLM 版本。生产测试通常还要显式设置：`--tensor-parallel-size`；`--max-model-len`；`--gpu-memory-utilization`；服务端口；其他调度参数。
每个参数都应先在 `vllm serve --help` 核对。
## 启动量化 checkpoint
对能够自动识别量化配置的模型，命令形态可能仍然只是：
```bash
vllm serve /path/to/quantized-model
```
某些版本或格式需要：
```bash
vllm serve /path/to/quantized-model \
  --quantization <method>
```
`<method>` 是占位符，不是可直接执行的参数值。应从以下来源确定：
1. 当前版本 `vllm serve --help`；
2. vLLM 官方量化文档；
3. checkpoint 模型卡；
4. 启动日志。
强行指定错误方法可能：加载失败；误解打包布局；跳过自动识别；使用不兼容 Kernel。
## 配置 FP8 KV Cache
当前版本支持时，命令形态为：
```bash
vllm serve /path/to/model \
  --kv-cache-dtype <supported-kv-dtype>
```
`<supported-kv-dtype>` 同样是占位符。必须检查：本机帮助列出的取值；GPU 是否支持；Attention backend 是否支持；scale 是从 checkpoint 读取还是在线计算；prefix cache、PD 解耦等组合功能。
KV dtype 应作为独立实验变量，不要同时更换权重量化和服务参数后再归因。

服务启动后，可先查询模型：
```bash
curl http://localhost:8000/v1/models
```
再发送确定性较强的请求：
```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "/path/to/model",
    "messages": [
      {"role": "user", "content": "用一句话解释什么是量化。"}

```

## 正确性测试矩阵
至少覆盖：空或极短 Prompt；常规聊天；长 Prompt；接近最大上下文；多并发；流式与非流式；stop token；JSON/结构化输出（若使用）；Tool Calling（若使用）；多 LoRA（若使用）。
观察：启动日志是否出现回退或警告；输出是否含 NaN；是否持续重复；finish reason 是否合理；token 数是否符合预期；多 GPU 是否死锁。
## 质量评测设计
### 固定生成配置
比较量化前后时保持：同一 Prompt；同一 chat template；同一 temperature；同一 top-p/top-k；同一 max tokens；同一 stop；尽可能固定 seed。
即使固定 seed，不同 Kernel 的数值差异也可能导致生成分叉。因此不要只做字符串完全匹配。
### 指标分层
第一层：基础数值信号
perplexity；logits 差异；层输出误差。
第二层：公开任务
选择题；数学；代码；多语言；长上下文。
第三层：业务指标
正确率；格式成功率；人工偏好；安全合规；关键失败率。
上线门槛应以第三层为核心。
## 性能压测设计
### 使用真实分布
请求集应保留：输入长度分布；输出长度分布；到达率；并发；Prompt 前缀复用率；业务采样参数。
均匀随机 token 适合微基准，不等于生产流量。
### 预热
预热可减少：Kernel 首次编译；CUDA context 初始化；CUDA graph 捕获；权重页首次访问；缓存冷启动。
记录预热请求数量与长度。
### 扫描负载
不要只测一个并发点。逐步增加：request rate；max concurrency；输入长度；输出长度。
直到：延迟越过 SLO；队列持续增长；出现 OOM；吞吐不再增加。
这能得到容量曲线，而不是一个偶然数字。
## vLLM Benchmark 命令原则
vLLM 提供 benchmark CLI，但接口会演进。先查看：
```bash
vllm bench serve --help
```
再根据当前帮助设置：backend；base URL；model；dataset；request rate；number of prompts；input/output length；percentile 指标。
下面仅是结构伪代码：
```bash
# 伪代码：参数名需按当前 `vllm bench serve --help` 替换
```

标注伪代码比给出可能过期的“可复制命令”更可靠。
## 显存测量
不要只看 `nvidia-smi` 的某一瞬间。至少区分：服务启动后的静态占用；预热后的占用；压测峰值；KV Cache 预分配；其他同卡进程。
可记录：
```bash
nvidia-smi \
  --query-gpu=timestamp,index,name,memory.used,memory.total,utilization.gpu \
  --format=csv
```
这是 `nvidia-smi` 的标准查询形式。生产报告还应从 vLLM 日志记录：可用 KV blocks；最大缓存 token；是否发生 preemption；prefix cache 命中情况。
日志字段会随版本变化，解析器应与版本绑定。
## 结果怎样归因
一次只改变一个主变量。例如评估 AWQ：基础模型相同；KV dtype 相同；max model len 相同；batch 调度参数相同；只改变 checkpoint/权重量化。
评估 FP8 KV：权重 checkpoint 相同；服务参数相同；只改变 KV dtype 与其必要 scale 配置。
否则无法判断收益来自：量化；batch 变化；KV 预算变化；Kernel 后端变化；并行度变化。
## 计算容量收益
假设 BF16 基线最多满足：
```text
并发 16，最大上下文 8K
```
量化方案可能允许：
```text
并发 24，最大上下文 8K
```
这不是简单的“吞吐提升 50%”。还要验证：请求到达率相同吗；TPOT 是否仍满足 SLO；输出长度是否相同；是否出现更多排队；质量是否过门槛。
容量收益应报告为：
> 在指定硬件、SLO 和流量分布下，可稳定承载的并发或请求率变化。
## 组合量化
可以同时使用：INT4 权重；FP8 KV Cache。
两者分别压缩：共享的模型权重；按请求增长的缓存。
组合可能释放更多显存，但也叠加：权重量化误差；KV 量化误差；两套 Kernel 限制；更多兼容性组合。
验证顺序建议：
1. 浮点基线；
2. 只量化权重；
3. 只量化 KV；
4. 同时量化；
5. 比较误差是否近似叠加。
不要直接从基线跳到最激进组合。
## 多 GPU 注意事项
Tensor Parallel 下检查：每个 shard 的量化维度；group 边界；scale 切分；Kernel 对齐；collective dtype；rank 间输出一致性。
Pipeline Parallel 下检查：不同 stage 的显存是否均衡；量化是否让某些 stage 仍然成为瓶颈。
PD 解耦下检查：Prefill 与 Decode worker 的模型格式；KV Cache dtype；scale 元数据传输；Connector 是否支持；两侧 vLLM 版本。
量化配置必须纳入集群发布契约。
## 上线灰度
离线通过后，仍建议小流量灰度。监控：TTFT/TPOT 分位数；OOM；preemption；请求失败率；输出长度变化；业务质量代理指标；用户反馈；GPU 显存和功耗。
保留：浮点或旧量化版本；快速回滚配置；checkpoint 校验和；完整环境镜像；量化校准记录。
如果质量指标只能离线获得，线上仍可监控异常模式：重复；空响应；格式失败；工具调用参数错误；安全规则违反。
## 常见选型错误
### 只看模型卡里的吞吐
硬件、输入长度、并发和 vLLM 版本不同，数字不可直接迁移。
### 只看平均延迟
量化可能改变调度容量，尾延迟比平均值更能反映生产体验。
### 只测试短 Prompt
看不到 Prefill、KV Cache 和长上下文质量问题。
### 把“能加载”当作“支持”
支持至少包括正确性、Kernel、性能和功能组合。
### 同时改太多参数
无法归因，也无法安全回滚。
### 忽略校准来源
同一算法的两个 checkpoint 可能因校准数据不同而表现差异很大。

这个模板没有预填数字，因为数字必须来自实际环境。
## 最终选择原则
如果目标是“先放下模型”：优先比较成熟的 Weight-only INT4 与 FP8。如果目标是“降低 Decode 权重带宽”：优先比较 AWQ/GPTQ 及其融合 Kernel。如果目标是“提高 Prefill 计算吞吐”：在 Hopper 上重点验证 FP8，也可验证成熟 W8A8。如果目标是“扩展长上下文并发”：重点验证 FP8 KV Cache，并做长上下文质量评测。如果目标是“利用 Blackwell FP4”：确认 NVFP4/MXFP4 的准确格式、checkpoint、Kernel 和工具链版本。如果任何低精度方案未通过质量或 SLO：保留 BF16/FP16 是正确的工程选择，不是优化失败。
## 本节小结
量化选型应从瓶颈开始，而不是从最低 bit 开始。权重容量、Decode 带宽、Prefill 计算、KV Cache 和通信瓶颈对应不同方案。在 vLLM 中，先核对版本、帮助、官方支持矩阵和 checkpoint 配置，再通过启动日志确认 Kernel。实验必须固定基线，一次改变一个主变量，同时测质量、TTFT、TPOT、吞吐、尾延迟和显存。最终报告的是指定 SLO 下的可用收益，而不是理论压缩比或未经上下文的单个性能数字。
