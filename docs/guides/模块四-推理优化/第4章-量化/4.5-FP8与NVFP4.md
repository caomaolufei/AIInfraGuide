## 先说人话：整数尺与科学计数法
INT8 像一把刻度间距固定的尺子。无论数值大还是小，相邻格子的距离由同一个 scale 决定。浮点数更像科学计数法：
```text
有效数字 × 2^指数
```
它能用指数覆盖很大的范围，但有效数字位数有限。对神经网络而言，有些张量既包含很小的值，也会偶尔出现很大的值。
低比特浮点保留指数，可以比同位宽定点整数更自然地覆盖动态范围。代价是：
- 编码规则更复杂；有效精度有限；不同格式不兼容；必须依赖硬件和 Kernel 支持。

FP8 是 8-bit 浮点家族。NVFP4 与 MXFP4 是 4-bit 路线，但二者不是同一个名字的两种写法。
## 浮点格式由什么组成
典型二进制浮点包含：
- 1 位符号；若干指数位；若干尾数位。

概念上：
\[x=(-1)^s\times m\times 2^e\]
指数位越多：
- 动态范围通常越大；能覆盖更大或更小的数量级。

尾数位越多：
- 相邻可表示数更密；局部相对精度通常更好。

总位宽固定时，指数与尾数在“范围”和“精细度”之间竞争。此外还要定义：
- exponent bias；subnormal；infinity；NaN；是否 finite-only；舍入模式；饱和规则。

因此只知道 `E4M3` 还不够，要知道框架采用的具体变体。

## 问题驱动：格式名为什么不能直接推出数值
要从 `fp8` 或 `fp4` 推到可执行模型，至少要补齐：

1. bit pattern 如何解释，是否有 Inf/NaN/subnormal；
2. scale 是乘数还是除数，按 tensor、row、block 还是二维块共享；
3. scale 自己是什么 dtype，是否再次舍入；
4. data 和 scale 怎样打包、转置与 swizzle；
5. GEMM 输入、累加和输出分别是什么 dtype；
6. GPU 的哪条指令和库 Kernel 消费该布局。

低比特浮点的“浮点”只描述元素网格。工程格式往往是：

```text
element codes + one or two levels of scales + layout contract
```

## 正常数、次正规数和 ULP
对一个具有 \(E\) 个指数位、\(M\) 个尾数位、bias 为 \(B\) 的常规二进制浮点格式，正常数近似解码为：

\[
x=(-1)^s\left(1+\frac{f}{2^M}\right)2^{e-B}
\]

其中 \(e\) 是非特殊指数编码，\(f\) 是尾数字段。次正规数没有隐含前导 1：

\[
x=(-1)^s\left(\frac{f}{2^M}\right)2^{1-B}
\]

在同一个 binade \([2^k,2^{k+1})\) 内，相邻正常数间距约为：

\[
\operatorname{ULP}=2^{k-M}
\]

所以浮点量化误差随幅值增大。最近邻舍入的绝对误差约受半个 ULP 控制，而相对误差在正常数区间大致由尾数位决定。跨到 subnormal、饱和和特殊值时，这个简化不再成立。

## E4M3 与 E5M2 的明确版本边界
《FP8 Formats for Deep Learning》定义的两种互操作格式中：

```text
                  E4M3               E5M2
sign bits         1                  1
exponent bits     4                  5
mantissa bits     3                  2
exponent bias     7                  15
max finite        448                57344
min normal        2^-6               2^-14
min subnormal     2^-9               2^-16
infinity          no                 yes
```

E4M3 为扩大有限范围牺牲了 IEEE 风格的 Infinity 编码，只保留特定 NaN；E5M2 保留 Inf/NaN。
PyTorch 中常见名称是 `torch.float8_e4m3fn` 和 `torch.float8_e5m2`，但还存在
`e4m3fnuz` 等变体。`fn`、`fnuz` 不是装饰后缀：zero、NaN、bias 或范围语义可能不同。

### 手解一个 E4M3 编码
取 bit pattern：

```text
0 1000 010
```

- sign \(s=0\)；
- exponent field \(e=8\)，bias \(B=7\)，真实指数为 1；
- fraction \(f=2\)，三位尾数表示 \(2/8=0.25\)。

因此：

\[
x=(1+0.25)2^1=2.5
\]

同一 binade 的 ULP 为：

\[
2^{1-3}=0.25
\]

所以 2.6 在最近邻下会落到 2.5，2.7 会落到 2.75；恰好中点使用哪边取决于舍入规则。

### 手解一个 E5M2 编码
bit pattern：

```text
1 10000 01
```

- sign 为负；
- exponent \(16-15=1\)；
- fraction \(1/4\)。

\[
x=-(1+0.25)2^1=-2.5
\]

同样的 2.5 可表示，但 E5M2 在该 binade 的 ULP 是 \(2^{1-2}=0.5\)，比 E4M3 粗一倍。

## 可复现实验：让 PyTorch 报告真实格式
这段代码依赖安装的 PyTorch 支持对应 dtype；CPU 上的部分算子可能不支持，但 `finfo` 和 cast
在多数较新版本可用。应把失败也记录为版本证据。

```python
import torch

dtypes = []
for name in ("float8_e4m3fn", "float8_e5m2"):
    dtype = getattr(torch, name, None)
    if dtype is not None:
        dtypes.append(dtype)

for dtype in dtypes:
    info = torch.finfo(dtype)
    print(
        dtype,
        "max=", info.max,
        "tiny=", info.tiny,
        "eps=", info.eps,
    )

x = torch.tensor([2.5, 2.6, 2.7, 440.0, 500.0], dtype=torch.float32)
for dtype in dtypes:
    try:
        q = x.to(dtype)
        print(dtype, q.float())
    except RuntimeError as exc:
        print(dtype, "cast unsupported on this device/build:", exc)
```

不要把 500 cast 到 E4M3FN 的某次输出泛化到所有 FP8 变体；饱和、NaN 与 Inf 行为由 conversion
指令/API 规定。
## FP8 的 E4M3 与 E5M2
### E4M3
名称表示：
- 1 位符号；4 位指数；3 位尾数。

直觉上，它在 FP8 家族中偏向更多有效精度。常用于前向计算中的权重和激活，但具体用途由框架策略决定。
### E5M2
名称表示：
- 1 位符号；5 位指数；2 位尾数。

它牺牲一位尾数，换取更大指数范围。训练中梯度动态范围较大时，E5M2 可能更有吸引力。推理并不要求“一律 E4M3”。
应由模型、校准方法、硬件指令和推理引擎共同决定。
## FP8 为什么仍需要 scale
“有指数”不等于“无需缩放”。设原张量为 \(x\)，量化可概念化为：
\[q=\operatorname{cast}_{FP8}(x/s)\]
\[\hat{x}=s\cdot\operatorname{cast}_{high}(q)\]
scale 的目标是让数据更充分地落入 FP8 有效范围。如果直接 cast：
- 大值可能溢出或饱和；小值可能下溢；有效编码利用不足。

scale 可以采用：
- per-tensor；per-channel；per-token；per-block；动态 scale；延迟更新的历史 scale。

粒度越细通常越适应局部分布，但元数据和运行时开销越大。
## FP8 手算直觉
不展开某个具体 FP8 变体的位级编码，先看缩放作用。假设张量绝对最大值为：
\[a_{\max}=1000\]
假设目标格式希望把最大幅值映射到某个有限上界 \(F\)。可选择：
\[s=a_{\max}/F\]
于是最大值缩放后约为：
\[1000/s=F\]
其余数值也按相同比例缩放。这个过程与整数 min-max scale 类似，区别是量化网格不是等间距。浮点数的相邻间距随指数区间变化。
所以 FP8 的误差更适合看相对误差与溢出，不能完全套用 INT8 的“半个固定 scale”结论。

## scale 的方向、余量与舍入
设格式最大有限值为 \(F\)，张量 amax 为 \(A\)。采用除数定义：

\[
s=\frac{A}{F},\qquad
q=\operatorname{FP8}(x/s),\qquad
\hat x=s\operatorname{float}(q)
\]

有些系统使用乘数：

\[
s_{\text{inv}}=\frac{F}{A},\qquad
q=\operatorname{FP8}(xs_{\text{inv}})
\]

两者互为倒数。若希望为分布漂移留余量 \(\rho>1\)，可令：

\[
s=\frac{\rho A}{F}
\]

这会减少饱和风险，却让数值落在较低的 exponent 区域，并可能增加下溢或有效精度损失。

scale 若保存为 FP32、FP16、E8M0 或 E4M3，\(\hat x\) 还会叠加 scale 舍入。block scaling
之所以不只是“更细粒度 per-group”，就在于 scale dtype 与 block layout 是格式的一部分。

### scaled FP8 手算
E4M3 最大有限值 \(F=448\)，张量：

```text
x = [0.25, 2.5, 1000]
```

用 amax 除数：

\[
s=1000/448\approx2.232142857
\]

缩放后：

```text
[0.112, 1.120, 448]
```

第三个值恰好用到最大范围；前两个再落到 E4M3 的非均匀网格。即使 1000 反量化可接近原值，
0.25 也可能因共享 scale 进入较粗或 subnormal 区域。per-tensor FP8 的离群值问题仍然存在，只是
指数范围让它通常比同粒度定点更缓和。

## FP8 GEMM 的数据流
设两个操作数使用除数 scale：

\[
A\approx s_AQ_A,\qquad B\approx s_BQ_B
\]

则：

\[
C=AB\approx s_As_B(Q_AQ_B)
\]

若 \(s_A\) 是 per-row、\(s_B\) 是 per-column：

\[
C_{mn}\approx s^A_m s^B_n
\sum_k Q^A_{mk}Q^B_{kn}
\]

Kernel 可以在 epilogue 中广播 scale 外积。若是 block scale，K 维每块 scale 不同，缩放要参与
每个 partial dot product，硬件和布局必须显式支持。

Hopper FP8 路径的概念执行：

```text
高精度 activation
  -> amax reduction / delayed or static scale
  -> cast to E4M3/E5M2 tile
FP8 weight + scale
  -> Tensor Core FP8 MMA
  -> FP16/FP32 等更高精度累加
  -> scale + bias/activation epilogue
  -> BF16/FP16 output
```

checkpoint 是 FP8 只能省权重带宽；要称 W8A8 FP8 计算，还需 activation 也进入 FP8 MMA。
## Hopper 上的 FP8
NVIDIA Hopper 架构引入面向 FP8 的 Transformer Engine 和 Tensor Core 能力。
“Hopper 支持 FP8”包含多层含义：
1. 硬件指令支持 FP8 矩阵乘；
2. CUDA/cuBLASLt 等库提供路径；
3. 框架能生成合适布局与 scale；
4. 推理引擎能加载 checkpoint；
5. 模型 shape 能命中高性能 Kernel。

缺少任何一层，都可能出现：
- 无法加载；dtype 转换；高精度回退；性能不及预期。

FP8 GEMM 常以更高精度累加。输入 dtype、累加 dtype 和输出 dtype不应混为一谈。
## FP8 量化的常见方式
### 静态 FP8
使用校准集确定 scale。优点：
- 推理路径可预测；少做运行时归约；更容易融合。

风险：
- 分布漂移时可能饱和；校准集必须代表线上输入。
### 动态 FP8
根据当前激活计算 scale。优点：
- 适应输入范围；对激活变化更稳健。

代价：
- 需要最大值归约；增加量化 Kernel；可能影响 CUDA graph；小矩阵时开销占比高。
### Block FP8
每个小块共享 scale。它在精度和元数据之间折中，也便于某些 Kernel 以 tile 为单位处理。
具体 block shape 必须与导出格式和 Kernel 一致。
## FP8 与 INT8 的差别
二者都是 8 bit，但数值网格不同。INT8 配合单个 scale：
- 网格等间距；加减和 zero-point 语义直接；整数矩阵乘生态成熟。

FP8：
- 网格随指数变化；更自然覆盖多数量级；对动态范围大的激活有优势；强依赖新硬件原生支持。

精度不能仅由位宽判断。同一数据上，INT8 per-channel 可能优于粗粒度 FP8，也可能相反。需要比较具体 scale 粒度和 Kernel。
## 从 8 bit 再到 4 bit
FP4 只有 4 个 bit。如果单个数值独立承担符号、指数和尾数，可表示能力非常有限。工程上的关键办法是：
> 让一小块数值共享一个额外 scale。
每个 4-bit 元素只表示局部小范围，共享 scale 负责把这个局部范围搬到真实数量级。
这类设计常称为 microscaling 或 block scaling。其成本包括：
- 共享 scale 元数据；block 边界；scale 计算；特殊打包布局；对应 Tensor Core 数据通路。
## MXFP4 是什么
MX 是 Open Compute Project 的 Microscaling Formats 规范。其核心思想是：
- 一组低精度元素共享 scale；scale 使用规范定义的格式；元素使用 MX 规定的低精度类型；block size 和语义由规范约束。

MXFP4 是该标准体系中的 4-bit 浮点方案。谈论 MXFP4 时，应明确：
- 使用哪个版本的 OCP 规范；block size；scale 格式；元素格式；实现是否完全遵循规范。

不要把所有“带 block scale 的 FP4”都称为 MXFP4。

## MXFP4：按 OCP MX v1.0 解码
OCP Microscaling Formats v1.0 明确定义：

```text
element format:       FP4 E2M1
elements per block:   32
scale format:         E8M0
scale bits:           8
```

不含额外对齐时，一个 block 逻辑存储：

\[
32\times4+8=136\ \text{bits}
\]

平均：

\[
136/32=4.25\ \text{bits/element}
\]

E2M1 元素的有限幅值集合可由符号乘以下非负值理解：

```text
0, 0.5, 1, 1.5, 2, 3, 4, 6
```

最大幅值为 6。E8M0 scale 只有指数、没有尾数，表示 power-of-two scale（并保留规范定义的特殊编码）。
概念反量化：

\[
\hat x_i=2^{e_s-127}\cdot \operatorname{E2M1}(q_i)
\]

### MXFP4 手算
一个 block 的最大绝对值为 20。若选共享 scale \(S=4=2^2\)，缩放后最大值为 5，落在
E2M1 范围内。对：

```text
x = [20, 10, 3, -1]
x / S = [5, 2.5, 0.75, -0.25]
```

最近 E2M1 网格可能得到：

```text
q_value = [4 or 6, 2 or 3, 0.5 or 1, -0 or -0.5]
```

中点的选择依赖规范舍入。这个例子刻意展示 power-of-two scale 的限制：scale 便于硬件处理，
但不能像任意 FP16 scale 那样精细拟合 block。

MX block 的 32 个“连续元素”必须由 layout 定义。逻辑矩阵行尾、转置和 TP shard 都可能改变
block 分组，converter 与 Kernel 必须采用相同展平顺序。
## NVFP4 是什么
NVFP4 是 NVIDIA 面向 Blackwell Tensor Core 的 FP4 数据格式与量化路线。公开资料描述的关键点包括：
- 4-bit 浮点元素；细粒度 block scaling；额外的张量级缩放；与 Blackwell 硬件数据通路配合。

它和 MXFP4 都使用共享缩放思想，但 block 组织与 scale 设计并不相同。因此：
```text
NVFP4 != MXFP4
```
checkpoint 标注为 NVFP4，不能假设 MXFP4 Kernel 可直接读取，反之亦然。
应以 NVIDIA 官方格式说明、TensorRT Model Optimizer 和目标推理引擎文档为准。
## 双层 scale 的直觉
假设张量被切成很多 block。每个 block 有局部 scale \(s_b\)，整个张量还有全局 scale \(s_t\)。
概念性反量化可以写成：
\[\hat{x}_{b,i}=q_{b,i}\times s_b\times s_t\]
局部 scale 负责：
- 适应每个小块的范围；减少块内量化误差。

全局 scale 负责：
- 调整张量整体范围；配合特定 scale 编码的表示能力。

这只是帮助理解的抽象公式。具体 NVFP4 scale 编码、block 大小和处理顺序应以官方规范与实现为准。

## NVFP4：两级缩放的明确公式
NVIDIA Transformer Engine 文档定义的 NVFP4 元素同样是 E2M1，最大幅值 6，但 scale 体系不同：

```text
element:              E2M1, 4 bit
1D local block:       16 consecutive elements
local block scale:    FP8 E4M3
global scale:         one FP32 value per tensor
required architecture (TE path): SM100 Blackwell or later
```

按 Transformer Engine 的除数/恢复语义，可概念化为：

\[
x_i\approx s_{\text{global}}s_{\text{block}}
\operatorname{E2M1}(q_i)
\]

文档给出的构造：

\[
s_{\text{global}}
=\frac{\operatorname{global\_amax}}
{448\times6}
\]

\[
s_{\text{block}}
=\frac{\operatorname{block\_amax}/6}
{s_{\text{global}}}
\]

其中 \(s_{\text{block}}\) 再舍入到 E4M3。全局 FP32 scale 防止局部 E4M3 scale 的有限范围溢出，
局部 16-element scale 提供细粒度适应。

### NVFP4 数值手算
假设整个张量和某个 block 都有：

\[
\operatorname{amax}=2688=448\times6
\]

则：

\[
s_{\text{global}}=1
\]

\[
s_{\text{block}}=(2688/6)/1=448
\]

最大元素缩放后：

\[
2688/(1\times448)=6
\]

恰好落到 E2M1 最大值。若另一个 block 的 amax 是 12：

\[
s_{\text{block}}=(12/6)/1=2
\]

该 block 的最大值同样映射到 6。真实 \(s_{\text{block}}\) 要经过 E4M3 舍入，因此反量化误差包括：

1. E2M1 元素舍入；
2. E4M3 local scale 舍入；
3. 浮点运算与 global scale 误差。

### 1D 与 2D scaling 不要混写
Transformer Engine 文档还描述训练 recipe 对权重可使用 16×16 二维 block scaling，以改善转置相关行为；
activation 常见 1×16 连续分块。模型量化工具的推理 checkpoint 是否采用相同 2D 规则，必须查其格式说明，
不能把训练 recipe 自动套到 vLLM 推理产物。

### scale swizzle 与双布局
Tensor Core 不只需要值，还需要 scale 按硬件消费顺序排列。Transformer Engine 的 NVFP4 路径要求
对 block scales 做 swizzle，并为 GEMM 的 rowwise/columnwise 操作数准备匹配布局：

```text
rowwise data:      [A, B], blocks along B
columnwise data:   transposed view/layout
scales:            与每 16 元素 block 对齐后再 swizzle
```

如果只把 E2M1 nibbles 打包正确，却没有转换 scale layout，Kernel 无法正确解释。

## MXFP4 与 NVFP4 的并排边界

```text
                         MXFP4 (OCP MX v1.0)    NVFP4 (NVIDIA TE)
element                  E2M1                   E2M1
1D block size            32                     16
local scale              E8M0                   E4M3
extra tensor scale       none in MX format      FP32 global scale
effective raw bits       4.25/element           depends on layout/alignment;
                                                logical 4 + 8/16 plus global
native target            MX-capable hardware    Blackwell SM100+ TE path
```

NVFP4 的 local E4M3 scale 有尾数，块更小；MXFP4 的 E8M0 是 power-of-two scale。两者都叫 E2M1
并不能让 checkpoint 互换。

## 可复现实验：E2M1 教学量化器
下面实现明确列出 E2M1 非负网格，只用于数值直觉，不实现 OCP/NVIDIA 的 bit-level 特殊规则、
scale 舍入、swizzle 或硬件 Kernel。

```python
import torch

E2M1_POS = torch.tensor(
    [0.0, 0.5, 1.0, 1.5, 2.0, 3.0, 4.0, 6.0],
    dtype=torch.float32,
)

def nearest_e2m1(x):
    sign = torch.sign(x)
    distance = (x.abs().unsqueeze(-1) - E2M1_POS).abs()
    index = distance.argmin(dim=-1)
    return sign * E2M1_POS[index]

def block_qdq(x, block_size, power_of_two_scale):
    assert x.numel() % block_size == 0
    blocks = x.reshape(-1, block_size)
    scale = blocks.abs().amax(dim=1, keepdim=True).clamp_min(1e-12) / 6
    if power_of_two_scale:
        # 教学选择：向上取 2 的幂，避免最大值饱和。
        scale = torch.pow(2.0, torch.ceil(torch.log2(scale)))
    q_values = nearest_e2m1(blocks / scale)
    return (q_values * scale).reshape_as(x), scale.squeeze(1)

torch.manual_seed(5)
x = torch.randn(64) * torch.linspace(1, 20, 64)
for block_size, pow2 in ((32, True), (16, False)):
    x_hat, scales = block_qdq(x, block_size, pow2)
    rel = (x_hat - x).norm() / x.norm()
    print(block_size, pow2, "relative_l2=", rel.item(), "scales=", scales)
```

`(32, True)` 只模仿 MXFP4 的“32 元素 + power-of-two scale”直觉；
`(16, False)` 也不是完整 NVFP4，因为它没有 E4M3 local/global scale 两级舍入。

## Hopper 与 Blackwell 的 Kernel 路径
### Hopper FP8
Hopper Tensor Core 原生消费 FP8 操作数。性能成立的条件链：

```text
checkpoint scale/layout
  -> runtime FP8 tensors
  -> cuBLASLt/CUTLASS/Transformer Engine/vLLM supported shape
  -> Hopper FP8 MMA
  -> supported accumulator/epilogue
```

旧 GPU 可能把 FP8 checkpoint 作为 weight-only 读取并通过 Marlin 类 Kernel 转为高精度计算；
这与原生 W8A8 FP8 MMA 是不同路径。

### Blackwell FP4
Blackwell 增加面向 FP4/MX block-scaled 数据的 Tensor Core 能力。以 NVFP4 为例：

```text
读取 packed E2M1 A/B tiles
读取并按硬件布局提供 E4M3 block scales
结合 per-tensor FP32 scale
执行 block-scaled Tensor Core MMA
更高精度累加
epilogue 写出 BF16/FP16 等
```

scale swizzle、K 维 block 对齐和 row/column layout 是执行路径的一部分。把 FP4 先完整反量化到
BF16 再调用普通 GEMM 可能仍节省磁盘，却不代表 Blackwell FP4 计算路径。

## 质量与性能测量
### 数值诊断
按层记录：

- amax 与 scale 分布；
- saturation、subnormal、zero 比例；
- E2M1 各 code 的直方图；
- local scale 达到边界的比例；
- layer output relative-L2 和 cosine；
- NaN/Inf 首次出现位置。

FP8 还应区分 overflow 与 underflow；FP4 要把 element error 和 scale error 分开做 ablation。

### 性能证据
用 profiler/日志回答：

1. activation scale reduction 是否在关键路径；
2. GEMM Kernel 是否为 FP8/FP4/block-scaled 路径；
3. layout conversion/swizzle 是否每次执行；
4. fallback 层占总时间多少；
5. Prefill 和 Decode 的 shape 是否分别命中。

微基准报告 \(M,N,K\)、batching、alignment、warmup 和 GPU clocks；端到端再报告
TTFT、TPOT、吞吐、显存和 P99。官方峰值 TFLOPS 不是应用测量值。

## 失败模式与决策边界
- **E4M3 变体混淆**：`fn`/`fnuz` 特殊值语义不同。
- **scale 方向混淆**：乘数与除数倒置。
- **scale 先舍入被遗漏**：模拟用 FP32 scale，硬件格式实际用 E8M0/E4M3。
- **block 展平顺序不同**：converter 按行，Kernel 按转置/tile 分组。
- **scale 未 swizzle**：数据 code 正确，矩阵结果仍错误。
- **只检查 GPU 名称**：同代不同 compute capability、库版本或 shape 仍可能回退。
- **动态 scale 开销过大**：小 GEMM 被 amax reduction 支配。
- **敏感层一刀切**：所有层 FP4 导致长尾质量退化。

选择边界：

- Ada/Hopper 且需要 W8A8 FP8：先确认当前 runtime 的 compute capability 与支持表；
- Turing/Ampere 读取 FP8 checkpoint：明确它可能是 weight-only 高精度计算，而非原生 FP8 MMA；
- Blackwell FP4：先确定 checkpoint 是 MXFP4 还是 NVFP4，再核对 block/scale/layout；
- GPU 无原生路径：把 FP4/FP8 当容量格式评估，不预设计算加速；
- 质量不达标：提高 scale 粒度、保留敏感层或退回 FP8/BF16。

## 版本边界
FP8 数值以 2022 年 FP8 格式论文和当前 PyTorch `finfo` 为核验入口；MXFP4 以
**OCP Microscaling Formats v1.0** 为准；NVFP4 的 block/scale/SM100 描述以
**NVIDIA Transformer Engine 2.17 文档**为准。未来版本可能新增 recipe 或硬件，不能反向改写旧 checkpoint 语义。

截至 **2026-08-13**，本文核对的 vLLM **v0.27.1** 量化支持页仍按架构区分 FP8 W8A8、weight-only Marlin 与 FP4 实现。
部署必须记录 GPU compute capability、driver/CUDA、PyTorch、vLLM、量化工具和 checkpoint revision，
并以运行时选中的 Kernel 为最终证据。
## 为什么 Blackwell 很关键
低比特格式只有在硬件能高效消费时，才可能把压缩变成计算吞吐。Blackwell Tensor Core 提供面向 FP4 的硬件能力。
在更早 GPU 上：
- checkpoint 也许能被读取；但可能先转换到更高精度；或根本没有兼容 Kernel；不应期待同样的 FP4 计算收益。

所以 NVFP4 不是一个“对任意 CUDA GPU 都更快”的格式。硬件代际是选型的首要条件。
## Kernel 看到的不只是 dtype
高性能 FP8/FP4 Kernel 还关心：
- 权重布局；scale 布局；block size；tile shape；K 维对齐；M/N 维规模；累加类型；epilogue 融合；Tensor Parallel shard 后的局部 shape。

模型配置写了 `fp8` 或 `nvfp4`，只是声明意图。运行日志、profiler 和硬件计数器才说明实际走了哪条路径。
## Transformer 中哪些张量量化
“FP8 模型”可能有多种含义：
- 权重 FP8，激活高精度；权重与激活 FP8；Linear 使用 FP8，其他算子高精度；KV Cache 也使用 FP8；checkpoint 以 FP8 保存但加载后转换；动态激活 FP8。

必须明确：
1. 权重存储 dtype；
2. 激活输入 dtype；
3. GEMM 输入 dtype；
4. 累加 dtype；
5. 输出 dtype；
6. KV Cache dtype。

否则不同方案无法公平比较。
## 校准与敏感层
FP8 比 FP16 范围和精度都更有限。NVFP4/MXFP4 又进一步压缩。常见工程策略包括：
- 使用代表性校准集；对不同层独立 scale；对敏感层保留 BF16/FP16；对输出头使用更高精度；对少数离群通道使用更细粒度；通过量化工具搜索配置。

哪些层敏感与模型有关。不能无证据地规定“第一层和最后一层永不量化”。应让质量评测决定保留策略。

## 性能验证
至少建立同源模型对照：
- BF16/FP16；FP8；NVFP4 或 MXFP4（硬件和引擎支持时）。

记录环境：
- GPU 型号；驱动；CUDA；vLLM；模型 revision；量化工具及版本；scale 粒度；并行配置。

分别测量：
- Prefill TTFT；Decode TPOT；吞吐；并发容量；峰值显存；P95/P99；功耗（若业务关心）。

FP4 的理论算力数字不能代替端到端服务压测。
## 质量验证
低比特浮点的误差与整数不同，但质量门槛相同。建议包括：
- 基础任务集；业务评测集；数学与代码；多语言；长上下文；结构化输出；多模态（若模型支持）。

除平均值外，报告最差子集和失败样本类型。还要检查：
- NaN/Inf；重复输出；退化为高频 token；置信度异常；长输出后质量漂移。
## Trade-off 总览
### FP8
优势：
- 相比 FP16/BF16 减少存储和带宽；保留指数，适合较大动态范围；Hopper 及更新硬件有原生计算路径。

代价：
- 需要 scale 管理；质量依赖粒度和校准；旧硬件收益有限；格式变体与工具链复杂。
### NVFP4
优势：
- 更激进的权重/激活压缩潜力；面向 Blackwell FP4 Tensor Core；细粒度 scaling 改善 4-bit 表示能力。

代价：
- 对硬件代际要求高；scale 元数据与布局复杂；生态和兼容组合仍在演进；比 FP8 更需要严格质量验证。
### MXFP4
优势：
- OCP microscaling 标准体系；通过共享 scale 支撑 4-bit 元素。

代价：
- 不能与 NVFP4 混用概念；实现仍取决于硬件与软件支持；block 和 scale 规则必须精确匹配。
## 常见误区
### FP8 等于 INT8
位宽相同，编码网格、硬件指令和 scale 语义不同。
### FP4 checkpoint 在所有 GPU 上都快
没有原生硬件与 Kernel，可能转换或回退。
### MXFP4 就是 NVFP4
二者共享 microscaling 直觉，但格式定义不同。
### 量化后所有算子都是低精度
Norm、Softmax、部分 Linear 和累加可能仍保持高精度。
### 理论 TFLOPS 就是线上吞吐
服务还受访存、调度、Attention、通信和 batch shape 限制。
## 本节小结
FP8 用指数和尾数在 8 bit 内平衡范围与精度。E4M3 偏向尾数精度，E5M2 偏向指数范围，但具体变体和用途要看实现。
scale 仍是 FP8 工程的核心。FP4 通过 block/microscaling 扩展有限编码的可用范围。
MXFP4 属于 OCP MX 规范，NVFP4 是 NVIDIA 面向 Blackwell 的格式与量化路线，两者不能互换。
最终选择必须从 GPU 原生能力出发，再核对 checkpoint、Kernel、质量和端到端 SLO。
