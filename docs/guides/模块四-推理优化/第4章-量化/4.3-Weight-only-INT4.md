## 先说人话：把仓库压缩，工人照常工作
大模型 Decode 常像这样：
1. 从显存搬来一大批权重；
2. 只为当前少量 token 做计算；
3. 再为下一个 token 重复搬运。

如果计算单元等着权重到达，瓶颈就是显存带宽。Weight-only INT4 的思路是：
- 把仓库里的权重压成 4 bit；
- 激活仍保留 FP16/BF16；
- Kernel 读取压缩权重；
- 在计算附近反量化；
- 完成高精度激活参与的矩阵乘。

像把家具拆成平板运输，送到施工现场再快速展开。运输量减少了，但“展开家具”也有成本。能否变快取决于展开是否融合得足够好。
## Weight-only 到底量化了什么
对线性层：
\[Y=XW\]
Weight-only INT4 保存的是：
\[W_q,\ s,\ 可能还有\ z\]
激活 \(X\) 通常仍是 FP16 或 BF16。逻辑计算可以写成：
\[Y\approx X\cdot\operatorname{dequant}(W_q,s,z)\]
高性能 Kernel 不会先把整个 \(W\) 写回显存。它通常在 tile 级别：
1. 读取打包的 INT4；
2. 解包 nibble；
3. 读取 group scale；
4. 在寄存器或共享内存中转换；
5. 送入矩阵乘流水线；
6. 以更高精度累加。

这类“边读边解”的融合是性能关键。
## 为什么选择 INT4
FP16 每个权重占 16 bit。理想情况下，INT4 原始权重只占其四分之一。但真实 checkpoint 还包含：
- scale；
- 可选 zero-point；
- 元数据；
- 对齐 padding；
- 未量化层；
- tokenizer 和配置文件。

所以整个目录不会严格缩小到四分之一。运行时显存还包括：
- KV Cache；
- CUDA graph；
- workspace；
- 通信 buffer；
- 激活；
- 引擎元数据。

因此模型权重压缩比不能直接等同于服务显存压缩比。
## INT4 的表示与打包
4 bit 只有 16 个编码。常见有符号范围可以抽象为：
```text
[-8, 7]
```
某些对称实现使用不同边界约定。两个 4-bit 值可打包进一个字节：
```text
高 4 bit | 低 4 bit
```
但格式还必须约定：
- nibble 顺序；
- signed/unsigned 解释；
- scale dtype；
- zero-point 是否存在；
- group 沿哪个轴；
- 权重矩阵是否转置；
- tile 重排方式。

“都是 INT4”不代表二进制布局兼容。模型格式、加载器和 Kernel 必须说同一种语言。
## Group-wise 量化
设一组权重为 \(w_1,\ldots,w_G\)。对称量化可写作：
\[s=\frac{\max_i|w_i|}{7}\]
\[q_i=\operatorname{clip}( \operatorname{round}(w_i/s),-8,7)\]
\[\hat{w}_i=sq_i\]
group size \(G\) 是重要超参数。较小 group：
- 更贴合局部分布；
- 通常降低重建误差；
- scale 数量更多；
- 元数据占比更高；
- Kernel 处理更复杂。

较大 group：
- 压缩更整齐；
- scale 开销更少；
- 更容易高效向量化；
- 不同范围权重共用刻度，误差可能更大。

工程上常见的 group size 不是数学常数。只能选择量化工具和目标 Kernel 共同支持的值。
## 手算一个 INT4 group
假设一组权重：
```text
[-1.0, -0.4, 0.2, 0.9]
```
使用对称范围 `[-7, 7]` 便于手算。scale：
\[s=1.0/7\approx0.1429\]
量化结果：
```text
[-7, -3, 1, 6]
```
反量化：
```text
[-1.000, -0.429, 0.143, 0.857]
```
误差：
```text
[0.000, 0.029, 0.057, 0.043]
```
如果组里混入 `8.0`，scale 会变成约 `1.143`。其余小权重可能大量变成 0。这说明：
- group 内离群值很危险；
- 缩小 group 可隔离部分离群值；
- 算法也可以识别并保护重要权重。

GPTQ 与 AWQ 就从不同角度处理这个问题。
## GPTQ：不仅看权重误差
### 直觉
量化一列权重后会产生误差。如果知道后续哪些方向更敏感，就可以调整尚未量化的权重，补偿已经产生的误差。
像切木板时前一刀偏了，后续切割会主动修正，而不是每一刀互不相干。
### 二阶信息
对一层输入样本矩阵 \(X\)，局部重建目标常写成：
\[\min_{\widehat{W}} \|XW-X\widehat{W}\|_2^2\]
它不是单纯最小化：
\[\|W-\widehat{W}\|_2^2\]
输入相关的二阶结构可由近似 Hessian 表达。
GPTQ 基于 Optimal Brain Quantization 思路，逐列量化并利用逆 Hessian 信息更新剩余权重。直观上：
- 经常被激活放大的方向更重要；
- 误差应按输入分布加权；
- 已量化列的误差可由未量化列补偿。
### 工程参数
常见 GPTQ 产物会涉及：
- bit width；
- group size；
- symmetric/asymmetric；
- activation ordering（常见名 `desc_act` 或 act-order）；
- dampening；
- block size；
- calibration dataset。

字段名称和支持组合随工具变化。不要只复制模型卡中的一个 `--quantization gptq`，还要读取 checkpoint 的量化配置。
### GPTQ 的 trade-off
优点：
- 无需完整再训练；
- 利用输入统计，通常优于朴素舍入；
- 生态成熟，已有多种推理实现。

代价：
- 离线量化计算较重；
- 对校准样本敏感；
- 不同 GPTQ 格式并不总兼容；
- act-order 等特性可能限制 Kernel 选择。
## AWQ：保护真正重要的权重
### 直觉
权重绝对值大，不一定代表它对输出最重要。一个权重是否重要，还取决于对应激活通道是否经常很大。AWQ 的观察是：
> 只保护很少一部分显著权重，就能明显减小量化造成的输出误差。它使用激活统计识别显著通道，再通过通道缩放寻找更适合量化的权重表示。
### 缩放思路
仍考虑：
\[Y=XW\]
可以插入通道缩放：
\[Y=(X\operatorname{diag}(s)^{-1}) (\operatorname{diag}(s)W)\]
AWQ 搜索有利于权重量化的缩放，使重要权重在 INT4 网格中得到更好保护。与 SmoothQuant 的形式看起来相似，但目标不同：
- SmoothQuant 重点是让激活更容易做 W8A8；
- AWQ 重点是提高 Weight-only 低比特量化质量。

不要把两者因为“都有缩放”就视为同一算法。
### AWQ 的 trade-off
优点：
- 训练后完成；
- 利用激活感知重要性；
- 有成熟的 INT4 推理生态；
- 通常适合权重带宽受限场景。

代价：
- 仍需要代表性校准数据；
- 搜索配置与导出格式要匹配引擎；
- 某些 shape 或硬件上未必走最佳 Kernel；
- 极端任务仍可能出现质量回退。
## GPTQ 与 AWQ 怎样选
两者都属于 Weight-only PTQ，但优化思路不同。GPTQ 更强调：
- 二阶误差补偿；
- 逐列或分块量化；
- 层输出重建。

AWQ 更强调：
- 激活感知；
- 显著权重保护；
- 通道缩放搜索。

不要只用算法名称选型。应比较具体产物：
- 同一基础模型 revision；
- 同一 bit 与 group size；
- 同一目标 GPU；
- 同一引擎版本；
- 同一质量集；
- 同一性能压测。

社区 checkpoint 的校准数据与参数可能不同，算法名相同也不能保证质量相同。
## Marlin Kernel：压缩如何变成速度
Marlin 是面向低比特权重、高精度激活矩阵乘的高性能 Kernel 路线。它解决的不只是数学计算，还包括：
- INT4 权重打包和重排；
- 合并全局内存读取；
- 高效反量化；
- scale 应用；
- Tensor Core 友好的数据供给；
- 不同线程块之间的工作划分。

可以把它理解为一条流水线：
```text
压缩权重读取
  -> 解包与转换
  -> scale 融合
  -> Tensor Core 计算
  -> 高精度累加
```
如果每个阶段配合不好，省下的显存带宽会被解包、同步或低占用率抵消。Marlin 不是所有 INT4 checkpoint 的通用开关。是否可用取决于：
- GPU 架构；
- 量化格式；
- bit width；
- group size；
- 是否有 zero-point；
- act-order；
- 矩阵 shape；
- vLLM 版本。

应以当前 vLLM 官方支持矩阵和启动日志为准。
## Prefill 与 Decode 的差异
Prefill 一次处理许多 token，矩阵乘规模较大。这时可能更偏计算受限，原生 W8A8/FP8 等路线也很有吸引力。
Decode 每步 token 数少，但每层都要读取权重。这时常更偏权重带宽受限，Weight-only INT4 的压缩价值更明显。
不过高并发 Continuous Batching 会改变矩阵 shape。所以不能笼统地说：
> INT4 只对 Decode 有用。
必须按线上 batch 分布分别测试 Prefill 和 Decode 指标。
## Tensor Parallel 的约束
权重矩阵会沿某个维度切到多个 rank。切分后需要检查：
- 局部维度是否满足 Kernel 对齐；
- group 是否跨越 shard 边界；
- scale 是否正确切分；
- 打包布局是否需要重新排列；
- 通信是否成为新瓶颈。

量化减少单卡权重，但不会自动减少所有 collective 通信。某些并行策略中传输的是激活，其 dtype 可能仍为 FP16/BF16。
## vLLM 使用前检查
先确认当前版本：
```bash
python -c "import vllm; print(vllm.__version__)"
vllm serve --help
```
然后阅读 checkpoint 的：
- `config.json`；
- 量化配置文件；
- 模型卡；
- 基础模型 revision；
- 推荐 runtime。

典型服务命令形态是：
```bash
vllm serve /path/to/quantized-model
```
是否需要显式传入 `--quantization`，以及允许的值，应以当前版本帮助和官方文档为准。不要为“看起来像 AWQ”的普通模型强行指定 AWQ。
## 验证真实性能
### 基线
至少比较：
- 原始 BF16/FP16；
- GPTQ INT4；
- AWQ INT4。

如果显存无法同时满足相同并发，应同时报告：
1. 相同服务配置下的性能；
2. 各自最大可承载配置下的容量。
### 指标
记录：
- checkpoint 大小；
- 加载后权重显存；
- 峰值显存；
- TTFT；
- TPOT；
- output token throughput；
- request throughput；
- P95/P99；
- GPU 利用率与显存带宽。
### 质量
不要只看一条聊天输出。应覆盖：
- 标准任务指标；
- 领域数据；
- 长上下文；
- 结构化输出；
- 代码与数学；
- 安全和拒答行为。
## 常见失败模式
### 格式不兼容
加载器理解的 packing 与 checkpoint 不一致。结果可能是直接报错，也可能是输出异常。
### group size 不支持
算法允许某个 group size，Kernel 却没有对应实现。
### act-order 限制
GPTQ 的列重排可能需要额外索引，影响特定 Kernel 的兼容性或性能。
### 小 batch 没跑满
省下权重带宽，但 Kernel 启动和反量化开销占比太高。
### 质量平均值掩盖长尾
总体得分接近，关键子任务却明显回退。
### 把磁盘压缩当作运行时压缩
某些 checkpoint 在加载时会展开到更高精度。需要看实际显存和 Kernel，不能只看文件后缀。
## 本节小结
Weight-only INT4 主要压缩固定权重，激活通常保持 FP16/BF16。
它尤其适合权重搬运占主要成本的场景，但性能依赖融合反量化 Kernel。GPTQ 用二阶信息和误差补偿改善量化，AWQ 用激活统计保护重要权重。
算法决定精度上限，打包格式决定能否加载，Marlin 等 Kernel 决定压缩能否转化为速度。
选型时要同时看质量、显存、shape、GPU 和服务 SLO。
