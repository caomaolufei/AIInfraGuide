## 1. 固定环境与实验输入

### 1.1 环境与模型

安装、模型下载和基础服务用法沿用第三章。本节单卡示例采用 `Qwen/Qwen3-8B` 作为 Target，`Qwen/Qwen3-0.6B` 作为独立 Draft，与官方 Draft 示例的模型组合一致。需要能同时容纳两者、KV 与运行工作区的设备；显存不足时先减小上下文或并发，并对全部实验使用相同限制。[官方示例](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/features/speculative_decoding/draft_model.md)

```bash
python -m venv .venv-spec
source .venv-spec/bin/activate
python -m pip install 'vllm==0.31.0'
python -c "import vllm; print(vllm.__version__)"
nvidia-smi
python -m pip freeze > environment.txt
```

记录 GPU、驱动、vLLM/PyTorch 版本、模型 revision、dtype 和启动命令。复测时使用相同的本地模型快照或固定 revision。第一轮暂不叠加权重或 KV 量化，以便把投机带来的差异分离出来。

### 1.2 两组可检查的输入

将下面代码保存为 `make_cases.py`。它生成代码局部修改与开放问答两组 JSONL，并提前应用同一 Chat Template，关闭本例的思考模式。之后通过 Completions 接口发送已经格式化的 Prompt，避免客户端与服务端重复套模板。

```python
import json
from pathlib import Path
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen3-8B")
code_prompts = []
for changed in range(4):
    source = "\n\n".join(
        f"def item_{i}(value):\n    return value + {i}"
        for i in range(8)
    )
    code_prompts.append(
        f"将 item_{changed} 的加法改成乘法，其余保持原样。"
        f"只输出完整 Python 代码。\n\n{source}"
    )
chat_prompts = [
    "一个人搬到陌生城市，怎样逐步建立日常生活？请给出具体建议。",
    "讨论远程工作对团队沟通的影响，并给出你的判断。",
    "设计一场让不同年龄的人都能参与的社区活动，解释设计理由。",
    "如果每天多出一小时，你会怎样安排？比较两种不同选择。",
]
for task, prompts in [("code", code_prompts), ("chat", chat_prompts)]:
    rows = []
    for i, content in enumerate(prompts):
        prompt = tokenizer.apply_chat_template(
            [{"role": "user", "content": content}],
            tokenize=False, add_generation_prompt=True,
            enable_thinking=False,
        )
        rows.append({"id": i, "prompt": prompt, "output_tokens": 384})
    Path(f"{task}.jsonl").write_text(
        "".join(json.dumps(row, ensure_ascii=False) + "\n" for row in rows),
        encoding="utf-8",
    )
```

```bash
python make_cases.py
```

这八条输入用于跑通流程。代码组有意包含可复制片段，适合观察 N-gram 的工作方式；不能据此得出所有代码任务都优于对话的结论。正式评测应换成足够多的独立业务样本，并记录输入与输出长度分布。不同任务首先分别与自己的基线比较，再分析组间差异。

## 2. 依次启动三组服务

在终端 A 中设置公共参数。三组实验每次只运行一个服务，完成一组后停止它，再启动下一组。关闭 Prefix Cache 以减少重复输入对本次对照的干扰；所有组都保持这一设置。

```bash
TARGET=Qwen/Qwen3-8B
COMMON=(
  "$TARGET"
  --host 127.0.0.1 --port 8000
  --served-model-name spec-target
  --dtype bfloat16
  --max-model-len 4096
  --max-num-seqs 16
  --gpu-memory-utilization 0.85
  --generation-config vllm
  --no-enable-prefix-caching
  --seed 42
)

# 第一组：普通 Decode。
vllm serve "${COMMON[@]}"
```

第二组使用 N-gram，匹配长度在 2 到 5 之间，最多提议 4 个 Token：

```bash
vllm serve "${COMMON[@]}" \
  --speculative-config '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_min":2,"prompt_lookup_max":5}' \
  --per-request-spec-decode-metrics summary
```

第三组使用独立小模型，同样最多提议 4 个 Token：

```bash
vllm serve "${COMMON[@]}" \
  --speculative-config '{"method":"draft_model","model":"Qwen/Qwen3-0.6B","num_speculative_tokens":4}' \
  --per-request-spec-decode-metrics summary
```

`--speculative-config` 接收 JSON 对象；匹配窗口控制 N-gram 查找，`num_speculative_tokens` 控制候选长度。温度等生成参数放在请求中。本实验保留默认的标准接受方法，避免引入模拟接受率等额外变量。[配置定义](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/features/speculative_decoding/README.md#--speculative-config-schema)

## 3. 采集每个请求的接受情况

v0.31.0 可以通过 `summary` 在单序列响应的 `metrics.speculative_decoding` 中返回计数。这是实验性接口，依赖该字段时需要固定版本；服务端未启用采集、普通 Decode 或多序列请求的字段可能为空。[指标定义](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/features/speculative_decoding/acceptance_metrics.md)

下面保存为 `probe.py`。它串行发送两组输入，保存原始输出与指标；预热请求不参与汇总，指标缺失和没有候选分开处理。

```python
import argparse
import json
import time
from pathlib import Path
from urllib.request import Request, urlopen

parser = argparse.ArgumentParser()
parser.add_argument("label", choices=["baseline", "ngram", "draft", "suffix", "eagle"])
args = parser.parse_args()

def complete(row):
    payload = {
        "model": "spec-target", "prompt": row["prompt"],
        "temperature": 0, "max_tokens": row["output_tokens"],
        "seed": 42, "n": 1, "stream": False,
    }
    request = Request(
        "http://127.0.0.1:8000/v1/completions",
        data=json.dumps(payload).encode("utf-8"),
        headers={"Content-Type": "application/json"},
    )
    start = time.perf_counter()
    with urlopen(request, timeout=600) as response:
        data = json.load(response)
    return data, time.perf_counter() - start

for task in ["code", "chat"]:
    rows = [json.loads(line) for line in Path(f"{task}.jsonl").read_text(
        encoding="utf-8").splitlines() if line.strip()]
    complete(rows[0])  # 预热，不纳入下面的计数
    records, stats = [], []
    for row in rows:
        data, elapsed = complete(row)
        metric = (data.get("metrics") or {}).get("speculative_decoding")
        if args.label != "baseline" and metric is None:
            raise RuntimeError("缺少投机指标，请核对版本与服务端采集开关")
        if metric is not None:
            stats.append(metric)
        records.append({
            "id": row["id"], "e2e_seconds": elapsed,
            "usage": data.get("usage"), "choice": data["choices"][0],
            "speculative_decoding": metric,
        })
    Path(f"{args.label}-{task}.jsonl").write_text(
        "".join(json.dumps(r, ensure_ascii=False) + "\n" for r in records),
        encoding="utf-8",
    )
    drafted = sum(s["num_draft_tokens"] for s in stats)
    accepted = sum(s["num_accepted_draft_tokens"] for s in stats)
    steps = sum(s["num_spec_steps"] for s in stats)
    print(task, {
        "drafted": drafted, "accepted": accepted, "steps": steps,
        "acceptance_rate": accepted / drafted if drafted else None,
        "accepted_per_step": accepted / steps if steps else None,
        "requests_with_drafts": sum(s["num_draft_tokens"] > 0 for s in stats),
        "requests": len(rows),
    })
```

服务就绪后，在终端 B 按当前服务对应的标签运行一次：

```bash
python probe.py baseline
# 切换到 N-gram 服务后运行：python probe.py ngram
# 切换到独立 Draft 服务后运行：python probe.py draft
```

汇总时先加计数再相除，不对各请求的百分比做简单平均。`drafted=0` 表示本组没有提议，接受率输出 `None`；它与“提议了但全被拒绝”含义不同。脚本打印的是不含额外 Token 的平均接受草稿长度，官方 `mean_acceptance_length` 字段另有包含额外 Token 的定义，应避免混用。

这里的 `e2e_seconds` 是非流式请求的总耗时，包含 Prefill、生成和通信，不能当成 TPOT。预热次数也可增加，但三组设置应保持相同。代码组与对话组的接受率差异由实际打印结果给出。

## 4. 比较延迟与吞吐

接受率探测完成后，用流式 Benchmark 测延迟。下面仍读取同一份 JSONL；因为 Prompt 已应用模板，必须传 `--skip-chat-template`。Completions 接口与 `openai` 后端配套使用。

```bash
# 根据终端 A 当前服务填写，后续组分别改为 ngram、draft。
label=baseline
mkdir -p results
for task in code chat; do
  num_prompts=$(wc -l < "${task}.jsonl")
  vllm bench serve \
    --backend openai --endpoint /v1/completions \
    --host 127.0.0.1 --port 8000 \
    --model Qwen/Qwen3-8B --served-model-name spec-target \
    --dataset-name custom --dataset-path "${task}.jsonl" \
    --skip-chat-template --num-prompts "$num_prompts" \
    --temperature 0 --seed 42 \
    --request-rate inf --max-concurrency 1 \
    --percentile-metrics ttft,tpot,itl,e2el \
    --save-result --result-dir results \
    --result-filename "${label}-${task}-c1.json"
done
```

`output_tokens` 提供输出预算，实际生成可能遇到 EOS 提前结束。更换为正式数据后，再将 `--max-concurrency` 改为 4、8 等值，并修改结果文件名；每个并发档位都要有普通 Decode 对照。只有四条样本时，高并发与尾延迟没有足够统计意义。[Benchmark 与 CustomDataset](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/benchmarking/cli.md)

| 记录项 | 为什么需要 |
|---|---|
| 接受数、提议数、验证轮数 | 解释平均推进长度 |
| 无候选请求数 | 解释历史匹配的覆盖情况 |
| TTFT、TPOT、端到端延迟 | 分开观察首 Token、生成阶段与整体体验 |
| ITL 与尾延迟 | 观察多 Token 成批输出后的间隔 |
| 实际输出 Token 数、吞吐 | 防止短输出造成表面上的加速 |
| KV 使用、抢占和 GPU 利用率 | 检查额外状态是否压缩服务容量 |

如果要单独比较固定生成长度的计算成本，可以另设忽略 EOS 的性能实验，明确标注这项变化；质量评测仍应保留正常停止条件。至少重复数轮并保留原始结果，用中位数和波动范围报告，而非挑选最好的一轮。

## 5. Suffix 与 EAGLE 的配置

### 5.1 Suffix Decoding

vLLM 的 Suffix 路径需要 Arctic Inference。安装后重新保存依赖版本，并检查其与当前 vLLM 的兼容性：

```bash
python -m pip install arctic-inference
python -m pip check
python -m pip freeze > environment-suffix.txt
vllm serve "${COMMON[@]}" \
  --speculative-config '{"method":"suffix","num_speculative_tokens":16,"suffix_decoding_max_cached_requests":0}' \
  --per-request-spec-decode-metrics summary
```

这里的 16 是动态候选长度的上限。将跨请求缓存上限设为 0，是为了先隔离其他请求历史的影响；随后可以另做开启全局历史的实验，并记录预热、输入顺序和缓存配置。运行 `python probe.py suffix` 可采集相同指标。[Suffix 配置](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/features/speculative_decoding/suffix.md)

### 5.2 EAGLE 与 EAGLE-3

EAGLE 需要针对具体 Target 训练的辅助检查点，不能把独立小模型路径直接填进去。固定版本的官方文档提供了匹配的 EAGLE 示例；EAGLE-3 则使用对应的 `eagle3` 方法。[加载示例](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/features/speculative_decoding/eagle.md)

下面使用本地路径占位，运行前必须替换为一对兼容的 Target 和 EAGLE-3 检查点：

```bash
EAGLE_TARGET=/path/to/target-snapshot
EAGLE_DRAFT=/path/to/matching-eagle3-checkpoint
vllm serve "$EAGLE_TARGET" \
  --host 127.0.0.1 --port 8000 --served-model-name spec-target \
  --max-model-len 4096 --no-enable-prefix-caching \
  --speculative-config "{\"method\":\"eagle3\",\"model\":\"$EAGLE_DRAFT\",\"num_speculative_tokens\":4}" \
  --per-request-spec-decode-metrics summary
```

核对 Target revision、Tokenizer、特征层、dtype 和辅助模型的训练来源。若换了 Target，需要用它的 Tokenizer 重新生成输入，并重新运行普通 Decode 基线；不能把前面的 Qwen3 结果当作这个新组合的对照。`method` 选择加载与执行路径，不保证后端逐项实现论文中的动态树结构。

## 6. 解释结果与排错

先检查普通 Decode 与投机输出。贪心实验中，明显的 Token 差异应排查模板、模型版本、停止条件及缓存状态；概率接近的候选还可能受数值差异影响。随机采样则需要分布或任务评测，不能要求同一个种子逐字复现。

代码样本应检查修改是否正确、未修改部分是否保留；正式代码任务运行相应测试。对话样本则按目标质量指标评估，不能把接受率当作回答正确率。

| 现象 | 优先检查 |
|---|---|
| 未知配置字段或没有指标 | vLLM 版本、JSON 格式、采集开关与 `n=1` |
| N-gram 接受率高，整体收益小 | 实际有候选的请求比例、查找成本、输出长度 |
| Draft 接受长度较长，延迟仍增加 | Draft 耗时、验证长度、额外通信 |
| 并发增加后投机更慢 | GPU 计算是否已充分利用、KV 容量与抢占 |
| EAGLE 加载失败或接受率异常 | Target 与辅助检查点、特征层及词表是否匹配 |
| 代码与对话结果接近或反转 | 重复模式、语言、长度、采样与 Draft 的任务匹配 |

下一轮调优只改一项，例如候选长度 2、4、8，或 N-gram 的查找窗口。把新配置与对应基线重新比较后，再决定是否引入量化、更大并发或树形候选。

## 📝 总结

- 固定版本、Target 和输入，依次运行普通 Decode 与不同草稿方案。
- 逐请求保存接受计数，区分无候选、拒绝和指标缺失。
- 分任务比较接受情况，再以相同并发和输出条件比较延迟、吞吐与质量。
- Suffix 依赖历史状态，EAGLE 依赖匹配检查点，两者都需要明确实验条件。
