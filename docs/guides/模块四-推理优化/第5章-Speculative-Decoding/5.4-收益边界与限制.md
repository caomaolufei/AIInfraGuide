投机解码最容易产生两种误判：

1. “平均一次接受 3 个 Token，所以一定有 3 倍加速。”
2. “论文在 batch=1 快 2 倍，所以线上吞吐也会快 2 倍。”

两者都忽略了系统正在交换什么：

- 少做若干轮 Target 串行 Decode；
- 多做 Proposer、候选 Verify、采样、KV 写入与回滚；
- 用一个请求的候选 Token 占据本可服务其他请求的 batch 空间。

本节把这些项放进同一张成本账，并推导何时有收益、何时应该降低投机深度、何时应该直接关闭。

## 1. 先定义要优化的指标

### 1.1 单请求延迟

低 QPS 交互式服务通常关注：

- TTFT：Time To First Token；
- TPOT：Time Per Output Token；
- ITL：Inter-Token Latency；
- E2E latency。

投机主要改善 Decode TPOT，对 Prefill TTFT 影响有限，甚至可能因初始化 Draft 或争抢调度预算让 TTFT 变差。

### 1.2 吞吐

离线批处理常看：

$$
\text{Throughput}
=\frac{\text{总输出 Token}}{\text{总时间}}
$$

### 1.3 Goodput

在线服务更应看满足 SLO 的请求速率：

$$
\text{Goodput}
=\text{满足 TTFT/TPOT/P99 SLO 的请求数每秒}
$$

即使总 tokens/s 上升，若 P99 TTFT 因 Verify 占预算而超标，业务 goodput 仍可能下降。

### 1.4 容量

还要记录：

- 最大可服务并发；
- KV Cache 可用 block；
- OOM 前最大上下文；
- 每 GPU request/s；
- 每千 Token 成本。

投机可能降低单请求 TPOT，却因 Draft 权重挤压 KV 而降低最大并发。

## 2. 完整轮次模型

普通 Decode 生成 \(N\) 个 Token：

$$
T_{\text{base}}
\approx
\sum_{s=1}^{N}
T_1(B_s,C_s)
$$

其中：

- \(B_s\)：第 \(s\) 步活跃 batch size；
- \(C_s\)：平均上下文长度；
- \(T_1\)：Target 普通一步时间。

若简化为稳态：

$$
T_{\text{base}}
\approx NT_1(B,C)
$$

投机每轮平均提交：

$$
\bar L
=1+\sum_{i=1}^{K}P(A_i)
$$

需要约：

$$
R\approx\frac{N}{\bar L}
$$

轮次成本：

$$
T_{\text{round}}
=T_d+T_v+T_a+T_m+T_k+T_c
$$

分别是：

- \(T_d\)：Draft/Proposer；
- \(T_v\)：Target Verify；
- \(T_a\)：验收与采样；
- \(T_m\)：mask、position、batch metadata；
- \(T_k\)：KV 分配、提交和回收；
- \(T_c\)：跨 rank/设备通信。

于是：

$$
T_{\text{spec}}
\approx
\frac{N}{\bar L}T_{\text{round}}
$$

加速比：

$$
S
\approx
\frac{\bar L\,T_1(B,C)}
{T_{\text{round}}(B,C,K)}
$$

临界条件：

$$
T_{\text{round}}
<
\bar L\,T_1
$$

这条不等式贯穿本节。

## 3. 接受长度的边际收益

逐位置无条件存活率：

$$
s_i=P(\text{前 }i\text{ 个候选全接受})
$$

则：

$$
\bar L=1+\sum_{i=1}^{K}s_i
$$

从深度 \(K\) 增加到 \(K+1\)，分子只增加：

$$
\Delta\bar L=s_{K+1}
$$

若深度越后存活率越低：

```text
s = [0.88, 0.71, 0.51, 0.32, 0.17, 0.07]
```

各深度的 mean acceptance length：

| K | \(\bar L\) |
|---:|---:|
| 1 | 1.88 |
| 2 | 2.59 |
| 3 | 3.10 |
| 4 | 3.42 |
| 5 | 3.59 |
| 6 | 3.66 |

第 6 个候选只带来 0.07 个期望提交 Token，却要增加 Draft、Verify 和临时 KV。固定“越深越好”不成立。

### 3.1 边际条件

当前轮次成本为 \(T\)，长度为 \(L\)。增加一个候选的成本为 \(\Delta T\)，长度收益为 \(\Delta L\)。有利条件：

$$
\frac{T+\Delta T}{L+\Delta L}
<
\frac{T}{L}
$$

等价于：

$$
\frac{\Delta T}{\Delta L}
<
\frac{T}{L}
$$

新候选的单位期望收益成本必须低于当前平均。

## 4. 用 Roofline 看 Verify

### 4.1 单步 Decode

令：

- \(W\)：每轮需读取的 Target 权重字节；
- \(M_{\text{kv}}(B,C)\)：历史 KV 和其他内存流量；
- \(F(B)\)：单 Token batch 计算量；
- \(\beta\)：可用 HBM 带宽；
- \(\phi\)：可用算力。

近似：

$$
T_1(B,C)
\approx
\max\left(
\frac{W+M_{\text{kv}}(B,C)}{\beta},
\frac{F(B)}{\phi}
\right)
$$

### 4.2 验证 K 个候选

$$
T_v(B,C,K)
\approx
\max\left(
\frac{W+M_{\text{kv}}'(B,C,K)}{\beta},
\frac{K F(B)}{\phi}
\right)
+\delta(B,K)
$$

\(\delta\) 包含 mask、padding、kernel shape 和框架开销。

### 4.3 最有利区域

当：

$$
\frac{W}{\beta}
\gg
\frac{F(B)}{\phi}
$$

且候选增量内存不大时，单步 Decode 是权重 memory-bound。Verify 让同一次权重读取服务多个候选，\(T_v\) 可远小于 \(KT_1\)。

### 4.4 最不利区域

当：

$$
\frac{KF(B)}{\phi}
$$

成为主项，Verify 变成 compute-bound。此时多候选接近多做计算，难以靠减少权重读取获益。

## 5. Batch 如何改变结论

普通 continuous batching 已在请求维摊薄权重读取。batch 越大，每次读取权重参与的 Token 越多。

粗略把普通 Decode 的有效工作宽度记为 \(B\)，投机 Verify 宽度为：

$$
B_{\text{verify}}
\approx
\sum_{r=1}^{B}K_r
$$

固定深度 \(K\) 时：

$$
B_{\text{verify}}\approx BK
$$

例如：

```text
B = 128
K = 5
```

一次 Verify 约处理 640 个候选节点，尚未计 bonus、树旁支和 Prefill chunk。

### 5.1 低 QPS

- \(B\) 小；
- GPU 未饱和；
- 普通 Decode memory-bound；
- Verify 利用空闲算力；
- 目标通常是 TPOT。

这是投机的甜点区。

### 5.2 高 QPS

- \(B\) 大；
- 普通 Decode 已高效；
- Verify 让有效 batch 膨胀；
- 候选挤占新请求和 Prefill；
- 目标通常是 goodput。

此时即使单请求接受长度不变，吞吐也可能下降。

## 6. 一个 batch 数值例子

假设相同 Proposer 在两个负载下均有：

$$
\bar L=3.2
$$

### 6.1 batch=1

```text
T1 = 10.5 ms
Td = 3.0 ms
Tv = 12.5 ms
Ta+Tm+Tk+Tc = 1.0 ms
```

$$
S
=\frac{3.2\times10.5}{3.0+12.5+1.0}
=2.04
$$

### 6.2 batch=64

普通一步因权重摊薄，每请求等效 Token 处理很高：

```text
T1 = 4.0 ms
Td = 3.4 ms
Tv = 9.6 ms
其他 = 1.2 ms
```

$$
S
=\frac{3.2\times4.0}{14.2}
=0.90
$$

同一个模型、同一个接受长度，在大 batch 下慢 10%。

### 6.3 为什么不能只用每请求时间解释

高并发下还要比较：

```text
baseline 每步服务 64 个请求
spec verify 每步处理约 64×K 个候选
```

即便某些请求 TPOT 改善，总系统每秒完成请求数也可能下降。必须直接测吞吐与 goodput。

## 7. Continuous Batching 的 Token Budget

调度器每步通常有总 Token Budget：

$$
\sum_{r\in D}K_r
+\sum_{j\in P}P_j
\le
B_{\text{token}}
$$

- \(D\)：Decode/Spec Verify 请求；
- \(K_r\)：请求 \(r\) 本轮验证候选数；
- \(P\)：执行 Chunked Prefill 的请求；
- \(P_j\)：Prefill chunk Token 数。

### 7.1 与 Prefill 竞争

若 Spec Verify 占满预算：

- 新请求 Prefill 延后；
- TTFT 上升；
- Prefix Cache miss 请求更明显；
- P99 排队变差。

### 7.2 变长接受造成调度抖动

请求 A 一轮接受 5 个，B 接受 1 个：

```text
A 的剩余输出迅速缩短
B 继续频繁参与调度
```

batch 组成和序列长度快速变化，可能影响：

- CUDA Graph 命中；
- padding；
- KV block 分配；
- 请求公平性。

### 7.3 长尾请求

短请求完成后，batch 逐渐变小，投机可能从“不划算”转为“划算”。RL rollout 就常出现：

```text
开始：大 batch，K 应小
尾部：少量长请求，K 可增大
```

这也是动态投机深度的动机。

## 8. 动态深度：负载是运行时变量

理想的 \(K\) 应依赖：

$$
K^\star
=f(B,C,\text{acceptance},\text{GPU busy},\text{SLO})
$$

简单策略：

```python
def choose_k(batch_size, recent_survival, gpu_util):
    if batch_size >= 128 or gpu_util > 0.95:
        return 0
    if batch_size >= 64:
        return 1
    if recent_survival[2] > 0.45:
        return 4
    if recent_survival[0] > 0.70:
        return 2
    return 0
```

这只是概念示例，不是通用最优算法。

vLLM v0.27.1 提供 `num_speculative_tokens_per_batch_size`，可按 batch 区间配置 \(K\)。例如：

```json
{
  "num_speculative_tokens": 3,
  "num_speculative_tokens_per_batch_size": [
    [1, 64, 3],
    [65, 128, 1],
    [129, 512, 0]
  ]
}
```

但文档说明：

- 主要测试于 EAGLE、EAGLE-3、DFlash；
- 与 data parallelism 不兼容；
- 启用 DP 时会退回静态 `num_speculative_tokens`。

动态策略必须核对启动日志，而不是只看 JSON。

## 9. KV Cache 成本

### 9.1 每 Token KV 大小

粗略估算：

$$
M_{\text{KV/token}}
=2L H_{\text{kv}}d_{\text{head}}b
$$

- 2：K 和 V；
- \(L\)：层数；
- \(H_{\text{kv}}\)：KV head 数；
- \(d_{\text{head}}\)：head dimension；
- \(b\)：每元素字节数。

例：

```text
L = 32
Hkv = 8
dhead = 128
BF16 b = 2 bytes
```

$$
M_{\text{KV/token}}
=2\times32\times8\times128\times2
=131072\text{ bytes}
=128\text{ KiB}
$$

100 个请求各临时验证 5 个候选：

$$
100\times5\times128\text{ KiB}
\approx62.5\text{ MiB}
$$

这只是候选 KV，不含 Draft KV、block 内碎片和 workspace。

### 9.2 树节点

树有 \(N_{\text{tree}}\) 个节点时，每节点都需要自己的新增 KV。祖先逻辑共享不意味着新增节点 KV 免费。

### 9.3 回滚与碎片

首次拒绝后未接受节点要释放。Paged KV 可按 block 管理，但仍可能遇到：

- block 内未用 slot；
- 短期峰值；
- 高频分配回收；
- batch 内请求不同深度；
- CUDA Graph 预留。

只看服务启动时显存不足以判断线上 OOM。

## 10. Draft 显存的机会成本

假设 Draft 占 6 GiB。两种使用方式：

### 方案 A

把 6 GiB 给 Draft：

- 单请求 TPOT 降低；
- 最大 batch 可能下降。

### 方案 B

把 6 GiB 给 Target KV：

- TPOT 不变；
- 可服务更多请求或更长上下文；
- goodput 可能更高。

因此评估要问：

$$
\text{Draft 带来的延迟收益}
\quad\text{vs}\quad
\text{KV 带来的容量收益}
$$

“模型能装下”只是最低门槛。

## 11. 长上下文：三个方向同时变差

### 11.1 Prefill 占比

总时延：

$$
T_{\text{e2e}}
=T_{\text{queue}}
+T_{\text{prefill}}
+T_{\text{decode}}
$$

Prompt 32K、输出 32 Token 时，即使 Decode 加速 2 倍，总时延改善也可能只有几个百分点。

### 11.2 Attention KV 带宽

Decode/Verify 的每个 query 都要读取更长历史 KV。上下文增长使：

$$
M_{\text{kv}}(C)\propto C
$$

Verify K 个 query 的 KV 访问也增加，原本“权重只读一次”的优势被历史 KV 流量削弱。

### 11.3 Draft 上下文

独立 Draft 也维护长历史 KV；N-gram/Suffix 索引也随历史变大。长上下文不是任何 Proposer 的免费区。

### 11.4 位置外推

Draft `max_model_len` 若小于 Target，超过 Draft 上限的请求可能：

- 停止投机并退回 baseline；
- 初始化失败；
- 产生位置编码不兼容。

需要专门测试跨越阈值时是否平滑降级。

## 12. 与量化的交互

### 12.1 Target 权重量化

量化降低权重字节 \(W\)：

$$
W_{\text{INT4}}<W_{\text{FP8}}<W_{\text{BF16}}
$$

基线 Decode 的 memory-bound 时间下降。投机原本靠摊薄权重读取获益，权重越小，收益空间可能越小。

但量化也可能：

- 释放显存给 Draft/KV；
- 改变 kernel 形态；
- 让 Verify 更 compute-bound；
- 改变 logits 和接受率。

结论不能预判，必须重测。

### 12.2 Draft 量化

Draft 量化减少：

- 权重显存；
- Draft 带宽；
- Draft 延迟。

同时量化误差可能增大：

$$
\operatorname{TV}(p,q_{\text{quant}})
$$

接受长度下降。要比较的是量化前后：

$$
\frac{D_\gamma+V_\gamma+O}{\bar L}
$$

而不是只看 Draft tokens/s。

### 12.3 KV Cache 量化

Target 或 Draft KV 量化降低长上下文带宽与容量，但会改变：

- baseline；
- Verify；
- Draft feature；
- 数值正确性。

组合优化的加速比不可直接相乘。

## 13. 与 Tensor Parallel 的交互

Target TP 将矩阵分片到多个 GPU。每个 Decode/Verify 层包含 collective：

$$
T_{\text{TP}}
=T_{\text{compute}}+T_{\text{collective}}
$$

投机减少 Target 轮数，可能减少 collective 次数；但每轮 Verify 工作更宽。

### 13.1 Draft TP=1

优点：

- 小模型不承担多卡 collective。

代价：

- 单卡放置；
- 候选和状态需送给所有 Target rank；
- Draft 单卡可能成为瓶颈。

### 13.2 Draft TP=Target TP

优点：

- 放置和分片对称；
- 大 Draft 可分摊显存。

代价：

- 每个 Draft step 都有 collective；
- 小模型通信占比高；
- \(\gamma\) 次串行通信可能吞掉收益。

### 13.3 Local argmax

greedy Draft 可在 vocab parallel rank 上先做局部最大，再归约候选值与 ID，通信从完整 vocab all-gather 降低。但它只适用于特定 non-tree、greedy 路径，不能泛化为所有方案。

## 14. 与 PP、DP、EP 的交互

### 14.1 Pipeline Parallel

PP 的问题：

- 每个 Draft/Verify 轮次跨 stage；
- 小 batch bubble 大；
- 候选树 metadata 跨 stage；
- 请求回滚更复杂。

vLLM v0.27.1 文档写明 `vllm<=0.15.0` 时 PP 不可与投机组合。这只说明旧范围；对 0.27.1 仍应按具体方法、模型和硬件实测，不应推断“所有组合都已支持”。

### 14.2 Data Parallel

各 DP rank 独立调度。静态 K 通常可由各 rank 独立执行；动态 batch-size K 若导致不同 rank 进入不同 collective 路径，可能死锁。v0.27.1 因此在 DP 下自动禁用 `num_speculative_tokens_per_batch_size`。

### 14.3 Expert Parallel / MoE

MoE 的候选 Token 会触发路由：

- Verify K 个候选增加专家负载；
- 不同候选路由不均；
- all-to-all 成本；
- Draft 与 Target 可使用不同 MoE backend。

高接受并不意味着候选专家计算没有浪费。MoE 模型必须单独压测。

---

## 15. 与 Prefix Cache 和 Chunked Prefill

### 15.1 Prefix Cache

Prefix Cache 主要减少重复 Prompt 的 Prefill，投机主要减少 Decode 串行轮数。二者阶段不同，可以组合。

但实验时要固定 cache 状态：

```text
冷 cache baseline vs 冷 cache speculative
热 cache baseline vs 热 cache speculative
```

不能一组命中、一组未命中。

### 15.2 Chunked Prefill

Chunked Prefill 与 Spec Verify 都是多 Token 工作。它们竞争统一 Token Budget，组合时重点观察：

- P99 TTFT；
- Prefill 饥饿；
- Decode TPOT；
- 调度公平性。

只看稳态 output tokens/s 会漏掉新请求延迟。

---

## 16. 与 Structured Output、Tool Calling 和 LoRA

### 16.1 Structured Output

Grammar 在每个位置产生 allowed-token mask。若 Draft 未应用同一语义：

- 提出大量非法 Token；
- 第一位频繁拒绝；
- 严格分布证明所需的 \(p,q\) 变换不一致。

树式候选每条路径的 grammar state 也可能不同，不能共享错误的 mask。

### 16.2 Tool Calling

工具调用 JSON 往往模板强，N-gram/Suffix 可能高接受；但参数值分支大，需看逐位置存活。Parser 和 stop token 必须在 baseline/spec 两组保持一致。

### 16.3 Multi-LoRA

不同 LoRA adapter 改变 Target 分布。共享一个 Draft 时：

$$
q\ \text{固定},\qquad p_{\text{adapter}}\ \text{变化}
$$

不同 adapter 的接受率可能差异巨大。应按 adapter 分桶，或为高流量 adapter 训练匹配 Proposer。

---

## 17. 输出质量边界

### 17.1 接受率不是质量

Draft 和 Target 都可能高置信地产生错误事实。接受率只度量局部分布相似：

$$
A=1-\operatorname{TV}(p,q)
$$

它不衡量：

- 事实正确性；
- 安全性；
- 指令遵循；
- 长程一致性。

### 17.2 严格路径

标准拒绝采样在数学上保持 Target 分布，但仍受：

- 浮点误差；
- batch 数值稳定性；
- logits transform 差异；
- kernel 非确定性；
- RNG 顺序。

### 17.3 近似路径

Typical acceptance、synthetic acceptance 或启发式阈值可能改变分布。上线前要定义可接受偏差和业务质量门禁，不可借用严格路径的“无损”结论。

## 18. 容量规划数值例子

假设一张 GPU：

```text
总可用显存：80 GiB
Target 权重与 runtime：52 GiB
剩余：28 GiB
```

### Baseline

全部 28 GiB 给 Target KV：

```text
最大稳定并发：96
饱和 goodput：80 req/s
P95 TPOT：42 ms
```

### 加 Draft

Draft + workspace 占 8 GiB，只剩 20 GiB KV：

```text
最大稳定并发：68
饱和 goodput：72 req/s
低并发 P95 TPOT：25 ms
```

结论：

- 低并发交互体验明显改善；
- 饱和容量反而下降 10%；
- 是否上线取决于业务是延迟优先还是吞吐优先。

可以按流量分池：

```text
低延迟池：启用 Spec
吞吐池：Baseline 或动态 K
```

比全局一刀切更合理。

## 20. 用测量反推问题

### 高接受、低加速

可能原因：

- Draft 太慢；
- Verify 已 compute-bound；
- TP 通信高；
- batch 已饱和；
- KV/metadata 开销大。

### 低接受、Draft 很快

可能原因：

- Draft 与 Target 不匹配；
- 领域漂移；
- temperature 高；
- structured mask 不一致；
- K 过深。

### 低并发快、高并发慢

这是典型 Roofline 转换。采用动态 K、流量分池或只对低并发启用。

### TPOT 快、TTFT 差

Spec Verify/Chunked Prefill 争 Token Budget，或 Draft 初始化/显存降低 Prefill 容量。

### 平均快、P99 差

检查：

- 长上下文桶；
- 低接受任务；
- batch shape；
- OOM 边缘；
- 跨请求缓存 miss；
- 调度饥饿。

## 21. 上线门槛

建议用多目标门禁，而不是“加速比 > 1”：

```text
P95 TPOT 改善 ≥ 目标值
P99 TTFT 不退化超过预算
饱和 goodput 不下降
最大稳定并发不低于容量要求
显存峰值保留安全余量
贪心回归通过
采样分布无显著异常
真实任务质量不下降
```

并提供：

- 按请求类别开关；
- 按 batch 动态 K；
- 快速回退 baseline；
- 接受率和速度回归告警；
- 模型 revision 变更后自动重测。

## 22. 原理—实现—实验—边界闭环

### 原理

投机用额外候选计算换更少 Target 串行轮次，收益条件是：

$$
T_{\text{round}}<\bar L T_1
$$

### 实现

完整轮次包含 Draft、Verify、采样、metadata、KV 和通信；调度器还要在 Spec Verify 与 Prefill 间分配 Token Budget。

### 实验

必须同时扫描 K、batch、上下文和任务，测算法、性能、资源与质量四组指标。

### 边界

- 小 batch memory-bound 最有利。
- 大 batch compute-bound 可能变慢。
- 长上下文同时提高 Prefill 占比、KV 带宽和 Draft 状态。
- 量化、并行和其他优化会改变基线，收益不可相乘。
- 低延迟收益可能以容量下降为代价。

---

## 📝 总结

- 接受长度只决定潜在前进距离，完整轮次成本决定真实速度。
- batch 增大会让普通 Decode 更高效，并让 Verify 的有效工作量接近 \(B\times K\)。
- 动态 K 应随 batch、接受率和 SLO 变化；高负载时关闭投机可能是最优策略。
- Draft 权重和候选 KV 有显存机会成本，单请求快不代表容量高。
- 长上下文、量化、TP/DP/PP、Chunked Prefill 和 structured output 都会改变收益。
- 最终上线依据应是 TPOT、TTFT、goodput、容量、显存和输出正确性的联合门禁。
