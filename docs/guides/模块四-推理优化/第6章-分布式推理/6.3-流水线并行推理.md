## 1. PP 把模型沿层切开

把 Transformer 划成 $p$ 个 Stage，第 $j$ 个 Stage 持有自己的层与对应 KV：

$$
h_{j+1}=F_j(h_j)
$$

Stage 之间传的是边界激活，通常不是把全模型权重或所有层的 KV 每次都发一遍。Embedding、最终 Norm、LM Head 以及采样位置要按实现放置，它们可能使首尾 Stage 更重。

与每层内部反复同步的 TP 相比，PP 的通信集中在阶段边界，因此常作为跨节点候选。代价是下一阶段必须等上游输出，算力不能简单相加。

### 1.1 用四层模型理解 Stage

假设一个模型只有四层。PP=2 可以让卡 0 保存第 1、2 层，卡 1 保存第 3、4 层。输入先由卡 0 处理，结果交给卡 1，最后才能得到输出。卡 1 没有前两层的权重，因此不能独立接过一条新请求并完成全部生成。

式子里的 $h_j$ 是一批 Token 到达某个边界时的隐藏向量；$F_j$ 是这一阶段负责的所有层。传给下游的是一组数字组成的激活张量，不是已经翻译好的一段文字。可以把它理解为流水线上的半成品。

| 存放内容 | Stage 0 | Stage 1 |
|----------|---------|---------|
| 模型权重 | 第 1、2 层 | 第 3、4 层 |
| 同一请求的 KV | 第 1、2 层所需的 KV | 第 3、4 层所需的 KV |
| 本轮输出送到哪里 | 把边界激活交给 Stage 1 | 完成后续计算，再按实现输出/采样 |

### 1.2 PP 与第七章的 PD 分离有什么区别

PP 是按**模型层**分工：每个 Stage 都要处理自己这些层的 Prefill 与 Decode。PD 分离是按**推理阶段**分工：Prefill 实例算输入，Decode 实例继续生成，需要在两者之间交接相应 KV。不能因为两者都有“阶段”，就把 PP 的边界激活传输等同于 PD 的 KV 迁移。

## 2. Micro-batch 怎样把流水线填起来

多个独立请求可以组成不同 Micro-batch：第一批到第二阶段时，第一阶段处理下一批。

```mermaid
graph LR
    A["Stage 0<br/>前半模型层"] -->|"边界激活"| B["Stage 1<br/>后半模型层"]
    B --> C["采样下一个 Token"]
    C -->|"同一请求的下一轮依赖"| A
    Q["其他请求 / Micro-batch"] --> A
```

Micro-batch 不是把一条序列拆成互不依赖的后半段。因果 Attention 的上下文依赖仍然存在；分块 Prefill 的后续 Chunk 也需要此前状态。填流水线依靠的是可调度的独立工作。

### 2.1 画出两阶段、三小批的时间表

先假设 A、B、C 是三份互不依赖的小批次，每个 Stage 处理一份都要 10 ms，阶段间传输暂时忽略：

| 时间 | Stage 0 | Stage 1 |
|------|---------|---------|
| 0～10 ms | 处理 A | 等 A 的上游结果 |
| 10～20 ms | 处理 B | 处理 A |
| 20～30 ms | 处理 C | 处理 B |
| 30～40 ms | 没有下一份工作 | 处理 C |

可以看到，A 仍要在 20 ms 才完成；但 B、C 不必等 A 完全结束后再进入 Stage 0。三批一起在 40 ms 内结束，而把三批全程串行处理需要 60 ms。这体现的是连续完成工作的效率，不能说 A 的耗时变成了 10 ms。

### 2.2 Micro-batch 与请求数不是固定的一比一

Micro-batch 是供一次阶段计算使用的一小批工作，可以包含多个请求的 Token。它不一定等于一条请求，也不一定等于整个服务当前所有请求。真实引擎会根据调度、Token 预算、上下文与实现约束组织工作。

直觉上，更多独立工作有助于填补空位；但“用户只提交了一条请求”时，不能靠随意把它切成许多独立请求来消除自回归依赖。

## 3. 理想气泡公式，适用范围是什么

先看一个严格简化的模型：$p$ 个等时 Stage，每段耗时 $\tau$；$m$ 个独立 Micro-batch；仅前向；无通信与调度开销。

$$
T_{\text{makespan}}=(m+p-1)\tau,\qquad
U=\frac{m}{m+p-1},\qquad
\text{Bubble}=\frac{p-1}{m+p-1}
$$

启动和排空造成空转。$m$ 增大时利用率提高，但这不代表单请求延迟降低，也不代表应无限增加并发：更多请求需要更多 KV，还会增加排队。

推理没有训练反向，不能直接套用训练的 1F1B 时间表；连续批处理、异步执行和请求结束又会使实际波形偏离这个静态公式。

### 3.1 公式从哪里来

第一份工作要经过 $p$ 段，花 $p\tau$；流水线填好后，每再完成一份，理想上只需增加一个时间槽 $\tau$。所以 $m$ 份共需 $p\tau+(m-1)\tau$。

总的有效工作是 $mp\tau$，而这段墙钟时间内，所有设备合计可提供 $p(m+p-1)\tau$ 的时间。两者相除，就是 $U=m/(m+p-1)$。**气泡**指本来可做计算、却因为上下游依赖或没有工作而空等的槽位；不是显存碎片。

| 两个等时 Stage | 总时间槽 | 理想利用率 | 如何理解 |
|----------------|----------|------------|----------|
| 1 个 Micro-batch | 2 | 1/2 | 两段轮流工作 |
| 3 个 Micro-batch | 4 | 3/4 | 正是上一节的时间表 |
| 8 个 Micro-batch | 9 | 8/9 | 开头、结尾空等被更多工作摊薄 |

这里的利用率是这个理想时间表的忙时比例，不是直接读取 `nvidia-smi` 的 GPU 利用率。真实内核即使处于“忙”的阶段，也未必吃满计算单元。

## 4. Decode 的反馈环为什么更难

同一序列的下一 Token，要等本轮最后阶段产生输出，再把新 Token 带回后续前向。PP 无法把尚未生成的未来 Token 提前交给第一阶段。

因此，低并发 Decode 很容易让多个 Stage 轮流空等。额外独立序列可以补空，但要在 KV 容量、批处理效率和尾延迟之间权衡。若只有一条短请求，PP 的主要价值可能是装载，而不是降低 TPOT。

首 Token 也需要走完整条路径。简化地写：

$$
T_{\text{first-pass}}\approx\sum_j T_j+\sum_j T_{\text{boundary},j}
$$

这是无排队时的路径成本，不包含服务端排队、Tokenizer 和网络响应。

### 4.1 跟着一句话生成两个 Token

假设模型接到“今天天气”，并假设本例的“很”“好”各对应一个 Token。第一轮从 Stage 0 走到 Stage 1，最后采样出“很”。只有知道这个新 Token，下一轮才能把它作为新输入，再经过 Stage 0、Stage 1，去预测“好”。不能在“很”尚未确定时，就提前计算以“很”为输入的下一轮。

反馈通常只需传回 Token ID 等必要信息，不是把所有权重重新送回第一阶段。即使反馈本身很小，**后续工作必须等结果产生**的时间依赖仍然存在。

### 4.2 为什么多条序列能帮忙，却也可能伤害延迟

当请求 A 正在 Stage 1，Stage 0 可以先处理独立请求 B 的工作。这样增加忙时比例，但如果一次接入太多请求，调度队列和 KV 压力会增大，某个请求等待下一步的时间可能更长。

因此需要分开观察：TTFT 是第一次返回 Token 前的等待；TPOT 反映后续生成的平均步间耗时；吞吐反映整个服务单位时间完成多少工作。PP 可能提高容量或稳态吞吐，同时让低并发的步间等待增加，这几项不矛盾。

## 5. 不均匀分层与链路，谁拖慢整条线

多批次进入稳态后，最慢 Stage 决定推进节奏，而非平均 Stage 时间。层数一样，不意味着耗时和显存一样：

- MoE 层、长上下文 Attention 和不同算子会改变计算分布；
- Embedding/LM Head 可能使首尾负载不同；
- 每个 Stage 的 KV 容量受本地层数和其他开销影响；
- 跨节点边界传输可能无法完全被计算隐藏。

边界激活的简化数据量为 $M H b$：处理 $M$ 个 Token、隐藏维度 $H$、每元素 $b$ 字节。TP×PP 下还要看边界张量是分片还是复制，不能把这个式子直接当成每条物理网卡的流量。

### 5.1 慢工位会让其他工位等着

若 Stage 0 每份只需 10 ms、Stage 1 却需 30 ms，下游每 30 ms 才能接着完成一份。上游即使继续变快，也无法让最终输出稳定达到每 10 ms 一份。应该先找慢阶段，检查层的计算量、缓存压力、通信和内核，而不是只看全局平均 GPU 利用率。

重新分层可以改善负载，但需要模型和框架支持，也要检查显存。把一层从慢阶段移走，可能减轻计算，却让另一个阶段的权重与 KV 放不下。“每段层数一样”只是起点，不是平衡的证明。

### 5.2 边界究竟传多少数据

例如处理 128 个 Token、隐藏宽度 4096、每元素 2 字节，未分片的边界激活为 $128\times4096\times2=1048576$ 字节，即 1 MiB。这是假设形状下的一次边界张量，不是整个请求生命周期的流量。

更多 Token、更宽隐藏层或多次调用都会增加传输；低并发 Decode 可能单次数据少，却频繁等待边界通信。分析时既要看总字节数，也要看每次传输带来的等待，不能只看带宽峰值。

## 6. 用小模拟器观察气泡与慢阶段

下面的时间单位纯属假设，不模拟真实 vLLM 调度：

```python
def pipeline_time(stage_times, batches):
    assert batches > 0 and all(t > 0 for t in stage_times)
    end = [0.0] * len(stage_times)
    for _ in range(batches):
        upstream = 0.0
        for stage, duration in enumerate(stage_times):
            end[stage] = max(end[stage], upstream) + duration
            upstream = end[stage]
    return end[-1]

assert pipeline_time([1, 1, 1, 1], 1) == 4
assert pipeline_time([1, 1, 1, 1], 8) == 11
assert pipeline_time([1, 3, 1, 1], 8) > 11
for batches in (1, 4, 8):
    elapsed = pipeline_time([1, 1, 1, 1], batches)
    print(batches, elapsed, "理想利用率", batches / elapsed)
```

同样四个 Stage，单批次利用率只有 1/4。八批次的理想利用率为 8/11；慢阶段加入后，还会进一步下降。

### 6.1 两种等待分别在哪里

`end[stage]` 记录该阶段处理上一批的结束时间，`upstream` 记录当前批次从上一阶段到达的时间。下一次计算必须同时满足“本阶段空闲”和“上游结果已到”，所以开始时间取两者的 `max`，再加上本阶段耗时。

循环不是在真的并行执行四个 Python 任务，而是在依次计算一张时间表。把时间单位当成毫秒或任意单位都可以，但只有填入真实测量且模型假设合适时，结果才有实际时间意义。

### 6.2 可以亲手改的两个参数

先将批次数从 1 改为 8，观察启动成本如何被摊薄；再把阶段时间改成 `[1, 3, 1, 1]`。处理八批时，总时间会从 11 增至 27：第一批共需 6，后面七批各受 3 单位的瓶颈阶段限制。

后一种情况下不能继续用“批次数除以总时间”当成全体设备的忙时比例，因为每批总工作已从 4 变成 6。这个例子的总体忙时比例应为 $8\times6/(4\times27)$。实际系统还要计入通信、调度和不同批次的形状变化。

## 7. TP×PP 的候选怎样落到节点上

假设两节点、每节点四卡，一个副本用 TP=4、PP=2。期望是节点内四卡形成 TP 组，两个 PP Stage 分别落在两节点。

在已经搭好的 Ray 集群中，v0.19.0 的启动形式为：

```bash
vllm serve /models/target \
  --tensor-parallel-size 4 --pipeline-parallel-size 2 \
  --distributed-executor-backend ray --max-model-len 4096
```

`/models/target` 是各节点一致的模型快照路径。**参数表达期望的并行度，不代替部署后的物理映射核对。** 用 Ray 资源视图、Worker 日志和通信路径确认实际落点；配置外的 GPU、异构节点和资源碎片都可能影响放置。

比较 PP 时，不只看一条请求。分别报告低并发延迟、稳态吞吐、气泡/阶段忙闲和每 Stage 的 KV 余量，才能解释容量与效率的取舍。

### 7.1 先画期望的放置，再核对实际放置

| 物理位置 | PP 职责 | 阶段内部的 TP |
|----------|---------|---------------|
| 节点 A 的四张 GPU | Stage 0：一部分连续模型层 | 四卡共同计算这一阶段中的层 |
| 节点 B 的四张 GPU | Stage 1：其余连续模型层 | 另四卡共同计算这一阶段中的层 |

这样安排的出发点是：层内频繁同步尽量留在节点内，节点间主要传阶段边界。它仍然是候选方案；如果节点内本身通信较差，或跨节点网络足够好，其他布局也值得实测。

命令中的 TP=4、PP=2 意味着一个副本需要八张 GPU。它没有指定“每段恰好多少层”，也不能替代模型对 PP 的支持检查。新手可以按“单机模型能跑 → Ray 资源能看到 → 分布式能生成 → 放置符合预期 → 性能对照”的顺序推进。下一节讨论 DP/EP，6.5 再补齐 Ray 的具体职责。

## 📝 总结

- PP 沿层切分，阶段间传递边界激活。
- 独立 Micro-batch 可以填流水线，同一请求仍有自回归反馈依赖。
- 气泡公式建立在等时、静态、仅前向的理想条件上。
- 跨节点部署要一起看阶段负载、边界链路和实际 Rank 映射。
