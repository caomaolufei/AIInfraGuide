## 1. 扩缩容到底在控制什么
推理副本像超市收银台。
顾客到来比结账快时，队伍会越来越长；临时多开收银台可以缓解，但新员工就位需要时间。
自动扩缩容控制的是“可用服务能力”，不是让单个 GPU 凭空变快。
```mermaid
flowchart LR
    Traffic["到达流量 λ"] --> Queue["等待队列"]
    Queue --> Pods["N 个推理副本"]
    Pods --> Done["完成速率 Nμ"]
    Queue --> Signal["扩缩容指标"]
    Signal --> HPA["控制器"]
    HPA --> Pods
```
扩容要同时满足：
- 集群有可调度 GPU
- 镜像和模型可在预期时间内准备好
- 新副本通过启动与就绪探针
- 网关把它加入负载均衡池
任何一环失败，`replicas` 数字增加都不等于容量增加。
## 2. 用排队理解容量
### 2.1 最小模型
设每个副本平均服务率为 $\mu$ 个请求/秒，副本数为 $N$，到达率为 $\lambda$。
一个必要但不充分的稳定条件是：
$$
\lambda < N\mu
$$
定义粗略利用率：
$$
\rho = \frac{\lambda}{N\mu}
$$
当 $\rho$ 接近 1 时，微小抖动就会导致队列和尾延迟快速上升。
LLM 请求长短差异很大，所以“请求/秒”只是粗粒度近似。
更可靠的容量单位可能是输入 token/s、输出 token/s，或按长度分桶后的请求率。
### 2.2 一个手算例子
以下数据均为假设：
- 峰值到达率 $\lambda = 5$ 请求/s
- 单副本在目标请求分布与 SLO 下，安全服务率 $\mu = 1.4$ 请求/s
- 希望运行利用率不超过 70%
副本数下界为：
$$
N \ge \left\lceil\frac{5}{1.4\times0.7}\right\rceil
= \lceil5.10\rceil = 6
$$
如果只按 $\lceil5/1.4\rceil=4$ 配置，平均吞吐可能勉强够，但没有吸收波动的余量。
实际值必须来自与生产长度分布、并发和采样参数一致的压测。
### 2.3 Little 定律的直觉
稳定系统中：
$$
L = \lambda W
$$
$L$ 是系统内平均请求数，$W$ 是平均停留时间。
若到达率为 4 请求/s，平均排队时间为 0.5 s，则平均有约 2 个请求在等待。
Little 定律描述平均关系，不能代替 P99 延迟分析。
## 3. 选择扩缩容指标
### 3.1 为什么 CPU 常常不够
推理瓶颈通常在 GPU、显存带宽、KV Cache 或调度队列。
CPU 可能只有 30%，用户却已经排队。
仅使用 CPU HPA，像根据收银台照明用电决定是否加开窗口。
### 3.2 指标优先级
可考虑以下信号：
1. **等待队列或排队时间**：最接近拥塞，通常最有价值
2. **运行请求数/副本**：反映并发压力
3. **token 到达率**：比 QPS 更能描述长短差异
4. **KV Cache 使用率**：可作为内存压力保护信号
5. **GPU 利用率**：适合作为辅助信号
6. **QPS**：简单，但必须结合请求长度分布
单个瞬时指标容易抖动。
控制器应使用时间窗口，并对扩容和缩容采用不同速度。
### 3.3 “每副本队列”比总队列更稳
假设总等待请求数为 $Q$，当前就绪副本为 $R$：
$$
q_{\text{per-pod}} = \frac{Q}{\max(R, 1)}
$$
如果目标是每副本最多等待 2 个请求，HPA 可以据此估算期望副本数。
指标管道应只统计就绪且接收流量的副本。

### 3.4 一个“队列长度”其实有多种口径
扩缩容前必须给指标写语义合同：
- **入口队列**：网关已接收、尚未分配后端的请求；
- **Router 队列**：已选模型、等待健康副本的请求；
- **Engine waiting**：已进入引擎调度器、尚未运行的请求；
- **running**：正在 Prefill/Decode 的请求；
- **in-flight**：通常包含 waiting + running，也可能包含网络发送阶段。

这些值不能随意相加，同一请求可能同时出现在上游 in-flight 和引擎 waiting。HPA 最适合使用“每个目标副本的 engine waiting”或由 Router 按一致口径计算的待分配工作量；入口队列更适合全局过载保护。

队列长度也没有表达请求重量。10 个 8k 输入请求和 10 个 100 token 请求完全不同。生产信号可进一步变为：
$$
W_{\text{queue}}
= \sum_i
\left(
\alpha N_{\text{in},i}
+ \beta N_{\text{out-est},i}
\right)
$$
其中 $\alpha,\beta$ 由单副本压测拟合，`out-est` 只能是有上限的估计。若无法可靠估计输出，至少按输入长度和租户/优先级分桶，避免一个超长请求与一个短请求权重相同。

### 3.5 看绝对值，也看等待时间和斜率
三个信号回答不同问题：
- `waiting`：当前积压多少；
- `queue_wait_seconds`：用户已经等了多久；
- `dQ/dt`：积压是在增长还是消退。

若 `waiting=20` 但斜率为负，扩容可能已生效；若 `waiting=5` 但斜率持续为正，可能正在进入故障。扩容触发可偏向斜率和绝对值，缩容则要求长窗口内队列接近零。

对流式生成，Little 定律可用于校验观测：
$$
L_{\text{in-system}}\approx
\lambda\times W_{\text{E2E}}
$$
如果仪表盘的 in-flight 与该数量级长期不符，先检查指标口径、客户端取消和采样，而不是立刻调 HPA。
## 4. 配置 HPA
### 4.1 先理解控制回路
HPA 不是事件触发器，而是周期性采样的反馈控制器。对 `Pods/AverageValue` 指标，可把核心计算近似理解为：
$$
N_{\text{desired}}
=
\left\lceil
N_{\text{current}}
\times
\frac{M_{\text{current}}}
{M_{\text{target}}}
\right\rceil
$$
假设当前 4 个副本，平均每 Pod waiting 为 6，目标为 2，则原始期望约为：
$$
\lceil4\times6/2\rceil=12
$$
最终还会受到 tolerance、`minReplicas/maxReplicas`、扩缩策略、稳定窗口和缺失指标影响。

完整回路存在多段延迟：
```mermaid
flowchart LR
    Q["队列变化"] --> S["引擎暴露指标"]
    S --> P["Prometheus scrape"]
    P --> A["Adapter 聚合"]
    A --> H["HPA sync"]
    H --> D["修改 desired replicas"]
    D --> K["调度 GPU"]
    K --> R["模型加载并 Ready"]
    R --> Q
```
若 scrape 15 秒、adapter 缓存 30 秒、HPA 同步 15 秒，控制器看到的可能已是几十秒前的队列。应监控指标时间戳和 adapter 错误；陈旧值比无值更危险，因为它看起来“正常可用”。

### 4.2 自定义指标链路
典型链路是：
```mermaid
flowchart LR
    V["vLLM /metrics"] --> P["Prometheus"]
    P --> A["Prometheus Adapter"]
    A --> C["Custom Metrics API"]
    C --> H["HPA"]
    H --> D["Deployment"]
```
HPA 不会直接查询任意 Prometheus 查询。
需要适配器把查询结果暴露为 Kubernetes 可识别的指标。
### 4.3 HPA 骨架
以下指标名与目标值都是示意：
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: chat-model
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: chat-model
  minReplicas: 2
  maxReplicas: 12
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 900
      policies:
        - type: Percent
          value: 25
          periodSeconds: 300
  metrics:
    - type: Pods
      pods:
        metric:
          name: inference_waiting_requests
        target:
          type: AverageValue
          averageValue: "2"
```
**前提**：`inference_waiting_requests` 由 Adapter 以 Pod 资源指标暴露，且只覆盖目标 Deployment 的 Ready Pod；`averageValue: 2` 来自队列与 SLO 压测。**危险点**：指标缺失、映射到错误 namespace/pod、总队列被误当每 Pod 队列，都会导致错误扩缩。`maxReplicas: 12` 还必须能被 GPU quota、节点池和预算支持。
HPA 接管后，应从 Deployment 的声明式清单删除 `spec.replicas`。否则后续 `kubectl apply` 或 GitOps 同步会把 scale 子资源改回固定值，与 HPA 反复争抢。

检查控制器看到的状态：
```bash
kubectl get hpa chat-model --watch
kubectl describe hpa chat-model
kubectl get --raw \
  "/apis/custom.metrics.k8s.io/v1beta1" | jq .
```
**前提**：已安装 `jq`，当前身份可读取 HPA 和 Custom Metrics API。**危险点**：`--watch` 会持续占用终端和 API 连接，排障结束应退出；API 输出可能很大，应在目标 namespace/metric 进一步收窄。检查 `AbleToScale`、`ScalingActive`、`ScalingLimited` 和事件，而不只看副本数字。
`minReplicas` 应覆盖基本高可用和突发缓冲。
`maxReplicas` 应受 GPU 配额、预算和下游容量约束，而不是写一个无限大的数。

### 4.4 多指标不是简单“投票”
HPA 配置多个指标时，会分别计算期望副本，通常取最大值扩容；若某指标取数失败，缩容可能被跳过以避免误删容量。可把 queue 作为主指标，running/token rate 作为提前量，但不要堆入十个高度相关信号。

建议把保护职责分开：
- HPA：根据持续负载调整 Pod 数；
- 网关：毫秒级限流、优先级和有界队列；
- 节点自动伸缩：准备 GPU 节点；
- 定时/预测扩容：应对已知活动；
- 人工容量上限：控制预算、配额和故障半径。

HPA 无法可靠“从 0 读每 Pod 指标”，GPU 模型冷启动又长。在线关键服务通常保留 `minReplicas >= 2`，而不是追求 scale-to-zero。
## 5. 冷启动与稳定性
### 5.1 扩容不是即时的
总扩容时间近似为：
$$
T_{\text{scale}}
= T_{\text{detect}}
+ T_{\text{schedule}}
+ T_{\text{image}}
+ T_{\text{model}}
+ T_{\text{ready}}
$$
假设检测 30 s、调度 10 s、镜像 40 s、模型加载 180 s、预热 20 s，总计 280 s。
这些数字仍是假设，应该分别测量。
如果业务尖峰只持续 60 s，事后扩容几乎帮不上忙。
这时需要最小热副本、定时扩容、预测扩容、请求准入或客户端退避。

冷启动要按状态拆分，而不是只报一个均值：
- **热 Pod**：镜像和模型都在节点缓存；
- **冷模型**：镜像在、模型需要下载；
- **冷节点**：还要创建节点、安装驱动/设备插件、拉镜像；
- **失败重试**：配额、库存或下载故障后再次尝试。

`T_scale` 应使用最坏可接受路径的 P95/P99。假设冷节点 P95 为 12 分钟，而请求等待预算只有 15 秒，节点自动伸缩只能恢复未来容量，不能挽救当前请求。当前请求必须依靠热余量、准入、降级或跨集群溢出。

扩容过程中，未 Ready Pod 不能被计入服务能力。若适配器用 desired replicas 做分母，会在模型仍加载时人为稀释“每 Pod 队列”，导致控制器误以为压力已缓解。分母应使用真正 Ready 且 Router 已纳入候选池的副本。
### 5.2 避免扩缩容振荡
振荡是“刚扩容就缩容，刚缩容又排队”。
常用手段：
- 扩容快、缩容慢
- 使用稳定窗口和冷却时间
- 缩容前观察完整业务周期
- 给队列指标做合理平滑
- 终止前先摘流量并排空请求

PodDisruptionBudget（PDB）适合保护节点维护、集群升级等通过 Eviction API 发起的自愿中断，**不会阻止 HPA 通过 ReplicaSet 缩容删除 Pod**，因此不是抑制 HPA 振荡的手段。振荡要靠 stabilization window、缩容策略和指标平滑控制。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: chat-model
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: chat-model
```
**前提**：至少有两个跨故障域副本，selector 精确匹配目标 Pod。**危险点**：只有一个副本时 `minAvailable: 1` 会阻止自愿驱逐，可能卡住节点维护；PDB 不会阻止 HPA/Deployment 缩容，也无法抵御节点突然掉电。
PDB 主要约束自愿中断，不保证节点故障时仍有副本，也不替代 HPA 的缩容策略。
### 5.3 缩容与在途请求
LLM 请求可能持续数十秒甚至更久。
缩容时应：
1. 让 readiness 失败或从网关摘除
2. 停止接收新请求
3. 等待在途请求完成或达到截止时间
4. 再终止进程
如果没有排空机制，扩缩容会直接制造 5xx 和重试风暴。
## 6. 多副本负载均衡
### 6.1 最少连接并不总是最少工作
两个连接的生成长度可能相差百倍。
Round Robin 实现简单，但不理解请求长度、KV Cache 和队列。
常见策略：
- **轮询**：简单、无状态，适合请求较均匀
- **最少连接/最短队列**：更贴近当前负载
- **加权路由**：用于异构 GPU 或金丝雀版本
- **一致性哈希**：维持租户或前缀亲和
- **SLO 感知路由**：按长度、优先级或截止时间分流
网关重试必须有边界。
流式响应已经输出 token 后，不能静默换副本重试而假装是同一次生成。
### 6.2 异构副本
不同 GPU 型号、量化方式或张量并行度的服务率不同。
不能假设所有 Pod 权重相同。
先分别压测，再按安全吞吐设置权重，并在指标中保留硬件和配置标签。
## 7. 前缀感知路由
前缀缓存像图书馆把同一套参考资料留在固定阅览室。
同一系统提示词的请求被送到同一副本，更可能复用已存在的 KV Cache。
```mermaid
flowchart LR
    R1["共享前缀 A"] --> H{"前缀哈希"}
    R2["共享前缀 A"] --> H
    R3["共享前缀 B"] --> H
    H --> P1["Pod 1\n缓存 A"]
    H --> P2["Pod 2\n缓存 B"]
```
收益依赖：
- 前缀足够长且重复率高
- 引擎启用并支持前缀缓存
- 路由哈希稳定
- 副本变更不太频繁
风险也很明确：
- 热门前缀形成热点副本
- 扩缩容改变哈希环，缓存大量失效
- 缓存亲和与最短队列可能冲突
- 跨租户共享要评估隔离与侧信道风险
实用策略是先过滤过载副本，再在候选中选择前缀命中更高者。
缓存命中不能凌驾于 SLO 和租户隔离之上。

### 7.1 一个可解释的缓存感知评分
Router 可为每个候选副本计算：
$$
\text{score}_j
=
w_c\cdot\text{prefix-match}_j
-w_q\cdot\text{queue-work}_j
-w_l\cdot\text{predicted-latency}_j
$$
但在评分前先做硬过滤：
1. Pod 必须 Ready、非 terminating、模型 revision 匹配；
2. 租户隔离与区域策略允许；
3. queue/并发/KV Cache 未超过保护阈值；
4. 请求长度不超过该池能力。

评分只是软偏好。热门前缀所在 Pod 过载时，应牺牲缓存命中选择较空副本。生产中应记录 `routing_reason`（cache-hit、shortest-queue、spillover、canary），但不要把原始前缀哈希作为 Prometheus 标签。

### 7.2 扩缩容如何扰动缓存
普通取模 `hash % N` 在副本数变化时会重映射大量 key。一致性哈希或 rendezvous hashing 能减少迁移，但不能消除：
- 新副本初始冷缓存，短期吞吐低于老副本；
- 缩容副本的缓存直接消失；
- 镜像/模型 revision 切换不能复用不兼容缓存；
- 跨区亲和可能增加网络延迟和故障耦合。

因此扩容后可设置缓慢加权：新 Pod 先接少量流量完成预热，再增加权重；缩容则先把权重降到 0 并 drain。HPA 只改副本数，不会替 Router 完成这两个状态转换。

## 8. Drain 与终止协议
### 8.1 为什么 readiness 不等于 drain
readiness 失败会把 Pod 从常规 Service endpoint 中摘除，但传播到 EndpointSlice、kube-proxy、网格和网关连接池需要时间；已经建立的 HTTP/2/keep-alive 连接也可能继续送请求。

可靠终止协议应有明确状态机：
```mermaid
stateDiagram-v2
    [*] --> Ready
    Ready --> Draining: 收到缩容/发布终止
    Draining --> Drained: 权重=0 且 in-flight=0
    Draining --> Forced: 超过 drain deadline
    Drained --> Terminated
    Forced --> Terminated
```

推荐顺序：
1. Pod 出现 termination 信号，Router 将其标为 draining；
2. 从新请求候选池移除，停止新流量；
3. 保留现有连接，只完成已开始请求；
4. 暴露 `in_flight`、`drain_age` 和强制终止计数；
5. in-flight 归零后退出；超过 deadline 才取消；
6. `terminationGracePeriodSeconds` 大于摘流量传播 + 最大允许请求完成时间。

`preStop: sleep` 只能提供传播缓冲，不能证明 in-flight 已排空。更成熟的实现由 Router/引擎提供 drain API 或终止感知；还要验证 HPA 缩容、滚动发布、人工删除和节点驱逐四条路径都执行同一协议。

### 8.2 重试边界
仅在请求尚未产生任何响应 token、失败明确可重试、且仍在客户端截止时间内时考虑换副本重试。需要：
- 全链路 deadline，而不是每跳重新计算完整 timeout；
- 最大尝试次数和重试预算；
- 避免重试到同一失败域；
- 幂等元数据，防止计费/审计重复；
- 流式首 token 后失败直接向客户端报告中断。

无界重试会把一个 Pod 故障放大为全池过载。

## 9. 故障域与过载保护
### 9.1 过载时先保护系统
扩容来不及时，要有背压：
- 网关按租户限流
- 限制输入与最大输出 token
- 设置有界队列
- 超过等待预算时尽早返回 429/503
- 客户端采用带抖动的指数退避
- 区分交互流量与离线批任务优先级
无限队列不会创造容量，只会把拒绝变成长时间超时并消耗内存。

### 9.2 副本数不等于故障冗余
先定义最大要容忍的故障域：GPU、Pod、节点、机架、可用区或整个集群。两个副本若都在同一 8 卡节点上，对节点故障没有冗余。

调度和路由要共同尊重故障域：
- `topologySpreadConstraints`/反亲和让副本跨节点或可用区；
- Router 避免把一次请求的重试送到同一失败节点；
- HPA `minReplicas` 至少覆盖目标故障后的剩余服务能力；
- PDB 保护自愿中断，但不保证突发硬件故障；
- 每个区预留足够 GPU，不能只看全区域总数。

若目标是容忍一个可用区故障，正常状态下剩余各区容量之和仍要满足关键流量。把 12 个副本均匀放 3 区，失去 1 区后只剩 8；如果峰值需要 10，形式上“跨区”仍然不满足目标。

扩缩容也应设故障半径：单次最多加多少 Pod、单区最多承载多少比例、指标异常时是否冻结缩容。否则错误指标可一次性把整池扩到配额上限或缩到最小值。

## 10. 安全与技术边界
### 10.1 安全边界
- 扩缩容指标端点不应公开
- 自定义指标适配器使用最小 RBAC
- 不以用户可控标签直接生成 Prometheus 高基数标签
- 限流键必须防伪造，并避免把原始密钥写日志
- 多租户路由需防止一个租户占满全部队列
### 10.2 技术边界
- HPA 只增加 Pod，不自动增加节点 GPU
- Cluster Autoscaler 或节点自动供给的冷启动通常更长
- 指标有延迟，控制动作永远落后于瞬时流量
- QPS 相同但 token 分布不同，容量可能完全不同
- 缓存亲和提高命中率，也可能破坏负载均衡
- 多副本提高可用性，但不能替代跨故障域规划
## 📝 总结
自动扩缩容是一个带延迟的反馈控制系统。
排队指标告诉我们供需是否失衡，HPA 调整副本，负载均衡决定请求如何使用这些副本。
真正可靠的方案还必须包含冷启动测量、过载保护、优雅排空、GPU 上限和安全隔离。
