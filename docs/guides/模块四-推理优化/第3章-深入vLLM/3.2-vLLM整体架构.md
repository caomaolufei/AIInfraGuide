## 1. 真实问题：一次请求到底在哪里排队

用户说“请求慢”，这句话可能指完全不同的瓶颈：

```text
HTTP 连接排队
→ Chat Template / Tokenize
→ EngineCore waiting
→ Scheduler 多轮 chunked prefill
→ KV block 分配或抢占
→ Worker 输入准备
→ GPU forward
→ sample / detokenize
→ SSE 与代理缓冲
```

如果不理解对象和状态在哪一层变化，就容易做出无效调参：

- Tokenizer CPU 饱和，却增大 `max-num-batched-tokens`；
- KV 不足频繁 preemption，却增加 `max-num-seqs`；
- 反向代理缓冲 SSE，却怀疑 CUDA Kernel；
- 请求被 API 校验拒绝，却去读 Scheduler。

本节的目标不是背组件名，而是能拿一个 `request_id` 追完整个生命周期。

## 2. 白话直觉：前台、调度室与 GPU 工位

可以先把 V1 看成三个工作域：

```text
前台进程
  协议、模板、Tokenize、每请求输出队列、Detokenize、SSE

EngineCore 进程
  Request 权威状态、waiting/running、token budget、KV block 生命周期

Worker 进程
  持久 batch、输入张量、block table、模型 forward、采样
```

关键边界是：

- 前台知道“客户端要什么”；
- EngineCore 知道“下一轮算什么”；
- Worker 知道“怎样在设备上执行这份计划”。

这不是严格的“微服务拆分”。它们仍属于同一 vLLM 实例，并通过内部 IPC 与执行器协议紧密协作。

## 4. 第一段：HTTP 到 `EngineCoreRequest`

### 4.1 API 路由

Chat Completions 入口位于：

```text
vllm/entrypoints/openai/chat_completion/api_router.py
  create_chat_completion()
```

路由取得 `OpenAIServingChat` handler，调用：

```text
vllm/entrypoints/openai/chat_completion/serving.py
  OpenAIServingChat.create_chat_completion()
  OpenAIServingChat._create_chat_completion()
```

这一层负责 OpenAI 协议语义，例如：

- 请求模型名与服务模型名是否一致；
- `messages` 如何渲染为模型输入；
- stream 与非 stream 如何包装响应；
- tool/reasoning/structured output 字段如何转换；
- 客户端断开时如何触发取消。

这时还没有 Scheduler `Request`。

### 4.2 Renderer 与 InputProcessor

Chat Template 先把消息渲染为 `EngineInput`。随后：

```text
vllm/v1/engine/input_processor.py
  InputProcessor.process_inputs()
  InputProcessor.process_inputs_async()
```

原始 Prompt 可能涉及阻塞 Tokenize 或多模态处理，所以 `AsyncLLM.add_request()` 对 raw prompt 使用异步预处理，避免阻塞 event loop。

`process_inputs()` 做四类工作：

1. 校验 Sampling/Pooling 参数与任务；
2. 校验 LoRA、DP rank、模型输入；
3. 拆分 encoder/decoder 输入并提取 token IDs 或 embeddings；
4. clone 参数、合并 generation config，构造 `EngineCoreRequest`。

### 4.3 `EngineCoreRequest` 的边界

定义位置：

```text
vllm/v1/engine/__init__.py
  class EngineCoreRequest(msgspec.Struct)
```

v0.27.1 的关键字段：

```text
request_id
prompt_token_ids
prompt_embeds
prompt_is_token_ids
mm_features
sampling_params / pooling_params
arrival_time
lora_request
cache_salt
data_parallel_rank
client_index
current_wave
priority
trace_headers
resumable
external_req_id
```

它是跨前台与 EngineCore 的传输对象，不等同于调度器内部 `Request`。

### 4.4 外部 ID 与内部 ID

`InputProcessor.assign_request_id()`：

```python
# 接近 v0.27.1 行为的伪代码
request.external_req_id = request.request_id
request.request_id = external_id + "-" + random_uuid()[:8]
```

原因不是美观，而是隔离状态。若两个客户端都传 `"chat-1"`，内部字典、取消和输出路由不能把它们当同一请求。

## 5. 第二段：`AsyncLLM` 的双向数据流

定义位置：

```text
vllm/v1/engine/async_llm.py
  class AsyncLLM
```

`AsyncLLM.generate()` 不是执行模型的循环，而是每请求异步流的编排器。

### 5.1 输入方向

核心动作：

```python
async def add_request(...):
    core_request = await input_processor.process_inputs_async(...)
    input_processor.assign_request_id(core_request)
    ensure_output_handler_running()
    queue = RequestOutputCollector(output_kind, core_request.request_id)
    output_processor.add_request(core_request, queue=queue)
    await engine_core.add_request_async(core_request)
    return queue
```

先把请求注册到本进程的 `OutputProcessor`，再发送给 EngineCore。这样 EngineCore 很快返回 token 时，前台已经有接收位置。

### 5.2 输出方向

`generate()` 消费 `RequestOutputCollector`：

```python
queue = await add_request(...)
while True:
    out = queue.get_nowait() or await queue.get()
    yield out
    if out.finished:
        break
```

另一个后台 output handler 持续从 EngineCore 拉取 `EngineCoreOutputs`，交给 `OutputProcessor`，再放入对应 request queue。

因此有两条并行流：

```text
请求协程：HTTP → add_request → per-request queue → SSE
后台协程：EngineCoreOutputs → OutputProcessor → per-request queue
```

慢客户端造成的背压应在前台输出路径处理，不能让 EngineCore 每生成一个 token 就同步等待网络。

## 6. 第三段：ZMQ IPC 与 `EngineCoreProc`

### 6.1 发送

在线多进程客户端是：

```text
vllm/v1/engine/core_client.py
  AsyncMPClient
```

`add_request_async()` 先写入 `client_index`，然后发送 `EngineCoreRequestType.ADD`。

伪代码：

```python
message = (
    engine_identity,
    EngineCoreRequestType.ADD.value,
    *msgpack_encoder.encode(core_request),
)
await input_socket.send_multipart(message, copy=False)
```

v0.27.1 使用 ZMQ multipart 与 msgpack；Tensor/ndarray 可走零拷贝 frame，ZMQ 保持底层对象引用直到发送完成。

### 6.2 接收

EngineCore 包装类：

```text
vllm/v1/engine/core.py
  class EngineCoreProc(EngineCore)
```

输入线程在 `process_input_sockets()` 中：

1. ZMQ DEALER socket 收 multipart；
2. 首帧解码为 `EngineCoreRequestType`；
3. ADD 使用 `MsgpackDecoder(EngineCoreRequest)`；
4. `preprocess_add_request()` 转换内部对象；
5. 放入进程内 `input_queue`；
6. busy loop 调 `_handle_client_request()`。

线程与进程不要混为一谈。ZMQ I/O 线程属于 EngineCore 进程；真正的核心循环也在该进程中。

### 6.3 为什么不是“IPC 越少越好”

IPC 有序列化、socket 和调度成本，但隔离带来：

- HTTP 与 Tokenize 不直接堵塞核心循环；
- output socket 可独立收发；
- 多前台可以通过 `client_index` 路由；
- EngineCore 的 Request/Scheduler 状态有清晰所有者。

性能问题是降低每 step 的重复传输，而不是把所有组件重新塞回一个 Python 调用栈。

## 7. 第四段：`Request` 与调度状态

### 7.1 从传输对象到权威对象

`EngineCore.preprocess_add_request()` 调用：

```text
Request.from_engine_core_request()
```

定义位置：

```text
vllm/v1/request.py
  class Request
  enum RequestStatus
```

`Request` 加入运行时状态：

```text
status
num_prompt_tokens
_output_token_ids / _all_token_ids
spec_token_ids
num_computed_tokens
num_output_placeholders
num_in_flight_tokens
num_preemptions
block_hashes
structured_output_request
events
prefill_stats
```

### 7.2 三个不能混淆的 token 计数

`num_tokens`：

$$
N_{\text{tokens}}
=N_{\text{prompt}}+N_{\text{accepted-output}}
$$

`num_tokens_with_spec`：

$$
N_{\text{with-spec}}
=N_{\text{tokens}}+N_{\text{draft}}
$$

`num_computed_tokens` 是 Scheduler 认为已计算到的位置；异步与 pipeline run-ahead 下，它可以包含仍在 flight 的乐观计数。

普通同步场景中可先理解为：

```text
要追到的位置 - 已计算位置 = 本轮候选工作量
```

异步场景还要处理 placeholders、in-flight 与回滚，不能把字段名当作“GPU 已经完成并提交”的绝对事实。

### 7.3 状态机

常见主路径：

```text
WAITING
  → RUNNING
  → FINISHED_STOPPED / FINISHED_LENGTH_CAPPED
```

KV 不足时：

```text
RUNNING
  → PREEMPTED
  → WAITING queue
  → RUNNING
```

结构化输出 grammar 尚未编译好时，请求可处于：

```text
WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR
```

所以 waiting 不是单一原因，也不一定只是 FCFS 队首。

## 8. 第五段：Scheduler 与 `KVCacheManager`

### 8.1 Scheduler 持有的权威集合

定义位置：

```text
vllm/v1/core/sched/scheduler.py
  class Scheduler
```

关键字段：

```text
requests: dict[str, Request]
waiting: RequestQueue
skipped_waiting: RequestQueue
running: list[Request]
finished_req_ids
max_num_running_reqs
max_num_scheduled_tokens
max_model_len
kv_cache_manager
structured_output_manager
```

`running` 表示“持有执行状态并可继续参与调度”，不表示此刻正在 GPU 上。

### 8.2 一个 step

`EngineCore.step()` 的 v0.27.1 主链：

```python
def step():
    if not scheduler.has_requests():
        return {}, False

    scheduler_output = scheduler.schedule()
    future = model_executor.execute_model(scheduler_output, non_block=True)
    grammar_output = scheduler.get_grammar_bitmask(scheduler_output)
    model_output = future.result()
    if model_output is None:
        model_output = model_executor.sample_tokens(grammar_output)
    process_aborts_arrived_during_forward()
    outputs = scheduler.update_from_output(scheduler_output, model_output)
    return outputs, scheduler_output.total_num_scheduled_tokens > 0
```

这里有一个重要并行点：模型非阻塞执行后，CPU 可以准备 grammar bitmask；输出回来前到达的 abort 也会在更新状态前处理。

### 8.3 KVCacheManager

定义位置：

```text
vllm/v1/core/kv_cache_manager.py
  KVCacheManager
  KVCacheBlocks
```

主要接口：

```text
get_computed_blocks(request)
allocate_slots(request, num_new_tokens, ...)
get_blocks(request_id)
free(request)
reset_prefix_cache()
```

`KVCacheBlocks.blocks` 的外层是 KV cache group，内层是该 group 的物理 blocks。它隐藏 hybrid Attention 下不同缓存组的内部布局。

### 8.4 全量命中为什么仍需算

`get_computed_blocks()` 把最大命中限制为：

```python
max_cache_hit_length = request.num_tokens - 1
```

因为需要至少重算最后位置以取得 logits。当前分配约束还可能让它重算一个完整 block，而不仅是单 token。

## 9. 第六段：`SchedulerOutput` 到 ModelRunner

### 9.1 计划对象

定义位置：

```text
vllm/v1/core/sched/output.py

```

`SchedulerOutput` 的主字段：

```text
scheduled_new_reqs

```

新请求发送较完整的 `NewRequestData`；已缓存请求使用 `CachedRequestData` 传增量。

### 9.2 Executor 与 Worker

`EngineCore` 调用的是 Executor 抽象。单进程、多进程或 Ray executor 再把命令分发给 Worker。

GPU Worker 的主入口：

```text
vllm/v1/worker/gpu_worker.py
  Worker.execute_model()
```

当前 Model Runner 主路径：

```text
vllm/v1/worker/gpu_model_runner.py
  GPUModelRunner._update_states()
  GPUModelRunner._prepare_inputs()
  GPUModelRunner.execute_model()
```

### 9.3 Persistent Batch 不是一个口号

Worker 维护：

```text
self.requests
self.input_batch
self.input_batch.req_id_to_index
self.input_batch.block_table
self.input_batch.token_ids_cpu
self.input_batch.num_computed_tokens_cpu
```

`_update_states()` 按 `SchedulerOutput`：

1. 删除 finished request；
2. 清理 persistent batch slot；
3. 对新 block 做必要的 zero/copy；
4. 移出本轮未调度请求；
5. 新增 `NewRequestData`；
6. 对 cached request 追加 block 和 token 增量；
7. resumed request 用新 block IDs 替换旧表；
8. `condense()` 压紧空洞；
9. 刷新 metadata。

如果连续两轮大部分请求相同，增量更新很省。若 batch 在两个完全不同的请求集合间交替，源码注释明确指出这个优化会变得低效。

## 10. 第七段：输出如何回到 SSE

模型执行产生 `ModelRunnerOutput`，包含：

```text
req_ids / req_id_to_index
sampled_token_ids
logprobs
prompt_logprobs_dict
pooler_output
kv_connector_output
cudagraph_stats
```

`Scheduler.update_from_output()`：

1. 减少 `num_in_flight_tokens`；
2. 处理 stale output；
3. 对 spec decode 拒绝 token 回滚 `num_computed_tokens`；
4. 追加已接受 token；
5. 检查 EOS、长度、stop；
6. 推进 structured grammar；
7. 完成请求时释放 KV；
8. 构造 `EngineCoreOutput`。

`EngineCoreOutput` 关键字段：

```text
request_id
new_token_ids
new_logprobs
finish_reason
stop_reason
events
prefill_stats
```

EngineCore 输出线程 msgpack 编码后通过 ZMQ PUSH 发回。前台 `AsyncMPClient` 的输出 task 解码，`OutputProcessor` 完成 Detokenize 和 OpenAI 输出对象组装，最后 per-request collector 唤醒 `generate()`。

完整闭环：

```text
ChatCompletionRequest
→ EngineInput
→ EngineCoreRequest
→ Request
→ SchedulerOutput
→ ModelRunnerOutput
→ EngineCoreOutput
→ RequestOutput
→ ChatCompletionStreamResponse
```

## 11. 一次请求的逐轮手算

设：

```text
max_num_batched_tokens = 8
block_size = 4
Prompt token IDs = [11, 12, 13, 14, 15, 16]
max_tokens = 3
无 Prefix Cache 命中
```

### Step 1：接纳

waiting 请求的：

```text
num_tokens = 6
num_computed_tokens = 0
num_new_tokens = min(6, 8) = 6
```

需要：

$$
\lceil 6/4\rceil=2\text{ blocks}
$$

假设分到物理 block `[7, 2]`。`SchedulerOutput`：

```text
scheduled_new_reqs = [R]
num_scheduled_tokens = {R: 6}
block_ids = ([7, 2],)
```

Worker 输入扁平 token 为 6 个，执行 Prefill 并采样第一个输出 token `21`。

更新后：

```text
num_computed_tokens = 6
all_token_ids = [11,12,13,14,15,16,21]
output_token_ids = [21]
```

注意采样出的 21 尚未作为下一位置完成 forward；它成为下一轮输入。

### Step 2：第一次 Decode

```text
num_tokens_with_spec = 7
num_computed_tokens = 6
need = 1
```

第二个 block 原有 2 个 token，还有 2 slots，不需新 block。执行 token 21 的位置，采样 `22`。

### Step 3：第二次 Decode

同理 need=1，使用 block 2 的最后一个 slot，采样 `23`。

达到 `max_tokens=3` 后请求完成，两个 block 的活跃引用释放。

这个例子解释了：

- “生成了 token”与“该 token 的 KV 已计算”相差一个迭代语义；
- Decode 本轮通常只调度 1 个输入位置；
- block 不必按请求逻辑顺序在物理上连续。

## 12. 张量维度与 block table 例子

某轮同时调度：

```text
A: 1 token，历史长度 100
B: 1 token，历史长度 40
C: 6 tokens，历史长度 0
```

总 query token：

$$
T_q=1+1+6=8
$$

hidden size 896 时，展平输入：

```text
input_ids:     [8]
positions:     [8]
hidden_states: [8, 896]
```

若每个逻辑 block 4 token，block table 可能是：

```text
A → [9, 4, 12, ...]
B → [1, 8, 3, ...]
C → [7, 2]
```

Attention metadata 还需知道每个 query 属于哪个请求、上下文长度与 slot mapping。Kernel 根据 block table 读取历史 K/V，而不是假设 A 的 100-token KV 连续存放。

如果模型有 4 个 KV heads、head dim 128，当前新增 K/V 每层概念形状：

```text
K_new: [8, 4, 128]
V_new: [8, 4, 128]
```

历史读取长度则分别为 A≈100、B≈40、C≤6。相同的 query batch 不代表每个序列 Attention 长度相同。

## 13. 可复现的链路实验

### 13.1 启动并记录最终配置

```bash
export MODEL=Qwen/Qwen2.5-0.5B-Instruct

vllm serve "$MODEL" \
  --host 127.0.0.1 \
  --port 8000 \
  --max-model-len 2048 \
  --max-num-seqs 16 \
  --max-num-batched-tokens 256 \
  --generation-config vllm 2>&1 | tee server.log
```

### 13.2 给请求显式 ID

```bash
curl -N http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'X-Request-Id: trace-arch-001' \
  -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [{"role": "user", "content": "分三点解释 KV Cache"}],
    "temperature": 0,
    "max_tokens": 96,
    "stream": true
  }'
```

不同版本对请求 ID 响应 header 的开放方式可能变化，但日志与 tracing 应保留可关联标识。

### 13.3 构造 Prefill/Decode 混合

终端 A 先发长输出请求：


## 14. 分层指标与排障

### 14.1 API / 前台

现象：

```text
4xx、模板错误、Tokenize CPU 高、SSE 不流
```

检查：

```text
请求体与 served model name
Chat Template 后 token 数
API 进程 CPU
反向代理 buffering
客户端读取方式
```

### 14.2 IPC / EngineCore

现象：

```text
API 接受请求但无输出
EngineCore dead
共享内存或 ZMQ 异常
```

检查 EngineCore 子进程是否存活、server log 是否有 handshake/serialization/executor failure。不要只看 `/health` 的 HTTP 状态而忽略核心进程日志。

### 14.3 Scheduler / KV

v0.27.1 指标包括：

```text
vllm:kv_cache_usage_perc
vllm:prefix_cache_queries
vllm:prefix_cache_hits
vllm:num_preemptions
vllm:request_queue_time_seconds
```

`kv_cache_usage_perc` 持续高且 `num_preemptions` 增长，说明调度在用重计算偿还过度接纳，不是健康高利用率。

### 14.4 Worker / GPU

现象：

```text
GPU 利用率锯齿
多卡某 rank 卡住
eager 正常、默认编译路径失败
```

检查 CPU 输入准备、NCCL、CUDA Graph/compile、shape fallback、模型特定 backend。GPU 低利用率只有在“Scheduler 有足够工作”前提下才说明执行路径喂不满。

### 14.5 输出路径

v0.27.1 延迟指标包括：

```text
vllm:time_to_first_token_seconds
vllm:inter_token_latency_seconds
vllm:e2e_request_latency_seconds
```

服务端 ITL 正常而客户端卡顿，重点检查代理与网络；服务端 ITL 同时恶化，才回到 Scheduler/Worker 查 Prefill 干扰或执行抖动。

## 15. 架构 trade-off

### 多进程

收益是前台 CPU 工作与 EngineCore 隔离；代价是 ZMQ、msgpack、生命周期与共享对象管理。

### 权威状态拆分

Scheduler `Request` 与 Worker cached state 各司其职，可以少传数据；代价是 preemption、abort、async run-ahead 下必须严格对齐计数和 block IDs。

### Persistent Batch

高重叠连续 batch 可显著减少 CPU 重建；低重叠 workload 会增加 remove/add/condense 成本。

### 乐观计数

异步调度能重叠 CPU/GPU；代价是 `num_in_flight_tokens`、placeholder、stale output 与 spec rejection 回滚变复杂。

### 分页 KV

避免按最大长度连续预留，并支持 Prefix Cache；代价是 Attention backend 必须理解 block table，元数据和 block 对齐也有成本。
