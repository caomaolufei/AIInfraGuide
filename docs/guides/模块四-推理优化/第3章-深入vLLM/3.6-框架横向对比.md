## 1. 真实问题：最快到底指什么

“vLLM、SGLang、TensorRT-LLM 谁最快？”至少缺少：

```text
模型与 revision
权重 / KV 精度
GPU 型号、数量、互联、功耗
Prompt / Output 长度联合分布
共享前缀与多轮比例
到达率与突发性
TTFT / ITL / E2E SLO
正确率与失败请求处理
```

同一框架可以在以下场景得到相反排名：

- 1 个短请求：launch 与单请求延迟主导；
- 512 个 Decode：batching 与内存带宽主导；
- 32K Prompt：Prefill、KV 与 chunking 主导；
- 8K 共享前缀：cache hit 与路由局部性主导；
- JSON schema：grammar 编译与 constrained sampling 主导。

正确问题是：

> 在目标模型、硬件、流量和质量门禁下，哪个方案以可接受运维成本提供最高 goodput？

## 2. 白话直觉：同一赛道、同一载重、同一终点

比较三辆车时，不能让：

```text
A 走高速、载 1 吨
B 走山路、载 3 吨
C 少跑最后 20 公里
```

然后只比较到达时间。

对应到推理：

- 相同 API 名不保证 Chat Template 相同；
- 相同 `max_tokens=256` 不保证实际输出都 256；
- 相同“FP8”不保证权重、KV 与 scale 配置相同；
- 相同并发不保证到达过程相同；
- 相同请求数不保证失败请求被同样计入。

公平 benchmark 先做**语义对齐**，再做性能测量。

## 3. 先定义候选与版本边界

vLLM 一侧固定：

```text
vLLM v0.27.1
https://github.com/vllm-project/vllm/tree/v0.27.1
```

SGLang 与 TensorRT-LLM 也必须锁定：

```text
容器 digest
Python package version
Git commit/tag
CUDA / driver / NCCL / TensorRT
模型转换工具版本
```

不要写“截至目前 SGLang”。实验记录应写：

```text
backend=sglang
image=repo/name@sha256:...
git_commit=...
```

TensorRT-LLM 若使用预构建 engine，还要保存：

```text
build command
builder config
engine artifact hash
profile / max batch / max sequence
```

否则复现者无法判断性能来自 runtime 还是 engine 构建差异。

## 4. 比机制，不比宣传名词

三个框架都在解决：

```text
动态请求调度
分页 KV
Prefill / Decode 混合
Prefix/KV 复用
多 GPU 并行
量化与 Kernel
OpenAI 风格服务
```

辨识度较高的机制：

### vLLM

```text
V1 统一 token Scheduler
KVCacheManager / PagedAttention
block-hash Automatic Prefix Caching
多 backend 与较广模型生态
```

### SGLang

```text
RadixAttention 的前缀树组织
cache-aware runtime
生成程序、structured generation
HiCache / PD 等扩展路径
```

### TensorRT-LLM

```text
TensorRT engine 与 NVIDIA 全栈优化
in-flight batching
paged KV / context chunking
构建期与运行期联合优化
```

这些描述用于提出实验假设，不用于直接宣布冠军。

例如“RadixAttention 更适合共享前缀”应转化为：

```text
在 cold/warm/churn 三种 cache 状态，
以相同 8K 前缀和相同后缀分布，
比较 hit tokens、TTFT、淘汰后 P99 与显存。
```

## 5. 公平性的不可变条件

### 5.1 模型语义

固定：

```text
同一 checkpoint revision
同一 tokenizer revision
同一 Chat Template 文本
同一 BOS/EOS 添加规则
同一 RoPE / max sequence 配置
```

服务启动后用同一组消息检查 tokenized input 长度。若框架不暴露 token IDs，可在外部用锁定 tokenizer 渲染，再调用 completions endpoint。

### 5.2 精度

固定：

```text
权重 dtype / 量化格式
KV dtype
量化 scale
是否有未量化层
```

不能拿 vLLM BF16 对 TensorRT-LLM FP8 engine，只比较吞吐，却不报告质量与显存。

如果某框架只在另一精度上有最佳路径，应做两组：

```text
iso-quality：质量相当的配置
best-validated：每框架自己通过门禁的最佳配置
```

不要混为同一个“公平排名”。

### 5.3 硬件

固定：

```text
GPU 数量与型号
MIG 配置
TP/PP/DP 资源
NUMA 绑定
GPU power limit / clocks
CPU / RAM / NIC
```

测试前记录：

```bash
nvidia-smi -q
nvidia-smi topo -m
lscpu
numactl --hardware
```

### 5.4 请求语义

固定：

```text
temperature / top_p / top_k
seed（若支持）
max_tokens
ignore_eos
stop strings / stop token IDs
logprobs
structured schema
stream=true/false
```

返回 usage 只作为核对；统一压测器应自己记录实际输出 token。

## 6. 正确性与 API 契约门禁

性能前先执行契约测试。

### 6.1 基础生成

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url=os.environ["LLM_BASE_URL"],
    api_key=os.getenv("LLM_API_KEY", "EMPTY"),
)

response = client.chat.completions.create(
    model=os.environ["LLM_MODEL"],
    messages=[
        {"role": "system", "content": "只回答事实。"},
        {"role": "user", "content": "1+1 等于几？"},
    ],
    temperature=0,
    max_tokens=16,
    seed=7,
)

print(response.choices[0].finish_reason)
print(response.usage)
print(response.choices[0].message.content)
```

不要求跨 Kernel 文本永远逐字一致，但必须满足任务正确性和终止规则。

### 6.2 需要覆盖的契约

```text
stream delta 拼接与最终文本一致
客户端取消后服务释放资源
超长请求返回一致类别的错误
stop string 不泄漏或语义一致
usage token 统计可解释
tool call / reasoning 字段符合业务解析器
JSON schema 可被标准解析器验证
logprobs 字段语义一致（如业务使用）
```

### 6.3 质量门禁

按业务选择：

```text
MMLU/知识
GSM8K/数学
HumanEval/代码
RAG 命中
JSON schema valid rate
工具调用 exact match
长上下文 needle retrieval
```

所有候选先过最低质量阈值。性能再高但 JSON valid rate 只有 97%，而业务要求 99.9%，不进入性能决赛。

## 7. 工作负载模型

### 7.1 二维长度，而非单一平均

输入与输出通常相关。应保存联合分布：

```text
短输入 / 短输出
短输入 / 长输出
长输入 / 短输出
长输入 / 长输出
```

四个桶示例：

```text
S:  128 in / 128 out  40%
D:  128 in / 1024 out 20%
P: 4096 in / 128 out  30%
L: 8192 in / 1024 out 10%
```

分别测试，再按生产比例混合。只报加权平均会隐藏 L 桶的尾延迟。

### 7.2 Prompt 内容

随机 token 适合控制长度，却不代表：

```text
真实 Chat Template
自然语言停词
重复前缀
工具定义
多轮历史
```

实验分：

```text
synthetic length-control
replayed production-shape（脱敏）
task-quality set
```

### 7.3 多轮会话

多轮不能拆成互不相关请求。需要保留：

```text
session ID
每轮新增 token
历史增长
think time
路由是否粘性
```

否则测不到 Radix/APC 和 DP 路由局部性的真实差异。

## 8. 到达过程与过载测试

### 8.1 closed-loop

固定 concurrency，一个完成再发一个。

适合测最大吞吐，但会自动降低实际到达率，不能显示队列发散点。

### 8.2 open-loop Poisson

固定 request rate，间隔指数分布。vLLM benchmark 的 `burstiness=1` 对应 Poisson。

适合在线容量曲线：

```text
2, 4, 8, 12, 16, ... req/s
```

找 queue P99 开始非线性增长的 knee。

### 8.3 Gamma burstiness

同一平均 request rate 下：

```text
burstiness < 1：更突发
burstiness = 1：Poisson
burstiness > 1：更均匀
```

只测均匀流量会高估真实生产稳定性。

### 8.4 overload 与恢复

三阶段：

```text
基线 5 分钟：0.6×估计容量
过载 2 分钟：1.3×估计容量
恢复 5 分钟：回到 0.6×
```

观察：

```text
队列是否有界
拒绝/超时策略
preemption 是否持续
过载结束后多久恢复 P99
是否需要重启才能恢复
```

峰值吞吐相同的框架，过载恢复行为可能完全不同。

## 9. Cache 的 cold、warm 与 churn

### 9.1 数据集构造

每个请求：

```text
8,192-token shared prefix
+ 256-token per-session branch
+ 64-token unique question
```

总输入约：

$$
8192+256+64=8512
$$

若 80% 请求共享主前缀，理论重复 Prefill 很高。

### 9.2 cold

重启服务或显式安全清空 cache，首轮所有前缀未命中。

测：

```text
cold TTFT
首次 Prefix 构建吞吐
启动后达到稳态的请求数
```

### 9.3 warm

先用不计分 warmup 填充，再发送相同前缀、不同后缀。

测：

```text
命中 token，而不是只看 hit requests
warm TTFT
cache 占用
```

### 9.4 churn

构造前缀 working set 大于 cache：

```text
prefixes A..Z 循环
每个 8K
Zipf 热度与生产近似
```

测淘汰下：

```text
hit ratio 随时间
P99 TTFT
cache lookup CPU
恢复到热集合后的速度
```

只测 warm cache 会把理想上限冒充线上表现。

### 9.5 DP 路由

四副本随机路由时，同一热前缀可能被复制四份。sticky/prefix-aware 路由可以提高局部性，却可能造成负载不均。

公平实验应分别测试：

```text
random routing
session sticky
prefix-aware（若方案支持）
```

并同时报告 max replica queue，不只报告整体命中率。

## 10. 指标与统计方法

### 10.1 请求级

```text
成功率 / timeout / cancel
TTFT P50/P95/P99
TPOT P50/P95/P99
ITL P50/P95/P99
E2E P50/P95/P99
goodput req/s
```

### 10.2 token 与资源

```text
input tokens/s
output tokens/s
总 GPU work tokens/s（若可观测）
GPU utilization / power / HBM
CPU cores / RSS
网络 bytes
KV usage / hit tokens / preemption
```

### 10.3 启动与运维

```text
cold startup to ready
first-request latency
warm restart
模型更新切换时间
失败恢复时间
engine artifact size
```

### 10.4 置信与重复

每个点至少 3 次，最好 5 次。随机化框架运行顺序，避免：

```text
GPU 温度
文件缓存
后台任务
编译缓存
```

造成固定顺序偏差。

对每轮 P99 不宜简单求所有请求混合 P99后只给一个数。保留 run-level 分布与 per-request 原始数据，报告中位数和范围。

## 11. vLLM v0.27.1 的可追踪测量链

vLLM benchmark 客户端源码：

```text
vllm/benchmarks/serve.py
  get_request()
  benchmark()
  calculate_metrics()
  parse_goodput()
```

到达过程：

```python
if request_rate == inf:
    delay = 0
elif burstiness == inf:
    delay = 1 / request_rate
else:
    delay ~ Gamma(shape=burstiness,
                  scale=1/(request_rate*burstiness))
```

goodput 支持：

```text
ttft
tpot
e2el
```

服务端指标定义：

```text
vllm/v1/metrics/stats.py
vllm/v1/metrics/loggers.py
```

v0.27.1 指标链：

```text
Scheduler.update_from_output()
→ EngineCoreOutputs.scheduler_stats
→ frontend metrics logger
→ /metrics
```

关键 metric：

```text
vllm:time_to_first_token_seconds
vllm:inter_token_latency_seconds
vllm:e2e_request_latency_seconds
vllm:request_queue_time_seconds
vllm:kv_cache_usage_perc
vllm:prefix_cache_queries
vllm:prefix_cache_hits
vllm:num_preemptions
```

跨框架排名应以统一外部客户端为主；内部 metrics 用于解释根因，不能直接拿名称相似的内部 histogram 拼排名。

## 12. 统一压测器与实验命令

### 12.1 vLLM 作为统一客户端

只要三者提供兼容 endpoint，可让同一个 v0.27.1 `vllm bench serve` 发请求。先查看：

```bash
vllm bench serve --help
```

模板：

```bash
vllm bench serve \
  --backend openai-chat \
  --base-url "$BASE_URL" \
  --model "$SERVED_MODEL" \
  --tokenizer "$TOKENIZER_REV_OR_PATH" \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --random-range-ratio 0.3 \
  --num-prompts 2000 \
  --request-rate 16 \
  --burstiness 1 \
  --max-concurrency 256 \
  --num-warmups 50 \
  --temperature 0 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,95,99 \
  --goodput ttft:800 tpot:50 e2el:15000 \
  --save-result \
  --save-detailed \
  --metadata \
    framework="$FRAMEWORK" \
    image_digest="$IMAGE_DIGEST" \
    model_revision="$MODEL_REV" \
    workload=M \
    run="$RUN_ID"
```

如果某 backend 的 OpenAI 字段语义不兼容，不应悄悄删字段继续比。要么收敛到三者共同且已通过契约测试的 API 子集，要么写一个统一 adapter 并把 adapter 成本计入三者。

### 12.2 外部计时

客户端与服务端尽量分机，避免压测器 CPU 抢占服务 CPU。同步时钟不是计算单客户端 TTFT 的必要条件，但跨主机 trace 对齐需要 NTP/PTP。

### 12.3 服务端命令记录

vLLM：

```bash
vllm serve MODEL \
  --tensor-parallel-size 1 \
  --max-model-len 8192 \
  --max-num-seqs 128 \
  --max-num-batched-tokens 4096 \
  --generation-config vllm
```

SGLang：

```bash
python -m sglang.launch_server \
  --model-path MODEL \
  --host 0.0.0.0 \
  --port 30000
```

TensorRT-LLM：

```bash
trtllm-serve MODEL_OR_ENGINE \
  --host 0.0.0.0 \
  --port 8000
```

后两条只是入口骨架。正式实验必须展开所有影响语义和性能的参数，而不是比较默认值。

## 13. 完整实验矩阵

### Phase 0：门禁

```text
API contract
token length alignment
quality suite
error/cancel behavior
```

不通过者停止。

### Phase 1：单请求

```text
S/P/D/L 四桶
batch=1
cold 与 warm startup
```

目的：看 Kernel/launch/单请求路径，不宣称线上吞吐。

### Phase 2：吞吐曲线

```text
closed-loop concurrency=[1,2,4,8,16,32,64,128,256]
```

目的：找饱和点。

### Phase 3：SLO 容量

```text
open-loop request_rate 从低到高
burstiness=[0.5,1,inf]
```

目的：找最大 sustainable goodput。

### Phase 4：Cache

```text
cold / warm / churn
共享前缀=[0,1K,8K]
DP routing=[random,sticky,prefix-aware]
```

### Phase 5：高级功能

按业务开启：

```text
JSON schema
tool calling
reasoning parser
LoRA
VLM
spec decode
```

高级功能不应只测“能返回”，要重复 Phase 2/3 的关键点。

### Phase 6：故障与运维

```text
过载恢复
客户端取消风暴
单 Worker 故障
模型滚动更新
节点重启
版本升级回归
```

## 14. 带数字的选型手算

假设同样 4×H100，质量门禁都通过，M workload 结果：

```text
候选 A：吞吐 120 req/s，SLO goodput 90 req/s，功耗 2.4 kW
候选 B：吞吐 110 req/s，SLO goodput 100 req/s，功耗 2.2 kW
候选 C：吞吐 135 req/s，SLO goodput 82 req/s，功耗 2.5 kW
```

若只看完成吞吐，C 第一。按 goodput，B 第一。

### 14.1 SLO 合格率

```text
A: 90/120 = 75.0%
B: 100/110 = 90.9%
C: 82/135 = 60.7%
```

C 做了最多工作，但尾延迟使大量请求失去业务价值。

### 14.2 每千 good requests 能耗

近似每小时 good requests：

```text
A: 90×3600=324,000
B: 100×3600=360,000
C: 82×3600=295,200
```

每千 good requests 的 kWh：

$$
A:\frac{2.4}{324}=0.00741
$$

$$
B:\frac{2.2}{360}=0.00611
$$

$$
C:\frac{2.5}{295.2}=0.00847
$$

B 同时有更高 goodput 与更低单位有效请求能耗。

### 14.3 运维成本

若 B 每周需要 6 工时维护 engine，A 只需 1 工时，而业务规模较小，B 的性能收益未必覆盖工程成本。

计算月度总成本：

$$
C_{\text{total}}
=C_{\text{GPU}}
+C_{\text{energy}}
+C_{\text{engineering}}
+C_{\text{risk}}
$$

工程成本必须显式，不要藏在“框架免费开源”后面。

## 15. 成本与运维实验

### 15.1 冷启动

从“进程开始”计时到：

```text
/health ready
第一条真实请求成功
P99 回到稳态
```

三者可能分别受权重加载、compile、CUDA Graph capture、TensorRT engine 加载影响。

### 15.2 模型更新

记录：

```text
checkpoint 到可服务 artifact 的时间
engine 构建时间
构建 GPU/CPU 资源
artifact 大小
质量回归时间
滚动更新峰值显存
```

固定模型半年不变时，TensorRT 构建成本容易摊薄；模型每天更新时，交付延迟可能比 10% 吞吐更重要。

### 15.3 可观测性

验证而不是数功能：

```text
能否关联 request ID 与 trace
能否区分 queue/prefill/decode
能否看到 KV hit/preemption
错误是否有稳定分类
指标升级是否兼容 dashboard
```

### 15.4 回退

让同一契约测试客户端通过环境变量切换 endpoint。演练：

```text
新框架 5xx
→ 停止导流
→ 旧框架恢复
→ 在途请求如何处理
→ 会话粘性与 cache 是否丢失
```

“支持 OpenAI API”不等于零成本回退。

## 16. 如何解释结果

### 16.1 不做总榜

按 workload 给 Pareto 前沿：

```text
交互 SLO 前沿
长 Prompt 前沿
共享前缀前沿
结构化输出前沿
单位成本前沿
```

同一候选可在一个前沿上、另一个不在。

### 16.2 找 knee，不追极限

request rate 从 20 到 24，goodput只增 5%，P99 TTFT 翻倍，24 不是健康容量。

通过曲线找：

```text
queue 开始持续增长
preemption 从 0 变为常态
P99 非线性上升
错误率增加
```

生产目标通常放在 knee 左侧。

### 16.3 区分机制与配置

如果 vLLM 表现差，先判断：

```text
框架机制上限
默认参数不适合
backend/quant 路径不成熟
benchmark API adapter 不公平
```

每个框架都应先做内部合理调优，再进入横向决赛。给 A 精调、B 默认不是公平。

### 16.4 记录失败点

OOM、启动失败、质量失败也是结果，不能从图中删除。应记录失败配置与阶段，防止团队再次尝试同一死路。

## 17. 失败模式与排障

### 17.1 Token 长度不一致

检查：

```text
Chat Template
add_generation_prompt
BOS/EOS
tokenizer revision
客户端是否二次模板化
```

先修语义，不能按“请求数”继续比。

### 17.2 输出长度不一致

检查：

```text
EOS
ignore_eos
stop
finish_reason
max_tokens 语义
服务端 generation config
```

### 17.3 一个框架错误率高但吞吐高

统一客户端必须把失败计入：

```text
success rate
goodput
请求吞吐分母
```

不能把快速失败当高性能。

### 17.4 客户端成为瓶颈

症状：

```text
服务 GPU 未满
客户端 CPU 100%
三个框架都在相似 QPS 封顶
```

扩大客户端、用多进程/Rust 客户端或分机。改变客户端后全部候选重测。

### 17.5 顺序偏差

第一个框架冷文件 cache，后两个热；或最后一个因 GPU 过热降频。

使用随机化/拉丁方顺序：

```text
run1: A B C
run2: B C A
run3: C A B
```

### 17.6 Cache 测试“意外全命中”

确认：

```text
cold 前真的清空或重启
请求 token 完全相同的范围
cache key 是否包含 adapter / salt
DP 是否路由到同一副本
counter 使用实验区间差值
```

### 17.7 TensorRT engine 不等价

engine profile、量化或 max sequence 不同，会改变可运行请求与性能。将 build manifest 纳入实验 artifact。

### 17.8 内部指标名字相似但语义不同

跨框架用外部计时为准；内部指标只解释本框架。若必须对齐，先写定义映射和采样时点，而不是按名字直接画在一张图。

## 18. trade-off 与决策模板

### vLLM 候选假设

适合优先建立通用基线：

```text
模型/硬件覆盖重要
OpenAI 服务能力广
团队希望快速迭代
需要可读的 Scheduler/KV 抽象
```

风险：

```text
版本迭代快
组合功能矩阵大
特定模型最佳 Kernel 需要逐项验证
```

### SGLang 候选假设

值得重点验证：

```text
共享前缀、多轮、分支生成比例高
复杂生成/structured workflow 重要
愿意运维高级 cache/PD
```

风险：

```text
无共享前缀时优势可能缩小
高级缓存与路由引入新状态
版本与模型组合仍需验证
```

更系统的 SGLang 学习见 [第 12 章：深入 SGLang](/AIInfraGuide/inference/模块四-推理优化/第12章-深入sglang/第12章-深入sglang)。

### TensorRT-LLM 候选假设

值得重点验证：

```text
硬件固定 NVIDIA
模型集合稳定
团队能维护 CUDA/TensorRT 矩阵
愿意为构建期优化投入
```

风险：

```text
engine 构建与 artifact 管理
新模型适配周期
版本矩阵与回归成本
非 NVIDIA 路径受限
```

### 决策记录

最终 ADR 应包含：

```text
业务 SLO 与质量门禁
候选版本与 artifact hash
实验矩阵与原始结果链接
各 workload Pareto 前沿
月度总成本
已知失败模式
回退方案
下次复评触发条件
```

复评触发：

```text
模型/硬件变化
流量长度分布变化
新版本声称解决当前瓶颈
运维成本超过阈值
SLO 或功能契约变化
```
