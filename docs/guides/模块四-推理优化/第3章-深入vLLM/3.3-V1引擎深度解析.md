## 1. 真实问题：GPU 为什么会等 CPU

Decode 一步可能只处理每个请求的一个 token。模型越小、GPU 越快，CPU 固定开销越显眼：

```text
接收上一轮输出
→ 更新请求状态
→ 选择下一批请求
→ 构造 token / position / slot mapping
→ Python 调用并发射 Kernel
→ 等 GPU
```

假设一次 GPU Decode 需要 0.8 ms，而 CPU 调度、输入准备与 launch 共需 0.5 ms。若完全串行：

$$
T_{\text{step}}=0.5+0.8=1.3\text{ ms}
$$

GPU 只有：

$$
\frac{0.8}{1.3}=61.5\%
$$

的时间在做该 step 的工作。

单纯把 Attention Kernel 再优化 20%，GPU 时间变 0.64 ms，总步长仍为 1.14 ms，只提升约 14%。若 CPU 与 GPU 能重叠，稳态步长更接近：

$$
\max(0.5,0.8)=0.8\text{ ms}
$$

V1 的设计重点是让状态表达、进程边界与执行路径支持这种重叠，而不是只替换一个算子。

## 2. 白话直觉：V1 重写的不是一个 Kernel

V0 像一个不断扩建的中央厨房：Prefill、Decode、Prefix Cache、LoRA、Beam/Spec Decode 各有历史路径。每增加组合，都可能在多个分支中同步维护状态。

V1 的动作更像重新设计物流协议：

1. 不再先问请求属于哪个阶段，而是问“已计算位置离目标位置还差多少”；
2. 前台与 EngineCore 分进程，协议工作不占住核心循环；
3. Scheduler 输出增量计划，Worker 保留 persistent batch；
4. 编译与 CUDA Graph 围绕稳定张量缓冲和 shape 集合组织；
5. 异步模式允许 CPU 准备下一步时 GPU 执行当前步。

所以 V1 是**状态机与数据流重构**。某些模型不一定在所有负载上都更快，但架构更容易把多种优化放进同一闭环。

## 3. V0 到 V1：抽象发生了什么变化

### 3.1 不把历史实现当作当前源码

本文源码固定到 v0.27.1。该 tag 的主引擎是 `vllm/v1/*`，不能在这个 tag 中用一个仍并存的 V0 Scheduler 做逐行对照。

V0→V1 应按设计差异理解：

```text
阶段分支更强
  → 统一“目标 token - 已计算 token”

前端与核心路径耦合更深
  → AsyncLLM / EngineCore 多进程边界

每轮更容易重建完整 batch 状态
  → Worker 维护 persistent batch，Scheduler 传 diff

Prefix Cache 是附加路径
  → 与普通 KV block 共用管理器和容量

同步点较多
  → non-block execute、batch queue、async scheduling
```

这些是方向，不表示 V0 完全没有异步、缓存或连续批处理。把 V1 描述成“V0 没有 PagedAttention，V1 才有”是错误的。

### 3.2 组合复杂度

若每个功能都独立分叉，四个二元特性理论组合数是：

$$
2^4=16
$$

例如：

```text
Prefill / Decode
cache hit / miss
spec on / off
structured on / off
```

统一 token 计数与统一 `SchedulerOutput` 不能消灭 16 种语义，但能让它们共享预算、KV 分配和 Worker 更新协议，减少主循环的重复结构。

## 4. V1 的状态所有权

固定 tag 的关键所有者：

```text
前台 AsyncLLM / OutputProcessor
  OpenAI 协议、外部 ID、per-request collector、文本增量

EngineCore Scheduler.Request
  waiting/running、token 计数、停止状态、preemption、block 生命周期

Worker GPUModelRunner.CachedRequestState
  设备执行所需 token、block IDs、采样状态

InputBatch
  req_id_to_index、token_ids_cpu、num_computed_tokens_cpu、block_table
```

### 4.1 为什么允许重复状态

如果所有状态只放 Scheduler，Worker 每 step 都要重新收全量请求对象并构造 batch。

如果所有状态只放 Worker，Scheduler 难以在不访问设备细节的情况下进行公平性、KV 与停止决策。

V1 选择“不同层保存各自权威子集”：

- Scheduler 决定生命周期和计划；
- Worker 保存执行缓存；
- `SchedulerOutput` 传递使两者收敛的 diff。

代价是状态一致性成为核心正确性问题。

### 4.2 可检查的不变量

每个 step 至少应满足：

$$
\sum_i n_i
\le max\_num\_scheduled\_tokens
$$

```text
running 数 ≤ max_num_seqs
SchedulerOutput.total = sum(num_scheduled_tokens.values())
finished_req_ids 到 Worker 后必须移除 slot
resumed request 的 block table 必须替换，不是追加旧表
spec rejection 必须回滚乐观 computed count
```

读源码时找这些 assert，比顺着所有特殊分支阅读更容易建立骨架。

## 5. IPC：请求如何低成本跨进程

### 5.1 对象编码

传输对象 `EngineCoreRequest` 是：

```text
vllm/v1/engine/__init__.py
  msgspec.Struct(array_like=True, omit_defaults=True, gc=False)
```

这些选择的含义：

- `array_like` 避免重复发送字段名；
- `omit_defaults` 减少默认字段；
- msgspec 比通用 Python pickle 更适合结构化消息；
- `gc=False` 减少对象参与循环 GC 的成本。

不能据此宣称 IPC 零开销。编码、socket、线程调度和队列仍存在。

### 5.2 输入 socket

`AsyncMPClient._send_input()`：

```python
message = (
    request_type.value,
    *encoder.encode(request),
)
await input_socket.send_multipart((engine_identity,) + message, copy=False)
```

EngineCore 侧：

```python
type_frame, *data_frames = input_socket.recv_multipart(copy=False)
request_type = EngineCoreRequestType(bytes(type_frame.buffer))
request = add_request_decoder.decode(data_frames)
internal_request = preprocess_add_request(request)
input_queue.put_nowait((request_type, internal_request))
```

### 5.3 tensor IPC

多模态 `prompt_embeds` 等 tensor 不适合先转大 Python list。v0.27.1 有：

```text
vllm/v1/engine/tensor_ipc.py
  TensorIpcReceiver
```

`MsgpackDecoder` 可使用 out-of-band tensor provider。普通文本请求主要是 token IDs 和小型元数据；多模态请求可能同时走 tensor IPC。

### 5.4 输出 socket

EngineCore 输出线程：

```text
output_queue
→ MsgpackEncoder
→ ZMQ PUSH
→ AsyncMPClient output_socket.recv_multipart()
→ MsgpackDecoder
→ asyncio.Queue
```

输入与输出各有独立处理路径，避免一个慢方向阻塞另一个方向。

### 5.5 IPC 故障边界

以下现象不应直接归因于模型：

```text
handshake 超时
EngineCore 子进程退出
msgpack 字段版本不一致
共享 tensor 生命周期错误
容器 /dev/shm 或进程限制不足
```

固定单一 wheel 和镜像能避免前台与 EngineCore 实际代码版本错配。

## 6. 统一 token 调度

### 6.1 核心差值

v0.27.1 `Scheduler.schedule()` 的注释明确说明没有固定 Prefill phase 与 Decode phase。

running 请求候选：

$$
n_{\text{new}}
=N_{\text{tokens-with-spec}}
+N_{\text{output-placeholders}}
-N_{\text{computed}}
$$

然后受以下上界裁剪：

```text
long_prefill_token_threshold
剩余 token_budget
max_model_len - num_computed_tokens - sampled_tokens_per_step
encoder budget
KV slots
```

### 6.2 三种请求同一表达

普通 Decode：

```text
num_tokens=1001
num_computed_tokens=1000
spec=[]
need=1
```

Chunked Prefill：

```text
num_tokens=4096
num_computed_tokens=1024
need=3072
budget=512
scheduled=512
```

Spec Decode：

```text
num_tokens=1001
spec_token_ids 长度=4
num_computed_tokens=1000
need=5
```

最后一种包括“当前真实输入位置 + draft candidates”。执行后只接受部分 draft 时，`update_from_output()` 回滚 rejected count。

### 6.3 乐观推进

`Scheduler._update_after_schedule()` 在模型完成前：

```python
request.num_computed_tokens += num_scheduled
request.num_in_flight_tokens += num_scheduled
```

这样 async/PP 模式可以继续准备后续计划。输出回来时：

```python
request.num_in_flight_tokens -= num_scheduled
request.num_computed_tokens -= num_rejected_spec_tokens
```

这是一种 speculative state update。收益是流水线重叠，代价是 abort、preemption 和 rejected draft 都要正确处理 stale/in-flight 状态。

## 7. Prefix Cache 与统一 block 池

### 7.1 block hash

`Request` 持有 `block_hashes`，每新增完整 hash block 时更新。EngineCore 初始化时根据：

```text
enable_prefix_caching
prefix_caching_hash_algo
hash_block_size
```

建立 request block hasher。

### 7.2 命中不是复制 KV

`KVCacheManager.get_computed_blocks()` 返回：

```text
KVCacheBlocks
num_new_computed_tokens
shared_prefix_boundary
```

命中 block 增加引用并进入该请求的 block table，不需要把整段 K/V 复制一份。

### 7.3 空闲与缓存可同时成立

一个无活跃引用的 block 可以进入 free queue，但内容与 hash 映射暂时保留。新请求命中时可重新 pin；真正被分配覆盖时旧映射才失效。

因此：

```text
free block ≠ 内容立即清零
cached block ≠ 永久不可回收
```

v0.27.1 还显式传递 `new_block_ids_to_zero`，Worker 在使用新分配 block 前清理，避免旧 NaN/数据污染新请求。

### 7.4 完整命中手算

Prompt 130 token，hash block 16 token：

$$
\lfloor130/16\rfloor=8\text{ full blocks}
$$

看似可命中 128 token，但 `get_computed_blocks()` 最大 hit 长度是 `num_tokens-1=129`。块对齐后仍最多 128 token；最后 2 token 需要计算。

若 Prompt 恰好 128 token，最大 hit 是 127，当前完整 block 约束可能只命中 112 token，最后一个 16-token block 重算以产生 logits。这是“100% 前缀相同但 hit token 不是 100%”的源码原因。

## 8. Persistent Batch 的真实数据结构

### 8.1 入口

当前主 Model Runner：

```text
vllm/v1/worker/gpu_model_runner.py
  GPUModelRunner._update_states()
```

persistent batch 对象：

```text
vllm/v1/worker/gpu_input_batch.py
  InputBatch
```

关键字段：

```text
req_ids
req_id_to_index
token_ids_cpu
num_tokens_no_spec
num_computed_tokens_cpu
block_table
sampling metadata
```

### 8.2 新请求

`NewRequestData` 让 Worker 建立 `CachedRequestState`：

```python
state = CachedRequestState(
    req_id=...,
    prompt_token_ids=...,
    sampling_params=...,
    block_ids=...,
    num_computed_tokens=...,
    output_token_ids=[],
)
self.requests[req_id] = state
self.input_batch.add_request(state)
```

### 8.3 已有请求

`CachedRequestData` 不重复发送全部 Prompt。Worker 更新：

```text
num_computed_tokens
new_block_ids
必要的新 token IDs
num_output_tokens
spec token IDs
```

如果请求从 preemption 恢复：

```python
state.block_ids = new_block_ids
```

如果只是正常延长：

```python
state.block_ids[group].extend(new_ids[group])
```

把两种情况写反会把已释放 block 留在表中，是正确性错误，不只是性能问题。

### 8.4 slot 压紧

本轮请求集合从 `[A,B,C,D]` 变成 `[A,C,E]`：

```text
删除 B、D
slot: [A, _, C, _]
加入 E
可能先填最小空位
condense 后得到密集前缀
```

密集 batch 有利于张量切片和 CUDA Graph shape。压紧本身也有 CPU 成本，所以 Persistent Batch 最喜欢相邻 step 高重叠。

### 8.5 元数据量手算

假设 256 个请求，每个全量 Python 状态序列化约 2 KiB：

$$
256\times2\text{ KiB}=512\text{ KiB/step}
$$

若本轮只有 2 个新增、3 个完成、251 个请求只更新计数与少量 block ID，diff 假设平均 32 bytes：

$$
2\times2\text{ KiB}
+3\times16\text{ B}
+251\times32\text{ B}
\approx12\text{ KiB}
$$

这是数量级直觉，不是 vLLM 实测字节数。真实数据取决于 SamplingParams、PP、spec、MM 和 block group。

## 9. CPU–GPU 重叠与 batch queue

### 9.1 普通 step

`EngineCore.step()`：

```text
schedule
→ execute_model(non_block=True)
→ 计算 grammar bitmask
→ future.result
→ update_from_output
```

这里已经把部分 CPU 工作放到模型执行窗口。

### 9.2 多 batch in flight

EngineCore 初始化：

```python
self.batch_queue_size = vllm_config.max_concurrent_batches
if batch_queue_size > 1:
    self.batch_queue = deque(maxlen=batch_queue_size)
    self.step_fn = self.step_with_batch_queue
```

`step_with_batch_queue()` 优先填队列：

```text
队列未满且有可调度工作
  → schedule batch N+1
  → execute non-blocking
  → 放入 batch_queue
  → 可能不等结果直接返回

队列满或无新工作
  → 等最老 future
  → update_from_output
```

Pipeline Parallel 需要它来减少 pipeline bubble。

### 9.3 异步调度的复杂状态

run-ahead 意味着 Scheduler 可能在 N 的输出回来前安排 N+1。v0.27.1 `Request` 因此有：

```text
num_output_placeholders
num_in_flight_tokens
num_stale_output_tokens
drop_stale_output
last_sched_seq
```

这些字段不是“冗余历史包袱”，而是异步状态正确性的账本。

## 10. `torch.compile` 与 CUDA Graph 不是一回事

### 10.1 torch.compile

编译目标是把 PyTorch 图变成优化后的执行代码，做图分割、融合和 Inductor/Triton codegen。

v0.27.1：

```text
vllm/config/compilation.py
  CompilationConfig.mode
```

V1 默认 mode 为 3，即 `VLLM_COMPILE`。它支持 vLLM 自定义 backend、piecewise compilation、shape specialization 与 pass。

### 10.2 CUDA Graph

CUDA Graph 捕获一组 GPU 操作，后续 replay，减少 Python/CUDA launch 开销。它要求捕获时的地址与 shape 约束可复用。

Persistent Batch 的固定容量 buffer、block table 与预分配张量，为 replay 提供稳定地址。

### 10.3 正交关系

源码注释明确：

- piecewise CUDA Graph 依赖 piecewise compilation；
- full CUDA Graph 可在有或没有 compilation 时工作；
- 编译图可支持动态范围；
- CUDA Graph 通常按具体 capture size 捕获。

因此不能把：

```text
--enforce-eager
```

只理解成“关闭 CUDA Graph”。在 v0.27.1 配置处理里，它等价于把 compilation mode 与 cudagraph mode 都设为 none。

## 11. CUDA Graph 的 shape 调度

### 11.1 默认 capture sizes

v0.27.1 生成候选尺寸的大意：

```python
max_graph_size = min(max_num_seqs * 2, 512)
sizes = [1, 2, 4]
sizes += multiples_of_8_below_256
sizes += multiples_of_16_from_256_to_max
```

最终还受：

```text
max_num_batched_tokens
max_cudagraph_capture_size
performance_mode
speculative decode query length
backend 支持
```

约束。

### 11.2 padding 手算

capture sizes 为 `[1,2,4,8,16]`，实际 Decode batch 有 13 个 query token。

选择最近可覆盖 shape：

```text
13 → pad 到 16
```

padding 比例：

$$
\frac{16-13}{16}=18.75\%
$$

launch 开销降低，但做了空 slot 工作。若捕获 13 的专用 graph，可减少 padding，却增加 startup 时间与 graph 显存。

### 11.3 FULL_AND_PIECEWISE

v0.27.1 `CompilationConfig` 文档给出的 V1 默认 CUDA Graph mode 是：

```text
FULL_AND_PIECEWISE
```

意图：

- Decode batch 用 full graph；
- Prefill 或 mixed batch 用 piecewise graph；
- backend 不支持时配置可能降级。

启动日志中的最终 resolved config 才是事实。不能只从 dataclass 默认值推断某模型实际跑了 full graph。

### 11.4 为什么 Graph 占显存

capture 会保留 graph、静态 buffer 和内存池。capture size 越多、size 越大，启动时间和显存通常越高。

这形成三角关系：

```text
更多 capture sizes
  → 更少 padding / fallback
  → 更长 warmup、更高显存
```

## 12. Model Runner V1 与 V2 的边界

v0.27.1 同时存在：

```text
vllm/v1/worker/gpu_model_runner.py
  当前 GPUModelRunner 主路径

vllm/v1/worker/gpu/model_runner.py
  Model Runner V2
```

选择由：

```text
VllmConfig.use_v2_model_runner
VLLM_USE_V2_MODEL_RUNNER
```

等配置解析决定。

“V1 Engine”描述 EngineCore/Scheduler 等整体架构；“Model Runner V2”只是 Worker 执行组件的下一代实现。它们不是同义词。

MRV2 的方向包括：

- 更设备化的请求状态；
- GPU 上维护 computed count；
- 更少 CPU↔GPU 同步；
- 为 async scheduling 和 PP 提供更清晰结构。

是否启用、支持哪些功能应以 v0.27.1 实际配置校验和启动日志为准。

## 13. 带数字的流水线手算

假设四阶段耗时：

```text
S: Scheduler       0.20 ms
P: Worker prepare  0.25 ms
G: GPU execute     0.80 ms
U: update/output   0.15 ms
```

### 完全串行

$$
T=0.20+0.25+0.80+0.15=1.40\text{ ms}
$$

每秒理论 steps：

$$
1000/1.40\approx714
$$

### CPU 准备与 GPU 重叠

把下一轮 S+P 放进当前 G 窗口。CPU 准备共 0.45 ms，小于 GPU 0.80 ms，稳态瓶颈近似：

$$
\max(0.45,0.80)+0.15=0.95\text{ ms}
$$

理论约：

$$
1000/0.95\approx1053\text{ steps/s}
$$

这是上界模型。IPC、同步依赖、grammar、spec rejection 和 output handling 都可能打破完全重叠。

### 如果 GPU 很快

小模型 GPU 只有 0.30 ms：

$$
\max(0.45,0.30)+0.15=0.60\text{ ms}
$$

CPU 成为瓶颈。此时继续优化 Kernel 收益很低，应关注 persistent batch、async scheduling、Tokenizer 与 Python overhead。

## 14. 可复现实验

### 14.1 eager 对照

默认路径：

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --port 8000 \
  --max-model-len 2048 \
  --max-num-seqs 64 2>&1 | tee default.log
```

eager 路径：

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --port 8001 \
  --max-model-len 2048 \
  --max-num-seqs 64 \
  --enforce-eager 2>&1 | tee eager.log
```

用同一客户端分别压测：

```bash
for port in 8000 8001; do
  vllm bench serve \
    --backend openai-chat \
    --base-url "http://127.0.0.1:${port}" \
    --model Qwen/Qwen2.5-0.5B-Instruct \
    --dataset-name random \
    --random-input-len 128 \
    --random-output-len 256 \
    --num-prompts 500 \
    --request-rate 16 \
    --max-concurrency 64 \
    --num-warmups 20 \
    --save-result \
    --metadata mode=default_or_eager port="$port"
done
```

脚本中的 metadata 值应按实际轮次分别写清，不能把两个结果都标成同一 mode。

应比较：

```text
启动到 ready 时间
启动峰值显存
稳态 TTFT / TPOT / ITL
output tokens/s
GPU 利用率与 CPU 占用
```

### 14.2 capture size 对照

先查看 v0.27.1 参数格式：

```bash
vllm serve --help | grep -n "compilation"
```

示例配置：

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --compilation-config \
  '{"cudagraph_capture_sizes":[1,2,4,8,16,32,64]}'
```

再用 batch/concurrency 扫描 `[1,8,32,64]`。目标不是证明“更多 graph 更快”，而是找：

```text
padding/fallback 降低带来的稳态收益
vs
额外 warmup 和显存
```

### 14.3 观察进程

服务运行时：

## 15. 指标、失败模式与排障

### 15.1 启动很慢

分解日志：

```text
下载
权重加载
memory profile
KV cache 创建
torch.compile
CUDA Graph warmup/capture
```

编译缓存命中与否会让两次启动差异巨大。比较时要明确是 cold start 还是 warm cache。

### 15.2 默认模式 OOM，eager 正常

这支持“编译/graph 路径有额外显存”的假设，但还不能证明是哪一个 capture size。

下一步：

1. 记录 eager 与默认启动峰值；
2. 缩小 `max_cudagraph_capture_size` 或 capture size 列表；
3. 固定 KV 配置；
4. 逐步恢复 compilation/graph，而不是永久停在 eager。

### 15.3 首次请求特别慢

可能是：

```text
lazy compilation
未覆盖 shape 的首次 graph
Tokenizer / 模型文件冷缓存
JIT Triton kernel
```

用 `--num-warmups`，并保存每请求详细延迟。不要删除第一个坏点后假装它不存在；冷启动 SLO 应单独报告。

### 15.4 Graph replay 比例低

可能原因：

```text
实际 token/batch shape 超出 capture sizes
mixed Prefill/Decode 走其他模式
LoRA/多模态/spec 使 descriptor 不兼容
backend 降级
请求并发太低
```

先从启动 resolved config 和可用 cudagraph metrics 查证，不要凭 `--enforce-eager` 对照猜测。

### 15.5 Persistent Batch 低效

症状可能是 CPU 高、GPU 仍有气泡，而并发并不低。检查相邻 step 的 batch overlap：

$$
overlap=
\frac{|B_t\cap B_{t-1}|}
{|B_t\cup B_{t-1}|}
$$

若两个请求集合交替，overlap 接近 0，remove/add/condense 频繁。根因可能是调度策略、PP cadence 或负载形态。

### 15.6 async 状态错误或崩溃

排障顺序：

1. 固定 v0.27.1 与最小模型；
2. 关闭 spec、structured、LoRA 等组合；
3. 对照 `--async-scheduling=false`（以 `--help` 的实际布尔语法为准）；
4. 若只在组合功能出现，保留请求 seed 与完整配置；
5. 查看 stale output、placeholder 或 block free 相关栈。

不要在生产 site-packages 中随手 print 改时序；使用独立源码环境和最小复现。

## 16. trade-off 与适用边界

### 统一调度

减少阶段分叉，能表达 chunked prefill 与 spec；但 token budget 不是精确 FLOPs，Prefill token 与 Decode token 成本不同。

### 多进程 IPC

隔离 CPU 工作并支持多前台；但小模型低并发下 IPC 固定成本可能更显眼。

### Persistent Batch

高 batch overlap 收益大；低 overlap 会频繁变更索引和 metadata。

### 乐观异步状态

提高 CPU–GPU 重叠；代价是 stale、abort、preemption、spec rollback 更复杂。

### torch.compile

融合和代码生成可提高稳态性能；代价是编译时间、缓存管理和模型兼容性。

### CUDA Graph

降低 launch overhead；代价是 shape 约束、padding、捕获时间和额外显存。

结论应是：

> V1 提供更适合重叠与组合优化的结构，但实际收益必须按模型、硬件、shape 与流量验证。
