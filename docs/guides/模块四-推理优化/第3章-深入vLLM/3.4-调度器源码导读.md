## 1. 真实问题：调度错了会怎样

线上常见四种“模型没错，但服务坏了”的现象：

```text
长 Prompt 到来后，已有对话的 ITL 突然变差
KV 使用率接近满，preemption 持续增加
Prefix Cache 命中很多，TTFT 却没有改善
Spec Decode 开启后调度 token 上升，实际接受率很低
```

它们都与 Scheduler 的三本账有关：

1. **计算账**：本轮 token budget 还有多少；
2. **存储账**：请求历史需要哪些 KV blocks；
3. **状态账**：哪些 token 已计算、在 flight、已接受或被回滚。

只看 `max_num_batched_tokens` 解决不了 KV 不足；只看 free blocks 也解释不了 structured grammar 为什么阻塞。

## 2. 白话直觉：预算表与状态账本

把每个 Engine step 想成一个预算周期。

Scheduler 不直接执行模型，只生成一份计划：

```text
本轮请求 A 算 1 token
本轮请求 B 算 1 token
本轮请求 C 算 126 token
A 追加物理 block 9
C 使用 blocks 11、4、20……
请求 D 本轮被抢占
```

GPU 执行后交回“实际发生了什么”：

```text
A 采样 1 token
B 的 4 个 draft 只接受 2 个
C 只是中间 Prefill，没有用户输出
D 已被客户端取消
```

Scheduler 再提交或回滚状态，进入下一轮。

## 4. 初始化：Scheduler 持有哪些状态

### 4.1 约束

`Scheduler.__init__()` 解析：

```text
max_num_running_reqs = scheduler_config.max_num_seqs
max_num_scheduled_tokens =
  max_num_scheduled_tokens ?? max_num_batched_tokens
max_model_len
block_size / hash_block_size
num_spec_tokens / num_lookahead_tokens
encoder compute budget
```

v0.27.1 区分：

- `max_num_batched_tokens`：模型 batch 可处理 token 上限；
- `max_num_scheduled_tokens`：Scheduler 本轮可发出 token 上限。

通常两者相等；某些会在 batch 内追加 token 的模式可以让调度上限更小。

### 4.2 请求集合

```text
requests: req_id → Request
waiting: 可接纳队列
skipped_waiting: 因异步依赖或约束暂时跳过
running: 已接纳请求
finished_req_ids: 通知 Worker 清理状态
reset_preempted_req_ids: 通知特定执行路径重置
```

### 4.3 blocked waiting

v0.27.1 的 blocked 状态包括：

```text
WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR
WAITING_FOR_REMOTE_KVS
WAITING_FOR_STREAMING_REQ
```

这些请求进入 `skipped_waiting`，避免一个尚未就绪的队首让整个 waiting 队列停住。

### 4.4 KVCacheManager

Scheduler 构造 KV 管理器时传入：

```text
kv_cache_config
max_model_len
max_in_flight_tokens
enable_prefix_caching
num cache groups
scheduler_block_size
hash_block_size
watermark
```

`watermark` 用于 waiting/preempted 接纳时保留空闲 headroom，降低刚接纳就频繁抢占的风险。

## 5. `schedule()` 的严格主干

接近 v0.27.1 的可追踪伪代码：

```python
def schedule():
    current_step += 1
    token_budget = max_num_scheduled_tokens
    kv_cache_manager.new_step_starts()

    # A. running
    for request in running:
        need = (
            request.num_tokens_with_spec
            + request.num_output_placeholders
            - request.num_computed_tokens
        )
        need = clamp_long_prefill(need)
        need = min(need, token_budget)
        need = clamp_model_len_and_encoder_budget(need)

        while True:
            blocks = kv_cache_manager.allocate_slots(
                request,
                need,
                num_lookahead_tokens=num_lookahead_tokens,
            )
            if blocks is not None:
                break
            victim = choose_lowest_priority_running_request()
            preempt(victim)
            if victim is request:
                break

        if blocks is None:
            break

        plan[request.id] = need
        token_budget -= need
        trim_and_record_spec_tokens(request, need)

    # B. waiting：本轮发生过 preemption 时不接新请求
    if not preempted_requests:
        while waiting_ready and token_budget > 0:
            request = select_queue_head()
            cached_blocks, cached_tokens = lookup_prefix(request)
            need = request.num_tokens - cached_tokens
            need = clamp_chunk_and_budget(need)
            blocks = allocate_slots(
                request,
                need,
                new_computed_blocks=cached_blocks,
            )
            if blocks is None:
                break
            move_waiting_to_running(request)
            plan[request.id] = need
            token_budget -= need

    output = SchedulerOutput(...)
    update_computed_tokens_optimistically(output)
    return output
```

这里省略多模态、KV connector、hybrid cache、async/PP 与 diffusion 分支，但调用顺序可以回到真实源码逐段核对。

## 6. running 流程：先算需求再要 KV

### 6.1 需求公式

running 请求：

$$
n_i=
N_{\text{with-spec}}
+N_{\text{placeholders}}
-N_{\text{computed}}
$$

裁剪：

$$
\hat n_i
=\min(
n_i,
T_{\text{long-prefill}},
B_{\text{left}},
L_{\max}-N_{\text{computed}}-N_{\text{sampled/step}}
)
$$

其中 long prefill threshold 为 0 时不启用该上界。

### 6.2 为什么 0 token 会 continue

源码不总是 `break`：

```text
PP 前一轮尚未完成
async 已达长度边界
encoder budget 耗尽
encoder cache 不足
hybrid/Mamba block 对齐后没有可调度 chunk
```

它会继续看低优先级请求。这不严格遵循纯 FCFS，但避免一个暂时不可执行请求冻结整轮。

### 6.3 先 running 的意义

running 请求通常已占 KV，并且用户在等待后续 token。先处理它们可以：

- 维持 Decode 流畅度；
- 让已接纳请求继续前进；
- 避免新 Prefill 无限挤占预算。

但 running 中的长 chunked prefill 仍可能占大预算，具体干扰由 token budget、threshold 与执行耗时决定。

## 7. preemption：预算够但 block 不够

### 7.1 两种预算独立

假设本轮 token budget 还剩 100，但物理 KV free blocks 为 0。

Decode 请求只需 1 token，如果当前最后 block 已满，仍需一个新 block：

```text
token budget: 可以
KV allocation: 失败
```

所以 `allocate_slots()` 返回 `None`，Scheduler 进入 preemption。

### 7.2 受害者选择

FCFS 策略下，源码从 `running` 尾部 pop，近似抢占更晚接纳的请求。

PRIORITY 策略下选择：

```python
max(running, key=(priority, arrival_time))
```

因为 priority 数值越小越高，`max` 得到最低优先级；同优先级取更晚 arrival。

### 7.3 同轮已经计划的受害者

若受害者已在本轮 `scheduled_running_reqs`：

```text
撤销它的 scheduled token
把 token_budget 加回来
移除新 block 与 spec/encoder 计划
再执行 preempt
```

否则 `SchedulerOutput` 会同时说“执行这个请求”和“它已被抢占”，状态冲突。

### 7.4 `_preempt_request()`

v0.27.1 主动作：

```python
free_request_blocks(request)
encoder_cache_manager.free(request)
request.status = PREEMPTED
request.num_computed_tokens = 0
request.spec_token_ids = []
request.num_stale_output_tokens = request.num_in_flight_tokens
request.num_output_placeholders = 0
request.num_preemptions += 1
waiting.prepend_request(request)
reset_preempted_req_ids.add(request.id)
```

这就是 recompute：以后从 Prefix Cache 可命中部分开始，否则重算上下文。它不是把 KV swap 到 CPU 再恢复。

### 7.5 为什么抢占后本轮不接新 waiting

源码 waiting 流程有：

```python
if not preempted_reqs:
    schedule_waiting()
```

刚为了 running 释放资源，又立即接纳全新 waiting，容易造成抖动与不公平。优先让被抢占请求在后续恢复。

## 8. waiting 流程：命中、接纳与阻塞

### 8.1 选择队列

FCFS 时优先处理已有 `skipped_waiting` 中现在可推进的请求，再看新 waiting。

Priority 模式比较两个队首的优先级与到达时间。

### 8.2 Prefix Cache 查询

首次接纳且 `num_computed_tokens == 0`：

```python
new_computed_blocks, local_cached_tokens, boundary =
    kv_cache_manager.get_computed_blocks(request)
```

如果有 KV connector，还要合并 remote hit、异步 load 与对齐边界。

### 8.3 计算新 token

普通本地路径：

$$
n_{\text{new}}
=N_{\text{request.tokens}}-N_{\text{cached}}
$$

然后：

```text
spec decode uniform padding
long prefill threshold
chunked prefill 开关
剩余 token budget
encoder budget
Mamba 对齐
```

### 8.4 分配成功才改变队列

顺序：

```text
peek
→ prefix lookup
→ allocate_slots
→ pop
→ append running
→ status=RUNNING
```

若先 pop 再分配，失败时要回滚队列、Prefix Cache 引用和 encoder cache，复杂度更高。

### 8.5 接纳容量

除 token/KV 外还要满足：

```text
len(running) + waiting_for_streaming_input < max_num_seqs
LoRA 数不超过 max_loras
grammar / remote KV 已就绪
完整输入是否满足 scheduler_reserve_full_isl
watermark headroom
```

“waiting 很长”不自动说明 `max_num_seqs` 太小。

## 10. `update_from_output()`：提交、回滚与释放

### 10.1 先减 in-flight

对本轮每个请求：

```python
request.num_in_flight_tokens -= num_tokens_scheduled
```

如果请求在 GPU 执行期间已 abort，`requests.get(req_id)` 可能为空，输出应丢弃，不能让已结束状态复活。

### 10.2 Spec 回滚

设调度 `K` 个 draft，加 1 个常规 sampled position。若模型最终返回：

```text
accepted drafts + one bonus/sample token
```

源码计算：

$$
N_{\text{accepted}}
=\max(N_{\text{returned}}-N_{\text{sampled/step}},0)
$$

$$
N_{\text{rejected}}
=K-N_{\text{accepted}}
$$

然后从乐观 `num_computed_tokens` 和 placeholders 中减掉 rejected。

### 10.3 Structured grammar

新 token 先通过 `_update_request_with_output()` 更新停止状态，再由 `StructuredOutputManager.should_advance()` 判断是否推进 grammar。

Reasoning 模型可能先输出 reasoning 内容，再进入受 grammar 约束的 answer。源码会 trim reasoning，只把 grammar 部分交给 `grammar.accept_tokens()`。

若 grammar 意外拒绝已采样 token，请求标记 `FINISHED_ERROR`。正常路径应在采样前用 bitmask 避免这种不一致。

### 10.4 完成与释放

停止后：

```text
取得 finish_reason
处理 resumable session
释放 KV / encoder / connector 资源
从 running 或 waiting 移除
构造 EngineCoreOutput
```

中间 Prefill chunk 不向用户发 partial output。源码有不变量：

```text
EngineCore returns no partial prefill outputs
```

## 11. 案例一：Prefill 与 Decode 逐轮手算

设置：

```text
token budget = 8
block_size = 4
free blocks 足够
调度策略 FCFS
```

初始：

```text
A running: num_tokens=101, computed=100，需要 1（Decode）
B running: num_tokens=41,  computed=40， 需要 1（Decode）
C waiting: Prompt 14 token，无缓存
```

### Round 1

running：

```text
A 分 1，budget 7
B 分 1，budget 6
```

waiting C：

```text
need=14
chunk=min(14,6)=6
C 分 6，budget 0
```

计划：

$$
1+1+6=8
$$

执行后：

```text
A 采样 a1；computed=101；num_tokens=102
B 采样 b1；computed=41； num_tokens=42
C computed=6；没有用户输出
```

### Round 2

```text
A need=1
B need=1
C need=14-6=8
```

分配：

```text
A:1，B:1，C:6
```

C computed 变 12。

### Round 3

```text
A:1
B:1
C:2
剩余 budget=4
```

C 完成 Prompt forward 并采样首 token。即使预算还剩 4，也不能在同一个 schedule 中立刻用刚采样但尚未返回的 token 再 Decode。

这说明 token budget 是**本轮已知输入位置**预算，不是“本轮最终能吐多少输出 token”的保证。

## 12. 案例二：KV 不足与抢占重算

设置：

```text
block_size=4
物理 blocks 总数=6
A 占 [0,1,2]，最后 block 已满
B 占 [3,4]，最后 block 还剩 1 slot
free=[5]
token budget=4
```

A、B 都 need=1。

### 先调 A

A 最后 block 满，需要新 block 5：

```text
A → [0,1,2,5]
free=[]
budget=3
```

### 再调 B

B 最后 block 还有 slot，不需新 block，因此仍可调：

```text
B 使用 block 4 剩余 slot
budget=2
```

这说明 free block 为 0 不等于所有请求都不能 Decode。

下一轮 A 与 B 的最后 block 都满，A 先申请失败。FCFS running 尾部 B 成为 victim：

```text
释放 B 的 [3,4]
B.status=PREEMPTED
B.computed=0
B 放回 waiting 前部
```

A 得到一个释放 block 并前进。

B 恢复时若没有 Prefix Cache 可用，要重算 Prompt 与已生成上下文。假设 B 先前 computed=8，被抢占一次至少浪费 8-token forward；反复 5 次就是 40-token 重算，吞吐统计若只看最终输出会隐藏这部分 GPU 工作。

## 13. 案例三：Spec Decode 的预算与回滚

设置：

```text
token budget=12
num_spec_tokens=4
A running 普通 decode
B running，已有 4 个 draft=[31,32,33,34]
C waiting 普通 decode，需要 spec uniform padding
```

### running A

```text
need=1
budget=11
```

### running B

```text
num_tokens=201
num_computed=200
len(spec)=4
need=5
budget=6
```

Scheduler 记录 B 的 4 个 draft。

### waiting C

等待请求本来 need=1，但在当前为纯 Decode 且启用固定 spec 长度时，源码可能 pad 到：

$$
1+num\_spec\_tokens=5
$$

budget 6 足够，于是：

```text
C schedule=5
scheduled_spec_decode_tokens[C]=[-1,-1,-1,-1]
budget=1
```

总计划：

$$
1+5+5=11
$$

### 输出回滚

B 的 4 个 draft 只接受 2 个，模型返回“2 accepted + 1 normal/bonus”，长度 3。

$$
accepted=\max(3-1,0)=2
$$

$$
rejected=4-2=2
$$

Scheduler 在 schedule 后曾乐观加 5，现在回滚 2。净 computed 前进 3。

预算消耗按验证的 5 个输入位置计算，用户得到的有效 token 只有 3。接受率低时，调度 token 吞吐可能升高，但 goodput 不一定提高。

## 14. 案例四：Structured Output 与 Spec 交互

目标 JSON：

```json
{"answer":"yes"}
```

假设当前 grammar 只允许 token 集 `{", y, n}` 中的某些 token，而 draft model 给出：

```text
[y, e, x, ...]
```

### 14.1 grammar 未编译

请求状态：

```text
WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR
```

Scheduler 把它放在 blocked/skipped queue，继续调其他请求。它不应消耗 GPU token budget。

### 14.2 grammar 已就绪

Scheduler/EngineCore 取得 grammar bitmask，采样时屏蔽非法 token。Spec draft 还需按 grammar 有效性处理。

`step_with_batch_queue()` 中若：

```text
pending_structured_output_tokens=True
```

采样可能推迟到前一批输出完成；拿到 draft 后：

```text
update_draft_token_ids_in_output()
→ 无效 draft 填 -1
→ 计算 grammar bitmask
→ sample_tokens()
```

### 14.3 数字例子

4 个 draft 中只有前两个 grammar-valid：

```text
原 draft: [101, 102, 103, 104]
过滤后:   [101, 102, -1, -1]
```

调度为 uniform shape 仍可能保留 padding，但有效验证候选只有 2 个。最终只接受第一个，则：

```text
draft proposed=4
grammar valid=2
model accepted=1
```

至少区分两个比例：

$$
grammar\_valid\_rate=2/4=50\%
$$

$$
model\_acceptance\_rate=1/2=50\%
$$

把二者合成“spec acceptance=25%”会失去排障信息：问题可能是 grammar 冲突，也可能是 draft 质量。

## 15. 公平性、优先级与跳过队首

### 15.1 FCFS 不是绝对不跳

当队首因为 grammar、remote KV、encoder budget 或 0-token 条件无法执行时，Scheduler 可能继续看其他请求。

严格队首阻塞会更“纯 FCFS”，却降低设备利用率。

### 15.2 priority 语义

v0.27.1 priority 数值越小优先级越高；同优先级按 arrival time。

优先级不能突破：

```text
token budget
KV capacity
max_num_seqs
模型长度
grammar readiness
```

### 15.3 starvation 风险

持续到达高优先级短请求时，低优先级长 Prefill 可能很久拿不到足够 budget。评估 priority 策略应记录：

```text
按 priority 分组的 queue time
每请求被跳过轮次
deadline miss / goodput
低优先级最大等待
```

总吞吐正常不能证明公平。

## 16. 可复现实验与断点方法

### 16.1 固定小预算观察 chunk

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --port 8000 \
  --max-model-len 2048 \
  --max-num-seqs 8 \
  --max-num-batched-tokens 64 \
  --generation-config vllm 2>&1 | tee sched-small.log
```

压入 512-token Prompt 与多个短 Decode 请求。再用 256 budget 重复。比较 TTFT 与 ITL，而非只看总吞吐。

### 16.2 强制小 KV 做 preemption 实验

公共 CLI 不应依赖内部 `num_gpu_blocks_override` 做生产配置，但源码测试环境可以使用 `CacheConfig.num_gpu_blocks_override` 构造确定性抢占。

更安全的黑盒方法是：

```text
固定模型与 max_model_len
逐步提高 max concurrency
观察 kv_cache_usage_perc 与 num_preemptions 增量
```

命令：

```bash
for c in 8 16 32 64; do
  vllm bench serve \

    --base-url http://127.0.0.1:8000 \
    --model Qwen/Qwen2.5-0.5B-Instruct \

    --random-input-len 1024 \

done
```

### 16.3 读取源码而不改 site-packages

```bash
python - <<'PY'
import inspect
from vllm.v1.core.sched.scheduler import Scheduler

```

需要断点时，从 v0.27.1 源码创建开发环境，在独立实验中用：

```python
breakpoint()
```

关注每轮：

```text
[r.request_id for r in running]
waiting/skipped queue heads
token_budget
num_scheduled_tokens
KV usage/free blocks
preempted_req_ids
scheduled_spec_decode_tokens
```

不要在生产循环里打印全量 token IDs，会放大 CPU 与 I/O 开销并改变时序。

### 16.4 Structured + Spec 复现

固定：

```text
同一模型 revision
同一 JSON schema
temperature=0
同一 draft 配置
固定请求集合
```

分别跑：

```text
structured only
spec only
structured + spec
```

保存成功率、TTFT、TPOT、grammar compile 时间、draft valid/accepted 指标。只有组合失败才能定位交互，而不是某个单项本身。

## 17. 指标、失败模式与排障

### 17.1 关键 v0.27.1 指标

```text
vllm:kv_cache_usage_perc
vllm:num_preemptions
vllm:prefix_cache_queries
vllm:prefix_cache_hits
vllm:request_queue_time_seconds
vllm:time_to_first_token_seconds
vllm:inter_token_latency_seconds
vllm:e2e_request_latency_seconds
```

所有 counter 用区间增量，histogram 用统一窗口和分位数。

### 17.2 TTFT 高、ITL 正常

优先检查：

```text
waiting queue
Prompt 长度
chunked prefill 轮数
Prefix Cache 命中
grammar compile
```

这通常不是 Decode 路径。

### 17.3 ITL 在长 Prompt 到来时抖动

把 `max-num-batched-tokens` 从大到小做单变量扫描，并观察：

```text
ITL P99 是否下降
长 Prompt TTFT 是否上升
总吞吐是否下降
Scheduler step 次数是否增加
```

小 budget 不是免费修复。

### 17.4 preemption 连续增长

说明 KV 容量与在途上下文不匹配。可能动作：

```text
降低 max_num_seqs
做准入/限流
缩短业务上下文
增加 KV 显存或使用验证过的低精度 KV
提高 Prefix Cache 命中
调整 watermark / reserve 策略前先验证版本语义
```

调高 token budget 不会凭空增加 KV。

### 17.5 Prefix hit 高但 TTFT 收益小

检查：

```text
命中的是多少 token，不只是请求数
末 block 是否重算
队列时间是否主导
命中后剩余后缀是否仍很长
是否发生 preemption 后重复查询
```

### 17.6 Spec 吞吐变差

分解：

```text
proposed drafts
grammar-valid drafts
model-accepted drafts
验证额外 token
draft model 时间
主模型节省的 Decode steps
```

如果平均接受 0.5 个，却每轮验证 4 个，token budget 和 KV lookahead 被大量无效候选占用。

### 17.7 Structured 请求长时间 waiting

确认它是 queue overload 还是：

```text
WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR
```

若 grammar 编译慢，应缓存/简化 schema 或扩展 CPU 资源；增大 GPU budget 没有帮助。

## 18. trade-off

### Token budget

简单、可组合；但不是 FLOPs 或 wall-time 的精确预算。

### running 优先

保护在途交互请求；但长 running Prefill 仍可能占据预算。

### 跳过暂不可执行请求

提高设备利用率；但弱化严格 FCFS，可产生公平性问题。

### recompute preemption

状态简单、无需 CPU swap；但浪费已完成计算并恶化尾延迟。

### optimistic scheduling

减少流水线气泡；但要求正确维护 in-flight、stale 与回滚。

### uniform spec padding

保持 CUDA Graph 友好 shape；但低接受率或 grammar 过滤下会浪费 token slots。
